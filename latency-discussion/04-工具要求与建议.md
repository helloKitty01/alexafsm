# 04 对工具的要求与建议（讨论稿）

01~03 的优化都在框架侧和模型侧做文章；本篇换一个方向：
**把时延压力前移到工具提供方**，形成一份"工具接入要求与建议"。
理由很直接——时延方程里的多个变量（参数 token、执行时长、loop 次数、
下一轮 prefill）在源头上由工具的设计质量决定，框架侧优化只能兜底，
不能替代源头治理。

每条要求标注两个属性：

- **强制力**：MUST（准入门槛，不满足不上架/整改）或 SHOULD（建议，影响评分与推荐权重）；
- **作用变量**：对应时延方程 `T ≈ k×T_SkillLoad + Σ(T_推理 + T_执行) + TTFT_Final`
  中被改善的项（`M` = loop 轮数，`tk_out` = 模型输出 token，`tk_in` = 下一轮 prefill token）。

## 0. 总览：五个维度与时延的映射

| 维度 | 作用变量 | 一句话要求 |
| --- | --- | --- |
| 1. 参数设计 | tk_out、M（幻觉） | 模型少写、写不错 |
| 2. 执行时长 | T_执行 | 时长可声明、可预算、可异步、不挂死 |
| 3. schema 信息 | 快系统可达性、M（选错工具）、prefill | 一切工具必须可 function call 化 |
| 4. 工具粒度 | M（乘数，杠杆最大） | 一次调用 = 一个用户可感知的完整动作 |
| 5. 返回值 | tk_in、M（纠错） | 少 token、可纠错、可续用 |

其中维度 3 是本篇的重点：它不只影响时延数字，
而是决定一个能力**能不能进快系统**（1~2s vs 10~40s，见 03），是资格问题。

## 1. 参数设计要求

目标：压低 `tk_out`（长尾 300tk → 9s 的削峰对象），同时结构性消除标识符幻觉（减 M）。

### MUST

| # | 要求 | 说明 |
| --- | --- | --- |
| 1.1 | 参数必须是结构化字段 | 禁止把整段命令串、序列化 JSON 字符串作为单个参数值（双重转义 token 膨胀、无法校验、易错） |
| 1.2 | 封闭值域优先 | 能用枚举/布尔的不得用自由字符串；枚举值写进 schema |
| 1.3 | 内部标识符不得要求模型直接填写 | bundleName、UUID、内部资源 ID 类参数：要么 schema 改为人类可读名（appName="抖音"，工具内部查表），要么声明支持变量/短句柄解析（`${app.抖音.bundleName}`、`f1`），由 pre-call 拦截器还原（见 01 §2、`docs/variable-resolution/`） |
| 1.4 | 可选参数必须有默认值 | 模型只输出非默认参数；必填参数原则上 ≤ 5 个 |

### SHOULD

| # | 建议 | 说明 |
| --- | --- | --- |
| 1.5 | 同类操作提供批量形态 | 数组参数：`forbidPermission(apps=[...], permission=...)`，N 个 loop 变 1 个 |
| 1.6 | 路径参数支持相对路径 | 会话级 cwd 等全局状态由框架持有，不要求模型每次输出绝对路径 |
| 1.7 | 参数命名与用户话术、skill 文档用词一致 | 减少模型"翻译"出错 |

### 量化锚点（待埋点数据校准）

单次调用参数合计目标 **≤ 50 token**；超过 **150 token** 的工具需说明理由并给出压缩方案
（对照已确认口径：平均 35tk，最坏 300tk）。

## 2. 执行时长要求

目标：压低 `T_执行`（现状 0.5~2s），并保证长耗时不把整个 loop 挂死。

### MUST

| # | 要求 | 说明 |
| --- | --- | --- |
| 2.1 | 注册时声明时长档位 | quick（<500ms）/ normal（0.5~2s）/ long（>2s），作为工具元数据，供框架做预算、超时与产品侧进度提示 |
| 2.2 | long 档必须提供异步形态 | 提交后立即返回任务句柄，后续轮询/回调取结果；模型可继续其他步骤（见 01 §3.4） |
| 2.3 | 必须响应框架的超时与取消 | 超时返回已完成部分与状态说明，而非空错误或无响应 |
| 2.4 | 声明只读/幂等属性 | 供安全校验分级（只读白名单跳同步校验，省 0.5s 固定税，见 01 §3.1）与失败安全重试 |

### SHOULD

| # | 建议 | 说明 |
| --- | --- | --- |
| 2.5 | 承诺 P95 时长 SLO 并纳入监控 | 对接优先级 0 的埋点体系；超 SLO 的工具进入整改清单 |
| 2.6 | 声明可并发性 | 能否与其他工具并行执行（无共享状态冲突），供框架做并行调用与流水线调度（见 02 成因三） |

## 3. schema 信息要求（function call 化，快系统准入门槛）

这是对工具提供方最核心的一条要求。

### 问题：CLI 与 ArkTS 脚本类工具缺结构化 schema

现状里有一批工具以 CLI 命令、ArkTS 脚本的形态存在，只有帮助文本 / 用法说明，
没有机器可读的参数 schema。后果是一条完整的链：

```text
无结构化 schema
  → 无法转换为 function call 声明
    → 快系统（小模型 FC）无法调用该能力          ← 直接堵死 03 的迁移路径
    → 慢系统里也只能靠模型拼自由文本参数：
        - 无法做参数级安全校验（只能整串审，慢且粗）
        - 无法接入变量解析 / 短句柄拦截器（1.3 的机制全部失效）
        - 无法识别参数从而并行调度、缓存校验结果
    → 该能力永远走 10~40s 的慢路径，且是长尾错误高发区
```

换句话说：**没有 schema 的工具，01~03 的几乎所有优化对它都不生效。**

### MUST

| # | 要求 | 说明 |
| --- | --- | --- |
| 3.1 | 所有工具提供机器可读声明 | name、description、参数 JSON Schema（类型/必填/枚举/默认值）、返回值 schema、错误码表。这是快慢双系统"同一工具执行层"的前提（03 一致性约束） |
| 3.2 | CLI 类工具不得以裸命令串形态接入 | 两条整改路径见下文；模型自由拼 shell 串仅保留给开发者场景，不进普通用户任务链路 |
| 3.3 | ArkTS 脚本类工具入口签名必须结构化 | 脚本内部多步执行没问题（对模型仍是一个 FC），但入口参数必须能生成 schema，路径见下文 |
| 3.4 | description 规范 | 一句话功能 + 何时用/何时不用 + 与易混淆工具的区分点。description 质量直接影响工具选择准确率，选错一次 = 多付一个 loop（5~11s） |

### CLI 类工具的两条 FC 化路径

| 路径 | 做法 | 适用 |
| --- | --- | --- |
| (a) manifest 映射 | 提供方写一份 manifest：子命令 + flags → 结构化参数字段；框架据此生成 FC schema，调用时由框架负责拼装命令行（模型永远不接触命令串） | 参数规整、子命令多的 CLI，一次接入全量覆盖 |
| (b) 高频子命令独立包装 | 把日志中高频的几个子命令各包装成一个独立 FC 工具，长尾子命令暂不暴露 | 参数复杂、难以整体映射的 CLI，按 ROI 渐进迁移 |

两条路径都把"拼命令行"从模型侧移到框架侧：模型输出的是结构化参数
（token 少、可校验、可进快系统），命令串拼装是确定性代码（不会幻觉、天然防注入）。

### ArkTS 脚本类工具的 schema 生成路径

| 路径 | 做法 | 权衡 |
| --- | --- | --- |
| (a) 装饰器 / 注解 | 入口函数加装饰器标注参数语义，编译期提取生成 schema | 一次建设，后续自动同步，推荐终态 |
| (b) 伴生元数据文件 | 脚本旁放一份手写的 schema 文件（类似 d.ts / manifest） | 无需动构建链路，先跑起来；风险是签名与元数据漂移，需 CI 校验一致性 |

### SHOULD

| # | 建议 | 说明 |
| --- | --- | --- |
| 3.5 | 单工具 schema token 预算 | 建议 ≤ 150 token；用法示例放 skill 正文（按需加载），不放常驻 schema——工具集 schema 总量直接进每次 prefill |
| 3.6 | schema 版本化 + 变更通知 | schema 变更要能触发：skill 示例同步更新、快系统对应已编译能力失效重训（对接 03 开放问题 4） |

## 4. 工具粒度要求

目标：直接压 `M`（乘数，全局杠杆最大，每减一轮省 5~11s）。

原则：**粒度对齐"用户意图中的一个步骤"，而不是"系统内部的一个 API"。**

### MUST（准入自查两条反模式）

| # | 反模式 | 自查问题 | 整改 |
| --- | --- | --- | --- |
| 4.1 | 过细 | "使用我的工具前，调用方是否必须先调另一个工具获取某个内部标识符？" | 把前置查询内化到工具内部，或参数改用人类可读名 + 变量解析（对齐 1.3） |
| 4.2 | 过粗 | "我是否用一个 action/mode 参数分发了很多种互不相关的行为？" | 拆分。万能工具伤选择准确率（description 写不清）、schema 膨胀、且安全校验无法按行为分级（一个高危行为拖累整个工具进完整校验） |

### SHOULD

| # | 建议 | 说明 |
| --- | --- | --- |
| 4.3 | 高频稳定序列合并为复合工具 | 由 02 的日志统计（高频二元/三元组）驱动，不预先猜测；只合并高频 + 稳定的序列 |
| 4.4 | 新工具准入评审 | 提供方须说明与既有工具的差异与不重叠性，控制工具集规模（工具集变大伤 prefill 与选择准确率） |

## 5. 返回值要求

目标：压低下一轮 `tk_in`（返回值全额进入后续每一轮 prefill），并保证失败时纠错只付 1 个 loop。

### MUST

| # | 要求 | 说明 |
| --- | --- | --- |
| 5.1 | 结构化返回，且有返回值 schema | 禁止日志转储、整文件内容、base64 直接进上下文 |
| 5.2 | 返回值大小上限 | 建议 ≤ 1~2k token（待校准）；超限必须截断/分页，并返回获取完整数据的句柄（模型按需再取） |
| 5.3 | 错误返回三要素 | 错误码 + 人类可读原因 + **可执行的纠错线索**（合法值列表、正确格式示例、当前状态）。保证"纠错只付 1 次 loop"（见 02 错误消息工程）。每种失败路径逐条检查 |
| 5.4 | 只返回模型需要的信息 | 内部 trace id、调试细节走日志系统，不进上下文 |

### SHOULD

| # | 建议 | 说明 |
| --- | --- | --- |
| 5.5 | 长值登记短句柄 | 返回长路径/长 ID 时同步给出短句柄（`f1`），后续模型引用短句柄（对接 01 §2.2，省 tk_out 且防抄写错误） |
| 5.6 | 成功返回附带下游常用字段 | 预判后续步骤需要的关键字段一并返回，避免模型为拿一个字段再付一个查询 loop |

## 6. 汇总：接入 checklist（草案）

| 维度 | MUST（不满足不上架） | SHOULD（影响评分） |
| --- | --- | --- |
| 参数 | 结构化字段；封闭值域；无裸内部标识符；可选参数有默认值 | 批量形态；相对路径；命名一致 |
| 时长 | 档位声明；long 必须异步化；响应超时取消；幂等声明 | P95 SLO；并发性声明 |
| schema | 机器可读声明齐全；CLI 不得裸命令串；ArkTS 入口结构化；description 规范 | schema token 预算；版本化 |
| 粒度 | 无强制前置查询；无万能 action 分发 | 数据驱动的复合工具；准入评审 |
| 返回值 | 结构化 + schema；大小上限；错误三要素；不含机器噪声 | 短句柄；下游字段预置 |

## 7. 开放问题（待讨论）

1. **强制力与存量迁移**：MUST 定为硬准入还是先软性评分？存量工具（尤其 CLI/ArkTS 类）
   给多长宽限期、按什么顺序整改（建议按调用频次 × 当前时延贡献排序，依赖埋点数据）？
2. **量化门槛取值**：参数 ≤50tk、schema ≤150tk、返回值 ≤2k tk、P95 分档阈值——
   先拍后调，还是等优先级 0 的埋点数据出来再定？
3. **CLI FC 化的分工**：manifest 由工具提供方写，还是框架方提供转换脚手架 + 提供方补语义？
   路径 (a) 与 (b) 按什么标准选？
4. **ArkTS schema 生成**：装饰器方案需要动构建链路，伴生文件方案有漂移风险——
   先 (b) 过渡再 (a) 收敛，还是直接上 (a)？
5. **万能工具的界定线**：action 分发到几种行为算"过粗"？是否以"能否写出一句无歧义的
   description"作为操作性判据？
6. **要求的载体**：这份要求落成什么形态——接入平台的自动化校验（schema lint、
   返回值大小检测、SLO 监控）能覆盖多少条，多少条只能靠人工评审？
