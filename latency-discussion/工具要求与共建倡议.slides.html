共建低时延工具生态：问题、要求与建议

T ≈ k×SkillLoad + Σᴹ(推理 + 执行) + TTFT

时延的源头变量由工具设计决定：参数 token、执行时长、loop 轮数 M、下一轮 prefill —— 框架侧优化只能兜底，源头治理靠工具提供方一起共建。

核心问题 CLI / ArkTS 脚本类工具缺少结构化 schema，无法转换为 function call —— 这不是时延数字问题，是快系统的资格问题
无结构化 schema只有帮助文本 / 用法说明，参数不可机读
→
无法转 function call模型只能拼自由文本命令串
→
快系统不可调用小模型 FC 快路径（1~2s）被堵死
→
慢系统里也全面失效参数级安全校验 / 变量解析 / 短句柄 / 并行调度均不可用
→
永远走 10~40s 慢路径且是长尾错误与幻觉高发区
◎ 没有 schema 的工具，框架侧的时延优化几乎全部失效 —— 所以第一条要求：一切工具必须可 function call 化。

①schema 信息（FC 化）

决定快系统资格 · 选对工具（M）· prefill
  • 机器可读声明：参数 JSON Schema（类型/必填/枚举/默认）+ 返回值 schema + 错误码表
  • CLI 类：manifest 映射 flags 或高频子命令独立包装，命令串由框架拼装，模型不接触命令行
  • ArkTS 类：装饰器编译期提取，或伴生元数据文件过渡（CI 防漂移）
  • description 说清"何时用 / 何时不用"，与易混工具可区分
锚点：单工具 schema ≤150tk，示例放 skill 不常驻

②参数设计

压输出 token · 消标识符幻觉
  • 结构化字段 + 枚举优先，禁整段命令串 / JSON 字符串作参数
  • 内部标识符（bundleName / UUID）不让模型直接填：人类可读名或变量 / 短句柄解析
  • 可选参数必有默认值，必填 ≤5 个
锚点：单次调用 ≤50tk（现长尾 300tk → 仅解码 9s）

③执行时长

压 T_执行 · 不挂死 loop
  • 声明档位 quick/normal/long；long 档必须异步化（句柄 + 轮询）
  • 响应超时与取消，超时返回已完成部分
  • 声明只读 / 幂等 → 校验分级，省 0.5s 固定税
锚点：同步工具 P95 ≤2s，纳入 SLO 监控

④工具粒度

压 M（乘数，杠杆最大）
  • 一次调用 = 一个用户可感知的完整动作
  • 反模式：强制先查内部 ID（过细）/ 万能 action 分发（过粗）
  • 批量数组参数；高频序列合并由日志数据驱动
锚点：每省 1 个 loop = −5~11s

⑤返回值

压下轮 prefill · 纠错一次到位
  • 结构化返回 + 大小上限，超限分页给句柄；禁日志转储 / 整文件回传
  • 错误三要素：错误码 + 原因 + 可执行纠错线索 → 纠错只付 1 loop
  • 长路径 / 长 ID 登记短句柄；机器噪声走日志不进上下文
锚点：单次返回 ≤1~2k tk
共建倡议 要求即邀请：分级推进、平台配套、收益共享，数字门槛均开放讨论
分级推进MUST（准入门槛）/ SHOULD（评分建议）两档；量化门槛先拍后调，以埋点数据校准
平台配套框架方提供 CLI / ArkTS 转换脚手架、schema lint、返回值大小与 SLO 自动化检测，降低接入成本
存量整改按 调用频次 × 时延贡献 排序分批迁移，不搞一刀切；新工具按 checklist 准入
收益共享达标工具进入快系统能力集：高频任务 10~40s → 1~2s，调用量与曝光随之提升
