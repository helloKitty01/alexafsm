# 04 开放问题

待确认 / 待讨论的问题清单，随讨论更新。

## 已确认的系统事实

- ✅ **UAT** = user / assistant / tool 三角色消息流，即 loop 链路与对话历史。
- ✅ **工具**：稳定，放 tools 参数（缓存友好，无需改动）。
- ⚠️ **skill**：按 query 动态检索，注入 system prompt（当前最大的缓存杀手，
  迁移方案见 02 的"渐进式加载"）。
- ✅ 设计方向：环境上下文、query 检索内容与 UAT 消息流结合，渐进式加载。

## 待确认的系统事实

1. **skill 的规模**：skill 库总量多大？单个 skill 正文平均多少 token？
   决定 L0 的 skill 索引是否放得下全量，以及是否需要分级索引。
2. **推理侧**：调用商用 API（哪家？决定断点机制）还是自建 vLLM/SGLang
   （决定是否需要会话一致性路由）？
3. **当前压缩的触发条件与幅度**：每轮做还是阈值触发？压缩后保留比例？
4. **有没有度量 KV cache 命中率？**（API 返回的 cached_tokens 字段 /
   自建推理的 prefix cache hit metrics）没有度量就无法验证任何优化。
5. **环境上下文的体积与变化率**：每轮全量快照多大？相邻两轮差异比例多大？
   决定"增量注入"的收益。

## 待讨论的设计取舍

- 主动加载（load_skill）会增加一次工具调用往返，对延迟敏感场景是否可接受？
  是否需要"检索 top-1 被动注入 + 其余主动加载"的混合模式？
- 检索去重的粒度：条目级 ID 去重 vs 语义去重（后者可能引入不确定性，慎用）。
- 分代摘要的层数上限：摘要的摘要会不会失真过快？
- 结果指针（落盘 + 路径）的存储生命周期与会话恢复。
- 渐进式加载的内容在压缩时如何处理：已加载的 skill 正文可压缩为
  "skill 名 + 已加载标记"（可通过 load_skill 恢复，属于可恢复压缩）。
