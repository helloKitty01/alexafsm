# 04 开放问题

待确认 / 待讨论的问题清单，随讨论更新。

## 已确认的系统事实

- ✅ **UAT** = user / assistant / tool 三角色消息流，即 loop 链路与对话历史。
- ✅ **工具**：稳定，放 tools 参数（缓存友好，无需改动）。
- ✅ **skill**：几百个，两级结构已存在（description 索引 + load 取正文）；
  因全量 description 放不下，按 query 做 skill search，结果注入 L2 槽位
  （重写点）。skill search 不依赖 L0 类目。
- ✅ **miss 粒度**：L2 重写导致的 miss 集中在每个新 query 的首轮；
  同一 query 内后续 loop 迭代可命中。
- ✅ **裁剪现状**：UAT 按轮数（10 轮）滑窗裁剪，10 轮后每新一轮都裁；
  T（tool result）单独高频裁剪。改造方向：按 token 长度、双水位、攒批。
- ✅ **推理侧**：自建集群；存在 eviction（被全网用户流量逐出），
  需会话亲和路由 / KV 分层扩容治理。模型为 DeepSeek V4 / GLM 5.2。
- ✅ **拼接方式**：L1、L2 拼在 System Prompt 正文内；tools 为独立字段
  （不支持嵌入 System Prompt 中间），模板拼接在 SP 之后、UAT 之前。
  推论：现状 Tools 块被 L2 重写连带失效，失效范围 = |L2|+|Tools|+|UAT|。
- ✅ **现网基线**：上下文 ~60K；平均每请求输入 37K、命中 25K、miss 12K，
  命中率 ≈66%（量化收益估算见 08）。
- ✅ 设计方向：取消 L2 槽位，query 级内容渐进式进入 UAT 流；
  skill 迁移方案 A（search 结果随消息注入）先行，方案 B（search 工具化）演进。

## 待确认的系统事实

1. **环境上下文的体积与变化率**：每轮全量快照多大？相邻两轮差异比例多大？
   决定"增量注入"的收益。
2. **有没有度量 prefix cache 命中率？** 需区分排布性 miss 与驻留性 miss
   （同会话相邻请求间隔短仍 miss → 排布问题；间隔长后 miss → 驻留问题）。
3. **集群侧现状**：是否已有会话亲和路由？推理引擎（vLLM/SGLang？）
   是否已开启 prefix caching / CPU offload？
4. **上下文容量上限与双水位阈值**：模型窗口多大？80%/40% 阈值需按
   实际流量调参。

## 暂缓事项

- "默认 search + 伪造 UAT 上下文"注入方式（系统侧代模型发起 search，
  以合成的 assistant tool_call + tool result 形式写入消息流）：
  作为方案 A/B 之间的变体，暂不体现在幻灯片中，待方案 B 评估时一并讨论。

## 待讨论的设计取舍

- 主动加载（load_skill）会增加一次工具调用往返，对延迟敏感场景是否可接受？
  是否需要"检索 top-1 被动注入 + 其余主动加载"的混合模式？
- 检索去重的粒度：条目级 ID 去重 vs 语义去重（后者可能引入不确定性，慎用）。
- 分代摘要的层数上限：摘要的摘要会不会失真过快？
- 结果指针（落盘 + 路径）的存储生命周期与会话恢复。
- 渐进式加载的内容在压缩时如何处理：已加载的 skill 正文可压缩为
  "skill 名 + 已加载标记"（可通过 load_skill 恢复，属于可恢复压缩）。
