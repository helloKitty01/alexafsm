为什么闲聊省得最狠

闲聊每轮真正的新内容只有 ~1K 用户消息 + 回复,但现状要为它重算 10~16K 上下文——花 13K 算力回答一句闲聊。目标态历史全命中,只算 2K(U + device 增量),多轮闲聊 -83%~-88%。

时延视角(对体验最敏感的场景)

闲聊用户期待"秒回"。首 token 等待 ∝ 现算量:轮 3 从现算 13K 降到 2K,TTFT 的 prefill 部分降 ~85%——闲聊是时延收益的第一受益者。

注意

轮 1(-45%)收益有限:query 级内容首次进入必须算(下沉不消灭首次,只消灭重复)。单轮闲聊会话的主要收益来自 Tools 不再被连带(4.5K)。

问答的收益结构:两段式

排布改造只能消灭"重复计算"那部分(query级 + Tools + history 重算);10K 检索内容是每轮的新增底线,占目标态 13K 的 77%。所以问答封顶 -63%,是三类中降幅最小、但绝对量不小(轮 3 省 22K/轮)。

再往下降:两条结构性手段(抬结构上限)

① 检索结果落盘 + 指针化:全文落盘,上下文只注入摘要/高相关段(10K→3~5K);
② 裁剪时 webSearch 结果退化为指针(可 re-fetch),避免 10K 大块反复裁剪重写前缀——问答型正是 history 触顶(15K)的主要制造者。

止血项:device_info 若每次调用刷新,任务型受害最大

任务型是唯一有 loop 内调用(调用②③)的业务。若前台应用信息在 loop 期间实时刷新,调用② 也从 query 级断:轮 3 一轮成本从 30K 恶化到 ~53K。修复只需"每 query 采样一次、loop 内冻结"——几行代码,任务型立省 ~40%。上表按 loop 健康建模,实测 60% 命中率暗示现实更接近恶化态,止血收益在上表之外另算。

preload(skill search)的缓存视角评价

preload 用模拟 A/T 把 skill 正文注入消息流——形态本身是缓存友好的(追加式,少一次调用往返);改造后它天然融入"query 级内容随消息流进入"的目标架构,无需推翻。3 调用版(模型自行 load)多付一次调用但 skill 按需精准,两者并存即可。

时延视角

任务型总时延 = 多次调用 TTFT 之和,对 prefill 最敏感:轮 3 调用① 现算 27K→6K,-78%;整轮任务端到端提速最明显。

收益为什么从稳态 -75% 回落到 -57%:轮数分布的稀释与集中

  • 51% 单轮会话稀释平均数:无 query 切换点,只省 Tools 连带 4.5K(-23%~-45%);query 级内容首次进入必算,下沉消灭的是"重复"不是"首次";
  • 算力集中在长会话:6 轮+ 的 11% 会话贡献现状 prefill ~44%,多轮会话合计 ~85%——它们的节省是 -60%~-88%,钱省在最该省的地方;
  • 两个放大器不在 -57% 内:① device_info 止血(若 loop 确在断,现状比建模更差,实际节省更大);② 检索/skill 大块内容指针化(抬结构上限,问答可 -63%→-83%)。

时延收益(TTFT ≈ 现算量 ÷ prefill 吞吐)

稳态轮次首调用:闲聊 -85%、任务 -78%、问答 -63%;绝对秒数待 prefill 吞吐参数回填换算。轮数越深、原来越慢的请求改善越大。

统计闭环:怎么证明这些数(不靠估算)

动作说明
① 引擎实报逐调用透传 cached_tokens → 实际推理量 = 输入 − 命中
② 应用记账当轮新增消息 tokenize 计数 → 必要推理量;白算量 = ①−②,验收 = 归零
③ 四维打标业务类型(闲聊/问答/任务)× 调用类型(query 首调/loop 调用)× 轮次 × 会话,直接验证 P2–P4 每格数字
④ 灰度 A/B同期同流量对比每调用实际推理量与 TTFT,收益即报表

待回填参数(不影响结论方向,影响精度)

① 三类业务真实流量占比(现按 40/40/20 假设);② prefill 吞吐(时延换算绝对值);③ device_info 刷新时机确认(决定止血收益大小);④ 6 轮+ 会话的轮数均值(现按 8 轮)。

结论:排布改造(query 级下沉 + Tools 解除连带 + 裁剪改造)按真实轮数分布加权,整体 prefill 算力与首 token 时延约降 57%;叠加 device_info 止血与检索指针化,长会话场景可达 -70%~-88%。每一格数字都可由"引擎实报 + 应用记账 + 四维打标"直接验证。
