⚡ 每个新 query 到来,这 8K 被整体重写 → 缓存从此断裂,其后 UAT 历史全部重新计算
◀ 稳定命中(静态全网共享 + 用户级会话内不变) 重写点 追加式历史,本可命中,却被前面 8K 连累 ▶

一轮 query 内部解剖:默认 2 次模型请求(skill load / 工具调用 / 融合回复,三选二)

U 用户query ~1.5K→ 请求①→ A 动作1(如 skill load)→ T 结果 ~2.5K
↳ 请求②→ A 动作2(工具调用 / 融合回复)
一轮 query 沉淀进历史的 UAT 增量 ≈ 5K(U 1.5K + 动作/结果 3.5K)。
请求② 是追加式:前缀=请求①的严格超集,天然命中,只算 ~3.5K 新增;
请求①(query 切换点)是 miss 重灾区:8K 重写 + 全部历史被连累重算。

现状:第 q 轮 query 首请求要重算多少

8K(重写) + 5K×(q−1)(历史) + 1.5K(新U)

第 1 轮 12.5K → 第 3 轮 19.5K → 第 5 轮 29.5K,随轮数线性增长——轮数越深,浪费越大。

目标:query 相关内容下沉进消息流

8K 槽位取消:skill 索引进静态区、正文按需 load(已在 T 中)、检索增量随 U 注入(去重后 ~2K)。前缀变为纯追加,历史全命中,每轮首请求只算 ~3.5K 新增,与轮数无关。

一句话:模型每次回答都要把整段上下文重新"读"(prefill)一遍;缓存让读过的部分免于重算,但 query 相关 8K 每轮重写,把它身后的全部历史一起拖下水——这就是推理算力浪费的来源。
KV Cache 收益闭环 · v2参数为内部预估:静态 20K / 用户 3K / query 相关 8K / UAT 5K·轮 / 每轮 2 次请求;待实测(文档12)回填修正

为什么轮数越深省得越多

现状每轮首请求重算 8K + 5K×(q−1),历史越长拖累越重;目标每轮只算 ~3.5K 新增,与轮数无关。两条线的差距随轮数张开——长会话、重度用户,恰恰省得最多。

怎么统计验证(不靠估算)

数据来源
实际推理量 = 输入 − 命中推理引擎逐请求实报 cached_tokens
必要推理量 = 当轮新增应用侧对新增消息记账
白算量 = 实际 − 必要改造达标 = 趋近 0,上看板防回退
收益确认改造灰度 A/B,同期对比每请求实际推理量

对照:无缓存世界

同一会话若完全无缓存需 prefill ~440K;现状 118K(缓存已省 73%),改造后 38K(再省 68%)。

结论:按当前预估参数,改造后每请求实际推理量 11.8K → 3.8K(prefill 计算量 −68%),且轮数越深省得越多(第 5 轮 −79%);模型推演的 11.8K 与现网实测 12K 吻合,账目可信、灰度 A/B 可验证。
