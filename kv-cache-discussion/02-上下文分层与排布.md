# 02 上下文分层与排布

## 原则：按"变化频率"排序，而不是按"逻辑重要性"排序

上下文从前到后，变化频率必须单调递增。稳定的在前，易变的在后。
这是 KV cache 友好排布的唯一硬原则。

```text
┌─────────────────────────────────────────────┐
│ L0 产品级稳定（整个产品所有会话相同）          │  ← 永不变化
│    - system prompt 主体（不含任何动态内容）    │
│    - 工具全集 schema（当前已是稳定的 ✅）      │
│    - skill 索引（名称 + 一句话描述，全量静态）  │
├─────────────────────────────────────────────┤
│ L1 会话级稳定（会话开始时确定，会话内冻结）     │  ← 每个会话变一次
│    - 用户画像 / 长期记忆快照                  │
│    - 会话级环境信息（工作目录、日期等粗粒度）   │
├─────────────────────────────────────────────┤
│ L2+L3 UAT 消息流（user/assistant/tool）      │  ← 只追加，不修改
│    - 用户 query + 随附的 query 级动态内容     │
│    - assistant 决策 / tool 调用与结果         │
│    - 渐进式加载的 skill / 知识 / 记忆          │
└─────────────────────────────────────────────┘
```

## 渐进式加载：动态内容与 UAT 消息流结合（核心方案）

结论：**可以且应该**。所有 query 级动态内容都不进前缀区（system prompt），
而是作为 UAT 消息流的一部分渐进进入上下文。具体分两条通道：

### 通道一：被动注入（随 user message 附带）

系统侧在构造当轮 user message 时，把 query 级内容包在结构化标签里一并注入：

```text
user#N: <env_context>本轮环境上下文（仅与上轮的增量）</env_context>
        <retrieved>本轮检索的知识/记忆（仅未注入过的条目，按 ID 去重）</retrieved>
        <query>用户原始问题</query>
```

- 之前的全部历史照常命中，只有新增部分需要 prefill。
- **不原位刷新**旧的注入块；环境上下文尽量注入增量（diff）而非全量快照。

适合：体积小、当轮大概率用到、模型不知道该主动去查的内容
（如环境状态变化、高置信度的检索命中）。

### 通道二：主动加载（skill 按需拉取，替代 system prompt 注入）

skill 从 system prompt 中移出，改为：

1. L0 只放**全量 skill 索引**（名称 + 一句话描述）。索引是静态的，
   skill 库更新才变，属于稳定前缀。
2. 提供稳定的 `load_skill(name)` 工具（工具集不变，只是加一个成员）。
3. 模型根据当前任务自行决定加载哪个 skill，skill 正文以 **tool result**
   形式进入 UAT 消息流。

好处：

- skill 正文进入的是消息流尾部，append-only，缓存零破坏；
- 只加载真正用到的 skill（原来按 query 检索 top-k 是"猜"，现在是模型按需拉取）；
- 已加载的 skill 在本会话内持续可见（就在历史里），无需重复检索。

若担心模型漏加载，可保留检索作为辅助：检索命中的 top-1 skill 通过
**通道一**随 user message 附带注入（依旧不进 system prompt），
其余靠模型主动 `load_skill`。

### 两条通道的选择标准

| 维度 | 通道一（被动注入） | 通道二（主动加载） |
| --- | --- | --- |
| 谁决定加载 | 系统（检索器） | 模型 |
| 进入位置 | 当轮 user message | tool result |
| 适合内容 | 环境增量、高置信检索命中 | skill 正文、低置信/大体积知识 |
| 额外成本 | 无 | 一次工具调用往返 |

## 其他决策点

### UAT 消息流本身：只追加，不修改

- 历史消息（含 tool result）一旦写入不回头改动；
  所有"重写历史"操作统一攒到压缩时刻执行（见 03）。
- 序列化必须确定性（JSON 键序、空白符固定），
  否则同样的数据两次生成不同 token 序列，缓存悄悄失效。

### system prompt 卫生

- 移除 skill 后，system prompt 应做到产品级静态：无时间戳（最多到"天"，
  或干脆把时间放 L1/消息流）、无用户变量、无检索内容。

### 缓存断点（Anthropic 风格显式 cache_control）

四个断点的典型分配：L0 工具区末尾、L0 system 末尾（含 skill 索引）、
L1 末尾、UAT 消息流尾部滚动。OpenAI / vLLM 自动前缀缓存则只需保证排布即可。

## 迁移前后对比

迁移前（每 query 全量 miss）：

```text
system: 静态指令… + [本轮检索出的 3 个 skill 正文]   ← 每 query 变，前缀全灭
tools:  [固定工具集] ✅
messages: UAT 历史…
```

迁移后（前缀完全稳定）：

```text
system: 静态指令… + [全量 skill 索引（静态）]
tools:  [固定工具集 + load_skill]
messages:
  user#1:   <env_context>…</env_context><query>…</query>
  assistant: load_skill("xxx")
  tool:      [skill xxx 正文]                        ← 渐进式进入消息流
  …全部 append-only，历史全命中…
```
