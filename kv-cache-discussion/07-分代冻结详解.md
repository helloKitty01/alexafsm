# 07 分代冻结详解

对 03/v2-P5 中"分代冻结"的完整展开：机制、两种形态、时间线算账、
工程陷阱。

## 1. 要解决的问题

裁剪/摘要 = 重写前缀，KV cache 从重写点断裂。若每轮都动历史
（如按轮数滑窗），则每轮都断。分代冻结的主张：

1. 裁剪产物（摘要块/指针块）一旦写入，**字节级不再改动**，
   成为新的稳定前缀的一部分；
2. 两次裁剪事件之间只有尾部追加，每轮前缀是上一轮的严格超集，全部命中；
3. 只在下一次裁剪事件、且只在固定的分代边界处允许改历史。

## 2. 两种形态

### 合并式（基础版）

每次压缩把"上一代摘要 + 一段原文"合成新一代，摘要区始终一块：

```text
压缩事件 k： [L0][L1][G_k][原文尾部]   G_{k+1} = summarize(G_k + 原文段)
```

缺点：每次压缩重写摘要块本身，miss 从摘要区起点开始。

### 堆叠式（推荐目标形态）

新摘要**追加**在旧摘要之后，旧代完全不动：

```text
[L0][L1][G1 冻结][G2 冻结][G3 冻结][原文尾部…追加中…]
```

- 压缩事件只写入新的一代，**miss 只从新代位置开始**，
  之前的 L0/L1/G1/G2 照常命中——连压缩那一次的重建量都大幅缩小。
- 代价：摘要块累积。当摘要区总量超预算（如 15k token）时做低频的
  **大合并（major compaction）**：G1..Gn 合成一块，这次 miss 从合并点起。
- 类比：LSM-tree 的 minor/major compaction；分代 GC 的新生代/老年代。
  高频改动在尾部小范围处理，越老的越少动，大整理低频执行。

## 3. 时间线示例（容量 100k，高水位 80k，低水位 40k，L0+L1 = 10k）

| 阶段 | 事件 | miss 量 |
| --- | --- | --- |
| 第 1–40 轮 | 原文累积至 80k | 每轮命中 |
| 压缩事件 1 | 第 1–30 轮（60k）→ G1 ≈ 4k；保留 31–40 轮原文 | ≈24k（G1+保留原文；L0/L1 命中）|
| 第 41–70 轮 | G1 冻结，只追加 | **每轮全命中** |
| 压缩事件 2 | 第 31–55 轮 → G2，追加于 G1 后 | ≈20k（G1 不动，从 G2 起）|
| 若干代后 | 摘要区超 15k → 大合并 G1..G4 → G' | 从 G' 起，低频 |

成本对比（50k 平均上下文、缓存价 0.1×）：

- 滚动摘要 / 每轮滑窗：每轮 ~50k 全 miss。
- 分代冻结：命中轮 ~5k 等效；压缩轮一次 ~25k 摊到 ~30 轮 <1k/轮。
- **每轮等效成本差 8 倍以上。**

## 4. "冻结"的工程含义：字节级不变

冻结不是"逻辑上不更新"，是渲染后的 token 序列一个字节不能变。
常见隐性破坏：

1. 摘要里含会更新的字段："截至第 N 轮"、"当前进度 60%"、时间戳
   → 每轮重渲染每轮全断。摘要内容必须只描述已冻结的过去。
2. 摘要以结构化数据存储、每次请求重新序列化：dict 键序、浮点格式、
   空白符的不确定性悄悄改字节。**正确做法：持久化渲染后的最终字符串**，
   会话状态存那串字节，会话恢复时原样拼回。
3. 事后修正冲动："摘要有个错顺手改一下" → 不行，攒到下一次压缩事件。
4. 分代边界未对齐消息边界 / 拆散 tool call-result 配对。
   注意 DeepSeek V4 将 T 合并渲染进 user 消息（见 06），
   边界要按**渲染后的真实 token 序列**划分。

## 5. 与现状的对照

| 维度 | 现状（10 轮滑窗） | 分代冻结 |
| --- | --- | --- |
| 裁剪事件频率 | 长对话阶段每轮 | 双水位触发，~几十轮一次 |
| 重写位置 | 可变区最前端 | 仅新代写入点（堆叠式） |
| 事件之间 | 每轮 miss | 零重写，全命中 |
| T 裁剪 | 单独高频执行 | 指针化攒批进同一事件 |

分工提醒：分代冻结治理**头部/中段**的重写；thinking 模式剔除历史
reasoning 造成的**尾部**分叉（见 06）是独立机制，度量时分开归因。
