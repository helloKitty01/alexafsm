统计点位:每次 LLM 调用记一条明细

点位内容状态
① 输入量prompt_tokens(引擎 usage)现成
② 命中量cached_tokens(引擎 usage)现成
③ 模块边界快照构造时记录各段 token 数与边界:SP 固定 / 动态上下文 / Tools / history / 当轮新增埋点
④ 新增记账当轮新消息 tokenize 计数 = 必要推理量埋点
⑤ 标签业务类型 × Q 序号 × 调用类型 × 会话 ID × 方案标识(当前/目标)埋点
⑥ 辅助completion_tokens / 时间戳现成

开发量只有 ③⑤ 两处:构造器本来就知道每段边界和标签,成本是"顺手写进日志";tokenizer 与推理侧一致。

一条明细长这样(含归因所需的全部信息)

{"session":"s-889", "biz":"问答", "q":2, "call":"首调",
 "scheme":"当前",              ← 方案标识,两方案同表
 "prompt":56200, "cached":26100, ← 引擎实报
 "bounds":[25500,30000,34500,45000], ← 模块边界
 "new":12100}                  ← 当轮新增记账

落地节奏:第 1 周接通 ①②,先出真实命中率基线 → 第 2 周补 ③④⑤,出完整归因 → 目标方案灰度起,两方案同表对比,收益即报表。

怎么算:断点归因——miss 构成自动拆解,无需人工

实际推理量 miss = 输入 − 断点d(=cached_tokens) = 白算(断点到 history 末,自动拆 动态│Tools│history) + 新增
命中 d=25.5K
动态 4.5
Tools 4.5
history 10.5
新增 12

收益页每个色块 = "断点 − 边界"的查询结果,图不是推演,是日志(示例:问答 Q2)。

怎么比:当前方案 vs 目标方案,同一把尺子

当前方案(对照)动态上下文在 SP 内、每轮重写 → 连带 Tools + 全部历史重算
目标方案(实验)动态上下文精简 2K、下沉 UAT 随 U 追加 → 除当轮新增外全部命中

对比方式:流量按会话粒度打方案标识(避免同会话混排布打脏缓存),两方案走同一套点位、同一条管线、同一张表;按业务 × Q 序号切片对齐,灰度放量 1% → 10% → 50%,质量护栏(回复质量/任务成功率)不劣化。

关键对比项当前方案目标方案(预期)判定标准
每调用实际推理量~15K(实测)~6-7K与推演偏差 <15%,收益模型成立
白算量/调用~10K<1K → 0硬验收线:除新增外全命中
命中率~60%85%+与白算量交叉验证
TTFT(prefill 部分)基线约 -69%分 Q 序号看单调改善
