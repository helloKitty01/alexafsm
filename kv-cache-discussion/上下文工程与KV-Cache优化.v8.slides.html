①　query 切换点全量 miss

query级内容重写 → 失效 = query级 + Tools + UAT 全部历史，随轮数线性增长；Tools 内容稳定却被连带重算。loop 内可命中，损失集中在每个新 query 首轮。

②　10 轮滑窗裁剪 = 长对话每轮全量 miss

聊过 10 轮后每新一轮裁最旧一轮，前缀头部每轮变化；T 体积大（skill 正文）被单独高频裁剪，进一步打碎前缀。长对话阶段比①更严重。

③　相关性绑定丢失 + 历史证据被覆盖

query级槽位与 query 无显式对应；每轮覆盖式更新，第 N 轮依赖第 N-2 轮检索结果时证据已丢，去重无从谈起。

④　驻留竞争（eviction）

自建集群缓存容量有限，被全网用户流量逐出——前缀不变 ≠ 命中。现网 34% miss 中两类占比未拆分。

综上，缓存失效有两个来源：问题① query级内容每次重写 ＋ 问题② 滑窗裁剪每轮改历史；另有问题④ 驻留竞争需集群侧配合 —— 下页逐项治理

附录 B裁剪改造细节：按轮数滑窗 → 按长度双水位

现状（反模式）

  • UAT 按轮数（10 轮）滑窗：聊过 10 轮后每新一轮裁最旧一轮 = 每轮重写前缀 = 每轮全量 miss
  • T（tool result）单独高频裁剪，skill 正文 token 大，裁剪更频繁，前缀被反复打碎

目标：按 token 长度、双水位、攒批、产物冻结

  • 按长度触发：达到 ~80% 容量才裁，与轮数解耦（轮数不反映真实占用，skill 大 T 尤其如此）
  • 一次多裁：直接裁到 ~40% 低水位，避免"裁一点→又满→再裁"的每轮抖动
  • 攒批：T 的裁剪与 UAT 裁剪合并到同一时刻，一次 miss 付清所有账
  • 产物冻结：裁剪/摘要产物写入后字节级不再改动，两次裁剪之间全部轮次命中（分代冻结与堆叠式详见文档 07）

从远到近分级保真（可恢复优先于有损丢弃）

内容裁剪处理恢复方式
已 load 的 skill 正文退化为"名称+已加载标记"re-load
retrieved 正文退化为 ID 指针按 ID 重拉

skill 正文和检索条目是最大的 token 占用，也恰好最容易指针化恢复——优先指针化，少做有损摘要。

附录 C缓存驻留诉求的参考实现方向（自建集群）

问题模型

  • 实际命中率 = 排布正确性 × 驻留概率：排布做对了，缓存仍可能被全网用户流量按 LRU 逐出
  • 两类 miss 成因不同：排布性 miss（前缀被改写，可根除）vs 驻留性 miss（容量竞争，只能缓解）
  • 度量上要拆开：同会话相邻请求间隔短仍 miss → 排布问题；间隔长后 miss → 驻留问题
  • 现网 66% 命中率中两类 miss 的占比，需度量拆分后校正收益预估
先根除排布性 miss，驻留治理才有意义——否则每 query 都在重建，驻留无从谈起

降低被逐出的概率

  • 会话亲和路由：同一会话固定路由到同一推理实例，避免跨实例必然 miss
  • 产品级 + Tools 公共前缀天然常驻：全网用户共享，是集群里最热的条目，几乎不会被逐出
  • 缓存分层扩容：HBM 之外用 CPU 内存 / 本地盘做 KV offload（vLLM / SGLang / LMCache 类方案）
  • loop 内迭代间隔短，天然处于驻留窗口内；危险区在用户两次 query 之间的长间隔

降低被逐出后的损失

  • 前缀瘦身：重建成本正比于前缀长度，按长度双水位裁剪直接控制损失上限
  • 指针化内容（skill / retrieved）本身不占前缀，被逐出后无需重建

估算口径：现网输入 37K/请求（命中 25K、miss 12K）；缓存价 0.1×；目标态 miss ≈ 当轮新增 ~2K + 裁剪/尾部剔除摊销 ~1K；驻留性 miss 占比待路径①度量校正。敏感性：目标 miss ±1K，成本降幅在 -50% ~ -59% 区间。

为什么上限是 ~92% 而非 100%：命中率分母含每轮首次出现的 token（新 query、工具结果、检索增量），缓存中不存在、必然 miss（~2K/37K ≈ 5 个点）；口径与业界一致（hit_tokens / prompt_tokens），DeepSeek V4 agent/RAG 生产负载社区实测为 90–96%，本预估处于该区间。若按"可缓存部分的命中率"口径（剔除首次出现内容），目标即接近 100%。故对外目标定为挑战 90%+，预留驻留性 miss 的不确定性空间。
