# 05 渐进式加载详细设计：L2 内容随 user message 结构化注入

本篇是 02 中"通道一（被动注入）"的详细设计。核心决策：
**所有 query 级动态内容（环境上下文、检索的知识/记忆）以结构化标签
包裹后放进当轮 user message，与 query 原文物理绑定，只追加、不修改。**

## 1. 为什么不放 system prompt：三个独立的理由

### 1.1 缓存（前面已讨论）

system prompt 位于前缀最前部，每轮改写 = 每轮全量 cache miss。

### 1.2 相关性绑定丢失

检索内容是**为特定 query 服务的**。放 system prompt 意味着：

- 它和它服务的 query 之间隔着整个对话历史，物理距离极远；
- 没有任何显式标记说明这批内容对应哪个 query，多轮之后模型只能靠猜；
- 模型普遍存在近因效应（对上下文尾部更敏感），把当轮证据放在
  离生成位置最远的头部，注意力利用效率最差。

放 user message 里则相反：证据与 query 相邻出现、显式绑定，
"这批知识是为回答这个问题准备的"这一关系无需推断。

### 1.3 历史证据丢失（时间线断裂）

system prompt 是单例槽位，每轮注入必然**覆盖**上一轮的检索内容。
后果：第 N 轮的回答如果依赖第 N-2 轮检索出的知识，证据已经不在上下文里了；
模型历史发言所依据的材料消失，历史对话变得"无据可查"，
既伤多轮推理，也伤可审计性。

放消息流里则天然保留完整时间线：每轮 query 和它的支撑证据一起
留在 UAT 历史中，成为事实记录的一部分。**这也是去重的前提**——
正因为旧条目还在历史里可见，后续轮次命中同一条目才可以不再注入。

## 2. 消息构造规范

### 2.1 当轮 user message 的结构

```text
<turn_context>
  <env>
    <!-- 首轮：全量快照；后续轮：相对上轮的增量（新增/变更/失效项） -->
    <item key="cwd" op="set">/workspace/proj</item>
    <item key="branch" op="set">feature/x</item>
  </env>
  <retrieved>
    <!-- 仅本会话未注入过的条目，按 id 去重；固定按 id 排序 -->
    <item id="kb_1042" source="knowledge" score="0.91">…正文…</item>
    <item id="mem_0335" source="memory"    score="0.87">…正文…</item>
  </retrieved>
  <skill_hint>
    <!-- 可选：检索 top-1 skill。低置信时只给名字，由模型决定是否 load_skill -->
    <item id="skill_deploy" mode="name_only"/>
  </skill_hint>
</turn_context>
<query>
用户原始输入，原样保留，永远放在消息最后
</query>
```

规则：

1. **标签顺序、属性顺序、排序规则全部固定**（确定性序列化，
   同样的数据必须生成同样的 token 序列）。
2. **query 原文永远在最后**：最接近生成位置；同时和系统注入内容
   界限清晰，模型不会把注入内容误当用户发言。
3. **空块省略**：无增量时不输出空标签，省 token。
4. **一旦发出，永不回改**（重写统一发生在压缩时刻，见第 4 节）。

### 2.2 构造伪代码

```python
def build_user_message(query: str, session: Session) -> str:
    env_now = collect_env(query)
    env_delta = diff(session.env_snapshot, env_now)   # 首轮为全量
    session.env_snapshot = env_now

    hits = retrieve(query, top_k=K)                   # 知识 + 记忆
    new_items = [h for h in hits if h.id not in session.injected_ids]
    session.injected_ids.update(h.id for h in new_items)

    skill = retrieve_skill_top1(query)
    hint = (skill.full_text if skill.score > HIGH_CONF
            else skill.name_only) if skill else None

    return render(env=env_delta,
                  retrieved=sorted(new_items, key=lambda h: h.id),
                  skill_hint=hint,
                  query=query)
```

会话级状态只有两个：`env_snapshot`（用于算增量）和
`injected_ids`（用于去重），都很轻。

### 2.3 去重的语义

命中已注入条目时**静默跳过**——内容仍在历史某轮的
`<turn_context>` 里，模型看得见。不需要"参见第 M 轮"之类的引用标记，
那是给模型增加解析负担。

## 3. 多轮时间线示例

```text
user#1:  <turn_context><env>全量快照</env>
         <retrieved>r1, r2</retrieved></turn_context>
         <query>Q1</query>
assistant#1: …（基于 r1/r2 回答）…
user#2:  <turn_context><env>增量: branch 变更</env>
         <retrieved>r3</retrieved></turn_context>      ← r1 再次命中，静默去重
         <query>Q2</query>
assistant#2: load_skill("deploy")
tool#2:   [skill 正文]                                  ← 通道二，append-only
assistant#2: …（基于 r1(历史可见) + r3 + skill 回答）…
```

每一轮的前缀都是上一轮的严格超集：**缓存全程命中，只为新增部分付费。**

## 4. 与压缩的交互（衔接 03）

压缩时对 `<turn_context>` 块按可恢复性分级处理：

| 内容 | 压缩处理 | 恢复方式 |
| --- | --- | --- |
| `<env>` 旧增量 | 直接丢弃，压缩摘要中给出当前快照 | 无需恢复 |
| `<retrieved>` 正文 | 退化为 id 列表（指针） | 按 id 重新拉取 |
| 已加载 skill 正文 | 退化为 "skill 名 + 已加载标记" | load_skill 恢复 |
| `<query>` 原文 | 近端保留原文，远端进结构化摘要 | — |

注意：`<retrieved>` 条目压缩成指针后，其 id 应从 `injected_ids`
中移除（或标记为 evicted），后续再命中时允许重新注入。

## 5. 示例：系统时间与手机前台应用的注入

这两类信息是"每请求都在变的环境上下文"的典型代表，处理原则相同：
**只进当轮 user message 的 `<env>` 块，追加式进入，绝不进前缀区。**

```text
user#N:
<turn_context>
  <env>
    <item key="time">2026-08-25 09:12（分钟级）</item>
    <item key="foreground_app" op="switch">微信 → 支付宝</item>
  </env>
  …
</turn_context>
<query>…</query>
```

为什么缓存安全：内容变化只出现在消息流尾部的**新增部分**，
历史前缀一个字节未动——哪怕每轮时间都不同，也只为几十个新 token
付 prefill。

三条禁忌：

1. **不进 system prompt / L0 / L1**：每请求重渲染 = 全量 miss。
   Manus 明确点名"system prompt 开头放秒级时间戳"是头号缓存杀手。
2. **不原位刷新**：loop 中途需要更新（时间推移、用户切换应用）时，
   以新消息或随下一条 tool result **追加 delta**，不回改已发出的块。
3. **粒度克制**：时间到分钟级即可（秒级无意义且引入 token 噪音）；
   前台应用只在**变化时**注入 delta，不每轮重复全量。

特殊情况：

- **需要精确当前时刻**（如定时计算）：提供 `get_current_time` 工具，
  用时查询、结果以 T 追加——精确且缓存安全。
- **天级日期**这类会话内基本不变的信息可放 L1（会话开始注入一次）；
  跨天的长会话不回改 L1，改为在消息流里追加一条日期变更通告。
- 对照业界：Claude Code 的易变状态一律以消息流 `<system_reminder>`
  标签注入、从不修改 system prompt——与本设计同构。

## 6. 收益小结

| 维度 | system prompt 注入（现状） | user message 结构化注入（本方案） |
| --- | --- | --- |
| KV cache | 每轮全量 miss | 全程命中，只为增量付费 |
| query 相关性 | 无绑定、距离远 | 物理相邻、显式绑定 |
| 历史证据 | 每轮覆盖，时间线断裂 | 完整保留，可去重、可审计 |
| 去重 | 不可能（旧内容已丢） | 条目级 ID 去重，天然支持 |
| 压缩配合 | 无 | 指针化可恢复压缩 |
