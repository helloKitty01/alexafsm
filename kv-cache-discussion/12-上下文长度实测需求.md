# 12 上下文模块长度实测需求

## 目的

替换 11 中的假设值(Tools/L2 等),锁定收益测算的输入参数。
请基于内部实际线上数据统计,按下方 schema 返回。

## 背景与模块定义(先读这节,再做映射)

我们在分析 agent 系统的 KV cache 命中率,需要把每次送给模型的完整
上下文按"变化频率"切成几个模块并测量长度。系统的上下文物理顺序为:

```text
[System Prompt(内含 L0 + L1 + L2)] → [Tools 块] → [UAT 消息流]
```

各模块定义与识别方法:

| 模块 | 定义 | 怎么识别 |
| --- | --- | --- |
| **L0 产品级静态** | system prompt 中**所有用户、所有会话都完全相同**的部分:agent 角色设定、关键原则、通用行为规范等 | 抽多个不同用户的会话对比 system prompt,逐字相同的公共部分即 L0 |
| **Tools 块** | 请求的 tools 参数(工具全集 schema)经 chat template 渲染后的文本块,拼接在 system prompt 之后、消息流之前 | 工具集稳定,取任一请求渲染后的 Tools 段落即可;注意测**渲染后**长度而非 JSON 原文 |
| **L1 会话级** | system prompt 中**同一会话内不变、但因用户而异**的部分:用户画像、长期记忆快照、会话级环境信息(工作目录、日期等) | 同一会话内多个请求间不变、跨用户不同的 system prompt 片段 |
| **L2 query 级槽位** | system prompt 中**每个新用户 query 到来时被整体重写**的部分:skill search 检索出的 top-k skill 描述、query 相关知识、query 相关用户信息、环境上下文 | 同一会话内相邻两个 query 的请求对比 system prompt,发生变化的片段即 L2(这是本次测量最关键的模块) |
| **UAT 消息流** | messages 数组:user(用户 query)/ assistant(模型回复,含 tool call)/ tool(工具执行结果)三种角色的消息序列 | 即对话历史本身;需分别统计三类消息的单条长度 |

术语对照:一个"query"= 用户发起的一轮对话;一个 query 内模型可能
多次调用工具循环执行,每次"assistant 发起 tool call → tool 返回结果
→ 再次请求模型"记为一次"loop 迭代",每次迭代就是一次独立的模型请求。

## 测量口径(必须遵守)

1. **单位一律为 token 数**,使用与推理侧相同的 tokenizer;
2. 对**渲染后的最终序列**计数(即 chat template 拼接完成、含控制 token 的
   实际送入模型的序列),不是对原始文本或 JSON 计数;
3. 分布字段给 **均值 / p50 / p90**;固定不变的模块(如 L0)给单值即可;
4. 注明样本范围(时间窗、会话数、请求数)。

## 补充说明

- `L2_query_slot` 是最关键的待测项:它决定 query 切换点 miss 的固定项;
- 若某模块无法单独拆出,可给"包含关系 + 合计值"并在 note 里说明;
- 有裁剪/压缩逻辑触发的会话,请在 note 标注其占比,避免污染分布。
