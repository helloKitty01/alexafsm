# 01 问题定义

## 现状架构（已确认）

系统当前的上下文**已经是四层结构**，从前到后依次为：

```text
┌────────────────────────────────────────────────────┐
│ L0 产品级：system prompt / agent 关键原则            │ 所有用户相同，稳定 ✅
│           工具全集（tools 参数，稳定）✅              │
├────────────────────────────────────────────────────┤
│ L1 用户级（会话级）：固定加载的用户相关信息            │ 与 query 无强相关，
│                                                    │ 更新维度覆盖多轮对话 ✅
├────────────────────────────────────────────────────┤
│ L2 query 级：基于 query 检索的 skill、               │ ⚠️ 每个 query 原位重写
│             query 相关知识、query 相关用户信息        │
├────────────────────────────────────────────────────┤
│ L3 loop 级：UAT（user/assistant/tool）消息流         │ 追加式，但位于 L2 之后
└────────────────────────────────────────────────────┘
```

## 核心问题：L2 是重写点，失效范围 = L2 + 整个 L3

分层意图本身是对的（L0/L1 的稳定性利用得很好），病灶只有一个：

**最易变的 L2 在物理排布上位于 L3（UAT 历史）之前。**

KV cache 要求前缀逐 token 一致。每个新 query 到来时 L2 被原位重写，
缓存从 L2 起点断裂，其后的**整个 UAT 历史全部重新 prefill**。

### 问题的三个维度

1. **失效范围大且随对话增长**：每轮 miss 的量 = |L2| + |L3 全部历史|。
   对话越长，L3 越大，浪费越大——成本随轮数近似线性增长，
   而长对话恰恰是最需要缓存的场景。
2. **相关性绑定丢失**：L2 是单例槽位，检索内容与它服务的 query 没有
   显式对应关系，且物理上与当前 query 隔着整个 L3。
3. **历史证据丢失**：L2 每轮覆盖式更新，上一轮 query 检索出的
   skill/知识被冲掉。第 N 轮如果依赖第 N-2 轮检索的内容，证据已不在
   上下文中；历史发言"无据可查"，去重也无从谈起。

### 排布原则的表述

上下文从前到后，变化频率必须单调递增；等价地：
**"原位重写"的区域绝不能排在"追加式"区域之前。**
现状的 L2（每 query 重写）排在 L3（追加式）之前，正好违反此原则。

### 次要问题

- 上下文超长时从远到近压缩：压缩本身必然造成一次性 miss（机制上无解），
  需要用触发策略摊销（见 03）。
- L1 更新时同样使 L1 之后全部失效，但更新频率覆盖多轮对话，
  属于低频事件，代价可接受；注意把 L1 的多项更新攒批执行即可。

## 解法方向（详见 02 / 05）

**取消 L2 这个固定槽位，把 query 级内容下沉进 L3 消息流**，
与各轮 query 物理绑定、渐进式进入：

- 被动注入：环境上下文增量、检索增量随当轮 user message 进入；
- 主动加载：skill 通过 load_skill 按需拉取，正文以 tool result 追加。

排布收敛为 L0 → L1 → UAT 流（append-only），每轮前缀是上一轮的
严格超集，缓存全程命中。
