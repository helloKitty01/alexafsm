# 01 问题定义

## 现状架构（已确认）

系统当前的上下文**已经是四层结构**，从前到后依次为：

```text
┌────────────────────────────────────────────────────┐
│ L0 产品级：system prompt / agent 关键原则            │ 所有用户相同，稳定 ✅
│           工具全集（tools 参数，稳定）✅              │
├────────────────────────────────────────────────────┤
│ L1 用户级（会话级）：固定加载的用户相关信息            │ 与 query 无强相关，
│                                                    │ 更新维度覆盖多轮对话 ✅
├────────────────────────────────────────────────────┤
│ L2 query 级：skill search 检索的 top-k description   │ ⚠️ 每个 query 原位重写
│（正文经 skill load 获取）、query 相关知识、用户信息    │
├────────────────────────────────────────────────────┤
│ L3 loop 级：UAT（user/assistant/tool）消息流；        │ 追加式，但位于 L2 之后；
│ 按轮数（10 轮）滑窗裁剪，T（tool result）另行高频裁剪  │ ⚠️ 裁剪即重写前缀
└────────────────────────────────────────────────────┘
```

补充事实：

- skill 库有几百个，全量 description 放不下，因此按 query 做 skill search，
  结果注入 L2 槽位；skill 正文本来就通过 load 按需获取（两级结构已存在）。
- 推理侧为**自建集群**，KV cache 容量有限，会被全网用户流量逐出（eviction）。

## 核心问题：L2 是重写点，失效范围 = L2 + 整个 L3

分层意图本身是对的（L0/L1 的稳定性利用得很好），病灶只有一个：

**最易变的 L2 在物理排布上位于 L3（UAT 历史）之前。**

KV cache 要求前缀逐 token 一致。每个新 query 到来时 L2 被原位重写，
缓存从 L2 起点断裂，其后的**整个 UAT 历史全部重新 prefill**。

### 问题的四个维度

1. **query 切换点全量 miss**：L2 重写导致失效 = |L2| + |L3 全部历史|，
   随轮数线性增长。注意粒度：同一 query 内的后续 loop 迭代前缀只增不改、
   可正常命中，**损失集中在每个新 query 的首轮**。
2. **滑窗裁剪 = 长对话阶段每轮全量 miss**：UAT 按轮数（10 轮）滑窗裁剪，
   聊过 10 轮后每新一轮都裁掉最旧一轮，前缀头部每轮变化；
   T（tool result）体积大（skill 正文），被单独高频裁剪，进一步打碎前缀。
   长对话阶段此问题比①更严重。
3. **相关性绑定丢失 + 历史证据丢失**：L2 是单例槽位，检索内容与它服务的
   query 没有显式对应关系；每轮覆盖式更新，第 N 轮如果依赖第 N-2 轮检索的
   内容，证据已不在上下文中，去重也无从谈起。
4. **驻留竞争（eviction）**：自建集群缓存容量有限，被全网用户流量逐出——
   前缀不变 ≠ 命中。实际命中率 = 排布正确性 × 驻留概率，
   排布性 miss（可根除）与驻留性 miss（只能缓解）要分开度量、分开治理。

### 排布原则的表述

上下文从前到后，变化频率必须单调递增；等价地：
**"原位重写"的区域绝不能排在"追加式"区域之前。**
现状的 L2（每 query 重写）排在 L3（追加式）之前，正好违反此原则。

### 次要问题

- L1 更新时同样使 L1 之后全部失效，但更新频率覆盖多轮对话，
  属于低频事件，代价可接受；注意把 L1 的多项更新攒批执行即可。

### 裁剪改造方向（详见 03 / v2 幻灯片 P5）

按 **token 长度**双水位触发（如 80% 触发、一次裁到 40%），与轮数解耦；
T 的裁剪与 UAT 裁剪攒批到同一时刻执行；裁掉的 skill 正文退化为
"已加载标记"（可 re-load 恢复）、检索条目退化为 ID 指针。

## 解法方向（详见 02 / 05）

**取消 L2 这个固定槽位，把 query 级内容下沉进 L3 消息流**，
与各轮 query 物理绑定、渐进式进入：

- 被动注入：环境上下文增量、检索增量随当轮 user message 进入；
- 主动加载：skill 通过 load_skill 按需拉取，正文以 tool result 追加。

排布收敛为 L0 → L1 → UAT 流（append-only），每轮前缀是上一轮的
严格超集，缓存全程命中。
