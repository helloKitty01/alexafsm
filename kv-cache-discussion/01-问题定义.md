# 01 问题定义

## 当前系统的上下文构成

每次处理用户 query 时，上下文中包含以下几类信息：

1. **环境上下文**：随用户 query 相关的环境信息（随 query 变化）。
2. **检索类信息**：基于 query 检索出的知识、记忆。
3. **能力类信息**:基于 query 检索出的工具（tools）、技能（skills）。
4. **用户相关信息**：UAT 等（含义待确认，见 04-开放问题）。
5. **对话/loop 历史**：随交互不断追加。

## 核心矛盾

上述 1–4 类信息都**依赖当前 query 动态生成或检索**。如果它们被放置在上下文的
前部（如 system prompt 或消息序列头部），那么每个新 query 都会改写前缀，导致
KV cache 全量失效——这是 agent 系统里最常见、代价也最高的缓存杀手。

同时，当上下文超长时，系统会**从远到近**进行压缩（先压缩最旧的内容）。
压缩最旧的内容意味着改写可变区域的最前端，其后所有 token 的缓存全部失效，
每次压缩都近似一次全量 cache miss。

## 需要回答的设计问题

- 动态检索出的知识/记忆/工具/skill，应该注入到上下文的哪个位置？
- 多轮交互中，检索内容是"原位刷新"还是"追加注入"？
- 检索出的工具如何注入——进 API 的 tools 参数（前缀区）还是以文本形式进消息区？
- "从远到近"压缩如何设计触发时机与幅度，把不可避免的 cache miss 摊薄？
