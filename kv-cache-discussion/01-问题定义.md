# 01 问题定义

## 当前系统的上下文构成（已确认）

每次处理用户 query 时，上下文中包含以下几类信息：

1. **UAT 消息流**：user / assistant / tool 三角色的消息序列，即 agent loop
   链路和对话历史本身，随交互不断追加。
2. **工具（tools）**：目前是**稳定的**，放在 API 的 tools 参数里。✅ 缓存友好。
3. **skill**：**基于 query 动态检索**，注入在 **system prompt** 里。
   ⚠️ 这是当前最大的缓存杀手——system prompt 位于前缀最前部，每个 query
   换一批 skill 等于每次全量 cache miss。
4. **环境上下文**：随用户 query 相关的环境信息。
5. **检索类信息**：基于 query 检索出的知识、记忆。
6. **压缩机制**：上下文超长时从远到近压缩（先压最旧的内容）。

## 核心矛盾

- skill、环境上下文、query 检索内容都**依赖当前 query 动态生成**。
  其中 skill 被放在 system prompt（前缀最前部），每个新 query 都改写前缀，
  KV cache 全量失效。
- "从远到近"压缩改写可变区最前端，其后所有 token 缓存失效，
  每次压缩近似一次全量 miss。

## 设计方向（详见 02）

把动态内容从前缀（system prompt）中移出，**与 UAT 消息流结合，
作为渐进式加载内容**：

- 被动注入：query 级环境上下文、检索增量随当轮 user message 进入消息流；
- 主动加载：skill / 知识 / 记忆通过工具调用按需拉取，结果以 tool result
  形式追加——天然 append-only，天然缓存友好。
