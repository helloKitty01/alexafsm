# 04 关键难题与开放问题

> 前三章给了需求、模型与架构。本章把讨论中点名的两大难题
> （对话与定时任务的结合、长时异步任务管理）拆开分析，并列出待拍板的开放问题。

## 1. 难题一：对话与自动化任务的结合

问题不在"能不能创建定时任务"，而在**对话与任务两条时间线的交织**。四个具体子问题：

### 1.1 创建：自然语言 → 精确触发器的置信落差

- 对话是模糊的（"下班前提醒我""盯一下发布会"），触发器必须是精确的。
- 建议：**编译 + 回读**两段式（02 章 §6）。难点在回读粒度的拿捏——
  逐项确认烦人，不确认又怕错。策略：按解析置信度和动作风险分级，
  默认一句话口头回读，低置信字段单独追问，高风险动作显式确认。
- 遗留风险：语义时间（"下班前"）解析错误的纠错体验要顺——
  用户说"不对，我一般六点下班"时要能改任务同时更新画像。

### 1.2 并发：用户在对话时任务触发了

- 前台永远只有一个实时会话，但后台随时可能有任务想说话。
- 已由打扰管理器（03 章 §4）收口：任务不直接开口，只能提交播报请求。
- 剩下的体验问题：**插话的话术与上下文切换**。插播后要能回到原话题
  （"……好，回到刚才说的行程"），这要求前台会话对"话题栈"有显式管理。

### 1.3 引用：对话中指代任务

- "那个研究先停一下""发布会盯到了吗"——口语指代要解析到具体 TaskRun。
- 任务摘要卡片（03 章 §2）让前台掌握活跃任务清单，指代解析在卡片集上做；
  歧义时口头二选一（"你说的是竞品研究还是旅行攻略？"）。

### 1.4 身份一致性：一个助手还是一堆任务？

- 用户感知上必须是**同一个秘书**在办所有事，而不是"闹钟 App + 自动化 App + 聊天机器人"。
- 这要求：任务的产出口径、称呼、记忆在前后台共享；后台完成的事，前台"知道并记得"
  （靠摘要卡片 + 完成后写回记忆）。

## 2. 难题二：长时异步任务管理

### 2.1 澄清回拨是双向打扰问题

- 传统 chat：用户等模型。长任务反过来：**模型等用户**，而用户可能几小时不理。
- 关键设计（已在 02/03 章）：`waiting_user` 一等状态 + 结构化澄清请求
  （必须带候选项和默认值）+ `clarify_timeout` 策略。
- 强约束建议：**任何澄清请求必须附带"若不回复，我将……"的默认路径**。
  这条能把"卡死等人"变成"降级完成"，是长任务可委托感的来源。
- 开放：默认路径的激进程度怎么定？（修图"默认保留"安全；订票"默认买上午票"就危险——
  钱相关永远无默认路径，宁可任务过期失败。）

### 2.2 steering：改需求不推倒重来

- 用户中途改口（"只看开源方案"）时，朴素实现是重启任务，浪费且体验差。
- 建议：steering 指令在**阶段边界**应用；执行器收到后做增量规划——
  评估已有 checkpoint 哪些仍有效（已读的开源材料保留，闭源部分丢弃）。
- 开放：增量规划本身要花一次深度推理，小改动是否值得？可能需要
  "微调（追加约束）vs 改题（重规划）"的二分处理。

### 2.3 可靠性：手机是个恶劣的运行环境

- 进程随时被杀、断网、低电。中枢与执行分离（03 章 §6）解决"触发不丢"；
  checkpoint 解决"进度不丢"。
- 开放：执行层放端上还是云上？倾向**混合**——
  GUI 操控必须在端上；研究/写作类适合云上跑（不受手机休眠影响），
  但云端执行引入账号体系、隐私边界和离线不可用问题，需要专门一章讨论。

### 2.4 失败呈现

- 长任务失败（订票网站改版、研究源全挂）不能静默，也不能只丢一句"失败了"。
- 建议格式：做到了哪一步 + 卡在哪 + 已产出的部分成果 + 建议下一步（重试/换方案/人来）。

## 3. 全双工特有的问题

1. **主动开口的社会性**：omni 模型让"随时插话"在技术上免费，在体验上极贵。
   打扰管理器是机制，但**什么值得说**是策略/品味问题，需要数据迭代
   （被用户打断/忽略的播报要作为负反馈回流）。
2. **实时会话的常驻成本**：全双工会话保持在线的推理成本不可忽略。
   需要分级在线：唤醒态（全双工）/ 半唤醒（本地小模型听唤醒词与高价值声学事件）/ 休眠。
3. **语音里的任务管理 UX**：口头管理十几个任务会失控。
   语音适合单点操作（问进度、改一个），批量管理要落到可视化收件箱；
   语音与屏幕的分工要明确设计。

## 5. 建议的推进顺序（按依赖关系）

1. **中枢先行**：任务模型 + 存储 + 触发器引擎（cron/系统事件），这是所有能力的地基；
2. **B/C 类打通**：定时与系统事件任务端到端（创建-触发-执行-交付），执行先用简单动作；
3. **E 类长任务框架**：生命周期 + checkpoint + `waiting_user` 澄清链路 + 任务收件箱；
4. **D 类 watch**：轮询 + 判定归约实现，复用 2/3 的全部设施；
5. **打扰管理器**从简单规则起步，随全双工前台上线迭代为策略模型；
6. **全双工前台**与任务摘要卡片集成，最后做 speak_at_pause 这类高级插话体验。
