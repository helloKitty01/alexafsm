# 02 统一任务模型：Trigger × Goal × Policy

> 01 章的五个能力域（对话/定时/事件/监视/长任务）如果各做一套机制，系统会碎掉。
> 本章给出一个统一抽象：**一切委托都是 Task；Task = Trigger + Goal + Policy**。

## 1. 核心抽象

```text
Task {
  id, created_by_conversation_id      // 溯源：哪次对话创建的
  trigger:  Trigger                   // 什么时候干（见 §2）
  goal:     自然语言目标 + 结构化补充   // 干什么（保留原话，避免翻译损失）
  policy:   Policy                    // 怎么干、怎么打扰、怎么交付（见 §4）
  state:    生命周期状态（见 §5）
  runs:     [TaskRun]                 // 每次触发产生一次执行实例
}
```

三点设计取舍：

1. **Goal 保留自然语言原话**。任务创建时不把用户意图过度结构化成僵硬的参数表——
   执行时由 Agent 重新理解原话 + 结合当时上下文。结构化的只有 Trigger 和 Policy
   （这两者需要被非 LLM 的系统组件精确执行）。
2. **Trigger 与执行解耦**。触发器引擎是个精确、低功耗、非 LLM 的系统组件；
   LLM 只在两个时刻介入：创建时（把口头描述编译成 Trigger）和触发后（执行 Goal）。
3. **Task（定义）与 TaskRun（执行实例）分离**。周期任务一个定义多次运行；
   查询进度、取消"这一次"与删除"整个任务"是不同操作。

## 2. Trigger 类型系统

| 类型 | 说明 | 例子 |
| --- | --- | --- |
| `immediate` | 立即执行（普通对话请求也是它——对话只是 Trigger 最简单的特例） | "帮我修这批图" |
| `at` / `cron` | 一次性 / 周期性时间点 | 每天 7:30 |
| `event` | 订阅系统事件管理器中的**可穷举事件**，可带条件表达式 | 到家 ∧ 工作日 ∧ 18 点后 |
| `watch` | 自定义监视：Agent 自己实现的"世界状态变化"判定 | 苹果发布会结束 |
| `manual/chained` | 被用户口头触发或被其他任务的完成所触发 | 研究完成 → 触发"发邮件"任务 |

**统一性带来的直接好处**：`immediate` 把普通对话请求也纳入同一模型——
"现在帮我修图"和"到家后帮我修图"只差一个 Trigger 字段，执行链路完全复用。

## 3. 事件系统：两层设计

### 3.1 第一层：系统事件管理器（可穷举）

- 一张**事件注册表**：`geofence.enter/exit`、`device.charging_started`、`device.bt_connected`、
  `notification.received(app, keyword)`、`calendar.event_starting(offset)`、`screen.unlocked` ……
- 订阅制：触发器引擎向 OS 层订阅，事件到达后本地评估条件表达式（不经过 LLM，毫秒级、零 token）。
- 事件带结构化 payload（哪个围栏、哪个 App 的通知、通知全文），作为 TaskRun 的启动上下文注入。
- LLM 的职责只在创建期：把"到家"编译成 `geofence.enter(home)`，其中 `home` 从用户画像取值；
  编译结果**展示给用户确认**（"我会在你进入家的 200 米范围时触发，对吗？"）。

### 3.2 第二层：自定义监视（watch，不可穷举）

关键认识：**自定义事件可以归约**，不需要发明第三种触发机制——

```text
watch = (cron 轮询 + LLM/规则判定)  或  (可订阅的外部源 → 降级为 event)
```

- **优先找推送源**：创建 watch 时 Agent 先尝试把它变成真事件
  （站内 RSS / webhook / 该 App 自己的推送通知 → `notification.received` 订阅）。
  找得到就零轮询成本。
- **找不到则轮询 + 判定**：Agent 生成一个检查程序（checker）——
  "每 30 分钟搜索一次苹果发布会实况，判断是否已结束且要点可获取"。
  checker 是一次轻量 LLM 调用（或 Agent 预编译出的规则，如页面上出现某类字样），
  输出三值：`未发生 / 已发生(带证据) / 需要调整检查策略`。
- **判定命中 → 视同事件发出**，走与系统事件完全相同的后续链路，触发主任务
  （整理发布会内容 → 写邮件 → 发送）。
- **预算与生存期**：每个 watch 声明检查频率、单次成本上限、生存期
  （defaults：命中即停 / 最长 7 天，到期主动问用户续不续）。

这样事件驱动在概念上只有一种："事件总线上出现了一个事件"；
差别只是事件的**生产者**是 OS（第一层）还是 Agent 自己养的 checker（第二层）。

## 4. Policy：打扰、交付与授权

Policy 是任务的"行为契约"，创建任务时由 Agent 从对话中推断 + 默认值补齐，关键字段：

| 字段 | 取值示例 | 说明 |
| --- | --- | --- |
| `attention` | `speak_now` / `speak_when_idle` / `push` / `digest` / `silent` | 主动触达的打扰等级（见 03 章打扰管理器） |
| `delivery` | 语音播报 / 卡片 / 邮件 / 文件存档 | 结果交付通道，"发邮件给我"就是 delivery=email |
| `clarify_timeout` | 等 2h → 用默认值继续 / 挂起到用户出现 / 放弃 | 中途澄清用户不回复时的策略 |
| `authorization` | 免确认动作清单 + 必确认动作清单 | 支付、对外发送、删除永远在必确认清单 |
| `budget` | 最长运行时长、最大 token/算力、轮询频率 | 防失控 |
| `priority` | 前台急件 / 普通 / 闲时批处理 | 影响调度与资源抢占 |

## 5. TaskRun 生命周期

```text
                    ┌────────────────────────────────┐
created → queued → running ─→ done → delivered → archived
                    │   ↑ │
                    │   │ └→ failed（→ 重试 or 报告用户）
                    ↓   │
              waiting_user（澄清/授权挂起，可超时走默认策略）
                    │
                 paused / cancelled（用户 steering）
```

要点：

- **`waiting_user` 是一等状态**：长任务中途需要澄清/授权时，任务挂起、释放执行资源，
  生成一个"澄清请求"进入交付队列，由打扰管理器决定何时、以何通道找用户；
  拿到答复后从 checkpoint 恢复。这是"长任务与用户交互"的标准通道。
- **checkpoint**：长任务按阶段落盘中间成果（研究笔记、已修图列表、订票进行到哪一步），
  支持进程被杀后恢复、支持用户改需求（steering）时带着已有成果继续。
- **一切可查询**：所有 Task/TaskRun 构成"任务收件箱"，对话中随口就能问
  （"发布会盯到了吗""修图修到多少了"），也有可视化列表兜底。

## 6. 从一句话到一个任务：创建链路

以"帮我盯一下苹果发布会，内容整理成邮件发我"为例：

```text
用户原话
  → 主 Agent 解析：这是委托，不是即时问答
  → 编译 Trigger:  watch（先探测推送源，无 → cron 每 30min + checker "发布会结束?"）
     编译 Goal:    原话 + 补充（邮箱地址来自画像；"内容"预期为要点摘要+发布产品列表）
     编译 Policy:  delivery=email, attention=push（邮件发完轻推送告知）, 生存期=发布会日+1天
  → 口头回读确认（一句话："好，发布会我盯着，结束后整理成邮件发到你 xx 邮箱。"
     异常字段才追问，不逐项审批）
  → 注册进触发器引擎，对话继续
```

**回读确认的粒度**是体验关键：默认一句话确认 + 用户可追问细节；
只有高权限动作（花钱、对外发消息）和低置信解析才升级为显式确认。
