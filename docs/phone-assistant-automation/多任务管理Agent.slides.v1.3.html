多任务管理 Agentv1.3：需求理解

范围：文本输出（omni 放下一步）｜双入口：Query 驱动 + 自动化触发（定时 / OS 事件 / 监视）
定位：对话即任务控制台 —— 会话不被任务阻塞，任务以卡片形式活在对话流里

场景回放一条对话流：即时任务 + 自动化任务同流

帮我生成一个小男孩玩耍的图片
好的，已经开始为您生成
T1生成小男孩玩耍图已替代?
不对，帮我生成一个小女孩玩耍的
好的，现在帮您生成女孩玩耍的图片
T2生成小女孩玩耍图生成中
再帮我生成 3 张图片，完成后再帮我生成一个视频
好的，3 张图片开始生成，完成后自动生成视频
T3.1–3.3组「3 图 + 视频」·图片 ×3 并行生成中
T4组「3 图 + 视频」·视频（输入 = 三图）等待依赖 0/3
每天 7 点半给我早报；另外到家后提醒我取快递
已设好：每日早报下次明早 7:30；到家提醒已订阅到家事件
T5每日早报（cron 7:30）待触发
T6到家提醒取快递（geofence 事件）已订阅

R0响应 ≠ 任务

"你好""心情不好""查天气"是即时响应：loop 就地干完，零任务对象。任务要够格才建（升格判据见 P2）—— 修正 v1.0/v1.1 "一切皆任务"的过重设计。

R1非阻塞应答

每个 Query 先秒回，任务后台跑。对话永远可用 —— T1 在生成时 Q2 照常处理，任务跑着照样闲聊。

R2任务卡片 = 任务的 UI 锚点

够格任务插卡，状态自更新（排队/生成中/完成/失败/已替代），进度不产生聊天气泡、不刷屏。

R3意图路由六分类

chat / new_task / followup / steer / control / query，与现有 Agent 概念（steer、followup、multitask）对齐（P3）。Q2 的"不对"是 steer 替换级。

R4批量 + 依赖编排

Q3 一句话 = fan-out（3 图并行）+ join（三张齐）+ 链式触发（视频引用三图产物）。同源任务成组，支持组级操作。

R5自动化任务（v1.3 补齐主线）

定时 cron / OS 系统事件 / watch 监视三类触发，与"3 图完成"走同一条事件总线。特点是创建与执行分离：触发不丢（进程被杀仍生效）、交付通道声明、错过补偿、到点"要不要叫醒 LLM"（L1/L2 分流的需求来源）。

v1.3 主张：两大入口殊途同归——一切入站皆消息，消息唤起主 loop；就地干完叫响应（含同步等待工具返回后作答，P2）；够格才建任务（Task = Trigger + Goal + Policy）。主 loop 是 player-coach（P4），对端是异构执行体，接口落在 UAT 上（P6）。

消息 · 响应 · 任务三层模型：任务要够格

回答"一切皆任务会不会太重" —— 会；聊天不建任务、不命名、不插卡，只留会话历史

① 消息层（一切入站）　Msg{type: user_query | event | task_callback | clarify_answer, payload, task_ref?} —— 统一进主 Agent 收件箱，串行唤起 loop
↓ loop 判断：能就地干完吗？
② 响应层（默认路径）　纯语言即答，或同步等待工具返回后作答（查天气必须拿到结果才能回）——就地完成，零任务对象：无卡片、无命名、无状态机
↓ 够格（判据任一命中）才升格 ↓
③ 任务层（够格才建）　Task = Trigger + Goal + Policy：插卡、命名、进任务表与生命周期管理 —— v1.0 的全部机制只作用于这一层

升格判据任一满足 → 建任务

#判据例子
1耗时超阈值或不可预估（拍 5s，待调）生成图/视频、深度研究
2非即时触发器（定时/事件/依赖）早报 cron、到家提醒、join 后做视频
3用户可能中途控制（停/改/看进度）批量修图、App 操控
4用户走开后还要继续（异步交付）盯发布会 → 邮件
5有副作用需重试/补偿发邮件、订票、支付类
兜底：溢出升格以为是轻查询，工具执行超阈值
→
自动转后台包装成任务 + 插卡，回一句"我在弄，好了叫你"
→
只升不降判据不必完美，判错有退路；降格无意义

任务命名管理只有够格任务才需要

  • title：动宾短语 ≤12 字（"生成小女孩玩耍图"），创建轮 loop 顺手产出，不额外调用；
  • 短号：会话内序号 T1 / T2 / T3.1，用于口头指代与卡片；
  • 组名：一次 Query 派生的多任务共享（组「3 图 + 视频」）；
  • 稳定性：title 创建时定死，仅 steer 改目标时允许改名 —— 保证指代解析与展示稳定；
  • 消费方只有三个：指代解析、卡片/收件箱展示、审计日志。

回复时机三分由工具返回契约决定（v1.3 修正"立即回复"）

形态行为决定者
纯语言即答"你好"直接回—
同步等待后答查天气：阻塞等结果，拿到再回答工具契约 latency=instant/short
异步 ack生图："好的，开始生成" + 插卡，不等结束工具契约 latency=long / async job

用户意图可覆盖（"慢慢弄好了发我"→ 任务化）；声明 short 实际超时 → 溢出升格兜底。

意图路由六分类：对齐 steer / followup / multitask

每条 user_query 先分类再动手；卡片按钮与口头指令走同一条路由

六分类chat 是默认路径，其余五类才碰任务系统

类别语义例子动作
chat聊天 / 问答 / 轻工具，就地完成"你好""心情不好""北京天气?"响应层直接回复，零任务
new_task新委托（含定时/事件/监视触发）"生成一张图""每天 7 点半早报""到家提醒我"建任务（可 fan-out 成组）+ 插卡 + 秒回
followup任务问我答，或补充信息，不改目标任务问"12 张存疑?"→"先保留"；"顺便说下我靠窗"答复路由回 blocked(user) 任务，唤醒继续
steer我要求改：动目标或约束"不对，要小女孩"（替换级）；"光线再亮点"（约束级）替换级：新任务 + 旧任务 superseded；约束级：阶段边界应用
control停 / 暂停 / 恢复 / 调优先级"都停了""先暂停，晚上再跑"控制面 API（支持组级批量）
query问进度 / 问定义"图好了吗""早报下次几点跑?"读任务表/注册表口头汇总，零新任务

分界线followup vs steer —— 最易混的一对

followup = 任务问我答 / 我补充信息，目标不变（答澄清、给验证码、补偏好）；steer = 我主动要求改，动了 Goal 或约束（换主体、改风格、改范围）。判不准时按 steer 处理并口头回读（"我把要求改成 XX，对吗？"）——回读成本低于改错方向的成本。

指代解析落到具体任务

  • 在活跃任务摘要表上做（每任务一行：短号/title/状态/进度）；
  • "那个视频""第二张""刚才那批"→ task_id / group_id；
  • 歧义先问再动："替换男孩那张，还是再加一张？"
与现有概念对齐：multitask = new_task 的 fan-out + 多任务并存（组管理）；followup = blocked(user) 答复路由；steer = 运行中任务的目标/约束变更。六分类是这三个概念在入口路由层的统一表达。

核心 loop 是谁：主 Agent loop = player-coach

回答"会话 Agent 是不是在拉皮条" —— 不是：短活亲手干，长活才派发，没有空心转发器

核心主 Agent loop（唯一的"大脑"，被消息唤起，永不阻塞）

对话与响应chat / 轻工具就地干完 —— 这部分活它亲手做，不外包
路由与编译六分类；够格委托编译为 Task（Trigger/Goal/Policy + 命名 + 依赖建图）
事件处置L2 事件入箱后决策：编排任务链 / 重试 / 找用户
穿透对话代表后台任务向用户澄清、汇报；答复路由回任务
↓ 只有"够格任务"才向下派发　　▲ 摘要卡片 / L2 事件 / 澄清请求向上穿透

中枢任务中枢（非 LLM，系统级常驻 —— 状态与触发的唯一权威）

任务表 + 依赖 DAG持久化、join 计数、产物句柄
触发器引擎 + 订阅表cron / OS 事件 / on_tasks_done / watch 计划
事件总线 + 三级分流L0 直驱卡片、L1 规则派发、L2 入收件箱
调度与控制面并发额度、组操作、cancel 信号、错过补偿
↓ 派发 TaskRun　　▲ 进度 / 终态 / 需澄清事件

支线异构执行体（v1.3 修正：不是统一的"执行 loop"，统一的只是任务外壳）

① 长时工具（无 loop）生图 / 生视频 / 修图：submit job + 状态回调；steer 能力：基本只能 stop 重来
② subAgent（内层 agent loop）深度研究 / App 操控：plan→act + checkpoint；可真 steer / pause / 中途澄清
③ A2A 三方 Agent（对端黑盒 loop）委托 = 影子任务 + 超时监护；steer 看对端协议支持
统一外壳TaskRun 生命周期 + 状态事件回调 + 产物句柄 —— 中枢只看事件，不关心内部形态
分工一句话：主 loop 干轻活 + 编排 + 处置（每次唤起一轮推理）；中枢管状态与触发（零 token）；对端执行体干重活（长时工具 / subAgent / A2A 三形态，支线上下文不进主会话）。"拉皮条"感来自 v1.1 把主 loop 削成纯路由 —— 修正：响应层的活全部由主 loop 亲手完成。

loop × 事件系统 × 双层上下文（主转录 / 任务线程）

OS 事件的订阅 / 阻塞 / 唤醒三段式；loop 永不阻塞，等待是数据不是线程

三段式以"到家提醒取快递"（OS geofence）与"订票等验证码"为例

① 订阅（loop 的一个动作）loop 调工具写订阅表 Sub{geofence.enter(home), L1, 派发提醒}，当轮即结束 —— OS 事件经系统事件管理器 → 事件网关 → 总线
→
② 阻塞（物化为数据）"等待"= 一条订阅 + 一个挂起任务 blocked{reason, wake_condition, timeout}；checkpoint 落盘、执行器释放 —— 没有任何线程在等
→
③ 唤醒（按分流路由）L1：中枢从 checkpoint 文本重建执行器上下文，事件 payload 作为新输入 append（KV cache 已失效是常态）；需决策的走 L2 入主 loop 收件箱

主干：主会话转录用户所见唯一对话流，UAT 消息结构承载（见 P6）

  • 承载：用户消息、助手回复、任务卡片、任务的澄清问答 —— 用户永远只面对一个会话；
  • 主 loop 每轮上下文 = 主转录近期窗口 + 活跃任务摘要表（每任务一行）+ 本轮触发消息 + 记忆摘要；
  • 摘要表让"图好了吗"不用翻支线全文就能答；
  • 冷任务折叠为计数，控制常驻 token 规模。
交汇一摘要卡片（几十 token/任务，常驻）
交汇二澄清请求穿透 ↑ 答复路由回 ↓
交汇三最终结果 / 失败报告

支线：TaskRun 线程每个够格任务一条，不进主转录

  • 持有：目标、计划、完整工具轨迹、中间产物、checkpoint —— 支线的脏活不污染主会话；
  • 阻塞唤醒后恢复自己的线程接着跑，与主转录无耦合；
  • checkpoint 必须文本可重建（目标 + 阶段摘要 + 产物句柄），不依赖驻留内存；
  • subagent 再分叉时挂在本支线下，树形汇报。
为什么双层是必需：成本 —— 主干不被支线工具轨迹撑爆（研究任务动辄数万 token）；体验 —— 支线不被闲聊污染、多任务互不串味；正确性 —— 澄清答复凭 task_ref 精确路由回支线，不靠语义猜。

UAT 接口设计：事件怎么进转录，LLM 输出什么

UAT = user / assistant / tool 消息结构；硬约束：tool 消息必须配对前置 tool call

主 loop事件 = user 角色 + 结构化信封

事件不是任何 tool call 的响应，不能走 tool 角色；以 user 角色注入，信封与真人发言严格区分：

<event source="os.geofence.enter" task_ref="T6"
  trust="system" ts="18:42">进入围栏：家</event>

  • 信封带来源与信任标记；外部内容（通知全文 / 三方回调）转义处理，防提示注入；
  • 与 system-reminder 模式同构（见 reminder-discussion）。

支线阻塞 = 一次未返回的 tool call

  • subAgent 发起 wait_event(pattern) / ask_user(question) 的 tool call → 事件 / 用户答复到达时作为该 call 的 tool result 返回——天然满足 UAT 配对约束；
  • "阻塞"在转录上就是"call 还没有 result"；checkpoint 重建 = 重放已完成的 call/result 对 + 追加新到的 result。

上下文组织<active_tasks> 每轮动态注入

  • 位置：转录尾部、最新消息之前——靠近末尾保注意力；不污染前缀、KV cache 友好（接 kv-cache-discussion 分层排布结论）；每轮替换旧快照只留最新；
  • 行格式：T2 | 生成小女孩玩耍图 | running 60% | —；blocked 任务附待决问题；终态折叠为计数；
  • 查询进度不需要工具调用：直接读表回答。

LLM 输出空间工具三层区分

层内容说明
业务工具openClaw 现有工具：查天气 / 修图 / 生图 / 日历…原样复用，只补注册契约 latency_class（决定同步等待 or 异步 ack，见 P2）
任务管理工具（新增框架层）create_task create_task_group steer_task stop_task/group pause/resume subscribe_event forward_user_reply delegate_external八件套，仅主 loop 可调

事件三级分流能不进 LLM 就不进

级去向例子成本
L0直写卡片/任务表进度 30%→60%0 token
L1触发器引擎直接派发/唤醒cron 到点、join 3/3、geofence、验证码到达0 token
L2入主 loop 收件箱watch 命中、失败处置、外部异常1 次 loop

分流边界：创建期由主 loop 声明（"到点直接执行"=L1，"到点叫我看看"=L2）；兜底：失败与需开口的必 L2。

订阅表Sub{pattern, subscriber, route, action, ttl}

  • 订阅者四类：触发器引擎（注册期）/ 运行中任务（动态）/ 主 Agent（常驻+按需）/ UI 卡片；
  • 生命周期：一次性命中即失效；任务终态自动退订；无主订阅定期 GC —— 订阅泄漏 = 幽灵触发。

TaskControl 控制面幂等，对话与卡片按钮同路由

操作要点
start / stopstop 级联：下游取消不上溯，上游取消询问下游
pause / resume阶段边界挂起 / checkpoint 恢复；App 会话态任务声明不支持 pause
steer未启动零成本改 Goal；运行中阶段边界增量重规划
query / list / group_*组级批量操作；排队卡片显示"第 k 位"

blocked 家族 + 定时注册表

  • blocked{reason: deps|event|user|timer, wake_condition, timeout_policy} —— 阻塞即释放执行器，强制带超时策略，不允许无限期悬挂；等的事件可能永不来（短信被拦）→ 唤醒条件须可人工替代；
  • 定时注册表：CRUD 全走对话；next_fire_time 可查；错过补偿 skip / catch_up / ask，默认 skip；
  • 外部 Agent：委托 = 影子任务 + 超时监护；回调统一封装为事件；敏感动作不随委托下放。

v1.3 已定主张与开放问题

六条主张对齐后即可落地；开放问题附倾向待拍板

已定主张

  • 双入口：Query 驱动 + 自动化触发（cron / OS 事件 / watch），殊途同归于同一消息模型；
  • 三层模型：消息 → 响应（含同步等待后答）→ 任务要够格（升格判据 + 溢出升格，只升不降）；
  • 回复时机由工具契约定：latency_class 决定同步等待还是异步 ack，用户意图可覆盖、超时升格；
  • 意图路由六分类 + 主 loop = player-coach，loop 永不阻塞（等待是数据不是线程）；
  • 对端三形态：长时工具 / subAgent / A2A 三方 Agent，统一 TaskRun 外壳，steer 能力分级；
  • UAT 接口：事件 = user 角色信封；支线阻塞 = 未返回的 tool call；<active_tasks> 尾部注入；回复只走 finalAnswer；
  • 工具三层：openClaw 业务工具原样复用（补 latency 契约）+ 任务管理八件套 + finalAnswer；
  • 中枢非 LLM 常驻：任务表 / 订阅表 / 触发器引擎独立于 LLM 存活。
