多任务管理 Agentv1.1：本版范围与优先级

v1.0 已对齐：六条需求、Task 模型、三层架构、场景验证（存档 history/）
v1.1 聚焦两大优先级的机制细化，文本输出，omni 仍放下一步

优先级 1事件驱动的 Agent 架构

  • Query 即时与事件驱动同构：两者都是"入站消息"，统一进主 Agent 的收件箱，被消息唤起同一个 Agent loop（P2）；
  • 事件不全进 loop：三级分流（直驱 / 规则 / 认知），只有需要理解决策的事件才消耗 LLM（P3）；
  • 事件订阅机制：谁订、订什么、命中后路由到哪、何时退订——订阅表是事件系统的中心数据结构（P3）；
  • 与外部 Agent 交互：外部 Agent = 执行器（委托 + 回调）或事件源（订阅），统一封装进事件总线，不开新概念（P4）。

优先级 2长时异步任务管理

  • 任务控制面：启动 / 停止 / 暂停 / 恢复 / 改需求 / 查询的统一 API，幂等、支持任务组批量操作（P5）；
  • 定时任务管理：schedule 注册表 CRUD、下次触发可查、错过补偿策略（P5）；
  • 事件阻塞任务管理：任务运行中等待事件（如等验证码短信）——blocked 状态家族统一 waiting_deps / event / user / timer（P5）；
  • 多异步任务并存：并发额度、优先级、任务组、卡片状态直驱——v1.0 骨架不变，本版补控制细节（P6 场景走查）。
v1.1 一句话：把 v1.0 的"任务模型 + 三层架构"往下落两层——消息/事件怎么进 loop（收件箱 + 三级分流 + 订阅表），任务怎么被管住（控制面 API + blocked 家族 + 任务组）。

事件融入 Agent loop：统一收件箱模型

主 Agent loop 不再只被用户唤起——它被"消息"唤起；Query 只是消息的一种

user_query用户即时输入（打字/语音转文本）——必须应答
event认知级事件：watch 命中、系统事件需编排、外部 Agent 异常
task_callback任务完成 / 失败 / 需澄清——处置期回调
clarify_answer用户对某个挂起任务澄清问题的答复（路由回任务）
↓ 全部封装为统一消息 Msg{type, source, payload, task_ref?} ↓
主 Agent 收件箱（串行化 + 合批 + 去重 + 限频）同一时刻只有一个 loop 实例在跑，天然避免并发写会话状态；低优消息可合批处理，一次唤起处理多条
↓ 取一条（批）消息，唤起 loop ↓
Agent loop：上下文（会话历史 + 活跃任务表 + 触发消息）→ 推理 → 动作动作空间：回复用户 ｜ 创建任务（含依赖/定时/订阅）｜ 控制任务（stop/pause/steer）｜ 订阅/退订事件 ｜ 委托外部 Agent ｜ 静默归档（无动作也是决策）

同构性Query 与事件在 loop 视角只差三点

user_queryevent / callback
应答义务必须回话（秒回）可静默处置，开口须过打扰门控
上下文焦点当前会话话题关联任务的摘要卡片（task_ref）
时效实时，优先抢占可延迟、可合批

关键约束loop 的纪律

  • user_query 优先抢占：用户开口时，排队中的事件消息让路（正在跑的 loop 跑完当轮）；
  • loop 内不干重活：超过秒级的工作一律转任务，loop 只做路由、编排、应答；
  • 消息风暴防护：事件在入箱前合批（同任务进度类合并）、去重（同一事件幂等键）、限频（digest 化）。

事件三级分流 与 订阅机制

原则：能不进 LLM 就不进——只有需要"理解与决策"的事件才消耗 token

三级分流事件总线出口处按订阅表路由

级别特征去向例子成本
L0 直驱级纯状态同步，无决策直写任务表 / 卡片 UI进度 30%→60%、心跳0 token，毫秒级
L1 规则级命中预注册的精确规则，动作在创建期已定触发器引擎直接派发 / 唤醒任务cron 到点、join 计数 3/3、geofence 进入、任务等的验证码短信到达0 token，派发即执行
L2 认知级需要理解、编排或向用户开口封装为 Msg 进主 Agent 收件箱watch 判定命中后编排后续、任务失败重试用尽、外部 Agent 回调异常、澄清答复路由一次 loop

订阅表事件系统的中心数据结构

Sub{ pattern, subscriber, route(L0|L1|L2), action, ttl }

订阅者典型订阅命中动作
触发器引擎（任务注册时写入）cron 到点、系统事件+条件、on_tasks_doneL1：派发 TaskRun
运行中的任务（执行中动态订阅）"验证码短信到达""支付结果通知"L1：唤醒 blocked 任务
主 Agent（常驻 + 按需）任务终态、失败、watch 命中、外部异常L2：入收件箱
UI 卡片所属任务的进度事件L0：直写状态

订阅生命周期防泄漏是纪律

  • 创建：任务注册期（触发器）或运行期（动态等事件）建立，声明 ttl 与路由级别；
  • 命中：一次性订阅命中即失效；持续订阅（cron / watch）命中后继续；
  • 退订：任务进终态自动退订其全部订阅；watch 到期主动问用户续不续；
  • GC：定期扫描无主订阅（订阅者已不存在）强制清理并告警——订阅泄漏 = 幽灵触发，比任务泄漏更隐蔽。
分流边界谁定：创建任务时由主 Agent 声明（"到点直接执行"= L1；"到点叫我看看情况"= L2）；系统兜底规则：失败与需要开口的一律 L2。

与外部 Agent 交互：执行器 或 事件源，不开新概念

外部 Agent 在系统里"长得像一个 worker + 一个事件源"——中枢与任务模型零改动

角色一作为执行器：委托 + 影子任务

① delegate创建影子 TaskRun + 卡片；发 goal + policy(预算/授权边界/超时)
→
② ack外部返回 job_id，登记映射 task_id ⇄ job_id
→
③ status 回调进度→L0 直驱卡片；需澄清→L2 进收件箱（转 waiting_user）
→
④ result产物登记句柄，完成事件上总线，可触发下游 join
  • 超时监护：委托即挂一个监护定时器（L1），外部到期不回 → 生成失败事件走 L2，主 Agent 决定重试 / 换执行器 / 报告用户；
  • 回调即事件：外部回调统一封装上事件总线，与本地 worker 的状态事件同一格式——下游（join、卡片、收件箱）无感知差异。

角色二作为事件源：订阅其推送

  • 外部 Agent / 外部系统的主动通知（webhook、推送、A2A 消息）接入事件网关，规范化后上总线；
  • 对订阅方而言与系统事件无差别——"券商 Agent 推送盘中异动" 与 "geofence 到家" 走同一条路由；
  • watch 的优化路径（v1.0 §3.2）在这里闭环：能订阅外部源就不轮询。

信任边界

  • 鉴权分级：一方 / 认证三方 / 未认证，决定可委托的任务类型与授权边界；
  • 外部回调内容视为不可信输入：进收件箱前过安全过滤，防提示注入；
  • 敏感动作（支付/对外发送）不随委托下放，外部 Agent 走到这一步必须回调 waiting_user。
协议主张：对外协议只需两个原语——任务委托（delegate/ack/status/result，类 A2A）与事件投递（webhook→事件网关）。内部则复用 TaskRun 生命周期与事件总线，外部 Agent 的接入成本收敛为一个适配器。

长时异步任务管理：控制面 + blocked 家族 + 定时注册表

对话指令与卡片按钮走同一套控制面 API；一切操作幂等、可审计

TaskControl API启动 / 停止 / 暂停…（幂等）

操作语义与要点
start创建即调度（immediate）或注册触发器（其余 Trigger）
stop取消：下发 cancel 信号 → worker 清理半成品 → 终态；级联策略：下游取消默认不上溯，上游取消询问下游
pause / resume阶段边界挂起 / 从 checkpoint 恢复；blocked 中的任务 pause = 冻结唤醒条件
steer改 Goal / Policy：未启动零成本改；运行中在阶段边界应用增量重规划
query / list单任务详情 / 按状态、组、类型过滤——支撑"图好了吗"与任务收件箱
group_*任务组：一次 Query 编译出的多任务共享 group_id，组级 stop/pause/query（"把刚才那批都停了"）

blocked 家族事件阻塞任务的统一表达

blocked{ reason, wake_condition, timeout_policy }

reasonwake_condition例子
deps依赖任务集完成（join）T4 等三张图
event动态订阅的事件到达（L1 唤醒）订票等验证码短信
user澄清 / 授权答复"选上午还是晚上的票？"
timer定时到点"暂停到明早再继续"

阻塞即释放执行器（checkpoint 落盘）；每个 blocked 必带 timeout_policy：超时走默认路径 / 升级问用户 / 失败——不允许无限期悬挂。

定时任务注册表

  • CRUD 全走对话："早报改到 8 点"= 修正路由落在 Task 定义（schedule 字段），不动历史 Run；
  • 可解释：next_fire_time 随时可查（"下次几点跑？"）；
  • 错过补偿（关机/勿扰错过）：skip / catch_up（补跑一次）/ ask，按任务声明，默认 skip。
多异步任务并存的秩序：调度器按资源池额度 + 优先级出队（排队卡片显示"第 k 位"）；user_query 触发的任务默认高于事件触发的后台任务；组内任务共享预算上限，防止一句"生成 100 张"打爆资源。

场景走查：v1.1 机制逐条验证

六个场景覆盖：即时 query、认知级事件、事件阻塞、组批量停止、定时变更、外部委托超时

场景链路验证的机制
"现在生成一张图"（query 即时） user_query 入箱 → loop 一次：路由=新增 → start（immediate）→ 秒回 + 插卡 → 之后进度全走 L0，loop 不再被打扰 收件箱同构性；L0 直驱
发布会 watch 命中 checker 判定"已结束"→ L2 事件入箱 → loop：编排"整理内容→写邮件→发送"任务链（on_tasks_done 串联）→ 静默执行，完成后按打扰门控轻推送 L2 认知级；事件后处置期编排
订票任务等验证码 TaskRun 运行中动态订阅 notification.received(短信, 验证码) → 转 blocked(event)、释放执行器 → 短信到达 → L1 直接唤醒任务，全程不进主 loop、不打扰用户 动态订阅；blocked(event)；L1 唤醒
"把刚才那批图都停了" loop：指代解析 → group_id（Q3 那批）→ group_stop → 三张卡片批量翻"已取消"；下游 T4 依赖不可满足 → 询问用户处置 任务组；stop 级联策略
"早报改到 8 点" loop：修正路由 → 落在 Task 定义的 schedule 字段 → 注册表更新 + 回读"好，以后每天 8 点，下次明早生效" 定时注册表 CRUD；next_fire_time 可解释
外部研究 Agent 委托后失联 监护定时器到期（L1）→ 生成失败事件 → L2 入箱 → loop 决策：重试一次 → 仍失败 → 转本地执行器降级完成 + 结果中注明 影子任务；超时监护;失败必 L2
token 账粗算：六个场景里 LLM 被唤起的次数 = 每个 user_query 一次 + 每个 L2 事件一次；进度刷新、join、事件唤醒任务共 0 次——事件驱动的规模化成本被 L0/L1 挡在 loop 外。

v1.1 待拍板项（附倾向）+ 落地顺序

开放问题

#问题倾向
1L1/L2 分流边界：哪些事件"到点直接执行"，哪些"叫醒 Agent 看情况"创建期由主 Agent 声明 + 系统兜底（失败/需开口必 L2）；上线后按误分流案例调
2收件箱调度策略：L2 事件积压时的优先级与合批粒度user_query 抢占；同任务事件合并；低价值事件 digest 化定时批处理
3blocked(event) 的订阅失效风险：等的事件永远不来（短信被拦截）强制 timeout_policy + 唤醒条件可人工替代（用户手动输入验证码）
4外部 Agent 的进度语义对齐：各家 status 粒度不一适配器归一化到 {进度%, 阶段名, 需澄清?}三元组，缺则只显示"进行中"
5组与依赖的边界：group_stop 时下游任务（跨组依赖）怎么办依赖不可满足 → 下游转 blocked(user) 询问，不静默取消
6pause 的资源语义：GUI 操控类任务 pause 后现场如何保持可 checkpoint 的阶段边界 pause；不可挂起的（App 会话态）声明为不支持 pause，只支持 stop

落地顺序按依赖关系

  • ① 中枢最小闭环：任务表 + 事件总线 + 订阅表 + 触发器引擎（immediate / cron / on_tasks_done）；
  • ② 控制面：start/stop/query + 任务组 + 卡片 L0 直驱；
  • ③ 收件箱 + loop 改造：user_query 与 L2 事件统一入箱，四分类路由；
  • ④ blocked 家族：join（deps）先行，动态订阅（event）与澄清（user）跟进；
  • ⑤ 外部接入：事件网关（webhook）→ 外部 Agent 委托适配器；
  • ⑥ v1.2 预告：watch（轮询+判定）、打扰门控策略化、长任务 steer 增量重规划。
与 omni 的衔接不变：收件箱 / 中枢 / 控制面全部与前台形态无关——下一步把文本前台换成全双工秘书时，只改"应答义务与打扰门控"两处策略。
