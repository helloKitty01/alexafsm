# 03 架构方案：秘书前台 + 调度中枢 + 执行后台

> 基于 01 需求与 02 任务模型，给出建议架构。核心思路：
> **全双工对话是"前台秘书"，永远轻、永远在线、永远可打断；
> 一切重活都异步化到后台，通过任务收件箱和打扰管理器与前台会合。**

## 1. 总体分层

```text
┌─────────────────────────────────────────────────────────────┐
│  前台：实时对话层（omni 全双工模型）                            │
│  · 听/说/看，随时 barge-in                                    │
│  · 秘书角色：应答、创建任务、查询任务、传达后台消息、代收澄清答复   │
│  · 原则：不在实时会话里干重活，凡是 >数秒 的工作一律降级为任务      │
└──────────────┬────────────────────────────────▲──────────────┘
        创建/查询/steering                 播报请求（经门控）
┌──────────────▼────────────────────────────────┴──────────────┐
│  中枢：调度与状态层（非 LLM 为主，可靠、低功耗、常驻）             │
│  · 任务存储（Task/TaskRun/checkpoint，掉电不丢）                │
│  · 触发器引擎（cron / 事件订阅 / watch 轮询计划）                │
│  · 事件总线（系统事件管理器 + watch 判定命中都发到这里）           │
│  · 调度器（并发额度、优先级、闲时批处理、资源抢占）                │
│  · 打扰管理器（所有主动触达的唯一出口，见 §4）                    │
└──────────────┬────────────────────────────────▲──────────────┘
         派发 TaskRun                    进度/澄清请求/结果
┌──────────────▼────────────────────────────────┴──────────────┐
│  后台：执行层（深度模型 + subagent 池）                          │
│  · Task Executor：每个 TaskRun 一个 agent loop（深度推理模型）   │
│  · subagent 编排：研究、修图、GUI 操控（App RPA）、写作…          │
│  · 工具与权限沙箱：敏感动作在这里强制拦截、走授权流程               │
└──────────────────────────────────────────────────────────────┘
```

## 2. 双脑设计：实时小脑 + 深度大脑

全双工 omni 模型擅长低时延对话，但不适合也不应该在实时会话里做长推理。建议**双脑**：

| | 前台小脑（omni 实时） | 后台大脑（深度推理模型） |
| --- | --- | --- |
| 职责 | 对话、意图识别、任务创建/回读、播报、代收澄清 | 执行 TaskRun：研究、修图编排、GUI 操控、写作 |
| 时延要求 | 数百 ms 级话轮响应 | 分钟~小时级 |
| 上下文 | 当前会话 + 用户画像摘要 + **任务摘要卡片**（见下） | 该任务全量工作上下文 + checkpoint |
| 是否可打断 | 随时 | 通过任务生命周期（pause/cancel/steer） |

**任务摘要卡片（task digest）**是两脑之间的关键胶水：
中枢为每个活跃任务维护一张几十 token 的卡片（目标、状态、进度、待决问题），
持续注入前台会话上下文。前台因此能随口回答"修图到哪了"，
并把用户的插话（"优先订票"）翻译成对中枢的 steering 指令——
**前台不需要读后台的全量上下文**，这是控制实时会话成本的关键。

## 3. subagent 与长任务执行

- **每个 TaskRun 是一个独立 agent loop**，可再派生 subagent（研究任务拆搜索/阅读/写作并行）。
  subagent 只向自己的父 TaskRun 汇报，父任务向中枢汇报，保持树形、避免网状通信。
- **阶段化 + checkpoint**：执行器把任务规划成显式阶段（plan → 执行 ×n → 汇总），
  每阶段结束落盘。收到 steering 时在阶段边界应用变更；进程被杀在阶段边界恢复。
- **澄清即挂起**：执行中发现需要用户拍板 → 产出结构化澄清请求
  （问题、候选项、默认值、超时策略）→ 状态转 `waiting_user` → 释放算力。
  不允许 subagent 空转等人。
- **GUI 操控（App RPA）特殊性**：路径不可完全预判，敏感动作多。
  执行前生成"动作预案 + 授权边界"（可自动做哪些、遇到什么必须停）；
  支付/发送/删除强制 `waiting_user`，且授权请求附带屏幕截图证据。
- **闲时调度**：算力型任务（批量修图）默认标记为闲时批处理——充电 + 夜间跑，
  除非用户说"现在就要"。

## 4. 打扰管理器：主动性的唯一出口

全双工让 Agent "能"随时开口，打扰管理器决定它"该不该、何时、以何种方式"开口。
**所有主动触达（播报、推送、澄清、追问）必须经过它**，没有旁路。

输入三要素：

1. **消息侧**：紧急度与价值（任务声明的 `attention` 等级 + 内容评估）；
2. **用户侧**：当下状态（在通话？在开会——日历/勿扰？深夜？正在与助手对话？在开车？）；
3. **历史侧**：近期打扰频次预算（一小时内已主动开口 N 次则降级）。

输出决策：

| 决策 | 行为 | 典型 |
| --- | --- | --- |
| `speak_now` | 立即语音插话（仅限用户正与助手交互或明确的高紧急） | 订票只剩 2 张，10 分钟内要拍板 |
| `speak_at_pause` | 等当前话轮/当前用户活动的自然间隙插话 | 对话中插播"修图完成" |
| `push` | 系统通知卡片，不出声 | 澄清请求"12 张照片拿不准" |
| `digest` | 积压进摘要，下次交互时或固定时段合并汇报 | 各类任务的例行完成 |
| `hold` | 暂不触达，条件变化后重评 | 用户在开会，非紧急 |

配套：**主动消息全部落任务收件箱**，用户任何时候都能翻到没被播报的内容——
打扰管理只是控制"推"，不影响"拉"。

## 5. 关键链路串讲

### 5.1 "盯发布会"全链路

```text
对话创建（前台）→ Task{watch} 注册（中枢）
→ 触发器引擎按计划唤起 checker（后台轻调用）×N 次
→ 某次判定"已结束"→ 事件总线 → 调度器启动主 TaskRun（后台深度模型）
→ 搜集/整理/成文 → 发邮件（delivery=email，发送属敏感动作？——
   本例目标就是发给用户本人，创建时已授权，免二次确认）
→ 完成消息 → 打扰管理器 → 判定 push："发布会纪要已发到你邮箱"
→ 用户晚上问起时，前台凭任务摘要卡片可直接口头复述要点
```

### 5.2 "对话中后台任务要澄清"链路

```text
修图 TaskRun 发现 12 张存疑 → 澄清请求 → waiting_user → 打扰管理器
→ 用户正与助手闲聊 → 决策 speak_at_pause
→ 前台在话轮间隙："对了，照片里有 12 张我拿不准，你有空扫一眼，或者我先按'保留'处理？"
→ 用户："先保留吧。" → 前台把答复路由回该 TaskRun → 恢复执行
→ 若用户当时没搭理：按 clarify_timeout（2h 后用默认值"保留"继续，并在结果中注明）
```

## 6. 工程要点

- **中枢必须独立于 LLM 存活**：触发器引擎、任务存储做成系统服务级常驻组件，
  cron/事件订阅注册到 OS 的对应机制（AlarmManager/geofencing/notification listener 等），
  进程被杀也能被系统拉起。LLM 挂了不丢任务，只是执行延迟。
- **一切消息过总线，全程审计**：触发、派发、澄清、授权、交付都是总线上的事件，
  天然获得任务时间线视图（调试与用户信任都靠它）。
- **成本护栏**：watch 轮询、subagent 并发、单任务 token 预算都在中枢强制执行，
  超预算挂起并请示，防止"自定义监视 + 长任务"组合成为吞金兽。
