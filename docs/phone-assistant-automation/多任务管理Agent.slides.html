多任务管理 Agent：需求理解

范围：文本输出（omni 全双工放下一步）｜入口：Query 驱动 + 事件驱动
定位：对话即任务控制台 —— 会话不被任务阻塞，任务以卡片形式活在对话流里

场景回放三轮对话，六个任务

帮我生成一个小男孩玩耍的图片
好的，已经开始为您生成
T1图片·小男孩玩耍已停止?
不对，帮我生成一个小女孩玩耍的
好的，现在帮您生成女孩玩耍的图片
T2图片·小女孩玩耍生成中
再帮我生成 3 张图片，完成后再帮我生成一个视频
好的，3 张图片开始生成，完成后自动生成视频
T3.1图片 ×3 并行生成中
T3.2图片 ×3 并行生成中
T3.3图片 ×3 并行生成中
T4视频（输入=T3 三图）等待依赖

R1非阻塞应答

每个 Query 先秒回一句话，任务后台跑。对话永远可用，不被任何任务占住 —— T1 还在生成时 Q2 照常处理。

R2任务卡片 = 任务的 UI 锚点

任务插入对话流成为状态自更新的卡片（排队/生成中/完成/失败/已取消），进度更新不产生新聊天气泡、不刷屏。

R3意图路由：Query 不都是新任务

每个 Query 先分类：新增 / 修正 / 取消 / 查询。Q2 的"不对"是修正 —— 要落到 T1 头上，而不是简单多开一个任务。

R4修正语义：替代 + 旧任务处置

修正 = 创建 T2 + 决定 T1 怎么办（取消 / 跑完标记"已被替代"）。这是场景中"[图片1卡片停止?]"的问号，需要一条明确策略（见 P4）。

R5批量 + 依赖编排

Q3 一句话 = fan-out（T3.1–3.3 并行）+ join（三张齐）+ 链式触发（T4 视频，输入引用三图产物）。T4 创建即插卡，状态"等待依赖"。

R6事件驱动统一

"T3 全部完成"是一个事件；定时、外部事件（系统事件/自定义监视）走同一条事件总线触发任务 —— 任务链只是事件驱动的特例。

一句话方案主张：一切请求统一为 Task = Trigger + Goal + Policy；即时 Query 是 trigger=immediate 的特例，"完成后再做 X"是 trigger=on_tasks_done 的特例 —— 一套中枢管到底。

统一任务模型：Task = Trigger + Goal + Policy

触发（什么时候干）与执行（怎么干）解耦；LLM 只在创建期与事件后处置期介入

Trigger 类型四种触发，覆盖全部场景

类型含义本场景对应
immediate立即执行（普通 Query 的默认）T1 / T2 / T3.1–3.3
on_tasks_done依赖任务集合全部完成（join）T4：deps=[T3.1,T3.2,T3.3]
at / cron定时（一次 / 周期）"明早 8 点再生成一批"
on_event事件总线上的事件（系统事件 / 自定义监视命中）"到家后……""盯发布会……"

Goal 保留自然语言原话（执行时结合上下文重新理解），只有 Trigger / Policy 结构化 —— 它们需要被非 LLM 组件精确执行。T4 的 Goal 里以产物句柄引用 T3 三图：inputs=[T3.1.out, T3.2.out, T3.3.out]。

意图路由每个 Query 先过四分类

新增创建 Task，插卡
修正新 Task 替代旧 Task + 旧任务处置
取消/暂停指向已有 Task
查询读任务表回答，零新任务
  • 指代解析在"活跃任务表"上做：会话上下文常驻一份轻量任务摘要（每任务一行：id / 目标 / 状态 / 进度），"不对""第二张""那个视频"都解析到具体 task id；
  • 歧义时先问再动："你是想替换刚才那张男孩的图，还是再加一张？"；
  • 卡片上的按钮（停止 / 重试）与口头指令走同一条路由，行为完全一致。

初步架构：会话 Agent + 任务中枢 + 执行器池

双通道消息流：对话流（话轮，LLM 生成）与任务状态流（卡片更新，事件直驱）分离

会话 Agent（LLM）—— 唯一与用户对话的角色

意图路由新增 / 修正 / 取消 / 查询四分类 + 活跃任务表上的指代解析
任务编译一句话 → N 个 Task（Trigger/Goal/Policy），fan-out + join 依赖建图
秒回应答"好的，已经开始生成" + 插入任务卡片占位
事件后处置失败 / 需澄清 / 全部完成时，代表任务向用户开口
① 创建/修正/取消任务 ↓④ 需要对话的事件（失败/澄清/汇总）↑⑤ 卡片状态更新（直驱 UI，不过 LLM）↗

任务中枢（非 LLM，可靠常驻）—— 状态与调度的唯一权威

任务表 + 依赖 DAGTask/TaskRun 持久化；join 计数；产物句柄登记
触发器引擎immediate / at·cron / on_tasks_done / on_event 统一管理
事件总线任务完成·失败·进度、定时到点、外部事件，全部过总线可审计
调度器并发额度、优先级、取消信号下发、失败重试策略
② 派发 TaskRun ↓③ 进度 / 完成 / 失败事件 ↑

执行器池—— 无状态 worker，可横向扩展

生图 worker接收 Goal + 上下文，产物写存储、登记句柄
生视频 worker输入 = 依赖任务的产物句柄
Agentic worker深度研究 / App 操控等长任务（subagent loop，后续接入）
取消协议响应中枢的 cancel 信号，及时释放资源、清理半成品
为什么这样切：① 卡片进度更新事件直驱 UI，零 token、零时延，LLM 不参与刷进度；② 中枢独立于 LLM 存活，会话模型故障不丢任务；③ 该中枢即 03 章"调度与状态层"，下一步接 omni 时前台换成全双工秘书、中枢与执行层原样复用。

→

设计决策修正时旧任务（T1）的处置策略

方案行为适用
A. 立即取消发 cancel，卡片→"已取消（被 T2 替代）"刚开始跑、成本未沉没 —— 默认
B. 跑完但降级继续生成，卡片→"已被替代"，产物静默入库进度 >80%，沉没成本已付，留着或许有用

建议：按进度阈值自动选 A/B，卡片明示结果；用户可在卡片上一键"还是要这张"。修正判定置信度低时先反问，避免误杀（见 P6）。

检验该场景验证了哪些机制

  • R1 非阻塞：T1 在跑，Q2/Q3 照常处理；
  • R3/R4 修正路由 + 替代语义（T2 ⇄ T1）；
  • R5 一句话编译出 fan-out + join + 链式任务；
  • R6 "3 图完成"作为事件自动触发 T4 —— 与定时/外部事件同一总线；
  • R2 六张卡片各自独立更新，对话流不被进度刷屏。

扩展场景验证：需求与方案是否兜得住

在同一模型下推演 7 个典型场景 —— 全部只用 P2/P3 已有机制，无需新增概念

场景（用户说）系统行为用到的机制
"图好了吗？" 路由=查询 → 读任务表汇总口头回答（"T2 快好了，3 张图完成 2 张"），不新建任务 意图路由·查询分支；活跃任务表
"第二张重新生成，光线亮一点" 指代解析 → T3.2；创建 T3.2'（原 Goal + 追加约束 + 引用原产物），T3.2 标记 superseded；T4 的依赖自动改指 T3.2'，若 T4 已启动则询问是否重做 指代解析；修正语义；依赖 DAG 改写
T3.2 生成失败（系统事件） 自动重试 ×N；仍失败 → T4 转 waiting_user，会话 Agent 开口："第二张失败了，重试 / 用两张先做视频 / 取消视频？" 失败事件；join 阻塞策略；waiting_user 澄清（带候选项）
"视频改成竖屏的"（T4 还在等待依赖） 路由=修正 → T4 未启动，直接改 Goal，零成本；若已 running，按 checkpoint 决定改参续跑或重启 修正落在 waiting 态任务；steering
"算了，视频不要了" 取消 T4；上游 T3.x 不受影响继续生成（产物本身仍是用户要的）；若 T3.x 仅为 T4 服务才级联询问 取消传播策略（下游取消默认不上溯）
"这批图片生成完发我邮箱" 追加任务 T5：on_tasks_done[T3.*]，delivery=email —— 与 T4 共享同一组依赖，一个事件可触发多个下游 事件多播；Policy.delivery
"明早 8 点把这些图再精修一遍" 创建 T6：at(明日8:00)，Goal 引用 T3 产物句柄 —— 定时与任务链是同一套 Trigger 的两个类型 at/cron Trigger；产物句柄跨任务引用
结论：7 个场景没有一个需要为它单独发明机制 —— 意图路由（4 分类）× Trigger（4 类型）× 生命周期（含 waiting_user / superseded）× 事件总线，这四件套的组合封闭性较好。下一步接入长任务（深度研究 / App 操控）时复用同一骨架，只是 worker 变成 agentic loop。

关键设计决策与开放问题

已定主张先对齐，开放问题带倾向供拍板

已定主张本次对齐的六条

  • 统一任务模型：即时 Query、定时、事件、任务链共用 Task = Trigger + Goal + Policy，不做多套机制；
  • 双通道消息流：进度更新事件直驱卡片 UI，不过 LLM、不产生聊天气泡；LLM 只管创建期与事件后处置期；
  • 意图路由四分类先于任务创建，指代解析基于会话内常驻的活跃任务表；
  • 修正 = 替代 + 处置：新增 superseded 终态，卡片保留可追溯、可一键找回；
  • join 由中枢计数，完成事件多播，一组依赖可同时触发视频、发邮件等多个下游；
  • 中枢非 LLM 常驻：任务与触发器持久化，会话模型故障不丢任务。
