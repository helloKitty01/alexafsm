# 03 平台能力：PC 能指定窗口，手机是录屏权限，iOS 最硬

> 四段管线里只有 Capture Adapter 是平台代码。判定逻辑（02）应做成纯函数，
> 输入小图 + ROI，输出 `skip / save`，方便用录像回放测，不绑在某一 API 上。

## 1. 能力对照

| 平台 | 推荐 API | 指定窗口 | 排除光标 | 脏区提示 | 系统强制指示 | 后台 | 一期建议 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| Windows 10+ | `Windows.Graphics.Capture`；全桌面可辅以 DXGI Desktop Duplication | 能 | 能 | DXGI 有脏矩形；WGC 无 | 采集指示（黄框等，随版本） | 窗口在就能采 | **主战场** |
| macOS 12.3+ | ScreenCaptureKit | 能（display / window / 过滤本应用） | 能 | 无（自己做分块差） | 菜单栏录屏点 | 受 TCC 与 App Nap 约束 | 与 Win 同期 |
| Linux | xdg-desktop-portal + PipeWire（Wayland）；X11 仅兜底 | portal 看合成器 | 视实现 | 无 | 各桌面不同 | 视会话 | 有余力再做 |
| Android 5+（实用 10+） | `MediaProjection` + `VirtualDisplay` + `ImageReader` | 14+ 可选「仅此应用」 | 无光标问题 | 无 | 15+ 状态栏大芯片，锁屏会停 | 必须前台服务（14+ `mediaProjection` 类型） | **手机主战场** |
| iOS | ReplayKit Broadcast Upload Extension | 不能（系统录屏） | 系统光标不在画面里 | 无 | **必有**红条 / 岛 | 扩展进程，主 App 可被挂起 | 能做但体验明显更「像在录屏」 |

共同产品规则：进入模式 = 打开 Capture Session；退出 / 锁屏 / `onStop` = 释放全部 Surface，已落盘文件保留。

## 2. Windows

**首选 Windows.Graphics.Capture（WGC）**：用户（或程序枚举）选一个窗口，
例如「腾讯会议」「Chrome」「PowerPoint 放映」。只采这个 HWND，桌面其它东西自然不进分析轨。
可请求排除光标。这直接消掉 01 章 S8 的一大部分。

**DXGI Desktop Duplication** 适合「整桌 + 脏矩形预检」。
`AcquireNextFrame` 后先看 dirty/move rects：空则 0 代价；只有右下角脏且落在忽略区也跳过。
代价是采到整桌，任务栏、弹出的聊天都会进画面，ROI 必须更强。

建议策略：

1. 能选窗口 → WGC 采该窗口；分析轨把帧缩到 320 边；
2. 用户坚持「整屏」→ DXGI + 脏矩形 + ROI；
3. 自己的悬浮计数条用 WGC 的窗口过滤或事后裁掉，避免「截到自己的 HUD」污染哈希。

注意：部分会议 App 的共享区是子窗口或硬件叠加，枚举不到「纯课件窗」。
这时退回整窗 + ROI，不要幻想去接 Zoom SDK 的共享流（权限、审核、多厂商组合爆炸）。

## 3. macOS

ScreenCaptureKit 与 WGC 同级：按 display 或 `SCWindow` 过滤，可排除自己的 App，
可关光标。TCC「屏幕录制」权限必须在进入模式时已经是 granted，否则黑帧。
权限被用户在系统设置里关掉 → 会话失败，走 01 的 S9。

Retina：分析轨按点（pixel）而不是点逻辑 pt 取，避免 2x 缩放把分块差打乱。
保存图按窗口的 pixel size 编码。

## 4. Android

标准路径：

1. `MediaProjectionManager.createScreenCaptureIntent()` → 用户确认；
2. 用返回的 token 建 `MediaProjection`，**先** `registerCallback`，再 `createVirtualDisplay`；
3. `VirtualDisplay` 的 Surface 接到 `ImageReader`（分析尺寸，例如 320×180，`RGBA_8888`）；
4. 另备一个按需的全分辨率 ImageReader，或对同一虚拟屏用更小的分析 Surface（虚拟屏本身就可以低于物理分辨率——判定够用；**保存时如果虚屏已经缩小，清晰度会不够**）。

清晰度权衡：虚拟屏设成分辨率过低，落盘会糊。
推荐虚拟屏跟被采内容走（听 `onCapturedContentResize`），分析轨在拿到 `Image` 之后 CPU 缩小。
内存上只持有最新一帧全分辨率（环形 1–2 帧），不要队列堆积。

Android 14+：

- 前台服务类型必须声明 `mediaProjection`，通知栏常驻「自动截图中 · 点此停止」；
- 投影目标尽量让用户选**单个应用**（会议 App），减少桌面/通知污染；
- 用户在系统芯片上点停、或锁屏 → `Callback.onStop()`，按 S9 收口。

Android 15：状态栏芯片更大，这是系统要求，产品不要试图藏。
文案写成「自动截课件」而不是「录屏」，降低惊吓，但系统 UI 仍可能写 Screen sharing。

`ImageReader.acquireLatestImage()`：始终拿最新、把旧的 close，避免生产者堵住。
分析线程独立，不要在 ImageReader 回调里做 pHash 以外的重活。

## 5. iOS（能做，但不能装成「静默截图」）

iOS 不允许普通 App 去截其它 App 的屏。唯一正规通道是 **ReplayKit 广播**：

- 主 App 调 `RPBroadcastActivityViewController` / 启动广播；
- `RPBroadcastSampleHandler`（Upload Extension）收 `CMSampleBuffer`；
- 扩展里跑 02 的纯函数；要保存时把 JPEG 写到 App Group 容器；
- 主 App 通过 Group 显示缩略图、提供停止入口。

硬约束，必须写进产品说明：

1. 系统会显示录制指示（红条 / Dynamic Island），无法去掉；
2. 扩展内存与时间都紧，分析必须更狠（更低分辨率、更低 fps）；
3. 主 App 进后台可能被挂起，**判定要能在扩展里独立跑完「存盘」**，不能指望主进程还活着；
4. 不能指定「只采腾讯会议」——整机画面都会来，ROI 变成刚需；
5. 审核：描述清楚是用户主动开启的课件截图，不要伪装成系统截屏。

若一期人力只够两端：先 **Windows + Android**。iOS 第二期用同一套纯函数，只换 Adapter。

## 6. 采集范围怎么选（产品 × API）

```text
用户进入模式
    │
    ├─ PC 且能列出窗口 → 默认选前台窗口，允许改成「整屏」或框选
    ├─ Android 14+ → 优先走单应用投影（系统 UI）
    └─ iOS / 旧 Android → 整屏 + 进入后可选「忽略区」（画一个头像框）
```

框选区域在分析前裁切，等于最强 ROI。对「网课浏览器里只有中间一块是课件」非常有效。
PC 一期就应该有；触屏画框也行，但不要挡住课。

## 7. 权限与生命周期（所有平台同一张状态图）

```text
idle
  │ 用户打开模式
  ▼
requesting_permission   （系统对话框；可取消 → idle）
  │ 成功
  ▼
capturing               （指示器可见；分析轨在跑；已保存 N）
  │ 用户停止 / 锁屏 / onStop / 空间满 / 超时
  ▼
stopping                （释放 VirtualDisplay / WGC session / ReplayKit）
  ▼
review                  （缩略图、删除、补截、导出）→ idle
```

`capturing` 期间进程被杀：下次启动扫描本场目录（按会话 id 分文件夹），
用已有 sidecar 哈希重建 Unique Filter，避免「杀进程后同一页再存一次」。
会话 id 在进入模式时生成，目录名带日期。

## 8. 不要做的平台捷径

- **无障碍 / 截屏快捷键模拟**：不稳定、审核风险、有的厂商会拦。正规采屏 API 是正路。
- **读会议 App 的缓存文件「直接拿 PPT」**：偶发能用，不是产品能力。
- **HDMI / 虚拟摄像头采集**：那是主播方案，和「用户手机上看网课」不是同一条路径。
- **浏览器扩展只截 DOM**：只能覆盖网页课，覆盖不了会议客户端，至多当 PC 的第三条 Adapter，不是主干。
