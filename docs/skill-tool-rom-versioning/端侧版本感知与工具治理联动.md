# 端侧版本感知与工具治理（与 skill 管理的联动）

> 承接[配套管理方案](./skill与工具ROM配套管理方案.md)的三个深化问题：
> 1. 小艺 / skill 需要感知哪些端侧版本信息？如何避免"太多、太碎"？
> 2. 工具管理是什么样的：哪些必须保证兼容，哪些允许破坏性变更？
> 3. 工具管理与 skill 管理如何联动？

---

## 一、感知哪些端侧版本信息：感知能力，不感知版本

### 1.1 碎片化的来源（为什么会"太多、太碎"）

端侧工具的实现方分散在多个独立发布的载体上：

| 载体 | 发布通道 | 节奏 |
| --- | --- | --- |
| ROM / 系统 framework | 整机 OTA | 月级~季级 |
| 系统应用（相机、图库、音乐、日历…） | 应用市场独立更新 | 周级 |
| 小艺端侧框架 / 助手 APK | 应用市场 / 随 ROM | 周~月级 |
| 基础服务（账号、推送、HMS 类） | 独立更新 | 周~月级 |
| 机型形态差异（折叠 / 平板 / 车机 / 手表） | 出厂即定 | — |

如果 skill 体系直接感知这些**组件版本号**，版本空间是它们的笛卡尔积，
必然失控。所以第一原则：

> **skill 体系永远不感知组件版本号，只感知"这台设备此刻的工具契约"。**
> 一个端侧信息值得进入 skill 体系，当且仅当它改变"模型能调什么工具、怎么调"。

### 1.2 两层收敛：把碎片化封装在正确的层

**第一层（端侧）：工具注册中心 → 能力清单。**
各 provider（系统服务、系统应用、三方）把工具注册到小艺端侧的统一注册中心；
会话建立时端侧上报**能力清单（capability manifest）**：

```json
{
  "tool_api_level": 7,
  "tools": [
    {"name": "open_app",   "schema_ver": 2},
    {"name": "send_msg",   "schema_ver": 3},
    {"name": "clipboard_read", "schema_ver": 1}
  ],
  "manifest_hash": "f3a9c1"
}
```

相机 app 是什么版本、framework 是什么版本——这些是**注册中心的输入**，
不是云端的输入。N 个组件版本在端侧折叠成一份清单：
碎片化没有被消除，而是被**封装**在它产生的那一层。

**第二层（云端）：能力清单 → tool API level（离散化）。**
云端不对任意工具集组合做分发决策（组合空间太大），而是把机队实际出现的
manifest 聚类映射到有限的、单调递增的 **tool API level 序列**：

- **API level 只随"计划内的成套工具变更"推进**——通常对齐 ROM 大版本 /
  小艺框架大版本，一年个位数次；
- 计划外的中间碎片（个别系统应用先升级、带来一两个工具的出现/变化）
  **不新开 level**，由 skill 的 `required_tools` 精确匹配或正文能力分支吸收。

两层各司其职：

| | 能力清单（细粒度事实） | tool API level（粗粒度句柄） |
| --- | --- | --- |
| 生产方 | 端侧注册中心 | 云端发布管理 |
| 消费方 | L0 拼装、pre-call 校验 | skill 兼容声明、分发路由、评估矩阵 |
| 数量 | 每台设备一份 | 全机队个位数~十几个在役 |

### 1.3 skill 作者的视角：感知面收敛到"一个整数"

skill 兼容声明只有两个字段，且第二个多数 skill 不需要写：

```yaml
min_tool_api: 7            # 必填：一个整数
required_tools:            # 选填：仅当依赖"计划外碎片工具"时才写
  - smart_clipboard_v2
```

- 常规 skill：只写 `min_tool_api`，感知面 = 1 个整数；
- 依赖某个"独立升级的系统应用刚带来的新工具"的 skill：
  加 `required_tools`，分发服务按能力清单精确匹配——**这就是碎片的
  逃生通道，代价只由用到它的少数 skill 承担**，而不是抬高全体的感知面。

### 1.4 明确"不感知什么"（防碎清单）

| 端侧信息 | 是否进 skill 版本体系 | 去处 |
| --- | --- | --- |
| ROM / 组件 / APK 版本号 | **否** | 端侧注册中心的内部输入 |
| 机型、芯片 | **否** | 若确实改变工具行为，必须表现为工具 schema / 能力清单差异 |
| 设备形态（折叠 / 平板 / 车机） | **否**（不是版本问题） | L1 会话级环境变量，skill 正文按环境变量分支 |
| 电量、网络、前台应用等运行时状态 | **否** | 环境变量通道（见 [skill 环境变量方案](../skill-env-variables/skill环境变量传入方案.md)） |
| 工具列表 + schema 版本 | **是** | 能力清单（唯一入口） |
| tool API level | **是** | skill 兼容声明的唯一常规句柄 |

判据复述：改变"能调什么、怎么调"的进能力清单；改变"该怎么做"的进环境变量；
两者都不改变的，根本不进上下文。

## 二、工具治理：分层稳定性契约

### 2.1 先澄清兼容方向

约定俗成容易混，用调用方视角说清楚：

- **必须保证的方向：老 skill × 新工具不坏**（工具的向后兼容，
  backward compatibility）。设备升级 ROM 后，还没适配的老 skill、
  以及全量单版本 skill 的既有正文，调用新版工具必须照常工作。
- **不要求的方向：新 skill × 老工具**。老设备上没有新工具，
  这由 skill 侧解决（`min_tool_api` 门控 / 能力分支），
  不要求工具做"前向兼容"——那在物理上也做不到（老 ROM 改不了）。

### 2.2 工具分层：不同层不同的稳定性承诺

一刀切"全部必须兼容"会扼杀迭代，一刀切"都可以变"会炸掉 skill 矩阵。
按**依赖面**分三层：

| 层 | 范围 | 稳定性承诺 | 破坏性变更 |
| --- | --- | --- | --- |
| **T0 核心冻结层** | 基础设备操作（打开应用、点击、返回、查询状态）、框架工具（`load_skill` 等） | 契约冻结：只允许加可选参数、返回加字段 | **永不允许**。几乎所有 skill 依赖它们，破坏一个 = 全量 skill 受影响 |
| **T1 领域稳定层** | 各垂域工具（消息、日历、相机、音乐…） | 默认向后兼容 | **例外允许**，走治理流程：评审 + deprecated alias 缓冲 ≥1 个 ROM 大版本 + 提前通知受影响 skill owner |
| **T2 实验层** | 新能力孵化、beta 工具，schema 显式标 `experimental` | 无承诺 | **自由变更甚至删除**；对应约束在 skill 侧：只有版本门控的 skill 才能引用 T2 工具，禁止进入全量单版本 skill 正文 |

工具晋级（T2 → T1）是显式动作：schema 去掉 experimental 标记、
纳入兼容承诺、进入 API level 快照——从此受治理流程约束。

### 2.3 变更分型的硬定义（写进治理规范，供 CI 自动判定）

| 类别 | 变更 | 判定 |
| --- | --- | --- |
| 兼容（直接发） | 新增工具 | ✅ |
| 兼容（直接发） | 既有工具加**可选**参数（带默认值） | ✅ |
| 兼容（直接发） | 返回结构**加**字段 | ✅（但见 2.4 行为兼容） |
| 兼容（直接发） | 错误信息文案改进、性能优化 | ✅ |
| 破坏（走流程） | 删工具、改工具名 | ❌ |
| 破坏（走流程） | 参数改名 / 变必填 / 类型或取值语义变化 | ❌ |
| 破坏（走流程） | 返回字段删除 / 改名 / 类型变化 | ❌ |
| 破坏（走流程） | schema 不变但**行为语义**变化（最隐蔽，必须人工申报） | ❌ |

### 2.4 LLM 消费方的特殊性：schema 兼容 ≠ 行为兼容

传统 API 治理到 schema diff 为止；工具的消费方是模型，还要多守一条：
**返回结构的大幅变化（哪怕纯新增）也可能改变模型行为**——字段多了、
顺序变了、体积涨了，模型的注意力和后续决策都可能漂移。所以：

- 兼容性判定 = schema diff（自动）+ **skill 回归评估**（T1 及以上工具变更
  必须跑受影响 skill 的回归集，行为指标不回退才准出）；
- 返回结构保持确定性序列化（键序、格式固定），这同时也是 KV cache 纪律。

### 2.5 把破坏性变更的成本压下来的工具箱

1. **deprecated alias**：老工具名保留 1~2 个 ROM 大版本，端侧转发到新实现；
   把"破坏性"降级为"增量"，skill 侧只需走能力分支甚至无感。
2. **框架层 shim**：schema 带版本号，pre-call 拦截器做老格式 → 新格式的
   参数适配（比 alias 更细粒度，适合"参数改名"类变更）。
3. **schema diff lint**：工具注册中心 CI 自动分类变更（对照 2.3 表）；
   判定为破坏性的提交必须携带治理审批 + 受影响 skill 清单（来自第三节的依赖索引）。

## 三、工具管理与 skill 管理的联动

### 3.1 数据基础：双向依赖索引

- skill → tools：来自 metadata 的 `required_tools` + **正文自动扫描**
  提取的工具名引用（skill 上架 CI 时静态解析，入库）；
- tools → skills：上表反查即得。

这张表是所有联动的基础设施：没有它，"破坏性变更影响哪些 skill"只能靠人肉记忆。

### 3.2 工具发布门禁：快通道先行原则

核心时序约束：**慢通道（ROM）的破坏性变更，必须等快通道（skill）先适配完成。**
skill 是云端天级下发的，让它先行没有任何成本：

```text
① 工具 owner 提交破坏性变更 → CI 判定破坏性 → 查依赖索引，列出受影响 skill
② 门禁：受影响 skill 逐个备好新版本（min_tool_api = N+1，云端提前上架——
   老设备解析不到它，不会误分发）或确认走能力分支
③ 门禁通过 → 工具变更随 ROM N+1 灰度发布
④ 设备升级 → 会话上报新能力清单 → 分发服务自动解析到新 skill
⑤ 老设备继续拿老 skill（max_tool_api = N 封顶冻结），无感知
```

注意 ④ 不需要任何"切换动作"：按能力解析的分发规则让 skill 版本
跟着设备升级**自动漂移**，这正是第一节地基的回报。

### 3.3 skill 发布门禁：静态校验 + 快照回归

反方向的门禁，杜绝"skill 让调 X 但工具列表里没有 X"：

- **静态校验**：skill 正文引用的每个工具，必须存在于其声明的
  `min_tool_api` 对应的**工具集快照（golden manifest）**中，且参数用法
  与 schema 匹配；引用 T2 实验工具的 skill 必须是版本门控的（带 required_tools）；
- **快照回归**：每个在役 API level 冻结时产出 golden manifest；
  skill CI 在其声明支持的每个 level 的模拟工具集上跑回归，
  能力分支的**每条路径**都要被覆盖（新路径在 level N+1 快照跑、
  降级路径在 level N 快照跑）。

### 3.4 节奏对齐与运行时回流

- **节奏**：tool API level 随 ROM 大版本推进；ROM 灰度期间新旧 level
  长期并存是常态，被按能力分发天然吸收，不需要"冻结窗口"；
- **运行时回流**：pre-call `tool_not_available` 拦截率（≈0，>0 报警定位
  分发通道 bug）、能力分支老路径使用占比（驱动删分支）、各 level 设备占比
  （驱动老 skill 冻结 / EOL）——三个指标把联动闭环从"发布时"延伸到"运行时"；
- **组织**：破坏性变更流程自动通知受影响 skill 的 owner（依赖索引精确到人），
  代替全员广播。

### 3.5 联动全景（一句话版）

端侧把组件版本折叠成能力清单，云端把能力清单离散成 API level；
skill 用一个整数声明兼容性，分发按能力自动解析；
工具按 T0/T1/T2 分层承诺稳定性，破坏性变更被 alias/shim 尽量降级，
降不掉的走"skill 先行"门禁；双向依赖索引 + 双向发布门禁 + 运行时三指标，
构成 tool 与 skill 两个管理体系之间的全部接口。
