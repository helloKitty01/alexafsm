本质：skill 与工具集强绑定v2.5 汇报版 · 背景与本质 → 问题与挑战 → 现状与迁移 → 分项方案 → 落地路线

一份 skill 正文是写给一个确定的工具契约集合的。ROM 版本、API level、机型、组件版本 —— 都只是定位工具集的代理变量，本身不是兼容性的对象，别的都是浮云。

现状卡点 · 工具集不是一个"第一类对象"

  • 当前没有一个地方能权威回答："这台设备此刻的工具集是什么"
  • 于是管理只能围绕代理变量打转：每条规则都要同时谈 ROM、机型、API level、组件版本 —— 规则复杂、彼此纠缠，且都在间接描述同一个东西
  • 版本感知"太多、太碎"的根源就在这里：碎的不是信息，是缺少收敛它们的对象

解法 · 把对象立起来，两条路线生产它

  • 路线 A · 构建端侧注册中心实报：各 provider 注册工具，会话时实报能力清单 —— 实然、准确，但要随 ROM 下场
  • 路线 B · 推导云端登记表推导：用现有信息（工具管理记录 × ROM 版本 × 机型）查表拼出工具集 —— 应然、立即可用
  • 上层机制面向对象设计、与来源解耦：skill 声明、分发、门禁、评估只见工具集对象，不见它怎么来的 —— 两条路线可共存、可切换，不推翻上层

工具集对象 · 两条路线共享的唯一抽象

toolset: { toolset_id: "ts-8-phone-a3f9", tool_api_level: 8, tools: [{name: send_msg, schema_ver: 3, tier: T1}, …], produced_by: device_report (路线A) | registry_derived (路线B), source_inputs: {rom: "X.Y.Z", model_series: "P-series"}（B 路线审计用） }

skill 的兼容声明只对这个对象（min_tool_api + required_tools）；ROM / 机型 / 组件版本降级为生产对象时的输入，被封装在生产侧，消费侧永远不可见。

现状三缺失与三步迁移路径比"缺登记表"更进一步：连"工具"都还不是第一类对象

现状：工具定义内嵌在 skill 正文里、无工具 ↔ skill 映射、无实时工具上报。三个缺失是同一根因的三个表现；迁移第一步是纯云侧动作，不动端侧、不动模型，立即可做。

现状三缺失

缺失直接后果
工具定义内嵌 skill，无中心注册同一工具在多个 skill 里各定义一份，schema 口径各改各的、悄悄漂移；工具没有独立生命周期与 owner

步骤动作解决
① 工具定义出仓schema 抽出 skill → 中央工具注册（唯一定义 · 唯一 owner · tier 标注）；skill 改为按名引用；CI 扫描引用自动产出依赖索引缺失 1 + 2；纯云侧

方案一 · 感知收敛：登记表推导工具集对应问题一 · 路线 B 为主，A 仅远期可选，长期并存

关键结论：路线 B 不是临时方案，而是存量设备的终态方案。停更机型永远不会有注册中心，且它们的工具集已冻结 —— 恰好最适合查表（登记一次，永久准确）。

对比 · 四个维度

维度路线 B（登记推导）路线 A（设备实报）
准确性应然（有漂移风险，靠三补偿）实然：天然覆盖机型 / 区域 / 独立升级 / 用户禁用
建设成本云端一张表 + 发布流程改造端侧注册中心，随 ROM 下场
可用时间立即随新 ROM 逐步覆盖
覆盖范围全机队（含停更机型）只有搭载注册中心的新设备

演进路径

现在 全机队查表（B） ↓ 注册中心随新 ROM 下场 过渡 新设备实报（A）+ 存量查表（B）同一对象接口 ↓ 存量自然淘汰 远期 A 为主，B 覆盖长尾 —— B 永不完全退役

路线 B 的固有风险 · 应然 ≠ 实然

登记表描述"这个 ROM × 机型应该有什么工具"，设备实况可能偏离：系统应用没升到位、区域裁剪、用户禁用组件。三个补偿机制：

  • 安全网升格为纠偏信号：B 阶段 tool_not_available 触发即说明表与实况漂移，按 (ROM × 机型 × 工具) 聚合上报，直接驱动修表
  • 采样审计：抽样设备实测工具可用性与登记表比对，漂移率进看板
  • 混合模式:漂移高发载体（独立升级的系统应用）优先切设备实报，其余仍查表 —— 对象 schema 相同，单设备内可混合拼装

为什么"登记即门禁"能守住表的质量

登记表不靠自觉：工具的任何上线 / 变更必须同步更新登记条目，否则发布门禁不放行。"人工维护易漏"被转化为流程强制 —— 表的准确性与工具发布的准确性同源；且与 AI Agent TMG 评审（2D API 规则）在同一流程节点，登记是评审产物的一部分，不新增负担。

API level 与 ROM 的关系（常见误区）

API level 不能代表 ROM，设计上也不应让它代表：同一 ROM 不同机型工具集可能不同；多个 ROM 小版本共享同一契约；独立 OTA 组件可不升 ROM 改变工具集。API level 语义锚定的是工具契约快照（对能力清单的离散化编号），运营节奏可对齐 ROM 大版本，但 skill 声明永远针对 API level + required_tools。自检规则：若发现"必须用 ROM 版本号才能表达某差异"，说明有能力没被清单表达 —— 正确动作是补清单字段，不是引入 ROM 维度。

解析与校验 · skillsearch 的防冲突 / 防遗漏

收敛规则：每个版本只声明 API 下界，按下界降序排列即回退链（skillsearch 新 → 旧首命中）—— 数学上自动互斥、自动全覆盖；最老版本的下界 = 该 skill 的最低支持线，低于它明确不支持。 三项上架静态校验：① 区间空集（如手写 >11.7.5.203 & <11.7.4.210 的写反区间，永假静默失效）② 相邻版本重叠 ③ 档位覆盖漏洞。 平台生成：条件一律由结构化声明（min_tool_api / 机型名单）生成，禁止手写表达式。 商用转正收编：转正校验强制清空研发期条件，只留主键 + 必要机型名单。

为什么 S1 的禁令和 S2 的拒答是同一个逻辑

风险不对称：新增子技能的失败模式是"老设备得不到新东西"（可接受）；修改既有流程去依赖新工具的失败模式是"老设备上原来能用的功能坏了"（功能回退，事故级）。前者轻流程，后者重流程 —— 判据不是"改了多少"，而是"是否触碰老设备的既有行为"。

跨版本还是按大版本开线？默认一个 skill 跨多版本（稳定业务：设备操控、全场景…）；快速演进业务（修图 Agent 等）允许按 ROM 大版本开版本线，但属受控例外：AI Agent TMG 准入 + 在役 ≤2~3 + 收编阶梯（P11），演进放缓后收敛回单 skill。

S2 与 S3 是同一件事的两端：S3 = 工具侧动作（新工具上线登记、T2 起步），S2 = skill 侧动作（内容用上新工具 + 老设备拒答 / 降级分支）—— 时序必然 S3 先行、S2 跟进，一次"新能力上线" = S3 + S2 配对。另注：新增子技能 ≠ 新增工具，用既有工具组合出新玩法是纯内容变更，走 S1。

7 / 14

机型与设备的工具差异管理由外部系统（登记表 / 分发配置）管理，不塞进工具内部

原则：静态已知的差异在分发层解决（子技能级门控 + 统一拒答）；运行时才能知道的差异才留给工具层兜底。差异的事实源永远是登记表，工具内部不隐藏机型逻辑。

差异来源 × 在体系中的表达

差异来源表达方式
硬件能力（SoC / 板卡 / 传感器）该机型登记表中不登记对应工具 → 分发门控与能力分支自动生效
上线节奏（部分机型先上）子技能级机型白名单，随节奏扩量；未配置机型继承既有体验（如修图继承 6.1）
形态（折叠 / 平板 / 车机）契约档位按设备品类分列；形态相关行为差异走 L1 环境变量

方案三 · skill 何时依赖端侧智慧助手 APP 版本对应问题三 · 判别总则、机制清单与设计约束

一句话总结：端侧是纯工具执行 → skill 不依赖 APP 版本；端侧含 Agent harness（skill 运行框架）→ skill 依赖 APP 版本。另有第二条链路：APP 同时是工具 provider，其工具变更同样牵动 skill（左下）。

两种端侧形态 · 依赖性由架构决定

形态一 · 纯执行器（目标形态）

云端 harness变量解析 · 结果信封 · pre-call 拦截 · 拒答结构 —— 协议全部云端解释
→
端侧 APP收到的已是解析完成的普通工具调用，纯执行

⇒ skill 零依赖 APP 版本：机制升级随云端 skill 库同源发布，天然配套。

形态二 · 端侧含 Agent harness

云端下发含协议语法的调用 / skill 逻辑
→

第二条链路 · 助手 APP 也是工具提供者

APP 自身注册业务工具（内置备忘、搜索、会话管理…），APP 升级 = 工具契约变化，skill 随之联动。处理回到常规工具管理轨道：以 provider = 助手 APP 进登记表（查表键含 APP 版本段），同样受 T0/T1/T2 稳定性承诺与 S3/S4 流程约束，破坏性变更走"快通道先行"。特殊点只在发布通道：应用市场周级更新、可独立于 ROM、可产品内引导升级 —— 它是"最快的工具慢通道"，登记与灰度节奏按周管理。

设计约束与兜底（机制链路）

① 端侧纯执行器原则：机制协议尽量云端解释，端侧只留纯执行 —— 依赖被结构性消除大半。 ② 无法云端化的收编为机制契约：runtime 能力（env_report、result_envelope: 2…）进登记表，查表键扩展为 ROM × 机型 × 助手 APP 版本段。 ③ required_runtime 由 CI 自动推导（正文用了 ${} 即要求对应 runtime）；机制降级与工具降级同一套能力分支写法（如"无 env_context 时改调 get_foreground_app"）。

方案五 · skill 多版本管理对应问题五 · 触发、处理、收编 —— 多版本是例外不是默认

三类定义：灰度 = 同一人群新旧短期共存（发布风控）；门控 = 不同契约档位各用其版（兼容性 —— 按登记表推导的 API level 分发，落地≈按 ROM 版本段，无需自建工具集）；实验 = 同一人群分桶 A/B（效果对比）。多版本是例外不是默认，开门控版本需 AI Agent TMG 审批。

  • ⑦ 工具分层承诺：T0 冻结 / T1 走流程 / T2 只许门控 skill 引用
  • ⑧ 快通道先行：skill 先上架，工具再随 ROM 灰度，升级自动漂移
