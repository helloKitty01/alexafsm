# 云侧单 skill 的可行性评估（单版本 vs 多版本）

> 问题：云侧能否只保持**一个 skill**，让它兼容所有在役设备（最新 skill 向下
> 覆盖老工具集），从而完全避免 skill 多版本？
>
> 术语先对齐：这里说的"前向兼容"，准确含义是**最新 skill 对老工具集向下兼容**
> ——一份正文在所有在役 tool API level 上都能给出正确指引。
>
> 前置：[配套管理方案](./skill与工具ROM配套管理方案.md)、
> [端侧版本感知与工具治理联动](./端侧版本感知与工具治理联动.md)。

---

## 一、把问题翻译成技术条件

"只保持一个 skill"等价于：单一正文必须覆盖**全部在役工具契约的并集**。
可行性因此不取决于 skill 侧的意愿，而取决于在役契约之间的**差异性质**：

- 差异全部是**增量的**（新 level 只是多了工具 / 多了可选参数）→
  正文用能力分支覆盖："若工具列表中存在 X 则用之，否则老路径"——可行；
- 差异存在**破坏性**（同名工具参数语义不同、工具被删改名）→
  一份文本要同时描述两套互斥协议——不可行（详见第三节）。

所以第一个结论：**单 skill 的可行性不是 skill 自己的性质，
是工具治理买来的**。T0 冻结 + T1 alias/shim 把到达机队的差异全部增量化，
单 skill 就成立；治理失守出现真破坏性差异，单 skill 就必然被击穿。

## 二、单 skill 的成立条件（三条，都可运营监控）

1. **工具差异全部增量化**：T0 永不破坏；T1 的破坏性变更全部被
   deprecated alias / 框架 shim 降级成增量后才触达机队。
2. **分支预算不超**：正文内在役能力分支 ≤ 2~3 个，且各分支步骤差异温和。
   分支多了或分支间步骤差异巨大（几乎是两个 skill），模型走错分支的
   风险和 token 成本都会失控。
3. **在役 level 跨度有限**（2~3 个）：靠 ROM 升级推进 + 老 level EOL
   持续收尾。跨度越大，"并集"越臃肿。

## 三、即使可行，单 skill 的真实成本

逐项列出，避免只看见"管理省事"：

| 成本项 | 说明 |
| --- | --- |
| token 与干扰 | 正文长期携带全部降级路径，每次加载全机队买单；分支间指令互相干扰，模型可能把新工具的参数习惯带进老路径（串扰） |
| 爆炸半径 | 一次编辑同时作用于**所有** level；坏改动伤及全机队。多版本下老 skill 冻结，老设备零回归风险 |
| 测试没有省 | 单 skill 仍须在每个在役 level 的工具集快照上回归，分支每条路径都要覆盖——**评估矩阵与多版本完全相同**，省掉的只是"维护多份文本" |
| 回滚粒度粗 | 无法只回滚"新 level 上的行为"，回滚即全机队回滚 |

## 四、多版本的真实成本

对称地列出：

| 成本项 | 说明 |
| --- | --- |
| 回灌漂移 | 同一处修复要打到多个在役版本，久之同一段话在各版本各改各的，事实源分裂——这是多版本最疼的一条 |
| 矩阵管理 | 版本上下架、索引分通道、依赖索引按版本维护 |

注意一个关键观察：这些成本的载体是"**多份独立维护的文本**"，
而不是"多个分发版本"本身。这直接引出第三条路。

## 五、第三条路：单源多渲染（推荐的稳态形态）

**管理面只有一个 skill 源**，正文里用显式条件块标注能力差异：

```markdown
## 发送消息
<cap tool_api="<8">
调用 send_msg(recipient, text)，收件人填联系人名称……
</cap>
<cap tool_api=">=8">
调用 message_compose(target, content, attachments?)，支持附件……
</cap>
```

云端构建流水线按每个**在役 level** 渲染出静态变体，
分发服务按设备 level 下发对应变体：

- **管理面 = 1**：单一事实源、一处修改，回灌漂移问题结构性消失；
- **运行面 = 每 level 一份干净单路径正文**：设备上下文里没有无关分支——
  更短、无串扰、静态确定（同一 level 的正文 token 序列恒定，
  KV cache 与回放纪律都保持）；
- **灰度与回滚可按 level 独立**：新 level 的变体单独放量，
  出问题单独回滚，爆炸半径被切开；
- 类比：Android 资源限定符（`res/layout-v21`）、`#ifdef` 编译多 target、
  一份源码编译多端。

成本：一条渲染流水线 + 每 level golden manifest 的 CI（后者在
[联动机制](./端侧版本感知与工具治理联动.md)里本来就要建，属于复用）。

**边界纪律**：条件块只准引用**编译期可判定的能力事实**
（`tool_api`、`required_tools`），不准引用运行时状态（前台应用、形态等）
——运行时分支仍留在正文里走环境变量通道，两类分支不许混。

## 六、与"运行时能力分支"的关系

单源多渲染并不取代正文里的运行时能力分支，二者处理不同粒度：

- **level 间的计划内差异**（成套工具变更）→ 编译期条件块，渲染掉；
- **level 内的计划外碎片**（个别应用先升级带来的工具，同一 level 的
  设备有的有、有的没有）→ 仍用正文运行时分支
  （"若工具列表中存在 X……"），因为同一渲染变体要服务清单不完全相同的设备。

## 七、结论

1. **可行，但有条件**：单 skill 成立当且仅当（a）工具治理保证到达机队的
   差异全部增量化，（b）分支预算 ≤ 2~3，（c）在役 level 跨度 ≤ 2~3。
   三个条件都可监控，破条件即报警。
2. **把"单 skill"定为稳态目标，不定为硬约束**：机制上保留多版本能力，
   作为真破坏性变更（治理例外）和 T2 实验工具引用的逃生通道——
   逃生通道的存在本身反过来保护了主路径的简单性。
3. **复杂度增长时切换到单源多渲染**：对作者永远是一个 skill，
   对设备是每 level 一份干净正文——同时消掉"多版本的回灌漂移"和
   "单版本的分支膨胀"两个痛点，是这个问题的稳态答案。
