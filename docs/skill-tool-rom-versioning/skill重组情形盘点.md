# Skill 重组的情形盘点与管理机制

> 问题：前文讨论的都是**单个 skill 的版本演进**（内容迭代、兼容声明、多版本门控）。
> 还有一类正交的变更：**多个 skill 之间的重组**——数量、边界、名称、层级的
> 结构性调整。本文盘点全部情形，并给出通用管理机制。
>
> 关键视角：重组改变的是 L0 里"模型可见的技能目录"（skill 索引），
> 而不只是某份正文的内容。索引是模型选 skill 的检索句柄，
> 所以重组的第一影响面永远是**模型的选择行为**。
>
> 前置：[配套管理方案](./skill与工具ROM配套管理方案.md)、
> [端侧版本感知与工具治理联动](./端侧版本感知与工具治理联动.md)、
> [云侧单 skill 可行性评估](./云侧单skill可行性评估.md)。

## 一、六种重组情形

### 情形 1：拆分（一拆多）

**触发**：单个 skill 覆盖场景过宽、正文过长（加载 token 贵、无关内容干扰）；
或其中一部分需要独立的迭代节奏 / 独立的兼容声明。

**动作**：`消息助手` → `发送消息` + `消息摘要` + `群管理`。

**管理要点**：

- **索引描述必须互斥**：拆出的各 skill 一句话描述之间边界要清晰，
  否则模型选择时摇摆（选错 / 多加载）。拆分上线前跑**选择评估**
  （给定 query 集，检查模型 load 的是否是预期 skill）；
- **兼容声明下沉细化**：原 skill 的 `min_tool_api` 是全部内容所需的 max，
  拆分后各子 skill 按自身实际依赖声明，通常可以**下降**——
  这是拆分的红利之一（老设备能用上其中不依赖新工具的部分）；
- **旧名处理**：旧 skill 名保留为 alias（见第二节），
  `load_skill("消息助手")` 返回指引："已拆分为 A/B/C，按需加载"。

### 情形 2：合并（多合一）

**触发**：多个相近 skill 内容重复、口径不一致（同一件事两份说明各改各的）；
或模型经常需要同时加载它们（说明边界切错了）。

**动作**：`闹钟设置` + `定时提醒` → `时间提醒`。

**管理要点**：

- **兼容声明取并集所需**：合并后 `min_tool_api = max(各源 skill)`，
  这可能把原本低门槛的内容抬高门槛——若不可接受，
  用正文能力分支保住低 level 覆盖，或干脆说明这次合并不该做；
- **正文体积核查**:合并是拆分的反操作，警惕合出"什么都讲"的巨型 skill
  （回到情形 1 的触发条件）；
- **旧名全部 alias 到新名**；索引里删两条、加一条，描述覆盖原有全部意图。

### 情形 3：抽公共片段（依赖化）

**触发**：多个 skill 含重复段落（通用的确认话术、通用的错误处理流程、
共同的前置检查），重复维护漂移。

**动作**：把公共段抽成共享片段，各 skill 引用。

**管理要点（这是六种情形里机制选择最关键的一个）**：

- **推荐编译期 include，不推荐运行时依赖**：共享片段在云端构建时渲染进
  各 skill 正文（与[单源多渲染](./云侧单skill可行性评估.md)同一条流水线），
  设备侧看到的仍是自包含的完整正文。
  - 若做成运行时 skill→skill 依赖（load A 自动触发 load B、或 A 正文里
    让模型再 load B），会引入：加载链路多一跳、公共片段单独进消息流
    重复占 token（多个 skill 引用时）、以及"半加载"中间态；
  - 编译期 include 下，公共片段改一处、全量重渲染受影响 skill，
    一致性由流水线保证——重复的是 token（各正文都含该段），
    但每份正文静态自包含，加载语义简单；
- **例外**：公共片段本身很大且常被单独使用（如"通讯录操作基础"），
  那它就该是一个独立 skill（模型显式按需加载），而不是 include 片段——
  判据：**模型是否需要单独用它**。

### 情形 4：改名 / 职责转移

**触发**：命名不准导致模型选择错误；或一块功能从 skill A 移到 skill B
（边界微调，不改变总数）。

**管理要点**：

- skill 名是模型的检索句柄，也可能沉淀在**压缩后的会话摘要、
  用户长期记忆、评估集**里——改名的影响半径比直觉大；
- **alias 必须有**（旧名可解析），且观测旧名加载率衰减后再摘除；
- 职责转移要成对发布（A 删该段与 B 加该段原子生效，见第二节 changeset），
  否则出现"两边都有"（冲突口径）或"两边都没有"（能力真空）的中间态。

### 情形 5：层级重组（引入 / 调整路由结构）

**触发**：skill 数量增长到索引本身变大、平铺目录让模型选择困难；
或某垂域内部出现"入口 + 子流程"的天然层次。

**动作**：引入路由 skill（`出行规划` 入口，正文引导按场景 load
`打车`/`导航`/`日程联动` 子 skill）；或反向拍平（层次证明多余时）。

**管理要点**：

- 层级 = 用**一次额外的加载往返**换**索引的收敛**，只有当索引规模
  确实造成选择困难时才值得（对照 02 渐进式加载的成本模型）；
- 子 skill 可以不进 L0 全量索引（只在路由 skill 正文里可见），
  这是控制索引体积的正规手段——但代价是子 skill 无法被直接检索，
  路由 skill 的引导质量成为单点；
- 层级深度纪律：**≤ 2 层**（入口 → 子 skill）。更深的链路每层都乘以
  一次往返和一次引导错误概率。

### 情形 6：工具驱动的重组（与工具重构耦合）

**触发**：工具层重构——多个细粒度工具合并成一个大工具（或反向拆分）、
垂域工具整体改版。工具边界变了，按工具边界组织的 skill 随之重划。

**管理要点**：

- 这是[联动机制](./端侧版本感知与工具治理联动.md)的复合情形：
  工具变更门禁（快通道先行）+ skill 重组 changeset **一起过**——
  受影响 skill 清单来自依赖索引，重组后的新结构必须在工具变更
  随 ROM 灰度**之前**备好上架（门控在新 tool API level 上）；
- 老 level 上保留老结构（老 skill 组 + 老工具），新 level 上启用新结构，
  两套结构按能力分发各自成立——**重组也可以是版本门控的**：
  结构本身随 tool API level 切换，而不必全机队同步切换。

## 二、横切机制：重组通用的五件套

六种情形共享同一批基础机制，逐一核对：

1. **原子 changeset**。重组天然涉及多个 skill 同时上 / 下线 / 修改，
   必须作为一个原子发布单元生效（索引的一次版本变更包含全部增删改）。
   任何中间态（A 已删、B 未上）都是能力真空或口径冲突。
   changeset 也是灰度和回滚的单元——回滚重组 = 整个 changeset 回滚。
2. **skill alias 表**。与工具的 deprecated alias 对称：旧名 → 新名（改名 /
   合并）或旧名 → 拆分指引（拆分）。`load_skill(旧名)` 永不硬失败。
   观测旧名加载率，衰减到阈值后摘除 alias。旧名的来源不只是模型习惯：
   压缩摘要、长期记忆、评估集、运营文案里都可能沉淀旧名。
3. **索引质量门禁**。重组 changeset 上线前跑两个自动检查：
   （a）**选择评估**——标准 query 集上模型 load 的 skill 与预期一致率不回退；
   （b）**描述互斥 / 覆盖检查**——拆分后描述不重叠，合并后描述不漏原意图。
4. **兼容声明代数**。拆分：各子 skill 按实际依赖重算（通常下降，红利）；
   合并：取 max（抬门槛需评估）；抽公共片段：片段自身的依赖并入引用方；
   层级化:路由 skill 的声明取子 skill 的 min（入口要尽量普适）。
   全部由依赖索引自动重算，不靠人工填写。
5. **会话与资产迁移**。运行中会话继续用钉住的老结构（重组只影响新会话）；
   评估集、日志分析口径、运营看板里的 skill 名跟着 changeset 同步迁移——
   否则重组后所有历史指标断线。

## 三、一张速查表

| 情形 | 索引变化 | 兼容声明 | 专属风险 | 关键动作 |
| --- | --- | --- | --- | --- |
| 1 拆分 | 删 1 加 N | 各自重算（降） | 描述不互斥 → 选择摇摆 | 选择评估；旧名 alias 指引 |
| 2 合并 | 删 N 加 1 | 取 max（升） | 门槛抬高伤老设备；巨型 skill | 覆盖检查；必要时正文分支保低 level |
| 3 抽公共片段 | 不变 | 片段依赖并入引用方 | 运行时依赖链 / 半加载态 | 编译期 include，不做运行时依赖 |
| 4 改名 / 转移 | 名称变 / 内容易主 | 随内容走 | 旧名沉淀面广；转移中间态 | alias + 衰减观测；成对原子发布 |
| 5 层级重组 | 索引收敛 | 路由取子集 min | 多一跳往返；路由成单点 | 深度 ≤2；子 skill 可不进全量索引 |
| 6 工具驱动 | 结构随 level 切换 | 门控在新 level | 与 ROM 灰度时序耦合 | 联动门禁 + changeset 一起过；两套结构按能力分发并存 |

## 四、与前文体系的衔接核对

- **L0 / KV cache**：任何重组都改 skill 索引 = L0 失效一次。
  changeset 本身就是攒批机制（一次重组一次失效，而不是 N 个 skill N 次）；
- **单源多渲染**：重组发生在**源层**（源文件的拆合），渲染流水线
  自动对每个在役 level 重新产出变体——重组与 level 门控正交组合
  （情形 6 就是两者的复合）；
- **依赖索引**：重组后 skill→tools 映射自动重扫描，tool→skills 反查表
  随 changeset 版本化——工具侧门禁查的永远是当前生效结构的清单。
