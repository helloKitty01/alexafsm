Skill 与工具的 ROM 配套管理

工具随 ROM 慢速 OTA（机队永久碎片化）· skill 云端天级迭代 —— 双速发布用 能力清单 + 兼容声明 + 按能力分发 配套管理

问题 · 双速发布

  • 工具 = ROM 内实现：月级 OTA，回滚极难，停更机型永远到不了新版本
  • skill = 提示词文档：天级云端下发，即时回滚，可全量收敛
  • 任何时刻机队都是工具集版本的一个分布，不是单一版本 —— 与 Android API level 处境同构

管理地基 · 三件套（任何策略的前提）

  • 工具侧：设备会话建立时上报能力清单（工具列表 + 工具集 API level，单调递增）
  • skill 侧：metadata 声明 min_tool_api / required_tools / max_tool_api
  • 分发侧：按设备能力解析，取满足要求的最新版本；skill 索引按工具 API level 分通道生成

核心原则 · 四条

  • 检测能力而非版本：L0 里就是设备真实工具列表，skill 分支零成本判断（≙ feature detection）
  • 分支是过渡态：老路径占比达标即删，回归单路径
  • 破坏性变更在 ROM 侧缓冲：deprecated alias 保 1~2 版，把破坏性降级为增量
  • "找不到工具→升级"只做安全网，不做主策略

+ 工具集 API level

安全网触发率按 ≈ 0 运营：> 0 即说明分发通道有 bug；"建议升级 ROM"只在替代路径也走不通时由产品层呈现，不写进 skill 文本

兼容性决策矩阵 · 按"工具变更类型"选策略

工具变更类型skill 策略怎么做在役版本
无变更 最新 skill 全量替换，旧版全部下线 灰度放量 + 即时回滚；索引攒批更新控制 L0 失效频率 1
增量：新增工具 / 加可选参数 单 skill + 能力分支（不开新版本） 正文写"若工具列表中存在 X 则用之，否则老工具组合（步骤…）"；模型看 L0 即可判断，零额外 loop；渗透率达标后删分支 1（含分支 ≤2 个）
破坏性：改名 / 参数语义变化 / 删除 版本门控：新旧 skill 并存，按能力分发 老 skill 用 max_tool_api 封顶冻结（只修安全问题）；ROM 侧优先做 deprecated alias，能不走到这里就不走 2（限期共存）
任何情况的兜底 pre-call 存在性校验（安全网） 拦截 → tool_not_available + 替代工具清单回喂模型自纠；防通道 bug / 索引陈旧等 corner case — 触发率 ≈ 0

反面教材：全量替换最新 skill + 老 ROM 上报"找不到工具"引导升级 —— 老 ROM 用户体验是"坏"而不是"旧"；且 L0 工具列表里根本没有新工具，"skill 让调 X 但列表没有 X"的矛盾上下文会诱发幻觉调用，错误以更隐蔽的方式劣化。

多版本运营纪律（版本门控的配套）

在役版本硬上限 ≤ 2~3· 修复默认打最新版，按老版本设备占比决定是否回灌· 评估只跑在役 (skill × API level) 组合，非笛卡尔积· 老路径占比 < 阈值 → 删能力分支· ROM EOL → 对应 skill 冻结归档

观测三指标

tool_not_available 拦截率（目标 ≈ 0）· 能力分支老路径使用占比（定删分支时机）· 各工具 API level 设备占比（定冻结 / EOL 时机）
