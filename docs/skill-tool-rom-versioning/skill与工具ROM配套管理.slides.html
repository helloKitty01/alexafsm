Skill 与工具的 ROM 配套管理双速发布下的版本感知、兼容策略、治理与联动 · 详解

skill 和工具是同一能力的两半：工具是 ROM 内的执行体，skill 是云端的使用说明书。发布节奏天然不同步 —— 问题不是"要不要对齐"，而是如何面对一个多版本长尾共存的工具集分布。

问题本质 · 双速发布

工具（ROM）skill（云端）
载体系统服务 / framework / 系统应用提示词文档
通道整机 OTA / 应用市场云端配置下发
节奏月级~季级，灰度数周天级甚至小时级
回滚极难即时
机队永久碎片化（停更机型到不了新版）可全量收敛

与 Android 的处境完全同构：OS API（工具）按 API level 演进，App（skill）用 minSdkVersion 声明兼容下界 —— 业界已把这套题做透。

本套片子回答的五个问题

  • P2 感知什么：小艺 / skill 需要感知哪些端侧版本信息？怎么避免"太多、太碎"？
  • P3 怎么配套：工具不变 / 增量变更 / 破坏性变更，skill 分别怎么发？
  • P4 工具怎么管：哪些必须保证兼容，哪些允许破坏性变更？
  • P5 怎么联动：工具管理和 skill 管理之间的接口是什么？
  • P6-P7 形态问题：云侧能否只保持一个 skill？多 skill 重组有哪些情形？

总纲一句话

感知能力而不感知版本（能力清单 + tool API level 两层收敛）；增量变更走能力分支、破坏性变更才开版本门控；工具按 T0/T1/T2 分层承诺稳定性；两个体系用依赖索引 + 双门禁 + "快通道先行"时序联动；"找不到工具→引导升级 ROM"永远只做安全网，不做主策略。

感知能力，不感知版本端侧版本信息的收敛 —— 回答"太多、太碎"

判据一句话：一个端侧信息值得被 skill 体系感知，当且仅当它改变"模型能调什么工具、怎么调"。其余的进环境变量通道，或根本不进上下文。

明确"不感知什么"（防碎清单）

端侧信息去处
ROM / 组件 / APK 版本号不进体系，注册中心内部输入
机型、芯片若改变工具行为，必须表现为 schema / 清单差异
形态（折叠 / 平板 / 车机）L1 会话级环境变量，不是版本问题
电量 / 网络 / 前台应用运行时环境变量通道
工具列表 + schema 版本能力清单（唯一入口）

为什么不能直接感知组件版本号

工具实现方分散在多个独立发布的载体上，直接感知则版本空间 = 各组件版本的笛卡尔积，必然失控。两层收敛后：碎片化没有被消除，而是被封装 —— N 个组件版本在端侧折叠成一份清单，机队的任意清单在云端折叠成个位数的 level。

2 / 8

兼容性决策矩阵按"工具变更类型"选 skill 配套策略

能力分支为什么零成本：L0 工具区就是设备真实工具列表，模型天然看得见自己有什么工具 —— 分支判断不占额外 loop（≙ Android SDK_INT 检查 / 前端 feature detection：检测能力而非版本）。

工具变更类型skill 策略怎么做在役版本
无变更 最新 skill 全量替换，旧版全部下线 灰度放量 + 即时回滚；会话内钉住版本；索引攒批更新控制 L0 缓存失效频率 1
增量：新增工具 / 加可选参数 单 skill + 能力分支（不开新版本） 正文写"若工具列表中存在 X 则用之，否则老工具组合（步骤…）"；老设备有计划内的降级路径；渗透率达标后删分支回归单路径 1（分支 ≤2 个）
破坏性：改名 / 参数语义变化 / 删除 版本门控：新旧 skill 并存，按能力分发 老 skill 用 max_tool_api 封顶冻结（只修安全问题）；ROM 侧优先做 deprecated alias，能不走到这里就不走 2（限期共存）
任何情况的兜底 pre-call 存在性校验（安全网） 拦截 → tool_not_available + 替代工具清单回喂模型自纠；防分发通道 bug / 索引陈旧等 corner case — 触发率 ≈ 0

反面教材 · "全量替换 + 报错引导升级 ROM"为何不成立

  • 老 ROM 用户体验是"坏"而不是"旧"：skill 无老路径指引，模型只能即兴发挥或放弃；停更机型被永久锁死在坏路径
  • 更糟的是不一致：L0 列表里根本没有新工具，"skill 让调 X 但列表没有 X"的矛盾上下文诱发幻觉调用，错误以更隐蔽的方式劣化
  • 同一 skill 跨 ROM 走出计划外行为，回归测试口径无法定义

3 / 8

工具治理 · 分层稳定性承诺哪些必须保证兼容，哪些允许破坏性变更

方向澄清：必须保证的是"老 skill × 新工具"不坏（工具向后兼容）；"新 skill × 老工具"由 skill 门控 / 能力分支解决 —— 老 ROM 物理上改不了，不要求工具"前向兼容"。

三层稳定性承诺（按依赖面划分）

层范围破坏性变更
T0 核心冻结 基础设备操作（打开应用、点击、返回、查状态）、框架工具（load_skill） 永不允许。几乎全部 skill 依赖，破坏一个 = 全量受影响；只准加可选参数 / 返回加字段
T1 领域稳定 各垂域工具（消息、日历、相机、音乐…） 例外允许，走治理流程：评审 + alias 缓冲 ≥1 个 ROM 大版本 + 自动通知受影响 skill owner
T2 实验 新能力孵化、beta 工具，schema 显式标 experimental 自由变更甚至删除；约束在 skill 侧：只有版本门控 skill 才能引用，禁止进全量单版本 skill 正文

T2 → T1 晋级是显式动作：去 experimental 标记、纳入兼容承诺、进 level 快照。

变更分型硬定义（供 CI 自动判定）

兼容 · 直接发 ✅破坏 · 走流程 ❌
新增工具删工具、改工具名
加可选参数（带默认值）参数改名 / 变必填 / 类型或取值语义变化
返回结构加字段返回字段删除 / 改名 / 类型变化
错误文案改进、性能优化schema 不变但行为语义变化（最隐蔽，须人工申报）

LLM 消费方的特殊性

schema 兼容 ≠ 行为兼容：返回结构大改（哪怕纯新增）也可能让模型注意力和后续决策漂移。T1 及以上变更必须跑受影响 skill 的回归评估，行为指标不回退才准出；返回保持确定性序列化（兼 KV cache 纪律）。

把破坏性变更的成本压下来的工具箱

deprecated alias · 老工具名保留 1~2 个大版本转发新实现，把"破坏性"降级为"增量" 框架层 shim · schema 带版本号，pre-call 做老格式→新格式参数适配（适合参数改名类） schema diff lint · 注册中心 CI 自动分类变更；破坏性提交必须携带治理审批 + 受影响 skill 清单
4 / 8

工具管理 ↔ skill 管理的联动一张索引 + 两道门禁 + 一条时序原则

核心时序约束（快通道先行）：慢通道（ROM）的破坏性变更，必须等快通道（skill）先适配完成 —— skill 是云端天级下发的，让它先行没有任何成本。

破坏性变更的标准发布时序

① CI 判定破坏性schema diff 自动分类（对照硬定义表）
→
② 查依赖索引tool→skills 反查，列出受影响 skill 清单
→
③ skill 新版先上架min_tool_api = N+1，老设备解析不到，不会误分发
→
④ 门禁放行受影响 skill 全部备好 → 工具变更随 ROM N+1 灰度
→
⑤ 自动漂移设备升级 → 上报新清单 → 分发自动解析到新 skill，无需切换动作
→
⑥ 老设备无感知继续拿 max_tool_api = N 封顶的老 skill

数据基础 · 双向依赖索引

  • skill → tools：metadata 的 required_tools + 上架 CI 对正文自动扫描提取工具引用
  • tools → skills：反查即得。破坏性变更影响哪些 skill、通知精确到哪个 owner，全靠这张表 —— 没有它一切联动是空谈

反方向 · skill 发布门禁

  • 静态校验：正文引用的每个工具必须存在于声明 level 的工具集快照（golden manifest）且用法匹配 schema —— 源头杜绝"让调 X 但列表没有 X"
  • 快照回归：能力分支每条路径在对应 level 快照上跑（新路径跑 N+1、降级路径跑 N）

运行时回流 · 三个指标把闭环延伸到线上

指标驱动的动作
tool_not_available 拦截率目标 ≈ 0；>0 报警定位分发通道 bug
能力分支老路径使用占比低于阈值 → 删分支，正文回归单路径
各 API level 设备占比驱动老 skill 冻结 / EOL 归档节奏

运营纪律：在役版本硬上限 ≤2~3；修复默认打最新版、按老版本占比决定回灌；评估只跑在役 (skill × level) 组合，非笛卡尔积；ROM EOL → 对应 skill 冻结归档。

5 / 8

云侧单 skill 可行性评估单版本 vs 多版本 vs 单源多渲染

结论：有条件可行。单 skill 的可行性不是 skill 自己的性质，是工具治理买来的 —— 差异全部增量化则成立，出现真破坏性差异必被击穿（一份文本无法描述两套互斥协议）。

成立三条件（都可运营监控，破条件即报警）

  • 差异全部增量化：T0 冻结 + T1 alias/shim 兜住，破坏性变更不触达机队
  • 分支预算 ≤ 2~3：且各分支步骤差异温和，不互相干扰
  • 在役 level 跨度 ≤ 2~3：靠 ROM 升级推进 + 老 level EOL 持续收尾

两种形态的真实成本对照

单 skill（即使可行）多版本
正文长期携带全部降级路径，全机队为 token 买单；分支间指令串扰回灌漂移：同一修复打多个版本，久之各改各的、事实源分裂（最疼）
爆炸半径：一次编辑作用于所有 level，坏改动伤全机队矩阵管理：上下架、索引分通道、依赖索引按版本维护
测试没有省：仍要每个在役 level 快照回归全部分支路径关键观察：多版本的成本载体是"多份独立维护的文本"，不是"多个分发版本"本身 → 引出第三条路
回滚粒度粗：无法只回滚新 level 上的行为

第三条路 · 单源多渲染（稳态形态）

## 发送消息（一个 skill 源，编译期条件块） <cap tool_api="<8"> 调用 send_msg(recipient, text)，收件人填联系人名称… </cap> <cap tool_api=">=8"> 调用 message_compose(target, content, attachments?)，支持附件… </cap>
  • 管理面 = 1：单一事实源、一处修改，回灌漂移结构性消失
  • 运行面 = 每 level 一份干净单路径正文：无无关分支、更短、token 序列静态确定（KV cache / 回放纪律保持）
  • 灰度回滚按 level 独立：爆炸半径被切开
  • 类比：Android res/layout-v21、一份源码 #ifdef 编译多 target

边界纪律：条件块只准引用编译期能力事实（tool_api / required_tools）；运行时状态（前台应用、形态）仍走环境变量通道的正文分支，两类不许混。level 内计划外碎片仍用运行时能力分支。

建议

把"单 skill"定为稳态目标，不定为硬约束：机制上保留多版本作为真破坏性变更与 T2 实验工具的逃生通道（逃生通道的存在反过来保护主路径的简单性）；分支数逼近预算或在役 level 拉长时，切换到单源多渲染 —— 它是"只保持一个 skill"与"每台设备拿到干净正文"同时成立的形态。

多 skill 重组的六种情形与"单个 skill 版本演进"正交的结构性变更

关键视角：重组改变的是 L0 里"模型可见的技能目录"（skill 索引），第一影响面永远是模型的选择行为 —— 不只是某份正文的内容。

情形触发兼容声明专属风险关键动作
1 拆分一拆多 覆盖过宽、正文过长、需独立迭代节奏 各子 skill 重算（通常下降，老设备红利） 描述不互斥 → 模型选择摇摆 上线前跑选择评估；旧名 alias 返回拆分指引

3 抽公共片段 多 skill 重复段落，维护漂移 片段依赖并入引用方 运行时依赖链 / 半加载中间态 编译期 include（复用渲染流水线），不做运行时 skill→skill 依赖；片段需被单独使用时应做成独立 skill
4 改名 / 职责转移 命名不准致选错；边界微调 随内容走 旧名沉淀面广（摘要 / 记忆 / 评估集）；转移中间态"两边都有 / 都没有" alias + 加载率衰减后摘除；成对原子发布
5 层级重组路由 + 子 skill 索引变大、平铺目录选择困难 路由取子集 min（入口普适） 多一跳往返；路由质量成单点 深度 ≤2；子 skill 可不进 L0 全量索引以收敛体积
6 工具驱动随工具重构 工具合并 / 拆分 / 垂域改版，skill 边界随之重划 门控在新 level 与 ROM 灰度时序耦合 联动门禁 + changeset 一起过；老 level 老结构、新 level 新结构按能力分发并存，不必全机队同步切换

横切五件套（六种情形共享）

原子 changeset · 多 skill 增删改一次索引版本生效，无中间态；也是灰度与回滚单元 skill alias 表 · 与工具 alias 对称，load_skill(旧名) 永不硬失败 索引质量门禁 · 选择评估 + 描述互斥/覆盖自动检查 兼容声明代数 · 拆分重算 / 合并取 max / 路由取 min，依赖索引自动重算 会话与资产迁移 · 运行中会话用钉住的老结构；评估集、日志口径随 changeset 同步，防历史指标断线

总结 · 原则清单与落地优先级整套体系的最小闭环

版本感知收敛到一个整数；工具按三层承诺稳定性；skill 用一个源覆盖机队；两个体系之间只有索引 + 门禁 + 指标三种接口。

原则清单（十条）

  • ① 感知能力不感知版本：组件版本折叠为能力清单，清单离散为 tool API level
  • ② skill 感知面 = 1 个整数：min_tool_api 必填，required_tools 仅碎片工具时用
  • ③ 检测能力而非版本：分支判断引用 L0 真实工具列表，零额外 loop
  • ④ 增量走分支、破坏才门控：分支是过渡态，渗透后删除
  • ⑤ 老 skill × 新工具必须不坏：T0 永不破坏，T1 走流程，T2 只许门控 skill 引用
  • ⑥ schema 兼容 ≠ 行为兼容：T1+ 变更须跑 skill 回归评估
  • ⑦ 快通道先行：ROM 破坏性变更前，skill 新版先上架，升级后自动漂移
  • ⑧ 安全网触发率 ≈ 0："找不到工具→引导升级"永远不做主策略
  • ⑨ 单 skill 是稳态目标非硬约束：复杂度上升切单源多渲染
  • ⑩ 重组走原子 changeset：alias 兜旧名、选择评估把关、资产同步迁移

落地优先级 · 重资产只有两个

优先级建设项说明
P0 端侧工具注册中心 + 能力清单上报 决定"感知面收敛"是否物理成立，一切的地基
P1 依赖索引 + 双门禁 CI tool→skills 反查表、schema diff lint、golden manifest 快照回归
P2 API level 定义、兼容声明、按能力解析分发 建在 P0/P1 之上的轻量规则，无重开发
P3 单源多渲染流水线、changeset / alias 机制 复杂度增长后启用；golden manifest 与 P1 复用
持续 运行时三指标看板 tool_not_available ≈0 / 老路径占比 / level 设备占比
