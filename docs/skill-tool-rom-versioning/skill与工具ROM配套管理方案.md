# Skill 与工具的 ROM 配套管理方案

> 深化篇：[端侧版本感知与工具治理联动](./端侧版本感知与工具治理联动.md)
> （感知哪些端侧版本信息、工具分层稳定性承诺、tool 与 skill 管理的联动机制）；
> [云侧单 skill 可行性评估](./云侧单skill可行性评估.md)
> （单版本 vs 多版本 vs 单源多渲染）；
> [skill 重组情形盘点](./skill重组情形盘点.md)
> （拆分 / 合并 / 抽公共片段 / 改名转移 / 层级重组 / 工具驱动重组）。

> 问题：手机 OS 上，工具（tool）的实现在 ROM 里，随 OTA 慢速升级且机队长期碎片化；
> skill 是提示词层的文档，走云端快速迭代。两者如何配套管理？
>
> 讨论起点（用户提出的三个候选）：
> 1. 工具不变 → 用最新 skill 把所有旧 skill 替换掉；
> 2. 工具有变 → 方案 A：仍然全量替换为最新 skill，老 ROM 上调用时报"找不到工具"，引导升级 ROM；
> 3. 工具有变 → 方案 B：新增一个 skill 版本，只在工具已更新的 ROM 上使用。
>
> 前置架构：[kv-cache-discussion/02](../../kv-cache-discussion/02-上下文分层与排布.md)
> 的分层排布（L0 含工具全集 schema 与 skill 索引，skill 经 `load_skill` 以 tool result
> 进入消息流）；[变量解析机制](../variable-resolution/工具参数变量解析机制方案.md)
> 的 pre-call 拦截器。

## 一、问题的本质：双速发布下的契约管理

skill 和工具是**同一个能力的两半**：工具是执行体（ROM 内实现），skill 是使用说明书
（教模型怎么组合调用）。它们的发布节奏天然不同步：

| | 工具（ROM） | skill（云端） |
| --- | --- | --- |
| 载体 | 系统服务 / framework | 提示词文档 |
| 发布通道 | OTA / ROM 升级 | 云端配置下发 |
| 节奏 | 月级，灰度数周 | 天级甚至小时级 |
| 回滚 | 极难 | 即时 |
| 机队状态 | **永久碎片化**（部分设备停更 / 用户不升级） | 可全量收敛 |

关键事实：**任何时刻，机队都是"工具集版本"的一个分布**，而不是单一版本。
所以问题不是"skill 要不要跟工具版本对齐"，而是"skill 分发系统如何面对一个
多版本共存、且尾部长期存在的工具集分布"。

这和 Android 的处境完全同构：OS API（工具）按 API level 演进，App（skill）
用 `minSdkVersion` 声明兼容下界、用运行时 `SDK_INT` 检查做条件降级。
业界已经把这套题做透了，我们可以直接借鉴结论。

## 二、先建立地基：契约版本化（任何方案的前提）

无论选哪条路，先把三件事做掉，否则所有方案都退化成"靠猜"：

1. **工具集能力清单（capability manifest）**。设备在会话建立时上报：
   工具清单 + 每个工具的 schema 版本 + 一个单调递增的**工具集 API level**。
   云端 harness 用它拼装 L0 的工具区——这一点现架构已经成立
   （L0 工具 schema 本来就来自设备），只需把"版本号"显式化。
2. **skill 兼容性声明**。每个 skill 的 metadata 增加：
   `min_tool_api`（兼容下界）、`required_tools: [...]`（硬依赖的工具名），
   可选 `max_tool_api`（明确不兼容的上界，用于破坏性变更后冻结老 skill）。
3. **分发时按能力解析**。skill 分发服务对每台设备执行：
   *在该设备能力清单满足要求的 skill 版本中，取最新的一个*。
   L0 的 skill 索引也随之按设备通道生成（同一 ROM 版本的设备共享同一份索引，
   索引本身带版本号，不破坏"产品级静态"的性质——只是"产品级"细化为
   "产品 × 工具 API level 级"）。

有了这个地基，用户提的三个候选就都变成同一套机制下的**策略参数**，
而不是三套互斥的系统。

## 三、逐案分析

### 案例 0：工具不变，skill 内容优化 → 全量替换，一票通过

结论与直觉一致：**只保留最新 skill，旧版全部下线**。skill 是纯提示词，
不存在二进制兼容问题，机队可以瞬间收敛到单一版本。三个纪律性补充：

- **会话内钉住版本**：skill 版本在会话开始（或首次 load）时解析并冻结，
  会话中途不换版本。否则同一上下文里出现两份不同的 skill 正文，
  既混淆模型又破坏"同一 skill 每次加载 token 序列一致"的回放性。
- **灰度与回滚**：skill 改的是模型行为，回归风险真实存在，
  全量替换应经过灰度（按设备比例放量）→ 这意味着基础设施本来就要支持
  "多版本并存 + 按设备路由"。**"只有一个 skill"是稳态目标，不是系统约束**——
  这个认识很重要，因为它说明方案 B 需要的基础设施和灰度发布是同一套，
  不是额外负担。
- **索引更新的缓存代价**：skill 索引在 L0，更新会使 L0 前缀失效一次。
  攒批更新（如每日一次合并发布）而不是逐条推送。

### 案例 1-A：工具有变，仍全量替换 skill，运行时报"找不到工具"→ 引导升级 ROM

先说结论：**作为主策略不成立，但其中的运行时兜底机制值得单独保留**。

逐条看问题：

1. **老 ROM 用户的体验是"坏"而不是"旧"**。最新 skill 只描述新工具的用法，
   老设备上模型照着说明书调用 → 浪费一个 loop → 拿到"找不到工具"→
   skill 里没有老路径的任何指引 → 模型要么即兴发挥（不可靠），
   要么放弃并告诉用户"请升级系统"。对手机助手来说，
   "不升级 ROM 助手就坏掉"是产品事故级的体验：ROM 升级触达周期以月计，
   停更机型**永远**到不了新版本，这部分用户被永久锁死在坏路径上。
2. **比"报错"更糟的是不一致**。L0 工具区来自设备真实上报，老设备的工具列表里
   **根本没有**新工具——于是出现"skill 正文让调用 X，工具列表里没有 X"的
   自相矛盾上下文。模型可能幻觉出工具调用，也可能被搞糊涂后连老工具都不敢用。
   错误甚至到不了"找不到工具"这一步，而是以更隐蔽的方式劣化。
3. **行为不可评估**。同一 skill 在不同 ROM 上走出计划外的不同行为，
   回归测试的口径没法定义。
4. "提醒升级 ROM"作为**增长手段**也不划算：用助手功能的损坏来倒逼系统升级，
   伤害的是助手自己的留存。

**但它包含一个正确的组件**：运行时的工具存在性校验。应该做成 harness 的
pre-call 拦截（与变量解析拦截器同层）：模型调用了当前设备不存在的工具时，
不透传给系统，而是返回结构化错误——

```json
{"error": "tool_not_available",
 "tool": "smart_clipboard_v2",
 "available_alternatives": ["clipboard_read", "clipboard_write"],
 "hint": "该能力需要系统版本 >= X；当前会话请使用替代工具完成任务"}
```

它的定位是**最后一道安全网**（防 skill 通道解析出 bug、索引缓存陈旧等
corner case），指标上应要求其触发率 ≈ 0；"建议用户升级 ROM"只在任务确实
无法用替代路径完成时，由产品层（而非 skill 文本）呈现。

### 案例 1-B：工具有变，新增 skill 版本，按 ROM 门控分发

结论：**破坏性变更下这是唯一正确的做法；但不该是所有工具变更的默认做法**，
因为它有真实的维护成本：

- 优点：每台设备拿到的 skill 与其工具集严格匹配，不存在坏路径；
  每个 skill 正文保持单路径、无分支，简单可测。
- 成本：**版本矩阵**。skill 的每个 bug 修复要回灌到所有在役版本分支
  （老 ROM 上的老 skill 也会有 bug）；测试矩阵 = skill 版本 × ROM 版本；
  索引、分发、日志、评估全部要带上版本维度。在役版本数不控制的话，
  矩阵会指数腐烂。

所以它需要配套的**版本收敛纪律**（见第五节）。

### 案例 1-C（用户候选之外，增量变更的更优解）：单 skill + 能力分支

工具变更里占多数的是**增量式**变更：新增一个工具、或给既有工具加可选参数。
这类变更下有比 A、B 都好的第三条路——**仍然只维护一个最新 skill，
但正文里写显式的能力分支**：

> 若工具列表中存在 `smart_clipboard_v2`，直接调用它完成 X；
> 否则用 `clipboard_read` + `clipboard_write` 组合完成（步骤：…）。

为什么成立：L0 工具区是设备真实工具集，**模型天然看得见自己有什么工具**，
分支判断零成本、零额外 loop（对比 [skill 环境变量方案](../skill-env-variables/skill环境变量传入方案.md)
里"模型要读的值必须进上下文"的原则——工具列表本来就在上下文里）。
这正是 Android `if (SDK_INT >= X)` 运行时检查、前端 feature detection
（检测能力而非检测版本号）的同一思想：**检测能力，而不是检测版本**。

- 优点：单版本维护（案例 0 的全部好处保留）；新老设备都有**计划内**的
  正确路径；老路径是显式写出的降级方案而非即兴发挥。
- 代价与边界：分支使 skill 正文变长、增加模型走错分支的风险。
  经验阈值：**一个 skill 内能力分支 ≤ 2 个**；超过（或分支间步骤差异巨大、
  互相干扰）就说明该拆版本了，转入 1-B。
- 生命周期：当老工具路径的实际使用占比降到阈值以下（ROM 渗透率足够高），
  删掉降级分支，skill 回归干净单路径。分支是**过渡态**，不是永久态。

## 四、决策矩阵

先给"工具变更"分型，再对号入座：

| 工具变更类型 | 例子 | 推荐方案 | 在役 skill 版本数 |
| --- | --- | --- | --- |
| 无变更 | 纯话术 / 流程优化 | 最新 skill 全量替换（案例 0） | 1 |
| 增量：新增工具 | 新增 `smart_clipboard_v2` | **单 skill + 能力分支**（1-C），渗透后删分支 | 1（含分支） |
| 增量：既有工具加可选参数 | `open_app` 增加 `page` 参数 | 同上；老 ROM 忽略/不写该参数即可，分支更轻 | 1（含分支） |
| 破坏性：改名 / 参数语义变化 / 删除 | `send_msg` 参数结构重构 | **版本门控**（1-B）：老 skill 冻结（`max_tool_api` 封顶），新 skill 门控分发 | 2（限期共存） |
| 行为变更（schema 不变，结果格式变） | 返回结构从文本改 JSON | 视影响面：小 → 1-C 分支描述两种返回；大 → 1-B | 1~2 |
| 任何情况的兜底 | 通道解析 bug、索引陈旧 | pre-call 工具存在性校验 + 结构化错误 + 产品层升级引导 | —（安全网，触发率 ≈ 0） |

配套的 ROM 侧要求：**破坏性变更尽量在 ROM 内做废弃缓冲**——老工具名保留 1~2 个
版本作为 deprecated alias（转发到新实现），把"破坏性"降级成"增量"，
让 skill 侧能走 1-C 而不是 1-B。工具契约的稳定性是用 ROM 侧纪律买来的，
这比在 skill 侧堆版本便宜得多。

## 五、多版本共存的运营纪律（1-B 的配套）

1. **在役版本数硬上限**：同一 skill 同时在役 ≤ 2~3 个版本。靠两头挤压：
   ROM 侧推升级收敛老版本占比；skill 侧到期冻结（只修安全类问题，不做功能）。
2. **版本分支管理像管 release branch**：修复默认打在最新版，
   按影响面评估是否回灌老版本；回灌要有明确的准出（老版本设备占比 < x% 则不回灌）。
3. **会话级钉住**：(skill 版本, 工具 API level) 在会话开始时解析并冻结，
   全程写入日志——没有这两个字段，"分支走错 / 调用失败"类问题无法复盘。
4. **评估口径带版本维度**：回归集按 (skill 版本 × 工具 API level) 的
   **在役组合**跑，而不是笛卡尔积全跑——第 2 条的版本上限同时控制了测试矩阵。
5. **观测指标**：
   - `tool_not_available` 拦截率（目标 ≈ 0，>0 即分发通道有 bug）；
   - 能力分支中老路径的使用占比（决定何时删分支）；
   - 各工具 API level 的设备占比（决定何时冻结老 skill / EOL）。
6. **EOL**：ROM 版本停更时，其钉住的 skill 版本同步冻结归档；
   功能演进只发生在最新版本线上。

## 六、KV cache 影响核对

对照 [02](../../kv-cache-discussion/02-上下文分层与排布.md) 的排布原则：

- L0 工具区本来就按设备工具集生成，不同 ROM 的前缀本来就不同——
  版本门控**没有引入新的缓存碎片**，只是让 skill 索引与工具区在同一维度
  （工具 API level）上对齐，同 cohort 设备继续共享前缀；
- skill 索引按通道生成、带版本号、攒批更新：L0 失效频率可控；
- 会话内版本钉住保证同一 skill 正文 token 序列一致，回放 / 缓存两不误；
- 能力分支（1-C）是 skill 静态正文的一部分，不引入任何动态渲染——
  与 [skill 环境变量方案](../skill-env-variables/skill环境变量传入方案.md)
  "正文保持静态"的纪律一致。

## 七、业界对照

| 业界机制 | 对应本方案 |
| --- | --- |
| Android API level + `minSdkVersion` | 工具集 API level + skill `min_tool_api` |
| Android 运行时 `SDK_INT` 检查 / 前端 feature detection | 1-C 能力分支（skill 正文引用工具列表判断） |
| `@Deprecated` API 保留数个版本再移除 | ROM 侧 deprecated alias 缓冲，破坏性降级为增量 |
| App Store 按系统版本分发不同 app 版本 | skill 分发服务按能力清单解析版本 |
| MCP 的运行时工具发现（tools/list） | 设备会话建立时上报能力清单，L0 按实际工具集拼装 |

## 八、结论（一段话版）

以"工具集 API level + skill 兼容性声明 + 按设备能力解析分发"为地基；
工具不变时全量收敛到单一最新 skill（配灰度与会话钉住）；增量式工具变更
优先走"单 skill + 能力分支"，靠上下文里的真实工具列表做零成本运行时检测，
渗透率达标后删分支收敛；只有破坏性变更才开新 skill 版本做门控分发，
且用 ROM 侧 deprecated alias 尽量避免走到这一步；"找不到工具 → 引导升级"
不作为主策略，降级为 pre-call 拦截的最后一道安全网，触发率按 0 运营。
