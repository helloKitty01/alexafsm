# 工具集对象与两条管理路线（构建 vs 推导）

> 本质认知：**skill 与"工具集"强绑定，其余都是代理变量。**
> 一份 skill 正文是写给一个确定的工具契约集合的；ROM 版本、API level、
> 机型、组件版本——都只是用来**定位工具集**的代理（proxy），本身不是
> 兼容性的对象。
>
> 现实约束：当前体系里"工具集"还**不是一个第一类对象**——没有一个地方
> 能权威回答"这台设备此刻的工具集是什么"。于是只有两条路：
> **要么构建这个对象（路线 A），要么基于现有信息推导它（路线 B）。**
> 本文定义对象本身、两条路线、演进关系与防错机制。
>
> 前置：[配套管理方案](./skill与工具ROM配套管理方案.md)、
> [端侧版本感知与工具治理联动](./端侧版本感知与工具治理联动.md)。

---

## 一、为什么"工具集"必须成为第一类对象

没有这个对象时，管理只能围绕代理变量打转，每条规则都要同时谈
ROM 版本、机型、API level、组件版本——规则复杂、彼此纠缠、且都在
间接描述同一个东西。把对象立起来之后：

- skill 的兼容声明**只对工具集**（`min_tool_api` + `required_tools`），
  不对任何代理变量；
- 分发、门禁、评估、日志全部以工具集为口径；
- ROM / 机型 / 组件版本降级为"**生产**工具集对象时的输入"，
  被封装在生产侧，消费侧永远不可见。

一句话：**上层管理机制必须面向工具集对象设计，与"对象怎么来的"解耦**——
这样两条路线可以共存、切换，而不推翻上层。

## 二、工具集对象的定义（两条路线共享的抽象）

```yaml
toolset:
  toolset_id: "ts-8-phone-a3f9"       # 唯一标识（含 manifest hash）
  tool_api_level: 8                    # 云端离散化编号，skill 声明的句柄
  tools:
    - {name: open_app,     schema_ver: 2, tier: T0}
    - {name: send_msg,     schema_ver: 3, tier: T1}
    - {name: smart_clip_v2, schema_ver: 1, tier: T2}
  produced_by: device_report | registry_derived   # 路线 A / 路线 B
  source_inputs:                       # 路线 B 时记录推导依据（审计用）
    rom: "X.Y.Z"
    model_series: "P-series"
```

消费方（L0 拼装、skill 解析、门禁、pre-call 校验）**不感知
`produced_by`**：同一接口，两种实现。

## 三、路线 A：构建——端侧注册中心实报（目标态）

各 provider（系统服务、系统应用、三方）把工具注册到端侧统一注册中心，
会话建立时实报能力清单。详见[联动篇](./端侧版本感知与工具治理联动.md)第一节。

- 优点：**实然**——报告的就是设备真实状态，天然覆盖机型差异、
  区域差异、组件独立升级、用户禁用等一切漂移源；
- 代价：注册中心是端侧框架能力，要随 ROM / 框架版本下场，
  落地周期以 ROM 节奏计；**存量老设备永远等不到它**。

## 四、路线 B：推导——用现有信息拼出工具集（立即可用）

端侧现在就能上报的信息：**ROM 版本 + 机型**（+ 小艺框架版本）。
云端建一张**工具集登记表（Toolset Registry）**：

```text
(ROM 版本段 × 机型系列) → toolset_id → 工具集快照
```

会话建立 → 端侧上报 ROM 版本 + 机型 → 云端查表 → 得到**推导的**
工具集对象 → 上层一切照旧（L0 拼装、skill 解析、门禁、评估）。

### 4.1 登记表由谁维护：登记即门禁

登记表不能靠自觉，必须做成工具发布流程的强制环节：

> **工具的任何上线 / 变更，必须同步更新登记表条目，否则发布门禁不放行。**

这样"人工维护易漏"被转化为流程强制——登记表的准确性
与工具发布的准确性同源。TMG 评审管控（2D API 规则）正好在同一个
流程节点上，登记是评审产物的一部分，不新增负担。

### 4.2 路线 B 的固有风险：应然 ≠ 实然

登记表描述的是"这个 ROM × 机型**应该**有什么工具"，
设备实际状态可能偏离：系统应用没升到位、区域裁剪、用户禁用组件。
三个补偿机制：

1. **pre-call 安全网升格**：在路线 B 阶段，它不只是兜底，
   而是**主动纠偏信号**——`tool_not_available` 触发即说明表与实况漂移，
   按（ROM × 机型 × 工具）维度聚合上报，直接驱动修表；
2. **采样审计**：抽样设备实测工具可用性，与登记表比对，
   漂移率进看板；
3. **混合模式**：漂移高发的载体（独立升级的系统应用）优先切设备实报，
   其余仍查表——对象 schema 相同，单设备内可混合拼装。

## 五、A / B 对比与演进：不是替代关系，是长期并存

| 维度 | 路线 B（登记推导） | 路线 A（设备实报） |
| --- | --- | --- |
| 准确性 | 应然（有漂移风险，靠三补偿） | 实然 |
| 建设成本 | 云端一张表 + 发布流程改造 | 端侧注册中心（随 ROM 下场） |
| 可用时间 | **立即** | 随新 ROM 逐步覆盖 |
| 覆盖范围 | 全机队（含停更机型） | 只有搭载注册中心的新设备 |

**关键结论：路线 B 不是临时方案，而是存量设备的终态方案。**
停更机型永远不会有注册中心，它们的工具集已经冻结、恰好最适合查表
（不再变化，登记一次永久准确）。所以演进路径是：

```text
现在：  全机队查表（B）
       ↓ 注册中心随新 ROM 下场
过渡：  新设备实报（A）+ 存量查表（B），同一对象接口
       ↓ 存量自然淘汰
远期：  A 为主，B 覆盖长尾——B 永不完全退役
```

上层机制从第一天就面向工具集对象设计，路线切换对 skill 体系零感知。

## 六、管理防错清单：每类错误一个结构性防错

"保证不出错"不能靠小心，要靠让错误**无法发生**或**立即暴露**：

| # | 错误类型 | 结构性防错 |
| --- | --- | --- |
| 1 | skill 让调不存在的工具 | 上架静态校验（对 golden manifest）+ pre-call 拦截兜底 |
| 2 | 设备拿到不匹配的 skill | 确定性分发函数（工具集 + 灰度桶 → 唯一版本）+ 会话钉住 |
| 3 | 工具变更漏通知 skill 侧 | 依赖索引（tool→skills 反查）+ 变更门禁强制查表 |
| 4 | 破坏性变更先于 skill 适配触达设备 | "快通道先行"时序门禁：受影响 skill 新版未备好，工具发布不放行 |
| 5 | 登记表与设备实况漂移（路线 B 特有） | 安全网触发聚合上报驱动修表 + 采样审计看板 + 高漂移载体切实报 |
| 6 | 多版本混乱、问题无法复盘 | 在役版本硬上限 ≤2~3；日志强制携带 (skill_version, toolset_id) |
| 7 | 重组出现中间态 / 旧名失效 | 原子 changeset + skill alias 表 + 选择评估门禁 |

## 七、日常操作手册（谁在什么场景做什么）

| 场景 | 标准动作序列 | 门禁 |
| --- | --- | --- |
| skill 纯体验优化（技能范围不变） | 改单源 → 静态校验 → 灰度 → 全量替换 | 禁止引入新工具依赖（CI 检测正文新增工具引用即拦截） |
| skill 新增子技能（依赖新工具） | 正文加能力分支（老设备拒答 / 降级，计划内话术）→ 上架 | 新工具须已登记；拒答分支必须存在 |
| 工具新增 | 登记表更新 → 默认 T2 experimental → 晋级 T1 后开放全量引用 | 登记即门禁 |
| 工具破坏性变更 / 删除 | TMG 评审 → 查依赖索引 → skill 先适配上架 → alias 缓冲 → 随 ROM 灰度 | skill 引用未清零 / 未适配，不放行 |
| skill 重组（拆合改名分层） | 原子 changeset → 选择评估 + 描述检查 → 灰度 → alias 兜旧名 | 见[重组盘点](./skill重组情形盘点.md) |
