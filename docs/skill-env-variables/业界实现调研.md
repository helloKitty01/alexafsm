# 业界实现调研：运行时环境变量如何进入 Agent 上下文

> 配套 [skill环境变量传入方案.md](./skill环境变量传入方案.md)。
> 调研问题：业界的 agent 系统如何把"运行时环境状态"（当前分支、屏幕内容、前台应用……）
> 传给模型/skill？各家做法与我们方案 A/B/C/C'/D 的对应关系，以及可直接借鉴的细节。

## 零、结论速览：方案 ↔ 业界对应

| 我们的方案 | 业界对应实现 | 印证结论 |
| --- | --- | --- |
| A：load skill 时渲染 | Claude Code skill 的 `!command` 激活时注入 | 机制存在，但语义明确为"执行一次、会话内缓存"——只适合加载时刻的定向快照，不承诺持续新鲜 |
| B：随 user message 被动注入 | Claude Code `<system-reminder>` 随 user 轮注入；会话级 git 快照 | 主流做法；且 Claude Code 对快照**刻意冻结不刷新** |
| C：主动查询工具 | Anthropic Agent Skills（模型自己跑命令查状态）；computer-use 的 screenshot 动作 | 官方 skill 哲学：skill 正文静态，状态靠模型运行时自查 |
| C'：工具结果侧带回 | computer-use 官方 harness 在 tool result 附加截图；Claude Code 在 tool result 内附加 system-reminder | 官方文档明确推荐，理由就是"省一个往返" |
| D：框架层求值、模型不可见 | LangGraph `InjectedState` / `InjectedToolArg` / `ToolRuntime` | 业界走得更彻底：直接从 schema 隐藏参数（印证变量解析文档 8.2 的 schema 改写方向） |

排布层面，Manus 的三原则（稳定前缀 / append-only / 确定性序列化）与
[kv-cache-discussion/02](../../kv-cache-discussion/02-上下文分层与排布.md) 完全一致。

## 一、Anthropic Agent Skills：skill 静态 + 状态自查

[官方 Skills 架构](https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills)
采用三级渐进式披露：启动时只加载 name + description（进 system prompt 的静态索引）；
触发时模型**用 bash 自己读** SKILL.md；更深的资源文件按需再读。

与本问题相关的关键设计取向：

- **SKILL.md 是纯静态文档**，官方机制里没有"load 时向 skill 传运行时变量"的参数化入口；
- 需要环境状态时，skill 的写法是**指示模型去查**（跑命令、调工具），而不是把状态渲染进正文；
- 脚本执行"只有输出进上下文，代码本身不进"——状态获取的成本被压到最低。

对应我们的结论：skill 正文保持静态 + 分支条件写成"引用式"（去 env_context / 工具结果里读值），
与官方哲学一致。

## 二、Claude Code：三种通道并存（最完整的参照系）

Claude Code 是目前公开信息最丰富的生产级 harness，恰好三种通道都有：

### 2.1 `!command`：load 时注入确实存在（方案 A 的业界形态）

Claude Code 的 skill/命令支持 `!` 前缀嵌入 shell 命令
（如 `Current branch: !git branch --show-current`），**skill 加载时执行、输出注入上下文**。
但其文档化语义值得注意：

- 执行发生在**加载那一次**，输出**在会话内缓存**，不承诺后续刷新；
- 社区实践中的典型用途是"激活时刻的定向快照"：PR review skill 注入 `!gh pr diff`、
  部署 skill 注入当前分支——都是**任务级准静态**数据，不是持续易变量。

印证我们对方案 A 的定位：机制可以有，但只用于"加载时刻正确即可"的变量；
前台应用这类 loop 级易变量不适用。

### 2.2 会话级快照刻意冻结（方案 B 的边界处理）

Claude Code 在会话开始时捕获 git 状态快照（分支、未提交变更、最近 5 次提交），
**整个会话不更新**。这是刻意设计：避免模型把快照当实时状态、"幻觉出实时变化"；
需要新鲜状态时模型自己跑 `git status`（即方案 C 兜底）。

借鉴点：**快照与实时的职责切分要显式**——注入的环境上下文要么声明"这是轮初/会话初快照"，
要么在静态规则里写明"以消息流中最近一次出现的值为准"，不能让模型猜时效。

### 2.3 `<system-reminder>`：双位置注入（方案 B + C' 的合体）

Claude Code 用 `<system-reminder>` 块把动态上下文注入两个位置：

1. **随 user 轮注入**：CLAUDE.md、当前日期、skill 目录、mode 标志等，作为同一 user turn
   里的多个 content block（一次抓包显示单个 user turn 含 6 层 block）——system prompt
   本体保持稳定，动态内容全部下沉到消息流；
2. **附在 tool result 内**：如 TodoWrite 使用提醒直接拼在某次 bash 结果的尾部；
   规范化阶段有专门的 `smooshSystemReminderSiblings` 步骤，把相邻的 reminder 块
   **合并进邻近的 tool_result**，避免产生多余的 user/assistant 轮边界。

借鉴点（直接可抄）：方案 C' 的"前台应用"字段应**合并进 tool result 本体**
（固定位置、固定格式），不要另起一条消息，避免多余轮边界破坏消息流结构。

## 三、Computer-use 官方 harness：动作后回传状态（方案 C' 的官方版）

Anthropic / OpenAI / Azure 的 computer-use 循环是同一个模式：
模型出动作 → harness 执行 → **harness 截取新屏幕状态随 tool result 回传** → 模型看新状态定下一步。

Anthropic 官方文档更进一步，明确写了 C' 的优化逻辑：

> 当一批动作没有以 screenshot 结尾时，harness 可以**主动在最后一个 tool result 上附加截图**，
> 让模型总能看到当前屏幕状态，**相比等模型自己请求截图省一个往返**。

这正是我们方案 C'（post-call 富化）的官方背书，连动机（省 loop）都相同。
"前台应用"本质上就是移动端场景下截图的一个极小化结构化投影。

## 四、移动端 GUI agent：每步观测里天然带前台状态

Mobile-Agent（v1–v3）、AppAgent 等移动端 agent 的标准循环：每个 step 开始时采集
**当前屏幕观测**（截图 + 无障碍树/UI 元素），模型基于"任务指令 + 历史 + 当前观测"出下一动作。
前台应用信息就包含在每步观测里，**不存在"加载时传一次"的概念**。

工程侧的例子：android-agent-bridge（设备端 MCP server）提供 `get_ui_tree`（含 active window）、
`list_apps`、`launch_app` 等工具，其 `run_script` 的 `capture` 操作把"最终状态"
（节点查询结果、截图、active window）打包进返回值——同样是"动作结果自带环境状态"的形态。

对我们的启示：如果 skill 的分支判断总是发生在若干设备操作之后，
C'（工具结果带回）就是主通道，B（轮初注入）只是初始基线。

## 五、LangGraph：模型不可见的运行时注入（方案 D 的框架级形态）

LangGraph 的 `InjectedState` / `InjectedToolArg` / `ToolRuntime` 提供了"工具要用、
模型不用知道"的标准机制：

- 工具签名里用注解标记的参数，**自动从暴露给模型的 tool schema 中剔除**；
- 模型生成 tool call 后、工具执行前，框架把运行时值（图状态、store、config）注入；
- 模型自始至终看不到这些参数的存在。

与我们方案 D（`${env.foregroundApp}` 变量语法）的对比很有信息量：

- LangGraph 走得更彻底——**schema 层直接隐藏**，模型连语法都不用学；
  这印证了[变量解析文档](../variable-resolution/工具参数变量解析机制方案.md)第 8.2 节
  "schema 改写"是业界主流方向；
- 变量语法的独特价值在 LangGraph 覆盖不到的场景：值需要**内嵌在模型可写的参数中**
  （如文本模板里嵌 bundleName）、或模型需要**跨命名空间显式指定实体**（`${app.抖音.bundleName}`）。
  两者分工共存，与 8.2 节的结论一致。

同样的限制也被印证：这类注入对"模型要读值来决定分支"无能为力——LangGraph 文档明确说
注入参数 "invisible to the model's tool-calling interface"。

## 六、Manus：排布纪律的量化背书

[Manus 的上下文工程实践](https://manus.im/blog/Context-Engineering-for-AI-Agents-Lessons-from-Building-Manus)
把 KV cache 命中率列为生产 agent 第一指标（输入输出比 100:1，缓存差价 10 倍），三原则：

1. **稳定前缀**：system prompt 里连精确到秒的时间戳都不放；
2. **append-only**：不回改历史动作/观测；序列化必须确定性（JSON 键序）；
3. **显式断点**：不支持自动前缀缓存的推理侧手动标记。

这与 02 文档的排布方案完全一致，也再次排除了"把前台应用放进 system prompt 并原位刷新"
这类做法。另一条相关经验："mask, don't remove"——工具集保持静态，用状态机 + logit masking
约束当前可选动作。延伸参考：若 harness 自身能感知前台应用，理论上可以在解码层直接约束
分支动作（如前台不对时禁止某些工具），不依赖模型读值判断；但这要求自建推理侧支持 logit
控制，可作为远期选项，不影响当前方案。

## 七、可借鉴清单（对我们方案的增强）

1. **C' 字段合并进 tool result 本体**（学 Claude Code 的 smoosh）：附加的
   `foreground_app` 字段拼进工具结果的固定位置，不另起消息，避免多余轮边界。
2. **快照时效显式声明**（学 Claude Code git 快照冻结）：env_context 注入块标明
   "轮初快照"，静态规则写明"以消息流中最近一次出现为准"，杜绝模型把旧值当实时。
3. **harness 主动附状态省往返**（学 computer-use 官方建议）：不等模型请求，
   设备操作类工具的最后一个结果统一附带前台应用——官方动机与我们相同。
4. **skill 指示"去哪读"而非"值是什么"**（学 Anthropic Skills）：skill 正文只写
   "根据 env_context / 最近工具结果中的 foreground_app 判断"，状态获取路径标准化。
5. **A 类注入限定为任务级快照**（学 `!command` 的语义边界）：若未来确有"加载时刻
   正确即可"的变量（如设备型号），可以支持 load 时注入，但必须文档化"一次执行、
   不承诺刷新"的语义。
6. **schema 层隐藏优先于变量语法**（学 LangGraph）：纯参数场景优先走 schema 改写
   （8.2），变量语法保留给"值内嵌在模型可写文本中"的场景。
