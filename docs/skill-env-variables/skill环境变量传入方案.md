# Skill 分支环境变量传入方案（以"当前前台应用"为例）

> 适用场景：skill 正文中存在分支逻辑，依赖一个运行时环境变量（如"当前手机前台应用是哪一个"）。
> 问题：这个变量该在什么时机、经什么通道进入上下文？是在 load skill 时传输吗？
>
> 前置架构：harness 采用 [kv-cache-discussion/02](../../kv-cache-discussion/02-上下文分层与排布.md)
> 的分层排布（L0 静态前缀 / L1 会话级 / UAT 消息流 append-only），skill 通过
> `load_skill` 工具渐进式加载，正文以 tool result 进入消息流；另有
> [变量解析机制](../variable-resolution/工具参数变量解析机制方案.md)（pre-call 拦截器 + `${...}` 语法）。

---

## 一、先回答核心问题

**不建议在 load skill 时把"前台应用"这类值渲染进 skill 正文。** 两个理由：

1. **时效性错位**。前台应用是**高易变量**：用户随时切换，agent 自己的动作
   （打开应用、返回桌面）也会改变它。而 skill 正文以 tool result 进入 UAT
   消息流后 append-only、整个会话可见——加载那一刻渲染进去的值**立即开始过期**，
   模型在后续 loop 里读到的是旧值，分支可能走错。若靠重新 `load_skill` 刷新，
   skill 正文会重复进入消息流，浪费 token。
2. **破坏 skill 正文的静态性**。同一 skill 每次加载的 token 序列应当完全一致
   （利于测试回放、日志比对，也保持"skill 即静态文档"的简单心智）。
   模板渲染让 skill 正文变成"skill × 环境快照"的笛卡尔积。

load 时渲染只对**会话级冻结**的变量成立（设备型号、系统版本、语言——L1 类），
这类变量更应该走 L1 注入而不是塞进 skill。前台应用不属于此类。

## 二、分析框架：两个维度决定通道

选通道前先回答两个问题：

**维度一：谁消费这个变量？**

| 消费方 | 含义 | 约束 |
| --- | --- | --- |
| 模型 | 变量决定 skill 分支走向，模型必须**读到**真实值才能决策 | 值必须进入上下文（消息流） |
| 工具 | 变量只是某个工具调用的参数，模型不需要知道真实值 | 可在框架层求值，模型全程不见真值 |

**维度二：变量的变化频率？**

| 级别 | 例子 | 归属 |
| --- | --- | --- |
| 产品级静态 | 工具集、skill 索引 | L0 |
| 会话级冻结 | 设备型号、系统版本 | L1 |
| 轮级变化 | 电量、网络状态、**轮初的前台应用** | 随 user message 注入 |
| loop 级变化 | **agent 动作后的前台应用**、屏幕内容 | 工具结果带回 / 主动查询 |

"当前前台应用"横跨最后两级：轮初有一个基线值，轮中会被 agent 自己的动作改变。
这正是它需要组合方案的原因。

## 三、候选方案对比

### 方案 A：load_skill 时模板渲染（不推荐）

skill 正文含 `{{foreground_app}}` 占位，`load_skill` 执行时由 harness 查询并渲染。
问题见第一节。**仅当变量会话级冻结时可接受**，且即便如此也更推荐放 L1。

### 方案 B：被动注入——随当轮 user message 的 env_context（通道一）

前台应用是典型的 query 级环境上下文。构造当轮 user message 时注入：

```text
user#N: <env_context>foreground_app: com.ss.android.ugc.aweme（抖音）</env_context>
        <query>用户原始问题</query>
```

skill 正文保持静态，分支逻辑写成引用式的：

> 根据 env_context 中的 foreground_app 判断：若当前前台是目标应用，直接执行 X；否则先打开应用再执行。

- 优点：零额外 loop；append-only 缓存友好；与现有架构无缝（就是 02 的通道一）。
- 局限：只保证**轮初新鲜**。一轮多个 loop 中 agent 打开了别的应用，该值即过期。

### 方案 C：主动查询——`get_foreground_app` 工具

模型在分支判断前调用工具取值，结果以 tool result 进消息流。

- 优点：任意时刻最新鲜，语义显式。
- 代价：一次工具调用往返（多一个 loop）。
- 适合：分支判断发生在 agent 自身动作之后，且方案 C'（见下）未覆盖时的显式兜底。

### 方案 C'：工具结果侧带回——post-call 富化（推荐的关键补充）

所有**可能改变前台应用的工具**（打开应用、点击、返回桌面、关闭应用……），
其 tool result 由框架在 post-call hook 统一附加"当前前台应用"字段——
工具本身零改动，与变量解析机制的 pre-call 拦截器**对称**（一个管进参，一个管出参）：

```text
tool result: {"status": "ok", "_env": {"foreground_app": "com.tencent.mm"}}
```

- 模型在自己的动作之后**免费**获得最新值（不占额外 loop），
  绝大多数情况下省掉方案 C 的显式查询；
- 类比 computer-use agent 每次操作后回传截图/无障碍树：**环境状态跟着动作走**；
- 实现要点：维护"会改变前台"的工具清单（或干脆对全部设备操作类工具统一附加）；
  字段保持确定性序列化（键序、格式固定），避免缓存悄悄失效。

### 方案 D：变量语法 `${env.foregroundApp}`——pre-call 解析

复用已有变量解析机制，注册 `env` 命名空间的 Resolver，工具调用时实时查询系统求值：

```python
RESOLVERS = {"app": AppResolver(), "env": EnvResolver()}

class EnvResolver:
    def resolve(self, entity: str, attr: str | None = None) -> str | None:
        if entity == "foregroundApp":
            return query_foreground_app()   # 调用时刻实时取值
        return None
```

**关键限制：只覆盖"工具要用"，不覆盖"模型要读"。** pre-call 替换发生在框架层，
模型永远看不到求值结果——如果分支逻辑需要模型根据前台应用**决定走哪条路**，
这个机制帮不上忙。它的价值在另一半场景：分支已经走定、只需把"当前前台应用"
作为参数传给某个工具时，模型写 `${env.foregroundApp}`，零 loop、零幻觉。

另注意：`env` 命名空间是**调用时刻实时求值**（与 `app` 命名空间的静态查表不同），
日志必须记录求值时刻的值，否则"分支走错"类问题无法复盘。

## 四、决策矩阵

| 场景 | 推荐通道 |
| --- | --- |
| 变量决定 skill 分支走向（模型必须读值），判断发生在轮初 | **B**（env_context 注入） |
| 同上，但判断发生在 agent 自身动作之后 | **C'**（工具结果带回）为主，**C**（主动查询）兜底 |
| 变量只作为工具参数，模型不需要知道真值 | **D**（`${env.foregroundApp}`，零 loop） |
| 变量会话级冻结（设备型号等） | L1 注入（load 时渲染 A 才可接受，但不必要） |

## 五、推荐组合（针对"前台应用"）

1. **轮初基线**：`foreground_app` 进入当轮 user message 的 `<env_context>`（方案 B），
   按增量注入（与上轮相同则可省略）。
2. **轮中刷新**：改变前台的工具，其结果统一附带最新前台应用（方案 C'），
   模型动作后免费拿到新值。
3. **显式兜底**：保留 `get_foreground_app` 工具（方案 C），供模型在不确定时主动查询。
4. **参数场景**：需要把前台应用传给工具时用 `${env.foregroundApp}`（方案 D）。
5. **skill 写法**：正文保持静态，分支条件写成"根据 env_context / 最近工具结果中的
   foreground_app 判断"，并给 few-shot 示例；**不做 load 时模板渲染**。

## 六、KV cache 影响核对

对照 02 的排布原则逐项核对：

- 方案 B / C / C' 的值全部落在 **UAT 消息流**（user message 附带或 tool result），
  append-only，不碰 L0/L1 前缀——缓存零破坏；
- skill 正文静态 → 同一 skill 每次加载 token 序列一致；
- 方案 D 在框架层求值，值根本不进上下文，对缓存无影响；
- 唯一要守住的纪律：**不要**为了"刷新前台应用"去原位改写历史消息里的旧值，
  旧值留在历史里没关系，模型以最近一次出现的值为准（可在 system prompt 的
  静态规则里写明"环境变量以消息流中最近一次出现为准"）。
