# 10 KV Cache 细化统计方案与分场景收益口径

> 本篇回答两个问题:
> ① 怎么把"KV cache 省了什么"讲清楚——在单轮对话、单轮 loop、多轮对话
> 等不同场景下收益分别是什么量级、来自哪里;
> ② 统计口径怎么细化——既能对上成本账,又能指导工程优化,
> 既有场景级切片,也有全局汇总。
> 与 08(量化收益评估)的关系:08 给的是"改造后能省多少"的一次性估算,
> 本篇给的是**长期运行的度量体系**,用来验证 08 的估算、并持续看住不回退。

---

## 0. 先把一个心智模型立住:一个 token 会被重算多少次

KV cache 只作用于 **prefill**(输入侧):命中的前缀 token 免于重算
(计价约 0.1×),miss 的 token 全价重算。**decode(输出侧)一个 token
都省不了**——但模型生成的输出会随 decode 自动进入缓存,
下一次请求把它作为历史消息带上时,它已经是"命中"的。

Agent 的成本结构由一个事实决定:**同一段上下文会被反复提交**。
loop 每迭代一次、对话每多一轮,历史全文都要重新作为输入发给模型。
所以讲收益最直观的问法是:

> **一个 token 进入上下文之后,到会话结束,会被 prefill 多少次?**

- 无缓存:每次请求都算一遍。会话有 N 次模型请求,早期进入的 token
  就被重算接近 N 次;
- 理想缓存:**只在第一次出现时算一次**,之后全部命中。

由此定义一个对管理层最好讲的全局量——**重复计算系数 ρ**:

```text
ρ = 会话内实际 prefill 总量 / 会话内首次出现的 token 总量
```

无缓存时 ρ ≈ 请求次数的一半量级(线性增长上下文的求和效应);
理想缓存时 ρ = 1。**一切优化都是在把 ρ 往 1 压。**

## 1. 分场景收益推演

三个场景的本质区别是**请求次数 N 和请求之间的前缀关系**。
缓存收益 = 重复提交的部分 × 命中与否,所以 N=1 时无会话内收益,
N 越大、上下文越长,收益越陡。

### 1.1 单轮对话(一问一答,无工具调用)

```text
请求序列:仅 1 次请求
输入构成:[L0 | Tools | L1 | (L2) | query]
```

- **会话内收益 = 0**:没有第二次请求,谈不上"重复提交"。
- 唯一收益来自**跨会话/跨用户的全局共享前缀**:L0 + Tools 块
  全网用户逐字节相同、流量极热,几乎必然驻留,首请求即可命中。
- 收益量级 = |L0 + Tools| / |首请求输入|。这部分收益**现状就已拿到**,
  且与排布改造无关;能做的只有控制 L0 的发布纪律(见 09 §2.2,
  改一个字节 = 全网失效一次)。
- **统计含义**:这类请求(以及一切会话首请求)不应与会话内请求
  混在一个命中率里——它的合理预期本来就低,混入只会把整体命中率
  拉低并掩盖真正的优化空间。08 已指出要分开统计,本篇落成标签口径(§4)。

### 1.2 单轮 loop(一个 query,N 次工具迭代)

```text
请求序列:同一 query 内 N 次请求,间隔秒级
请求 i 输入 = 请求 i-1 输入 + A(i-1) + T(i-1)   ← 严格追加
```

- 这是缓存收益**最大、也最"免费"**的场景:loop 内前缀只增不改
  (append-only),且间隔短、驻留风险低,天然应该全命中。
- 算一笔账(示意,C₀=首请求 30K,N=8 次迭代,每次新增 Δ=2K):

```text
无缓存 prefill 总量 = Σ (30K + 2K·i) ≈ 296K
理想缓存 prefill    ≈ 30K + 7×2K   ≈  44K     (节省 ~85%,ρ 从 6.7 → 1)
```

  N 越大差距越陡:无缓存是 **O(N·C₀ + N²Δ/2)** 的平方级增长,
  理想缓存是 **O(C₀ + NΔ)** 的线性增长。深 loop 的 agent
  没有缓存根本跑不起经济账——这就是"输入输出比 100:1、
  成本几乎全在 prefill"(09 §1)的场景来源。
- **现状**:loop 内命中基本已拿到(04 已确认)。两个破坏因素:
  ① T(tool result)高频裁剪——loop 中途重写前缀,当场打断缓存;
  ② 驻留逐出——迭代间隔短,概率低但非零。
- **统计含义**:loop 内命中率不是"优化空间",而是**健康度 SLO**
  ——它理应接近结构上限,一旦下跌就是回归事故
  (裁剪时机错了、序列化不稳定、或集群逐出恶化),要报警而非分析。

### 1.3 多轮对话(M 个 query,每个 query 带自己的 loop)

```text
请求序列:M 个 query × 各自 N 次迭代
query 内:追加式(同 1.2,应全命中)
query 之间:现状 L2 原位重写 → 缓存从 L2 断裂,
           Tools + 全部 UAT 历史重新 prefill(01 §核心问题)
```

- 这是**主战场**。现状每个新 query 的首请求 miss ≈ |L2|+|Tools|+|UAT 全史|,
  随轮数线性增长;叠加 10 轮滑窗裁剪后,长对话阶段每轮都在重写前缀头部,
  每轮都接近全量 miss(01 §问题维度②)。
- 目标态(L2 下沉 + 按 token 双水位裁剪 + 分代冻结):query 首请求的
  miss 收敛为**当轮新增**(新 query 文本 + 注入增量 ≈ 2K),
  上一 query 的全部历史照常命中。
- 现网基线正是这个场景的混合结果:输入 37K / 命中 25K / 66%,
  目标 92%(08)。收益几乎全部来自"把 query 切换点的全量 miss
  变成增量 miss"。
- 多轮独有的第二个风险:**query 之间的长间隔**(用户思考几分钟到几小时)
  是驻留逐出的高危窗口(09 §2.5 同一判断)。loop 内间隔秒级、
  query 间隔分钟级——**排布性 miss 集中在 query 切换点,
  驻留性 miss 也集中在 query 切换点**,两者在同一位置叠加,
  这正是必须在统计上把它们拆开的原因(§3、§5)。

### 1.4 场景收益汇总

| 场景 | 请求数 | 天然命中来源 | 必然 miss(结构性新增) | 现状主要损失 | 该场景的正确指标 |
| --- | --- | --- | --- | --- | --- |
| 单轮对话 | 1 | 全网共享 L0+Tools | L1、query 本身 | 无(收益已拿到) | 全局前缀命中率 |
| 单轮 loop | N(秒级间隔) | 上次请求的全部前缀 | 每轮 A+T 增量 | T 高频裁剪打断前缀 | loop 内达成率(SLO≈100%) |
| 多轮对话 | M×N(query 间分钟级) | 上一 query 的全部历史 | 新 query + 注入增量 | **L2 重写 + 滑窗裁剪 + 长间隔逐出** | query 切换点达成率(主优化指标) |
| 跨会话 | — | 仅 L0+Tools | 其余全部 | 无(前缀缓存原理性限制,08 边界情况) | 不设指标,只在首请求口径中体现 |

一句话版本:**单轮对话没得省、单轮 loop 已经在省、多轮对话是省钱的主战场;
统计体系的任务是把第二类看住(SLO)、把第三类量化(优化指标)。**

## 2. 统计的原子模型:每请求输入的四分解

> 口径澄清:讨论中说的"命中长度 / 输出长度"里,分母实际是
> **每次请求送入模型的完整上下文长度(prompt tokens,输入侧)**。
> 输出(completion)是 decode,缓存不作用于它,不进这个比值;
> 建议统一叫"**每请求输入长度 P**",避免歧义。
> "输入包含可被 cache 的部分 + 新增部分"这个两分法是对的,
> 下面把它细化成四分。

每次模型请求的输入 P(token 数)恰好切成四块:

```text
P = H + M_new + M_layout + M_evict

H         实际命中:引擎报告的 cached tokens,免 prefill(0.1× 计价)
M_new     结构性新增:本轮首次出现的 token——新 query 文本、
          本轮工具执行结果、检索/环境注入增量。第一次见必 miss,
          任何优化都消不掉;但每个新 token 只该 miss 这一次。
M_layout  排布性 miss:曾经 prefill 过、本可命中,但因前缀被改写
          (L2 重写 / 滑窗裁剪 / 序列化不稳定)导致位置错位而重算。
          ——工程可根除(01 的全部改造都在打它)。
M_evict   驻留性 miss:前缀逐字节未变、本该命中,但 KV 已被集群
          逐出而重算。——只能缓解(亲和路由 / 分层存储,09 §3)。
```

四块的判定方法(§5 详述):H 由引擎直接返回;M_new 由应用层
消息记账得出(本次请求比上次多了哪些消息,tokenize 计数);
"理论可命中 T"由本次输入与上次序列的最长公共前缀(LCP)得出,
于是 `M_evict = T − H`,`M_layout = P − M_new − T`。

两个必须想清楚的边界:

1. **上一轮的模型输出算什么?** 上次请求的 completion 随 decode
   已进缓存,本轮把它作为 assistant 消息带上时属于**可命中**部分,
   不是新增。所以 LCP 的比较对象是"上次输入 ⧺ 上次输出",
   而非仅上次输入。
2. **会话首请求可能 H > 会话内理论值**:L0+Tools 命中来自
   跨会话共享,不在本会话的 LCP 里。首请求单独打标(§4),
   不进达成率,单独报"全局前缀命中率"。

## 3. 三层指标体系:一个比值不够,需要三个

只用"命中 / 输入"一个比值,会把三件不相干的事搅在一起:
业务形态变了(新增占比升高)、工程回退了(排布 miss 增加)、
集群紧张了(逐出增加)——同样表现为命中率下跌,但责任方和动作完全不同。
因此拆成三层:

### 指标 1:命中率(成本口径)

```text
命中率 = H / P        (全局按 token 加权:Σ H / Σ P)
```

直接对应账单和 prefill 算力,是对外报数、算成本的口径。
现网 66%,目标 92%(08)。**缺点:分母含 M_new,受业务形态污染**
——某轮工具结果特别大(新增多),命中率数字就难看,
但这不是工程退化;反之靠"少干活"也能把它做好看。
所以它适合报账,不适合当优化的方向盘。

### 指标 2:结构上限(业务形态口径)

```text
结构上限 = 1 − M_new / P = (P − M_new) / P
```

由业务形态决定的天花板:每轮必然有首次出现的 token。
只能靠"少进上下文"(落盘指针化、工具输出不进上下文、
defer_loading)抬高,与缓存工程无关。现网估算 ≈ 94.6%(08)。
**单独跟踪它,才能发现"命中率跌了"其实是"业务变重了"。**

### 指标 3:达成率(工程执行口径,北极星)

```text
达成率 = H / (P − M_new) = 实际命中 / 理论可命中
```

在"本可命中"的 token 中实际命中的比例。**理论上可打到 100%**,
与业务形态解耦、跨场景可比——loop 内迭代和 query 切换点
可以放在同一把尺子上比(前者应≈100%,后者的差距就是改造空间)。
这是工程团队的主指标。三者关系:

```text
命中率 = 结构上限 × 达成率
 66%   ≈  94.6%  ×  70%      ← 现状:执行落差 30 个点
 92%   ≈  94.6%  ×  97%      ← 目标:落差压到 3 个点
```

达成率进一步按责任方拆两半:

```text
1 − 达成率 = 排布性落差 (M_layout / 可命中)   ← 应用层责任,可根除
           + 驻留性落差 (M_evict  / 可命中)   ← 集群侧责任,可缓解
```

这就是 04 待确认问题②("需区分排布性 miss 与驻留性 miss")的
落地形式,也是 08 敏感性分析里"最大不确定项"的测量手段——
**统计体系上线的第一个产出,就是把现网 34% miss 拆出这两半的占比,
直接决定排布改造(P3–P5)与驻留治理(P6)的投入配比。**

### 成本侧派生指标(向上汇报用)

| 指标 | 定义 | 现状 → 目标 |
| --- | --- | --- |
| 等效输入成本/请求 | 0.1·H + 1·(P−H) | 14.5K → 6.4K(-56%) |
| prefill 计算量/请求 | P − H | 12K → 3K(-75%) |
| 重复计算系数 ρ(会话级) | 会话 prefill 总量 / 会话首见 token 总量 | 新增,最直观的浪费度量 |

## 4. 场景标签与看板:场景级与全局怎么共存

### 4.1 请求打标(埋点时写入,一次打标、处处切片)

每次模型请求带上:

```text
session_id / query_index / loop_index
request_type ∈ {
  session_first   会话首请求(含单轮对话)
  query_first     新 query 的首请求(query 切换点)
  loop_iter       loop 内后续迭代
  compact         压缩/摘要请求(缓存安全分叉的验证点,09 §2.4)
}
业务场景标签:产品线 / 任务类型(用于业务切片)
inter_request_gap:与上次请求的间隔秒数(驻留分析用)
```

### 4.2 每类请求的预期与用途

| request_type | 达成率预期 | 数字的含义 | 异常时查什么 |
| --- | --- | --- | --- |
| session_first | 不适用 | 只看全局前缀命中率 = H / \|L0+Tools\| | L0 变更纪律、公共前缀驻留 |
| query_first | 现状低,**改造主战场** | 直接度量 L2 下沉/裁剪改造的效果 | 排布(L2/裁剪)+ 驻留(长间隔)分别看 |
| loop_iter | **≈100%,SLO** | 健康度,跌 = 回归事故 | T 裁剪时机、序列化稳定性、逐出 |
| compact | ≈100% | 验证摘要请求复用了主会话前缀 | 压缩实现是否天真分叉(全价重付) |

### 4.3 看板分层

1. **全局页(成本视角)**:token 加权命中率、等效成本/请求、
   prefill 量/请求、ρ;附结构上限曲线做参照——命中率贴着上限走
   才是健康,上限本身波动是业务形态在变。
2. **工程页(达成率视角)**:总达成率及排布/驻留两半的拆分;
   按 request_type 分列;**驻留性落差 × inter_request_gap 的分布曲线**
   ——多长的间隔后开始 miss,直接给出集群驻留时长的量化诉求
   (对应 09 §3 的演进路线该走到哪一步)。
3. **场景页(业务视角)**:按产品线/任务类型切片的命中率与成本。
   注意:**全局命中率会因场景 mix 漂移**(深 loop 任务占比升高,
   全局命中率自然上升,不代表工程有进步)——这是必须同时有
   场景切片和达成率口径的第二个理由。

## 5. 埋点与实现:三个数据源,三步落地

### 数据源

1. **引擎侧(拿 H)**:vLLM / SGLang 开启 prefix caching 后,
   response usage 里逐请求返回 cached tokens
   (vLLM:`prompt_tokens_details.cached_tokens`;SGLang:`cached_tokens`)。
   这是唯一需要引擎配合的点,且是现成能力,确认开启并透传即可。
2. **应用侧(拿 M_new)**:请求构造器本来就知道"这次比上次多了
   哪些消息"(新 user 消息、上轮 assistant、新 tool result、注入增量),
   对新增消息 tokenize 计数即得 M_new。
3. **应用侧(拿理论可命中 T)**:对每次请求,在**消息边界**记录
   前缀滚动哈希(逐消息一个 hash,几十个整数,成本可忽略);
   下次请求与上次的哈希链比对,找到最长公共消息前缀,其 token 数即 T。
   消息级粒度足够——前缀改写都发生在消息边界
   (L2 重写、裁剪、注入),不必逐 token 比对。
   随后 `M_evict = max(T − H, 0)`,`M_layout = P − M_new − T`。

### 三步落地(每步独立产出价值)

| 阶段 | 做什么 | 产出 |
| --- | --- | --- |
| ① 只接引擎 | 透传 cached_tokens + 请求打标 | 全局/分场景命中率、等效成本——第一次有真实数,校准 08 的 66% 基线 |
| ② 加新增记账 | M_new 计数 | 结构上限、**达成率**上看板,优化有了方向盘 |
| ③ 加前缀哈希 | LCP 求 T | **排布/驻留拆分** + 驻留-间隔曲线,回答 08 的最大不确定项,决定投入配比 |

### 实现注意

- **tokenizer 一致性**:应用侧计数用与推理侧相同的 tokenizer,
  否则 M_new 有系统偏差;chat template 的控制 token 会让
  "消息 token 和"与引擎 prompt_tokens 有少量固定差,允许小残差,
  监控残差率即可发现模板变更等异常。
- **压缩事件的记账**:压缩发生的那次请求 M_layout 会激增,属预期内
  (07 的摊销分析);看板上对 compact 及其后首请求单独标注,
  不计入回归报警。
- **A/B 能力**:达成率口径与业务形态解耦,天然适合做改造前后对比
  ——L2 下沉灰度期间,实验组/对照组直接比 query_first 的达成率。

## 6. 遗留讨论点

1. **ρ 的会话归因**:跨天恢复的会话算一个 session 还是两个?
   影响 ρ 的分母(首见 token 是否重算一次)。倾向:以缓存可达性为准,
   恢复时若必然全 miss,则视为新 session。
2. **M_new 的进一步细分是否值得**:拆成 query 文本 / 工具结果 /
   注入增量三类,可以指导"少进上下文"方向(结构上限的抬高),
   但埋点成本增加;建议阶段②先不拆,阶段③视需要加。
3. **引擎命中的块粒度**:prefix cache 按 block(如 16/64 token)命中,
   H 与理论值有零头差异,达成率长期贴近但到不了字面 100%,
   SLO 阈值要留裕量(如 ≥98%)。
4. **驻留曲线的采样偏差**:长间隔请求本身稀疏,曲线尾部置信度低,
   需要按间隔分桶累积足够样本再下结论。
