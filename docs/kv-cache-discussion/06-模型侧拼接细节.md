# 06 模型侧拼接细节（DeepSeek V4 / GLM 5.2）

自建集群上模型的 chat template 决定最终 token 序列，直接影响缓存分析。
本篇记录两个候选模型的已查证行为（信息来源：官方 encoding 参考实现 /
HuggingFace chat_template.jinja，2026-08 查证）。

## 1. tools 的拼接位置：system 区内、UAT 之前

两家一致：tools 序列化在**前缀最前部（L0 区）**，对话历史之前。

- **DeepSeek V4**（DSML 格式）：渲染顺序为
  `system 正文 → "## Tools" 块（JSON schema）→ response_format → 对话消息`。
  tools 通过顶层 tools 字段挂在 system/developer 消息上。
- **GLM 5.2**：chat template 将 tools 渲染为 system 区的 `# Tools` 段，
  `<tools>` XML 标签内放 JSON schema，位于对话历史之前。

推论：

- 与我们的分层排布假设一致，tools 属于 L0，**保持稳定即缓存友好**；
  任何工具增删/顺序变化 = 全量 miss。
- skill 型能力若以"动态工具"下发会打碎前缀；以文本随消息注入则不触碰
  tools 区（方案 A/B 的前提成立）。

## 2. GLM 5.2 原生 defer_loading

GLM 5.2 模板对每个工具判断 `defer_loading` 字段：**标记为 true 的工具
不序列化进开头的 # Tools 块**（`strict` 字段也会被模板剔除）。

- 与方案 B 思路天然吻合：长尾 skill 型工具可标 defer，不占前缀。
- 具体运行时行为（模型如何感知/调用 defer 工具）需实测验证。

## 3. 内建的前缀重写：历史 reasoning 剔除

两家在 thinking 模式下都默认剔除历史轮的 reasoning：

- **DeepSeek V4**：编码器 `drop_thinking=True`，只保留最后一个 user 消息
  之后的 reasoning；文档提及 reasoning 保留规则存在"tools 存在时的覆盖"，
  具体行为待实测。
- **GLM 5.2**：模板默认清除旧 reasoning。

影响：每次新请求的前缀在**最后一轮 assistant 消息处**分叉，其后 miss。
分叉点在尾部、量小、机制上不可避免，但做命中率度量时必须把这部分
**预期内的尾部 miss** 与排布性 miss 区分开，否则会误判优化效果。

## 4. 其他已查证细节

- **DeepSeek V4**：tool result 无独立角色，合并包在 user 消息的
  `<tool_result>` 标签内（多个 result 按 tool_calls 顺序排序）。
- **DeepSeek V4**：官方仓库以 Python 参考编码器（encoding_dsv4.py）为准，
  通用 OpenAI 兼容端点需确认所用 chat_template 与参考编码器逐 token 一致
  （社区曾发现 reasoning_effort 档位在通用模板下行为不一致）。
- **GLM 5.2**：需固定 tokenizer revision，不同 revision 的模板行为有差异。

## 5. 排布正确性验证脚本（建议纳入度量工具）

```python
from transformers import AutoTokenizer
tok = AutoTokenizer.from_pretrained(MODEL, trust_remote_code=True)

def render(messages, tools):
    return tok.apply_chat_template(
        messages, tools=tools, tokenize=False, add_generation_prompt=True)

# 同一会话相邻两次请求各渲染一次，计算公共前缀长度：
# 公共前缀应等于上一次请求的完整 prompt（严格超集），
# 否则某处发生了原位重写，即存在排布性 miss。
def common_prefix_len(a: str, b: str) -> int:
    n = min(len(a), len(b))
    for i in range(n):
        if a[i] != b[i]:
            return i
    return n
```

注意：thinking 模式下，分叉点出现在最后一轮 assistant 消息处属预期
（见第 3 节），再往前的分叉才是排布问题。
