## 1. 账目逻辑与目标（P2 底部两行）

**第一行 · 账目逻辑**

- ① 输入 = 已缓存 + 白算 + 必算（每次模型调用）。已缓存 = 前缀逐 token 一致的深度；白算 = 本该命中却因前缀改写而重算；必算 = 本次必要新增的内容。
- ② **实算** = 白算 + 必算 = 输入 − 已缓存。prefill 真正计算的量，账单与 TTFT 都跟它走，成本收益就看它降多少。
- ③ **cache 命中率** = 已缓存 ÷ 输入。业界通用健康度；分母含必算，必算越多命中率越低——不如实算直观，但按业界口径一并上报。

**第二行 · 目标与衡量**

| 目标 / 尺子 | 演示会话（6 次调用） | 说明 |
| --- | ---: | --- |
| 目标 ① 白算 → 0 | 97.2K → 0 | 验收线，排布改造唯一可控项；目标态 loop 白算 > 1 块即报警 |
| 目标 ② 必算尽可能小 | 39.6K = 39.6K | 必要新增，两边相同，本次不记成绩；下一步靠动态只带变化、工具结果精简去压 |
| 成本看实算降幅 | 136.8K → 39.6K（−71%） | 省额 = 白算；Q≥2 首调 28.3–36.7K → 3.4K，与轮数脱钩 |
| cache 命中率 | 62% → 89%（全业务加权 91%） | 受必算拖累：会话首调 8.5K、webSearch 10K 在分母；长会话单轮到 95% 左右，1Q 81% |

## 2. 三类业务每 Q 的必算与沉淀

| 类型 | 占比 | 调用链 | 每 Q 必算（n≥2） | 当前方案下沉淀进 UAT |
| --- | ---: | --- | ---: | ---: |
| 问答 | 47% | 调① tool call → 调② webSearch 10 + answer | 3.35 + 10.2 = **13.55** | 0.1 + 10.2 + 0.25 = **10.55** |
| 任务 | 25% | 调① tool call → 调② SkillLoad 5 + 工具 2.5 + answer | 3.35 + 7.7 = **11.05** | 0.1 + 7.7 + 0.25 = **8.05** |
| 闲聊 | 28% | 调① answer | **3.35** | 0.1 + 0.25 = **0.35** |

3.35 = 动态 3 + query 0.1 + 上轮 answer 0.25。当前方案里动态在 SP 内原位重写、不进 UAT，所以沉淀不含动态；目标方案动态留在 U 里，输入每 Q 多 3K，已计入命中率分母。

加权：每 Q 必算 T(n≥2) = **10.1K**；沉淀速率 α = 0.47×10.55 + 0.28×0.35 + 0.25×8.05 = **7.1K/轮**；加权 loop 新增 = 0.47×10.2 + 0.25×7.7 = 6.72K。

### 4c. 首调 TTFT 预估

TTFT ≈ 首调实算 × prefill 单位耗时。参考实测：14K prefill ≈ 640 ms → ≈46 ms/K，线性折算；loop 两边相同、不变。待 prefill 吞吐实测（14 的 E6）替换。

| 轮次 | 当前首调实算 → TTFT | 目标 | 目标 + 会话级预热 |
| --- | ---: | ---: | ---: |
| Q1 | 17.5K ≈ 800 ms | 11.6K ≈ 530 ms | 3.1K ≈ 140 ms |
| Q2 | 24.8K ≈ 1.1 s | 3.4K ≈ 150 ms | 150 ms |
| Q4 | 39.0K ≈ 1.8 s | 3.4K ≈ 150 ms | 150 ms |
| Q6 | 53.1K ≈ 2.4 s | 3.4K ≈ 150 ms | 150 ms |
| Q12 | 95.5K ≈ 4.4 s | 3.4K ≈ 150 ms | 150 ms |

**会话级预热的收益与代价**（参考实测）：14K 一次 prefill 640 ms；拆成 6K 预热 + 8K 实时 = 320 + 380 ms，用户感知 TTFT 640 → 380 ms（−40%）；两次 prefill 总算力 700 ms（+10%）。另两条代价：预热到用户开口之间的缓存要靠 TTL 保住（逐出则白热）；开了会话没开口的预热白费。只改 TTFT，不改账。

## 6. 口径边界（页脚已写）

1. −66%（全业务）/ −71%（演示会话）是**实算 token** 降幅，费用按实际计价折算，TTFT 由实测验证。
2. cache 命中率全业务加权 91%：会话首调 8.5K、问答 webSearch 10K 是必算，且一半会话只有 1 轮；长会话单轮到 95% 左右。**验收看白算归零，命中率按业界口径一并报。**
3. 前提是会话内缓存不被逐出。实测 21 次调用里 2 次 loop 全 miss 20K+ 属引擎侧逐出 / 路由，排布改不了，需会话粘性 + TTL 配合并单独报警。
4. ≥11 轮按 12 轮计是下限口径，不外推。
5. TTFT 按参考实测 46 ms/K 线性折算，待 E6 实测替换。
6. 未计入：动态"只带变化"可再压目标每轮实算（必算），是下一步。上线后由日报（引擎 `cached_tokens` + 应用边界埋点）替换推演。
