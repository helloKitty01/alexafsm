## 00. 三个汇总维度（v4.2 起 P3 的读法）

命中率的**定义只有一个**：某次模型调用的 已缓存 ÷ 输入。P3 上的差别只是**汇总范围**（输入与已缓存分别求和再相除）：

| 维度 | 含义 | 页面位置 | 目标侧例子 |
| --- | --- | --- | --- |
| **第 n 轮（单轮）** | 一个 session 里第 n 轮的全部调用 | P3 左列：折线图、逐轮账表 | 第 6 轮命中率 92%、第 10 轮 95% |
| **L 轮的 session（累计）** | 第 1 ～ L 轮全部调用累加 | P3 右列：分桶表、"一条 session 省多少"柱图 | 6 轮 session 88%（被第 1 轮 75% 拉低） |
| **全量** | 所有 session 全部调用累加 | P3 标题、加权行、高亮横带；P2 尺子④ | 80% |

**两层权重**：每轮、每 session 的数都已按业务 47 / 28 / 25 加权（第一层）；"全量"= 再按实测 session 长度分布加权（第二层）。之前叫"全业务加权"容易被理解成只有第一层，v4.2 起统一叫**全量加权**。

## 0. 调用链与两个必算口径

| 业务 | 占比 | 消息流 | 模型调用 | 首调必算（n≥2） | 第二次调用 |
| --- | ---: | --- | ---: | ---: | ---: |
| 问答 | 47% | Δ+U → 伪造 A 0.2 / T 检索 10 → **调①** answer | 1 | 3.85 + 10.2 = **14.05** | — |
| 任务 | 25% | Δ+U → 伪造 A 0.2 / T skill 5 → **调①** tool call 0.2 → T 工具 2.5 → **调②** answer | 2 | 3.85 + 5.2 = **9.05** | 2.7 |
| 闲聊 | 28% | Δ+U → **调①** answer | 1 | **3.85** | — |

- **首调必算** = 动态 3.5 + query 0.1 + 上轮 answer 0.25 = **3.85K**（闲聊基准，页面显示 3.9K）+ 当轮业务必带（伪造 A/T：问答 10.2 / 任务 5.2）。决定 **TTFT**。业务必带两边相同、预热不覆盖。
- **整轮实算 T(n≥2)** = 业务加权（14.05 × .47 + 9.05 × .25 + 3.85 × .28）+ 任务第二次调用 2.7 × .25 = **10.6K**。决定**成本**。
- 沉淀速率 α（当前方案下每 Q 进 UAT、下一 Q 被整段白算）= .47 × 10.55 + .28 × 0.35 + .25 × 8.25 = **7.1K/轮**。当前方案动态在 System Prompt 内不沉淀；目标方案动态留在 U 里，输入每 Q 多 3.5K，已计入命中率分母。

### 3b. 首调 TTFT 预估（v4.2 起并入左列逐轮账表）

TTFT ≈ 首调实算 × 46 ms/K（参考实测 14K prefill ≈ 640 ms）。表按闲聊基准；预热后统一 170 ms（动态 + query ≈3.6K ≈165 ms + 预热损耗）。

| --- | ---: | ---: | ---: |

| Q2 | 22.4K · 1.0 s | 3.9K · 180 ms | 170 ms |
| Q6 | 50.8K · 2.3 s | 3.9K · 180 ms | 170 ms |
| Q12 | 93.6K · 4.3 s | 3.9K · 180 ms | 170 ms |

**当轮业务必带、两边相同、预热不覆盖**：问答 +伪造 A/T 检索 10.2K ≈ +470 ms，任务 +skill 5.2K ≈ +240 ms。

**预热**：会话创建时 prefill 会话级 + 历史（5.5K）；每轮开口前（ASR 阶段）再灌上轮 answer。收益 / 代价（参考实测）：14K 一次 640 ms → 6K 预热 320 + 8K 实时 380 ms，感知 −40%；总算力 +10%；需 TTL 保住预热到开口之间的缓存。只改 TTFT，不改账。

## 5. 结论（P3 四条）

1. **session 数 17% / 算力 49%**（迷你横条）：2 轮以上的 session 只占 17%，却吃掉 49% 的算力，贡献 69% 的节省；越长省得越多，新架构上线后 session 变长、收益放大。
2. **3.9K**：会话级可提前算，首调时延与轮数脱钩。Q≥2 首调钉在 3.9K + 当轮检索 / skill；83% 的 session 只有 1 轮，预热后 TTFT ≈ 170 ms + 业务必带，是短 session 的主要时延收益。
3. **白算 → 0**：验收线；整轮必算 10.6K 与会话首调 5.5K 是剩下的成本：历史 4K 整段载入改摘要、available skills 3K 升会话级。命中率受必算拖累，加权 80%、长 session 90%+。
4. **效果不变**：动态下沉 U、随轮追加已上线，对当前对话效果影响不大（定性，暂无指标）；后两步只改顺序不改内容，不引入新的效果风险。

## 6. 口径边界（页脚已写）

1. −45%（全量，实测 session 分布，第 10 轮起裁剪）/ −70%（P2 演示 4 轮 session）是**实算 token** 降幅；成本按计价折算 ≈0.79 × token（−35%），TTFT 由实测验证。
2. cache 命中率全量加权 62% → 80%（当前侧与实测约 60% 相符）；单轮 / session 累计 / 全量三个维度见 §00；实测对照：当前平均实算约 12K/调用，目标 7K，上线后以实测替换推演。**验收看白算归零，命中率按业界口径一并报。**
3. 前提是会话内缓存不被逐出。实测 21 次调用里 2 次 loop 全 miss 属引擎侧逐出 / 路由，需会话粘性 + TTL 配合并单独报警。
4. 第 10 轮起上下文裁剪（本会话史累积封顶 9 轮）；10 轮+ 按 12 轮计；日口径均 2.52 轮只在 P1 提一句，不作为任何口径的上限。
5. TTFT 按 46 ms/K 线性折算、预热后统一 170 ms，待 E6 实测替换。
6. 未计入：available skills 升会话级、动态"只带变化"、检索 / 工具结果精简可再压必算，是下一步。上线后由日报（引擎 `cached_tokens` + 应用边界埋点）替换推演。
