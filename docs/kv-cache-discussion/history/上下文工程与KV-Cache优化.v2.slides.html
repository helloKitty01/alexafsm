02现状架构与四个问题

现状四层结构（从前到后）

L0 产品级 system / agent 关键原则 + 工具全集　稳定 ✓
L1 用户级 固定加载的用户信息，与 query 无强相关，更新覆盖多轮　低频 ✓
L2 query级 skill search 检索的 top-k description（正文经 skill load 获取）+ query 相关知识 / 用户信息　每 query 重写 ✗
L3 loop级 UAT 消息流；按轮数（10 轮）滑窗裁剪，T（tool result）另行高频裁剪　✗

skill 库几百个，全量 description 放不下 → 按 query 做 skill search，结果注入 L2 槽位。

两个重写点：L2（query 切换时） + 滑窗裁剪（长对话每轮），再叠加驻留竞争

①　query 切换点全量 miss

L2 重写 → 失效 = |L2| + |UAT 全部历史|，随轮数线性增长。loop 内后续迭代可命中，损失集中在每个新 query 的首轮。

②　10 轮滑窗裁剪 = 长对话阶段每轮全量 miss

聊过 10 轮后每新一轮都裁掉最旧一轮，前缀头部每轮变化；T 体积大（skill 正文）被单独高频裁剪，进一步打碎前缀。长对话阶段比①更严重。

③　相关性绑定丢失 + 历史证据被覆盖

L2 单例槽位与 query 无显式对应；每轮覆盖式更新，第 N 轮依赖第 N-2 轮检索结果时证据已丢，去重无从谈起。

④　驻留竞争（eviction）

自建集群缓存容量有限，会被全网用户流量逐出——前缀不变 ≠ 命中。排布问题与驻留问题需分开度量、分开治理（详见 P6）。

03目标方案：取消 L2 槽位，query 级内容下沉进消息流

目标排布（L0 → L1 → UAT 流，全程 append-only）

L0 产品级 system 关键原则 + 工具全集（含 search_skill / load_skill），全网共享、天然常驻
L1 用户级 会话开始加载后冻结；中途更新攒批执行（低频，代价可接受）
UAT 流 query 级内容随各轮消息渐进进入，与 query 显式绑定——只追加，不修改

原 L2 三类内容的去向：知识 / 用户信息 → 随当轮 user message 注入；skill description → 两个迁移方案见 P4（load 机制不变）；环境上下文 → 增量随消息注入。

效果：每轮前缀 = 上一轮的严格超集

无任何区域被原位重写，排布性 miss 归零，只为当轮新增内容付 prefill 成本。

相关性与历史同时修复

  • 证据与 query 物理相邻、显式绑定
  • 每轮 query 和证据一起留在时间线里，可查可审计
  • 旧条目历史可见 → 条目级 ID 去重得以成立

前缀瘦身本身就是缓存策略

驻留竞争下 miss 无法根除，而 miss 的重建成本正比于前缀长度——按长度控制上下文总长（见 P5）同时服务两个目标。

核心原则：变化频率从前到后单调递增，重写区绝不排在追加区之前

04渐进式加载：被动注入 + skill search 迁移的两个方案

通道一 · 被动注入（系统检索，随当轮 user message）

<turn_context>
  <env>首轮全量快照，后续只注入相对上轮的增量</env>
  <retrieved>仅未注入过的条目（ID 去重，固定排序）</retrieved>
  <skills>方案 A：skill search 的 top-k description</skills>
</turn_context>
<query>用户原文，永远放在消息最后</query>
  • 序列化完全确定性：标签顺序、排序规则固定，空块省略
  • 会话级状态仅两个：env_snapshot、injected_ids
  • 一旦发出永不回改，重写统一攒到裁剪/压缩时刻

方案 A · search 结果随消息注入（改动最小）

  • 保留系统侧 skill search，top-k description 从 L2 槽位挪进当轮 user message（上方 <skills> 块）
  • 检索链路不动，只改注入位置；load 机制保持不变

方案 B · search 工具化（更彻底）

assistant: search_skill("部署发布")
tool:      [top-k description]
assistant: load_skill("deploy")
tool:      [skill 正文]
  • 模型自主决定检索时机与关键词，结果以 tool result 追加，不依赖 L0 放索引
  • 多步任务中可按阶段多次检索，比"query 切换时检索一次"更贴合需要
A 可先行落地拿到缓存收益，B 作为演进方向；两者不互斥，可 A → B 平滑过渡

05裁剪改造：按轮数滑窗 → 按长度双水位

现状（反模式）

  • UAT 按轮数（10 轮）滑窗：聊过 10 轮后每新一轮裁最旧一轮 = 每轮重写前缀 = 每轮全量 miss
  • T（tool result）单独高频裁剪，skill 正文 token 大，裁剪更频繁，前缀被反复打碎

目标：按 token 长度、双水位、攒批

  • 按长度触发：达到 ~80% 容量才裁，与轮数解耦（轮数不反映真实占用，skill 大 T 尤其如此）
  • 一次多裁：直接裁到 ~40% 低水位，避免"裁一点→又满→再裁"的每轮抖动
  • 攒批：T 的裁剪不再单独执行，与 UAT 裁剪合并到同一时刻，一次 miss 付清所有账
  • 分代冻结：裁剪/摘要产物写入后不再改动，两次裁剪之间全部轮次命中

从远到近分级保真（可恢复优先于有损丢弃）

内容裁剪处理恢复方式
已 load 的 skill 正文退化为"名称+已加载标记"re-load
retrieved 正文退化为 ID 指针按 ID 重拉
env 旧增量丢弃，摘要给当前快照无需恢复
大 tool result落盘，留路径 + 摘要重新读取
远端对话结构化摘要（目标/结论/待办）—（有损）
近端 K 轮原文保留—

skill 正文和检索条目是最大的 token 占用，也恰好是最容易指针化恢复的内容——优先指针化，少做有损摘要。

裁剪的真正代价是信息丢失而非那一次 prefill——重心放在可恢复指针与摘要保真上

06缓存驻留：eviction 治理（自建集群）

问题模型

  • 实际命中率 = 排布正确性 × 驻留概率：排布做对了，缓存仍可能被全网用户流量按 LRU 逐出
  • 两类 miss 成因不同：排布性 miss（前缀被改写，可根除）vs 驻留性 miss（容量竞争，只能缓解）
  • 度量上要拆开：同会话相邻请求间隔短仍 miss → 排布问题；间隔长后 miss → 驻留问题
先根除排布性 miss（P3–P5），驻留治理才有意义——否则每 query 都在重建，驻留无从谈起

降低被逐出的概率

  • 会话亲和路由：同一会话固定路由到同一推理实例，避免跨实例必然 miss
  • L0 公共前缀天然常驻：全网所有用户共享同一 L0，是集群里最热的条目，几乎不会被逐出——L0 越长收益越大
  • 缓存分层扩容：HBM 之外用 CPU 内存 / 本地盘做 KV offload（vLLM / SGLang / LMCache 类方案），扩大可驻留总量
  • loop 内迭代间隔短，天然处于驻留窗口内；危险区在用户两次 query 之间的长间隔

降低被逐出后的损失

  • 前缀瘦身：重建成本正比于前缀长度，P5 的按长度双水位直接控制损失上限
  • 指针化内容（skill / retrieved）本身不占前缀，被逐出后无需重建
