① 该命中 / 命中量
cached_tokens = d
前缀逐 token 一致的深度。目标态:产品级全网命中;会话级首调后命中;query / loop 只命中已写入的历史。实测:当前 d 恒停在 SP·固定末(24.6 / 26.6 / 29.6K)。
② 命中率 = 被 cache 的比例
命中率 = d / 输入
健康度,分母漂、折算不成钱。实测:当前 21 次调用加权 65.5%(首调 53–58%);前缀稳定的 loop 已达 95–99%。目标随 Q 上升、当前从 Q2 被压住。
③ 推理长度 = miss
miss = 输入 − d = 白算 + 新增
真实 prefill,账单和 TTFT 跟它走。实测:当前首调后 miss 里白算占 90–99%;前缀一稳定,miss 就只剩新增(附录 A 已验证)。
④ 验收
白算 → 0(裕量 1 块)
白算 = miss − 新增,新增 ≈ 本次输入 − 上次输入。loop 白算恒为 0 是报警线——当前任务 / 问答会话各有 1 次 loop 全 miss 20–21K(P4 / P5),这类调用都该被自动抓出来(P8)。

为什么能预热

目标态会话首调 miss = 会话级 ~1K + 历史 10 轮 0.1–10.9K + U1 + Δ动态(P4–P6 目标列 Q1 行)。其中会话级与历史在用户开口之前就已确定,却要等到首调才进 prefill、直接计入首 token 等待——这部分可以提前算。

两次 prefill 各覆盖什么

  • ① 覆盖会话首调:首调 prefill 从 3–14K 降到 U1 + Δ动态 ≈ 2K;历史越长收益越大(问答会话历史 10.7K → 首调 ~14K → ~2K)。
  • ② 覆盖 Q2 起的首调:ASR 期间把上轮 answer 灌进缓存,Q 首调只剩 U + Δ;同时起"保活"作用,降低 P5 那种 loop 全 miss(逐出)的概率。
  • 不进账本:预热的 prefill 仍要算一次,总算力不变,只是从用户等待路径挪到后台;P4–P7 的 miss / 节省口径都按"无预热"计。
