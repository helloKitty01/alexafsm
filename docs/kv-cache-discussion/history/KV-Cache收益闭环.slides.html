口径:实际推理量 = 输入 − 命中(引擎逐请求实报,非估算)

实际推理量 = 必要推理量 + 白算量
必要: 本轮首次出现的 token —— 新 query、
      注入增量、工具结果        ≈ 2K/请求,消不掉
白算: 曾经算过、因前缀被改写而重算    ≈10K,可根除

白算从哪来:每换一个问题,历史全部重算一遍

  • query级槽位(检索 skill/知识)每个新 query 原位重写,缓存从该点断裂;
  • 其后的 Tools 块 + UAT 全部对话历史被连带重新计算,且随轮数线性增长(右图 17K→44K);
  • loop 内迭代是追加式,本来就命中——损失集中在 query 切换点。

怎么统计:两个计数器 + 一个验收等式(不依赖估算)

计数器① 引擎逐请求实报 cached_tokens(现成能力)
        → 实际推理量 = 输入 − 命中
计数器② 应用侧记账本轮新增消息的 token 数
        → 必要推理量(新query/注入/工具结果)
验收等式 白算量 = 实际 − 必要  → 改造达标 = 趋近 0
        (允许压缩事件摊销残量 <1K/请求)

闭环四步(给出可验证的承诺)

1测基线:接通计数器①现网跑一周——验证 12K,并确认 miss 集中在 query 切换点(与左侧账目形状一致,归因即成立)。
2灰度 A/B:改造灰度期,实验组 vs 对照组直接比"每请求 / 每会话实际推理量",同期同流量,不受业务波动干扰。
3折算收益:节省 GPU 算力 = (基线 − 改造后) × 请求量 × 单位 prefill 成本;体现为同硬件更高并发 + TTFT 下降。
4防回退:"白算量"长期上看板,loop 内白算应恒为 0,超阈值即回归报警。
结论:改造上下文排布后,每请求实际推理量 12K → ~3K(−75%),会话越长省得越多;统计上引擎实报命中、应用侧记账新增,两数相减即浪费,灰度 A/B 直接验证。
