# 11 收益闭环:实际推理量省了多少、怎么统计(汇报版)

> 本篇是给领导闭环用的版本。前提约定:**不考虑驻留问题**
> ——默认一段时间内,只要被缓存过就不会失效。这个假设下,
> 每次请求"实际需要推理的 token"只由两件事决定:
> ① 哪些是真正的新内容(必须算);② 哪些是被前缀改写连累的重算(白算)。
> 全部结论围绕一个核心量:**实际推理量 = 每请求输入 − 命中 = miss 量**,
> 它就是 prefill 阶段真实消耗 GPU 的 token 数,引擎逐请求实报,不是估算。

---

## 1. 各层模块长度盘点(算账的输入)

| 模块 | 长度 | 性质 | 来源 |
| --- | --- | --- | --- |
| L0:system 主体 + skill 索引 | ~8K | 产品级静态,全网相同 | 07 算例参数 |
| Tools 块(工具全集 schema) | ~3K(**待实测**) | 静态,但现状排在 L2 之后被连带失效 | 假设值 |
| L1:用户画像/会话环境 | ~2K | 会话级,会话内基本冻结 | 07 算例参数 |
| L2 槽位:检索 skill 描述 + 知识 | ~4K(**待实测**) | **每 query 原位重写**(现状病灶) | 假设值 |
| 每轮 user(query + 注入) | ~1–2K | 每 query 新增一次 | 07/08 |
| 每次 loop 迭代(A + T) | ~2K | 每次迭代新增一次 | 07/08 |
| 会话总上下文 | ~60K | — | 08 现网实测 |
| 平均每请求输入 | 37K | — | 08 现网实测 |

**敏感性说明**:Tools 与 L2 的长度是假设值,但它们只影响
query 切换点 miss 里的固定项(合计 ~7K);miss 的大头是
**UAT 全史重算,随轮数线性增长**(第 5 个 query 时已 ~36K)。
所以下文"节省 70%+"的结论对这两个假设不敏感,
且这两个数导出一次渲染后的 token 序列即可锁定,建议列为埋点前置动作。

## 2. 核心口径:实际推理量 = 输入 − 命中

```text
每请求:  实际推理量 = P − H          ← 引擎逐请求实报(cached_tokens)
无驻留假设下:
        实际推理量 = 必要推理量 + 白算量
        必要推理量 = 本轮首次出现的 token(新 query、注入增量、工具结果)
        白算量     = 曾经算过、因前缀被改写而重算的 token(可根除)
```

**给领导的一句话**:现网每请求实际推理 12K token,其中约 2K 是必要的、
约 10K 是白算的;改造的全部目标就是把这 10K 拿掉。

## 3. 多轮对话完整算例:逐请求账目

典型会话:**5 个 query,每个 query 带 4 次 loop 迭代,共 20 次模型请求**。
参数用第 1 节的盘点值(每 query 结束 UAT 增长 ~9K,
第 5 个 query 结束总上下文 ≈ 62K,与现网 ~60K 会话规模吻合)。

### 现状(L2 每 query 重写,缓存从 L2 断裂)

| 请求 | 实际推理量(miss) | 构成 |
| --- | --- | --- |
| q1 首请求 | 10K | L1 2 + L2 4 + Tools 3 + U 1(L0 8K 全网共享,命中) |
| q1 迭代×3 | 2K × 3 | loop 内追加式,天然命中,只算增量 |
| q2 首请求 | **17K** | L2 4 + Tools 3 + **UAT 全史 9** + U 1 |
| q3 首请求 | **26K** | L2 4 + Tools 3 + **UAT 全史 18** + U 1 |
| q4 首请求 | **35K** | L2 4 + Tools 3 + **UAT 全史 27** + U 1 |
| q5 首请求 | **44K** | L2 4 + Tools 3 + **UAT 全史 36** + U 1 |
| 各 query 迭代×3 | 2K × 12 | 同上 |
| **会话合计** | **162K** | 平均 8.1K/请求 |

query 切换点的 miss 随轮数线性涨(17→26→35→44K),
**每换一个问题,就把整段历史重新算一遍**——这就是钱花在哪了。

### 目标态(L2 下沉,前缀 append-only)

| 请求 | 实际推理量(miss) | 构成 |
| --- | --- | --- |
| q1 首请求 | 7K | L1 2 + Tools 3 + U 2(query+注入;L0 命中) |
| q2–q5 首请求 | **2K × 4** | 只算新 query + 注入增量,**历史全命中** |
| 全部迭代×15 | 2K × 15 | 不变(本来就命中) |
| **会话合计** | **45K** | 平均 2.3K/请求 |

### 三级台阶(同一会话的三种世界)

| 方案 | 会话 prefill 总量 | 相对上一级 | 说明 |
| --- | --- | --- | --- |
| 无缓存 | ~780K | — | 每次请求全量重算(37K 均值 × 20 次的量级) |
| 现状(有缓存,排布不佳) | 162K | **-79%** | 缓存本身的收益,已经拿到 |
| 目标(排布改造后) | 45K | **-72%** | 本次改造的增量收益 |

换个更直观的说法:**必要推理量就是 45K**(每个新 token 只算一次)。
现状实际算了 162K,即 **3.6 倍**——每花 3.6 份 prefill 算力,
只有 1 份是必要的;改造后 1 份就是 1 份。

## 4. 与现网基线互相验证

算例与现网实测互相印证,给领导的数用现网口径:

| 指标 | 现网实测/估算(08) | 本篇算例 | 一致性 |
| --- | --- | --- | --- |
| 每请求实际推理量(现状) | 12K | 8.1K | 同量级;现网更高因会话更长、已进滑窗裁剪阶段(见 §5) |
| 每请求实际推理量(目标) | ~3K | 2.3K | 一致(08 额外含压缩摊销 + thinking 剔除 ~1K) |
| 命中率 | 66% → 92% | — | — |
| **prefill 计算量** | **-75%** | **-72%** | 两条独立路径得到同一结论 |
| 等效输入成本 | 14.5K → 6.4K(**-56%**) | — | 命中按 0.1× 计价折算 |

**汇报建议**:对领导报 **-75%(prefill 计算量,算力/延迟口径)** 和
**-56%(等效成本口径)** 两个数;前者对集群容量和 TTFT,后者对账单。

## 5. 长对话阶段:现状更糟,差距拉大

上面 5-query 算例还没触发滑窗裁剪(现状按 10 轮滑窗)。
超过 10 个 query 后,现状**每轮**都裁掉最旧一轮、前缀头部每轮变化,
每个请求都接近全量 miss(~37K/请求);而目标态用双水位 + 分代冻结,
压缩几十轮才发生一次、单次 ~13–15K,摊销后 <1K/请求(07 算例)。
即:**会话越长,改造收益越大**——短会话省 ~72%,
长会话阶段差距拉到 10 倍以上(07:同区间等效成本 900K vs 220K)。

## 6. 怎么统计:两个计数器 + 一个验收等式

不考虑驻留后,统计极简,不需要复杂机制:

```text
计数器①(引擎侧,现成能力):每请求返回 cached_tokens
    → 实际推理量 = prompt_tokens − cached_tokens
    这是引擎逐请求实报的真实值,不是估算、不是抽样。

计数器②(应用侧,消息记账):本次请求相比上次新增了哪些消息,
    tokenize 计数 → 必要推理量(新 query / 注入增量 / 工具结果)

验收等式:实际推理量 → 必要推理量
    白算量 = 实际推理量 − 必要推理量,改造达标的标志是白算量趋近 0
    (允许压缩事件的摊销残量 <1K/请求)。
```

### 闭环路径(给领导的验证承诺)

1. **先测基线**:接通计数器①,现网跑一周,拿到真实的
   每请求实际推理量分布(验证 12K,并按 query 切换点/loop 内拆开
   ——预期看到 miss 集中在 query 切换点,即本篇算例的形状)。
2. **灰度 A/B**:排布改造灰度期间,实验组 vs 对照组直接对比
   "每请求实际推理量"与"每会话推理总量",这两个数不受
   业务形态波动干扰(同期同流量)。
3. **成本折算**:prefill GPU 消耗 ∝ 实际推理量,
   节省算力 = (基线 − 改造后) × 请求量 × 单位 prefill 成本;
   自建集群下体现为同硬件承载更多并发 + TTFT 下降。
4. **防回退**:白算量上看板长期跟踪,>阈值报警
   (loop 内白算量应恒为 0,一旦出现即回归事故)。

### 与 10 的关系

10 是完整度量体系(含驻留拆分的阶段③);本篇的两个计数器
即 10 的阶段①+②。若实测发现白算量降不到 0 且集中在
长间隔请求上,说明驻留假设不成立,再启用阶段③(前缀哈希拆分)即可,
统计框架不用推倒重来。

## 7. 三十秒汇报话术

> 模型每次回答,都要把整段对话从头"读"一遍(prefill),这是 agent
> 推理成本的大头。缓存能让读过的部分几乎免费,但我们现在的上下文拼装
> 方式,每换一个问题就把缓存打碎:现网每请求 37K 输入里要实际重算 12K,
> 其中约 10K 是重复计算。改造上下文排布后,每请求只算真正新增的 ~3K,
> **prefill 计算量降 75%,等效成本降 56%,会话越长省得越多**。
> 统计上不靠估算:推理引擎逐请求实报命中量,应用侧记账新增量,
> 两数相减就是浪费,灰度 A/B 直接验证。
