# 08 量化收益评估（基于现网基线）

## 现网基线（已确认，2026-08）

- 会话上下文规模：~60K token
- 平均每请求输入：37K token
- 平均命中：25K token，miss：12K token
- **命中率 ≈ 66%**

## 成本模型

设缓存命中 token 计价为全价的 0.1×（prefill 复用），
每请求等效输入成本 = 命中量 × 0.1 + miss 量 × 1。

- 现状：25 × 0.1 + 12 = **14.5K 等效 token / 请求**

## 目标态估算

排布性 miss 消除后（L2 下沉 + 裁剪改造 + 分代冻结），每请求 miss 构成：

| miss 来源 | 估算量 |
| --- | --- |
| 当轮新增（U 注入 + 上轮 A/T 增量） | ~2K |
| 压缩事件摊销（~30 轮一次，一次 ~15–25K 局部重建） | ~0.5–0.8K |
| thinking 尾部 reasoning 剔除（模板内建） | ~0.3–0.5K |
| **合计** | **~3K** |

- 目标命中率：34K / 37K ≈ **92%**
- 目标等效成本：34 × 0.1 + 3 = **6.4K 等效 token / 请求**

## 收益汇总

| 指标 | 现状 | 目标 | 变化 |
| --- | --- | --- | --- |
| 命中率 | 66% | ~92% | +26pp |
| miss 量 / 请求 | 12K | ~3K | **-75%** |
| 等效输入成本 / 请求 | 14.5K | 6.4K | **-56%** |
| prefill 计算量 / 请求 | 12K | ~3K | **-75%**（TTFT、吞吐同步改善） |

prefill 计算量下降 75% 的两个衍生收益：

1. **TTFT**：首 token 延迟主要由 prefill 决定，miss 量即需实时计算的
   prefill 量，长对话场景改善最明显；
2. **集群吞吐**：prefill 占用的 GPU 算力被释放，同硬件可承载更多并发
   （具体折算取决于集群 prefill/decode 算力配比）。

## 口径说明：等效 token 与结构上限

**等效 token**：把命中与 miss 折算到同一把尺子——命中按 0.1、miss 按 1。
现状 25×0.1+12=14.5K，目标 34×0.1+3=6.4K。对自建集群，
-75%（prefill 计算量）是算力/延迟视角（更物理），
-56%（等效成本）是成本视角；对领导讲成本、对集群团队谈容量。

**命中率的结构上限**：每轮必然有首次出现的 token（query、工具结果、
检索/环境增量），第一次见必 miss——但**每个新 token 只 miss 一次**，
下一轮起即成为前缀开始命中。因此：

    结构上限 ≈ 1 −（每轮新增 token / 平均输入 token）
             ≈ 1 − 2K/37K ≈ 94.6%（再扣低频事件摊销 → 可达 ~92%）

管理框架：命中率 = 结构上限 −（排布性 miss + 驻留性 miss）。
结构上限由业务形态决定（只能靠"少进上下文"抬高，有天花板）；
**执行落差理论上可打到零**，是优化的全部战场（现状 66% vs 上限
94.6%，落差 28.6 个点）。看板可直接报"命中率 / 结构上限"达成率，
不受业务形态波动干扰。

边界情况：跨会话重复内容（如同一 skill 正文）因前缀缓存要求从头
逐 token 一致，中段相同不命中，实践上不指望；首轮请求除全网共享的
L0+Tools 公共前缀外全部 miss，故"会话内命中率"与"含首轮整体命中率"
应分开统计。

## 敏感性与校正

- 若目标态 miss 实际为 4K（新增内容偏大），等效成本 7.3K，仍 **-50%**；
  若为 2.5K，等效成本 5.9K，**-59%**。结论对 miss 估值不敏感。
- **最大不确定项**：现网 34% miss 中排布性与驻留性的占比未拆分。
  若驻留性 miss 占比高，则 P3–P5（排布改造）收益上限下调、
  P6（驻留治理）承担更多——这正是落地路径①（度量拆分）先行的原因。
- 缓存计价 0.1× 为行业常见折算；自建集群下对应的是 prefill 算力节省，
  实际折算比例按集群成本模型校正。
