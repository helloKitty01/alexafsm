# 工具参数变量解析机制方案（Variable Resolution）

> 适用场景：Agent 框架（openClaw）中，工具参数依赖"确定性可查"的标识符（如应用 bundleName），
> 但工具本身不可修改、也无法逐个改造所有相关工具。

---

## 一、背景与问题

以"禁用抖音的麦克风权限"为例，工具签名为 `forbidPermission(bundleName, permission)`：

- 大模型不知道"抖音"对应的 bundleName，必须先调用 `getAllInstalledApps` 查询，再调用目标工具，**每次都要两次 loop**，浪费 token 和延迟；
- 若模型凭记忆直接填写 bundleName，存在**幻觉风险**（如把抖音写成 `com.douyin.app`）；
- 约束条件：**工具不可修改**，且带 `bundleName` 参数的工具很多，**无法逐个改造**。

## 二、目标

1. 正常路径一次 loop 完成工具调用；
2. 工具零改动，所有同类工具自动受益；
3. 结构性消除标识符幻觉：模型只表达"哪个应用"，真实值永远来自查表。

## 三、核心设计：变量语法 + 框架层求值

### 3.1 变量语法

```
${<namespace>.<entity>.<attribute>}
```

- 现阶段实现 `app` 命名空间：`${app.抖音.bundleName}`
- 命名空间通过 Resolver 注册表扩展，未来可加 `contact`、`device`、`result` 等
- 转义规则：需要字面 `${` 时写 `$${`

### 3.2 核心组件

**（1）Resolver 注册表**

```python
RESOLVERS = {"app": AppResolver()}   # 新命名空间只需注册新 Resolver

class AppResolver:
    def resolve(self, entity: str, attr: str) -> str | None:
        canonical = self.alias_table.get(normalize(entity), entity)  # 同义词归一
        return self.static_table.get(canonical, {}).get(attr)        # 查静态表
```

**（2）两张表**

| 表 | 结构 | 说明 |
|---|---|---|
| 静态表 | `{规范名: {bundleName: ..., ...}}` | 如 `{"抖音": {"bundleName": "com.ss.android.ugc.aweme"}}`，只放高频应用 |
| 同义词表 | `{别名: 规范名}` | 如 `{"douyin": "抖音", "Douyin": "抖音"}`，查表前先 normalize（去空格、英文小写化） |

**（3）Pre-call 拦截器**（挂在工具分发的统一入口，工具无感知）

```python
VAR = re.compile(r"\$\{([^}]+)\}")

def pre_call_hook(tool_name, args):
    unresolved = []
    def walk(v):
        if isinstance(v, str):
            def repl(m):
                ns, entity, attr = m.group(1).split(".", 2)
                r = RESOLVERS.get(ns)
                val = r.resolve(entity, attr) if r else None
                if val is None:
                    unresolved.append(m.group(0))
                    return m.group(0)
                return val
            return VAR.sub(repl, v)
        if isinstance(v, dict):  return {k: walk(x) for k, x in v.items()}
        if isinstance(v, list):  return [walk(x) for x in v]
        return v

    resolved_args = walk(args)
    if unresolved:
        raise VariableResolutionError(unresolved)   # 短路，不把 ${...} 字面量传给工具
    return resolved_args
```

## 四、兜底流程（解析失败时）

解析失败**不静默、不透传原文**，拦截器短路后框架自动执行两级兜底：

1. **框架自愈（不占模型 loop）**：框架自己调用 `getAllInstalledApps`，用返回结果增量更新静态表缓存；
2. **重试解析**：
   - 命中 → 直接继续执行原工具调用，模型无感知，仍是一次 loop；
   - 仍未命中（应用未安装或名字错误）→ 把已安装应用列表连同错误信息作为 tool result 返回给模型：
     > 变量 `${app.XX.bundleName}` 解析失败，未找到该应用。已安装应用列表如下：[...]，请确认应用名后重试。

只有最后一种情况需要第二次 loop。

## 五、提示词分层：SystemPrompt + Skill

两层都写，职责不同，不冲突：

**SystemPrompt（通用机制，一次写死）：**

> 工具参数支持变量语法 `${namespace.entity.attribute}`，系统会在工具执行前自动求值。
> 当前支持的命名空间：`app`——引用已安装应用的属性，如 `${app.抖音.bundleName}`。
> 凡是可用变量表达的参数，优先使用变量而不是直接填写具体值，禁止凭记忆编造 bundleName 等标识符。

**Skill（具体场景用法 + few-shot 示例）：**

> 所有权限管理类工具的 `bundleName` 参数直接填 `${app.应用名.bundleName}`，无需先调用 getAllInstalledApps。
> 示例：禁用抖音麦克风 → `forbidPermission(bundleName="${app.抖音.bundleName}", permission="麦克风")`

- SystemPrompt 保证机制在所有 skill 下可用，并约束模型"不许编造标识符"；
- Skill 把机制落到具体工具参数上，用示例提高遵循度。

## 六、执行时序总结

```
正常路径（1 次 loop）：
模型输出 forbidPermission(${app.抖音.bundleName}, 麦克风)
  → 拦截器查同义词表+静态表 → 替换为真实值 → 执行工具 → 返回结果

自愈路径（仍 1 次 loop）：
解析失败 → 框架调 getAllInstalledApps → 更新表 → 重试解析成功 → 执行工具

兜底路径（2 次 loop，仅应用不存在/名字错误时）：
重试仍失败 → 把已安装列表+错误返回模型 → 模型纠正应用名重试
```

## 七、实现注意点

| 项 | 说明 |
|---|---|
| 替换后校验 | 求值结果要过一遍工具的参数 schema，避免类型不匹配静默出错 |
| 表的时效性 | 自愈路径更新的缓存建议带 session 级生命周期；静态表只放高频应用，长尾靠自愈路径补 |
| 日志 | 每次变量替换记录"原文 → 求值结果"，排查"权限禁错了应用"类问题的关键证据 |
| 安全性 | Resolver 只做只读查表，求值过程绝不执行任意表达式，防止提示注入通过变量语法扩大攻击面 |
| 启发式兜底（可选） | 若模型忘了语法直接传"抖音"，可用"值不像反域名格式则查表"的启发式兜底；显式变量优先 |

## 八、扩展方向

同一套 `${...}` 求值器未来可支持引用前序工具的输出，如
`${result.getAllInstalledApps[0].bundleName}`，让模型在一次规划里写出带数据依赖的多个工具调用，
进一步压缩 loop 次数（plan-and-execute 类框架的标准做法）。

---

**方案不变量：模型永远只表达"哪个应用"，真实标识符永远来自查表——幻觉被结构性消除，loop 数量在绝大多数情况下压到一次。**
