# 01 三个方向的判断：自演进 / 全模态 / 与 OS 深度结合

> 讨论起点：手机 Agent 的下一步是什么？候选方向有三个——自演进、全模态、与 OS 深度结合。
> 本篇给出判断，并结合 2026 年 9 月的业界状态（Muse、work agent、code agent、Android / iOS / 豆包）说明理由。
> 结论在 [02](./02-八个议题与Harness迭代.md) 被进一步展开为八个议题。

## 1. 总判断

三个方向不在同一层，不必三选一：

| 方向 | 在体系中的位置 | 判断 |
| --- | --- | --- |
| 与 OS 深度结合 | 地基 | 决定 Agent 能不能可靠办成事、能不能在后台一直在线。终端厂商必须做，也是差异化所在 |
| 自演进 | 长期壁垒 | 只有「记忆 + 技能积累」这一层现在值得做；端侧改权重三年内不是主线 |
| 全模态 / 全双工 | 交互层放大器 | 改变体验，不抬高能力上限；但在手机上是 OS 厂商的独占能力，对应的用户需求与 Muse 不同 |

比这三者更根本的一条：**从「你说我做」走向「长期委托」**。手机 Agent 的代际跃迁不是某一项能力，而是使用范式的变化——交代一件事 → Agent 长期负责 → 在对的时间、以对的方式回来找你。这个范式要成立，恰好需要三者各出一部分，再加一件三者都不覆盖的事：信任机制。

另一个视角：手机 Agent 眼下缺的不是能力，而是 code agent 已经拥有的那套「工作环境」。Code agent 能在 2025–2026 年先跑出来，靠的不只是模型强，而是它碰巧活在一个成功可以验证（测试、diff）、出错可以回滚（git）、记忆就是文件（`AGENTS.md`）、用户能看懂产出的环境里。手机 Agent 这四样一样都没有。**下一步是给生活类任务造出 git + 测试 + 沙箱的等价物**，三个方向都应该围绕这件事排优先级。

## 2. 业界状态（核对日期 2026-09-24）

### 2.1 OS 结合已经分成三条路线，冲突点不在技术

| 路线 | 代表 | 做法 | 现状 |
| --- | --- | --- | --- |
| 结构化接口 | Apple iOS 27 Siri AI | App Intents / App Schemas 声明内容与动作；View Annotations 让 Siri 解析屏幕上「这个」「第三个」 | 可靠，覆盖面取决于 App 开发者是否接入 |
| 两条腿 | Google Android | AppFunctions（端侧版 MCP，`EXECUTE_APP_FUNCTIONS` 权限基本只给 Gemini，2026-05 仍私测）+ 平台级 UI 自动化框架 | UI 自动化只在 Galaxy S26 / Pixel 10 上开放外卖、买菜、打车三类精选 App。Android Police 评价「笼子造好了，里面还是空的」 |
| 系统级 GUI | 豆包手机助手 | 系统签名拿 `INJECT_EVENTS`，虚拟屏注入触摸事件，用户照常用手机，Agent 后台操作 | 2026-09 消费者版落地努比亚机型；推出 SAEP 协议，第三方 App 声明允许 / 拒绝被自动化 |
| 系统级 Skill 化 + GUI 兜底 | 华为小艺（详见 [03](./03-小艺架构与HDC盘点.md)） | 系统应用全面 Skill 化（2100+ 能力）、A2A / MCP 接生态、HMAF 2.0 首次向开发者开放 GUI 操控 | 2026-07 起 GUI 已能操作淘宝 / 支付宝 / 拼多多，微信未接入 |

四条路线最后都撞上同一堵墙：**App 生态愿不愿意被 Agent 绕过**。Agent 替用户点完所有按钮，App 的流量、广告和交叉销售就没了。SAEP 本质上是一份谈判协议；网页端同样在上演：有大型零售站点直接屏蔽 Muse，Shopify 和 PayPal 则主动接入 Agent 结账。所以 OS 结合的下一步是**技术接口 + 利益分配协议**，而不只是开放更多 API。

### 2.2 Muse 的反直觉信号：最火的个人 Agent 不住在手机里

Meta Muse（2026-09-08 发布）的执行跑在云端 Secure VM + 浏览器里，入口是 App 和 WhatsApp，交互基本是文字。12 天约 280 万装机；同时在 RuntimeWire 同题实测里任务完成度垫底（细节见 [muse-insight/](../muse-insight/)）。两点结论：

- 普通用户买单的是**产品形态**：长期在线、可以委托、主动汇报、零运维。模态和 OS 深度都不是用户增长的前提。
- 装机成功和把事做对是两张成绩单。可靠性的差距要靠 OS 结合去补，Muse 补不了。

### 2.3 Code agent 已经把「实用的自演进」跑通

不是改模型权重，而是把成功轨迹提炼成 `SKILL.md`，配一个维护循环：合并重复、淘汰不用、坏了回滚（Hermes Agent 的 curator 机制及其在 Claude Code / Codex 上的移植）。CodeSkill（arXiv 2605.25430）用 RL 训练「技能库管理策略」，在 SWE-Bench 等基准上平均通过率 +9.69。它能成立，是因为有**可验证的执行反馈**（测试过没过）。

## 3. 分方向展开

### 3.1 与 OS 深度结合：瓶颈在执行，不在理解

现在手机 Agent 的主要短板不是「听不懂」，而是**执行不可靠**：靠截屏 + 模拟点击的 GUI 操作，超过十几步成功率断崖式下降；慢；被反自动化和界面改版打断。模型再强只能缓解，根治靠 OS 给 Agent 开放原语。

「深度」通常被理解成更高权限。真正稀缺的是三个 OS 原语，目前没有一家做全：

1. **先预览、再提交**：每个 App 动作先返回预览（订单详情、要发出的消息、要删的文件列表），提交是另一个独立调用。这是生活任务的 `git diff`；有了它，「停在付款前」才是系统保证，而不是指望模型自觉。
2. **授权放在模型之外**：授权卡由系统弹出，调用用系统签发的一次性凭证，模型拿不到真凭证，也按不到「允许」按钮。Muse 的 Sentinel 在云端做了这件事；手机上更适合做——生物识别、安全芯片、锁屏状态都是现成的硬件信任根。
3. **可回放的活动日志**：Agent 在后台干了什么，事后能看、能审计、能申诉。

做好这三样，App 厂商和监管才敢开放接口，用户才敢委托。

需要 OS 提供的完整原语清单：结构化动作接口（Intents / AppFunctions / MCP，GUI 只作兜底）、语义化 UI 树（比无障碍树更干净）、事件订阅总线、后台常驻与调度、按动作授权 + 事务 / 撤销、跨 App 的状态与记忆托管。

### 3.2 自演进：三层拆开，只有前两层现在能落地

| 层级 | 内容 | 可行性 |
| --- | --- | --- |
| L1 记忆 / 偏好 | 习惯、常用联系人、默认选项 | 现在就该做，基础能力 |
| L2 技能积累 | 成功轨迹沉淀为可复用流程或按 App 的操作手册；失败回退到探索 | **性价比最高的「演进」** |
| L3 端侧更新权重 | 按个人数据微调 | 远期，风险大 |

L3 难，关键不在算力，而在于**缺少可靠反馈信号**：手机上「用户没抱怨」不等于「任务成功」。反馈稀疏且有噪声，边学边改容易学偏，回归难发现。

手机比 code agent 更适合做 L2：App 流程高度重复、高度结构化；同一款 App 的同一个流程有几百万台设备在跑，可以做脱敏后的**群体学习**——A 用户摸索出的改签步骤成为所有人可用的技能，App 改版后几台设备先失败，系统自动修复并下发。这是云端 Agent 拿不到的数据飞轮。

自演进的新攻击面：**记忆和技能可能被投毒**（条件式注入可潜伏到后续某轮再触发，见 [agent-radar 2026-09-24](../agent-radar/2026-09-24.md)）。演进产物必须可审计、可回滚、用户能看见；技能应是显式可审查的产物，不是悄悄改掉的权重。

### 3.3 全模态 / 全双工：在手机上的价值是「补全上下文」和「陪着办事」

- 语音、视觉、屏幕理解融进一个实时模型，2026 年各家基本都有。有差异的是**全双工**和**环境感知**：持续看屏、听环境，知道用户此刻在干什么。
- Muse 和全双工助手对应不同需求：Muse 是「把事交出去」，全双工是「此刻陪我一起把事办了」——开车、做饭、走路、边看边问，是手机独有的高频现场。豆包很大程度押的是这个。
- **全双工在端侧是 OS 厂商的独占能力**：唤醒、音频管线、低功耗常听、barge-in 话权抢占、与来电和媒体的音频焦点仲裁，第三方 App 拿不到。这是差异化，不是入场券。
- **看屏不应只是截图**：OS 可以同时喂像素和语义树（iOS 27 View Annotations 的思路），指代消解和屏幕问答会甩开只能截图的方案。
- 模态是前台的事，不是后台的事。双脑设计保持：omni 模型负责听、说、看、指代、创建任务、代收澄清；凡超过数秒的工作一律降级为任务。不要让全模态模型扛 GUI 操控。
- 代价：打扰成本（技术上随时能插话、体验上极贵）、常开感知的隐私与功耗。

## 4. 优先级

1. **P0 信任基础设施**：授权在模型外、真凭证不进上下文、先预览再提交、活动日志可回放。同时解锁用户委托、App 开放、合规审查；手机硬件信任根是云端 Agent 抄不走的。
2. **P0 混合执行路由**：能走结构化接口就走；走不了在后台虚拟屏做 GUI；没有 App 或要开放网页的交给云沙箱。模型只表达「做什么」，路由层决定「怎么做」。
3. **P1 技能层自演进 + 群体学习**。
4. **P1 长期委托的产品形态**：任务比对话活得久，主动汇报有门槛（Goals 视图）。
5. **P2 全模态**：作为上下文捕获和关系表面按场景加。

## 5. 一个需要严肃对待的判断

「手机 Agent」这个品类可能会消解。赢家也许是一个住在云端、把手机当作节点之一的个人 Agent（Muse、OpenClaw 节点模式）。手机不可替代的不是「执行场所」，而是三样东西：**身份与授权的锚点、现场传感器（来电、位置、支付、相册）、端侧私密记忆**。OS 厂商最该抢的生态位是「所有 Agent 都必须经过的信任层和现场层」，而不是和云端 Agent 比谁更聪明。

## 6. 度量

单任务成功率榜单（AndroidWorld 一类）很快饱和。更有信息量的：

- 用户愿意打开哪几类授权、打开后又关掉的比例
- 长程任务（10 步以上）到达终态且可回放的比例
- 不可逆动作零误放行；注入后不外带
- 主动触达被接受的比例
- App 改版后技能自动修复的时长
- 全双工场景下的误插话率与 barge-in 时延
