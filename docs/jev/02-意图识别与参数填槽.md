# Jev 如何做意图识别与参数填槽

> 基于 2026-09-24 查阅的官方接口；示例是设计说明，未调用 API 验证。来源见[来源索引](./04-来源索引.md)。

## 1. 255 个选项究竟限制什么

官方明确：**单个 Choice 问题最多 255 个选项**。[S8]

- 上限按每道问题计算，不是全系统意图数量上限。
- `other`、`none`、`unspecified` 等自定义出口也占名额。
- 一次请求可包含多道题，但不能据此认为问题数量或计算量无限；仍受输入 token 与服务限制约束。
- 容量上限不是准确率保证。相似意图需要明确包含条件、排除条件和示例。

选项描述是自然语言判定标准。意图名可作为程序 ID，但问题 ID 本身不传给模型，因此 `instructions` 必须写完整。[S3][S8]

## 2. 意图和参数拆开，不做组合枚举

用户输入：

> 帮我把订单 A123 的收货电话改成 13800138000。

应拆成意图、修改字段、目标订单、新电话号码。不要把所有“意图 × 订单 × 字段 × 参数值”组合放进一个 Choice。

官方 function calling cookbook 将函数和封闭参数分别描述，再由程序组装调用；它并不意味着可以直接生成任意自由文本参数。[S9]

### 固定枚举参数

例如舱位、图表类型、时间粒度，用独立 Choice；布尔值可用 Noul。缺失参数应保留“未说明”，或另问用户是否明确给出。缺失必填参数进入补全流程，不能把最可能选项当成用户授权的值。

### 动态候选参数

例如“取消我昨天买的那双鞋”：程序先取当前用户的候选订单，提供 ID、商品、时间等描述，再由 Jev 选目标。候选可逐请求构造；读取哪个用户的记录及允许哪些操作，由程序决定。

### 开放值参数

电话、邮箱、订单号、金额等可以先由正则或解析器找候选，再由 Jev 判断哪个候选是目标参数，最后由代码原样取值与规范化。[S10]

地址、备注等不易枚举的自由文本，适合实体抽取器或生成模型。Jev 不擅长凭空产生任意字符串；不要通过逐字符 Choice 模拟生成。

## 3. 一次请求还是两次请求

**候选和问题已知**：把多个问题放进同一请求，独立评估后在程序中组合。无关参数结果可以丢弃。

**存在真实依赖**：先识别意图，再查询某类记录或构造候选时，使用第二次请求。同一请求中的参数题不能自动读取意图题的答案。[S3]

多轮补全由外围程序维护：保存已确认的槽位，将用户最新修改与相关历史传入 state；对冲突、代词指代和缺失值设明确规则，避免默默覆盖已确认参数。

## 4. 请求示意

前置代码已从原文识别订单号和手机号。以下使用动态候选 ID；模型判断候选，业务代码持有真实值。

```json
{
  "model": "jev-1.13.0",
  "state": {
    "message": "把订单 A123 的收货电话改成 13800138000",
    "candidates": {
      "order_1": "A123",
      "phone_1": "13800138000"
    }
  },
  "questions": {
    "intent": {
      "type": "choice",
      "instructions": "用户要求执行什么订单操作？",
      "criteria": {
        "query": "查询订单信息",
        "cancel": "取消订单",
        "update_shipping": "修改收货信息",
        "other": "以上均不匹配"
      }
    },
    "field": {
      "type": "choice",
      "instructions": "用户明确要求修改哪个收货字段？",
      "criteria": {
        "phone": "联系电话",
        "address": "收货地址",
        "recipient": "收货人",
        "unspecified": "未说明或不适用"
      }
    },
    "order": {
      "type": "choice",
      "instructions": "哪一个候选是用户要求修改的订单？",
      "criteria": {
        "order_1": "订单号 A123，对应 state.candidates.order_1",
        "none": "没有符合要求的候选"
      }
    },
    "new_phone": {
      "type": "choice",
      "instructions": "哪一个候选是用户明确要求设置的新收货电话？",
      "criteria": {
        "phone_1": "电话 13800138000，对应 state.candidates.phone_1",
        "none": "没有符合要求的候选"
      }
    }
  }
}
```

后续代码根据意图使用相关答案，将 `order_1`、`phone_1` 映射回原值，验证格式、归属与业务条件，再构造调用。此示例只演示单个修改任务；真实输入可能包含多字段或多任务。

## 5. 大意图空间与多意图

### 超过 255 个意图

官方方案是层级分类：业务域 → 子类 → 叶子意图。可保留多条候选路径再深入，避免单一路径早期错误；官方 cookbook 提供 beam search。[S18]

另一种工程方案是先通过关键词或向量检索召回候选，再由 Jev 判定。召回率是上限：正确意图没进候选，后续无法选出。应保留拒识与回退，观察候选遗漏。

不要将分组 Choice 的最大概率直接跨组排序为全局概率；每组候选集合不同，概率是各自选项集内的相对结果。需要后续统一候选复核，或采用经过验证的层级评分策略。

### 一句话包含多个意图

例如“查物流，顺便开发票”。单个 Choice 是单选，可分别用 Noul 判断候选意图是否出现；复杂复合请求先拆任务，再给各任务绑定参数。

同一句包含两个订单、两个动作时，仅分别识别“动作集合”和“订单集合”不够，还要保留动作与对象的对应关系。必要时由生成模型分解为任务，再用 Jev 校验或路由。

## 6. 验收建议

在真实中文数据上比较现有规则、小分类器、小 LLM 和 Jev。至少检查：

- 单意图、多意图、近义意图、域外请求的识别与拒识。
- 必填参数缺失、纠正已有槽位、多个同类候选的角色选择。
- 单槽位准确率与整条任务全部参数正确率。
- 自动处理覆盖率、回退率、p50/p95 延迟、每个正确任务的总成本。

阈值由业务样本确定，不直接把 confidence 当正确率。英文公开测试不能替代中文参数填槽验收。
