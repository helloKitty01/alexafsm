① 边界与职责首版边界

三条原则定边界：模型负担轻 · 机制少 · 与官方一致

首版覆盖定时、单事件、简单即时条件、本人提醒与少量固定动作；遇到暂缓场景明确说明并给替代，用户接受才建任务

01模型负担轻

模型只在创建期出场一次：识别属于 5 个模式中的哪一个、填对象 / 时间 / 阈值 / 文案、回读一句。不写脚本、不写 filter、不碰 state、不定限额。运行期默认不过模型（只有 S1 晨报要生成内容）。

02整体机制少

不新增调度体系、任务表、事件适配器、判定模型工具、结束 / 限额协议。工程新增只有两件：5 个固定模板 + 创建处理函数、EventHub → stream 的桥接命令。

03与官方一致

运行时语义全部沿用 openClaw 官方：at / every / cron / stream、trigger.script、once、script payload 的 notify / state / nextCheck、approval card、runs / delivery / failureAlert。实施前锁定版本，三栏区分官方已有 / 我们的适配 / 暂不支持（P18）。

① 边界与职责模式库

模式库：5 个固定模板，每个只有几个参数，背后是一种官方 job 形态

模板 = 固定 JS / prompt 骨架 + 参数注入，有版本、工程维护。不建模板语言，不建通用编译器；模板覆盖不了就追问或回答不支持

模式模型填的参数程序生成的 job（官方形态）模板里固定的逻辑首版场景
① 定时生成内容cron / tz · 主题 · 来源 · 长度 · 接收渠道cron + agentTurn（isolated）；prompt 三段由模板填；toolsAllow = 来源读取工具；announce 本人来源不可用则说明缺失、不伪造；NO_REPLY 静默S1

③ 单事件 → 固定动作事件类型 · 对象 ID（filter 参数）· 动作参数（设备 · 目标状态）· 时段stream（桥接 argv 带 filter）+ script payload：解析批 → 去重 → 过期 → 幂等动作逐行解析、event_id 去重（state 记 24h）、occurred_at 过期丢弃、目标状态而非 toggle、时段在脚本内判断S3

⑤ 单事件 → 查现况 → 条件 → 提醒事件类型 · 对象 ID · 查询字段 · 阈值 · 文案stream + script payload：三步 + phone.lookup(state) 一次 + 判 + notify只判断处理事件时的现况，不回溯、不持续监听；查询失败与"不成立"分开记S10

模板是产品资产：加一个场景 = 加一个模板 + 一条创建处理分支；每个模板附验收用例（同一意图几种说法、缺参、重名、旧事件、批截断）。
模板不开放的条件：对应工具（weather / homekit / phone.lookup）或本人交付渠道未接入、事件中心不支持该事件——此时模式列表里不出现它，模型无从选择。

② 运行时 · 官方为准限制

限制分四类，三类对模型隐藏；阈值到达后的行为各不相同

debounce ≠ cooldown；source 级冷却挡不住多源；停止接收事件会破坏状态正确性。所以：source 只做输入整形，冷却与窗口在运行时（模板脚本）里集中管

类回答的问题在哪实现到达阈值后模型可见?
① source 整形输入抖动、事件合并（同一次到家连发两条）事件中心目录 debounce；桥接命令按实例订阅、重连只收新事件合并成一条事实否
② 动作冷却 · 执行窗口"别一直提醒 / 只在晚上"——job 级，跨源共用模板脚本：state 记 lastActionAt，窗口在脚本内判断（事件仍收，只是不动作）返回 {}，记一次 run时段 / 频率作为参数填；机制不可见
③ 用户业务限制"每天最多提醒一次"、"成功后停止"模式参数 → 编译进脚本（state 记日期）；一次性任务用官方 once每日限制次日恢复；once 完成安静结束作为参数填
④ 平台配额资源保护官方：script timeout 300 s / tool budget 50、trigger 30 s / 5 次、最小间隔 30 s、stream 批 ≤16 KB；路线图的模型判定另加 checks/dayrun error → 退避 → failureAlert，暂停告警否
不能合并的原因："每天最多检查 400 次"是资源保护，"每天提醒一次"是用户期望，"买到就停"是完成条件——到顶行为分别是暂停告警 / 次日恢复 / 安静结束。旧稿把它们统一成"到顶暂停 + 告警"是错的。
为什么不在 source 层过滤窗口：窗外的"到家"可能正是取消某个 deadline 所需的事实（路线图 S12）；首版虽无此场景，规则先定对——source 不丢事实，脚本决定动不动。
"刚做过别再做"用什么：不是 lastRunAt（上次是开始、成功还是等待确认？语义不清），而是脚本在动作成功后写 state.lastActionAt——state 仅成功 run 后持久化，天然就是"上次成功动作"。

payload:  { kind: "script", script: <模板 arrive_home_action 注入 living_main / on / 18:00-23:00> },

官方 stream 行为照抄，不改

  • 批在 batchMs（默认 250，50–5000）静默后关闭，或到 16 KB 截断（末尾 [truncated]）；payload 运行期间后到的行并入下一批，最多保留一个待处理批。
  • 内建 30 s 触发间隔；失败的 payload 不重试（可能不幂等）；丢批 / 合批计数在 runs 里可见。
  • 五次连续 <60 s 的进程退出进入 error，需手动 re-enable；禁用 / 删除 job 即停进程。
  • 源身份在 disable / remove / replace 时轮换，旧进程的迟到批不会再 fire。

模板固定三步每个事件模板都有，模型不写

1
逐行解析 trigger.streamBatch；解析失败或带 [truncated] 的行丢弃，记原因。
2
去重：event_id 在 state.seen（24 h 环）里见过 → 跳过；动作成功后才写回（state 仅成功持久化）。
3
过期：now − occurred_at > staleAfter（目录默认，如 geofence 10 m）→ 丢弃；不会"20 分钟前到家现在才开灯"。重连只收新事件，离线期间不补执行。

桥接命令的规则我们的适配，标清

  • 一个事件 job 一个源进程；按实例管理订阅租约，进程退出即退订或到期。
  • 只把业务事件写 stdout，日志走 stderr（stream 也会收 stderr 行——用 mode: match 只接 ^\{ 开头）。
  • filter 传给事件中心侧评估（首选）；事件中心不支持时桥接侧过滤——待事件中心确认（S4 的 contact_id 过滤取决于此）。
首版不承诺：逐条处理 · 毫秒级响应 · 动作恰好一次 · 离线补执行。因此抢票（S5）、比分（S9）这类高频 / 时效场景进路线图；到家、来电、电量这类低频事件可以。本人提醒可能重复（重连），开灯用目标状态所以重复无害。

③ 事件 · 审批 · 结束审批 · 结束

审批与结束："判定到了"和"做成了"由 run 结果分开，全是官方语义

结束语义两种含义，官方各有对应

含义官方对应例
完成本次动作后结束trigger.once: true：fired payload 成功后停用；失败 / 拒绝 / 超时 → 不停用，state 不持久化，下次条件仍成立可再 fire"通知我一次就行"（路线图 S9）
不再需要观察无 payload 可执行时由脚本 return {} + 用户 / 程序 disable；或 at 一次性 job 跑完自删比赛结束条件未成立；S5 放票提醒（at）
形态 B 的"完成"script payload 成功即本次结束；"成功后不再提醒"= state 记标记，脚本下次 return {}S2 今天已提醒

state 与执行结果分离官方既有行为，照抄

  • 条件门：fired payload 失败 → 本次返回的 state 不持久化，下次评估看到旧 state、可再 fire——所以条件门要写成只读检查，动作放 payload。
  • script payload：state 仅成功 run 后持久化——所以去重键、"今天已提醒"、lastActionAt 都在动作成功后写，失败自然回滚。
  • 运行中修改脚本或 state：官方保护该编辑不被旧运行的返回覆盖。

审批agentTurn 才有；script payload 不能 ask_user

情形官方行为
agentTurn 的 exec 需审批approval card 投到连接的审批面，run 进 waiting；答复后继续
"Always allow"铸一枚 standing grant（有作用域与生命周期，可列出 / 撤销），以后同类不再问——这就是旧稿 D3 的"二期免确认"
拒绝 / 超时run error → failureAlert；once 不生效
script payloadunattended，无对话；不进入需确认的动作——模板只做创建期已授权的固定动作（开灯、提醒本人）
可能 ask_user 的 jobdelivery 必须能把问题送到用户（announce），否则问题无处可去

权限面三条官方规则

  • agent 创建的 job 工具面 ≤ 创建轮次可见的工具，不能放宽；模板再收窄到最小白名单。
  • trigger / script payload 默认以 agent 的完整工具策略运行（含 exec）——所以模板必须显式 toolsAllow；cron.triggers.enabled: false 是操作员的硬停。
  • 创建者 exec 能力绑定 Gateway 时，自动化沿用该目标；不满足则阻断而非换主机。
首版权限结论：S1 晨报读工具；S2 weather；S3 homekit + phone.lookup；S4 只 notify；S10 phone.lookup + notify。没有对外发送、支付、交易——这三类全在路线图，且进入时走 agentTurn + 审批。

④ 验证与拍板轨迹推演

四条轨迹推演：先确认行为一致，再画图

用首版场景把 Codex 评审点到的四种边界跑一遍；每条写清"官方保证的"与"模板负责的"

T1同一批里两条事件（S3 连发两次到家）

官方：250 ms 静默内的两行进同一批，payload 只跑一次。模板：逐行解析，两条 event_id 都进 seen；动作 homekit.set(on) 幂等，只执行一次；state 在 run 成功后一次性写回。若跨批到达：第二批解析后 event_id 已在 seen → 跳过。事件中心侧 debounce 5 m 通常已合并，这里是双保险。

T2旧事件迟到（S10 一条 30 分钟前的到家）

官方：stream 不判过期，原样交给 payload。模板：第三步 now − occurred_at > 10 m → 丢弃并记原因，不查电量、不提醒。路线图 S12 的"旧事件取消新计时"：因为 source 不丢事实（P10），到家事件仍会到脚本，脚本按 occurred_at 与 deadline 比较——这条规则首版先定对，场景以后再开。

T3最后一次动作失败（S3 homekit 超时）

官方：script 抛错 → run error、退避、failureAlert；返回的 state 不持久化，seen 里没有这条 event_id；stream 失败不重试这一批。结果：灯没开、用户收到失败告警、下次到家正常处理；不会出现"记了 seen 却没开灯"。动作成功但 notify 投递失败：run 与 delivery 分别可查，执行完成 ≠ 用户已收到。

T4等待确认时条件改变（路线图 S6 卖出）

官方：agentTurn 在 approval card 上 waiting；期间新 tick 的条件门照常评估，但同 job 的新 fire 排队 / 合并由 scheduler 管（maxConcurrentRuns）；用户拒绝 → error，once 不生效，state 不持久化。结论："等待确认时价格又变了"由动作 agentTurn 在被允许后重新读现价决定是否执行——这是模板 prompt 要写的一句；首版无此场景，规则先记。

推演结论：四条轨迹在"官方状态模型 + 模板三步 + 幂等目标状态"下都能给出确定行为，不需要自定义事务、补偿或恢复协议。这也是首版能砍掉 onTick / done / quota 的原因。

三段固定模板：stream 三步前缀 · 查判提醒后缀 · 晨报 prompt

{{...}} 是创建处理函数注入的参数，其余一个字不由模型写。示意代码，工具名以锁定版本为准

模式 ③ arrive_home_actionS3 · stream + script payload

// ---- 固定前缀：解析 → 去重 → 过期（③④⑤ 共用）----
const s = { seen: [], ...(trigger.state ?? {}) }, now = Date.now();
const lines = (trigger.streamBatch ?? '').split('\n').filter(l => l.startsWith('{'));
const fresh = [];
for (const l of lines) {
  let e; try { e = JSON.parse(l); } catch { continue; }                  // 解析失败丢弃
  if (s.seen.some(x => x.id === e.event_id)) continue;                   // 去重
  if (now - Date.parse(e.occurred_at) > {{staleMs}}) continue;             // 过期
  fresh.push(e);
}
if (!fresh.length) return {};
// ---- 模式 ③ 后缀：时段 → 现况 → 幂等动作 ----
const h = new Date().getHours();
if (h < {{windowStart}} || h >= {{windowEnd}}) return {};                // 窗外：收到但不动作
const st = await tools.call('phone.lookup', { kind: 'state', fields: ['zones'] });
if (!st.zones.includes('{{zoneId}}')) return {};                     // 已不在家，不开
await tools.call('homekit.set', { device: '{{deviceId}}', state: '{{targetState}}' }); // 目标状态，非 toggle

附录 · 规格filter 语法

filter 语法：单事件布尔，仅此而已

在事件中心侧逐事件评估、无状态；openClaw 只在 cron add 时静态校验，不解释。写不了的不扩语法；首版模型不写 filter，由模板按对象 ID 生成

文法EBNF

expr    := or
or      := and ( "||" and )*
and     := not ( "&&" not )*
not     := "!" not | cmp
cmp     := operand ( ("==" | "!=" | "<" | "<=" | ">" | ">=") operand )?
         | operand "in" "[" literal ( "," literal )* "]"
         | operand ( "contains" | "startsWith" ) string
         | "(" expr ")"
operand := field | literal
field   := ident ( "." ident )*          // 目录 fields 里的名字，不带 payload. 前缀
literal := string | number | "true" | "false" | "null"
string  := "'" … "'"                     // 单引号

例子全部来自主稿场景

需求filter
到家（S3 / S10 / S11）zone == 'home'
离开公司（S12）zone == 'office'（geofence.exit）
张三来电且非视频（S4 变体）contact_id == 'c_12' && !is_video
微信或钉钉的通知package_name in ['com.tencent.mm','com.alibaba.android.rimet']
电量低于 15%level <= 15（device.battery_low）
北京明天大概率下雨（派生事件消费者）city == 'beijing' && rain_prob >= 0.6

cron add 时校验四条，都对着目录

校验不通过怎么办
eventType 在目录（内建或已登记派生）拒绝，回"目录里没有这个事件"
每个 field ∈ 条目 fields；类型匹配拒绝，列出可用字段
enum 字段的值在枚举内拒绝，列出合法值
must_filter 字段已被约束拒绝："geofence.enter 必须约束 zone"

写不了的归哪

想写为什么不在 filter归哪
时间函数 hour() weekday()是 job 的属性，不是事件的模板脚本内判断（D6）
频率"别一直 / 刚做过"需要跨事件记忆模板脚本 state.lastActionAt
另一个事件的字段、"之后 / 没有"跨事件 = CEP，事件中心不做路线图（跨事件 state）
当前状态"在充电时"不在事件 payload 里模式⑤ 脚本查 phone.lookup(state)
"持续 N 分钟"需要到点叫醒路线图（nextCheck + pacing）
为什么限得这么死：语法小才能在 cron add 时机械校验、才能在事件中心侧零成本评估、才不会让事件中心长成 CEP。语法之外的每一类需求都已有归属。
