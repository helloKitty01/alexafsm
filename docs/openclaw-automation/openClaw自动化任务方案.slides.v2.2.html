G1一个任务工具，一张表

模型只面对原生 cron 工具；job 表就是任务表。外部事件是 schedule 的一种 kind，模型判定是 trigger 的一种 kind；另加的只有只读的 event_catalog。

① 总体原生能力

openClaw 原生 cron 工具全貌：一个工具，不是多个

来源：cron-tool.ts 工具描述 + Scheduled tasks 文档。结论：时间 / 脚本轮询 / 进程流原生就有，只缺外部事件（schedule kind）和模型判定（trigger kind）

层级"cron" 既是工具名又是一种 schedule kind

工具 cron（显示名 Automations）                             ← 模型看到的唯一任务工具
 └ action: status | list | get | add | update | remove | run | runs
    └ add 的参数 job:
       ├ schedule.kind ∈ { at | every | cron | stream | event|multi(新增) } ← 何时 tick
       ├ trigger.kind  ∈ { script | agent(新增) } + stateSchema        ← 先判定，fire 才跑
       ├ limits(新增)  { activeWindow · cooldown · maxRunsPerDay · once } ← 限额
       ├ payload.kind  ∈ { systemEvent | agentTurn | script }         ← 触发后干什么
       ├ sessionTarget ∈ { main | isolated | current | session:<id> } ← 在哪个 session
       └ delivery · pacing · contextMessages · enabled

job 字段取值与本方案用法

字段取值说明
scheduleat / every / cron{expr,tz} / streamcron expr 是 tz 墙上时间，整点默认错峰 ≤5min；stream 是 schedule 不止于时间的先例
event{eventType, filter} / multi{sources[]}新增：事件源；多 tick 源可混排，每个 tick 都交给同一个 trigger（P12）
trigger{kind:"script", script}条件监视器：挂在任一 tick 源上，返回 {fire, message, state, nextCheckAt?}；失败也 fire
{kind:"agent", prompt, …}新增：判定者换成受限 agentTurn，契约不变（P10）
limits{activeWindow, cooldown, maxRunsPerDay, once}新增：job 级限额，四种触发共用；可选，只在用户明说时写（P12）
payloadagentTurn{message, toolsAllow, …}本方案统一执行形态；message 三段是编译产物（P18）
systemEvent / script塞主 session（仅 main）/ 无模型脚本（路 B publish 用）

运行时保障Gateway 内，原生

  • job / state / runs 持久化 SQLite；每次执行产生 background task 记录；
  • 一次性任务限流类错误重试 3 次，周期任务 30s→60m 退避；maxConcurrentRuns 默认 8；
  • isolated 任务分阶段 watchdog；启动时过期任务重排不回放；
  • failureAlert / failureDestination 可按 job 配。

运行中的限制

自动化任务运行中只能对自己 status / get / runs / remove；不能 cron add（是否也限制 current 待核实，P15）。

对方案的直接影响：v0.1 想造的 checker、Task 表、事件入口层，前两件原生已有（trigger / job 表）。本方案做四件事：给 schedule 加 event / multi，给 trigger 加 agent kind 与 tick / nextCheckAt 契约，加 job 级 limits，在 cron service 里放一个事件中心适配器。trigger / script / stream 需 cron.triggers.enabled（已确认可开）。

② 四种触发外部事件 ⑴

触发 ③ 外部事件：新增 schedule.kind = "event" 规格与事件中心契约

投递语义：事件中心 at-least-once + openClaw event_id 去重（24h） + 双侧 staleAfter（目录默认，模型不写）；先回 200 再执行

job.schedule模型只写两个字段 → cron service 补默认值后 EventHub.subscribe

// 模型写的（cron add 里）
"schedule": { "kind": "event",
  "eventType": "geofence.enter",        // 目录里的 type
  "filter": "zone == 'home'" },        // 只比较 payload 字段，无函数
"limits": { "activeWindow": "18:00-23:00 Asia/Shanghai" }   // 用户确认过才写，cron service 评估

// cron service 实际发给事件中心的 subscribe（模型不可见）
subscribe({ eventType, filter, tag: job_id,
  debounce: "5m", staleAfter: "10m" })     // 来自目录 internal 默认
字段谁写谁评估说明
eventType模型openClaw 校验在目录来自 event_catalog，不能凭空造
filter模型事件中心逐事件、无状态；字段只能来自目录 fields；must_filter 字段必须约束（geofence: zone）
limits模型（可选）cron serviceactiveWindow / cooldown / maxRunsPerDay / once；四种触发共用，取代 guards（P12）
debounce / staleAfter目录默认事件中心 + openClaw 兜底模型不写；cron service 订阅时从目录 internal 带上

openClaw 不解释 filter，只校验字段在目录 fields 里、must_filter 已约束。filter 逐事件无状态——跨事件的与 / 非 / 时序、"持续 N 分钟"全部落 trigger + state（P12）。

事件中心 → openClaw 推送POST /hooks/eventhub

{
  "event_id": "evt_9c21",               // 幂等键
  "job_id": "job_7f3a",                  // 订阅时带过去，原样带回
  "event_type": "geofence.enter",
  "occurred_at": "2026-09-08T18:42:10+08:00",
  "payload": { "zone": "home", "confidence": 0.93 }
}

openClaw 侧处理四步，几十行

1
去重：event_id 24h 内见过 → 直接 200，不执行。
2
过期：now − occurred_at > staleAfter → 200 + 记 skipped。不会"20 分钟前到家现在才开灯"。
3
先回 200，再异步执行；否则 agent 跑 30s，事件中心早已超时重推。
4
作为 tick 进触发层：有 trigger 先判定；fire → limits → 拼信封（P16）→ 与其他触发同一段 runJob；失败走 failureAlert。
对用户的三句承诺：事件不丢（at-least-once）· 动作不重复（幂等）· 过期不执行（双侧 TTL）。

② 四种触发外部事件 ⑵

事件入口：传输 × 点火——一个事件怎么变成一次 run

"POST /hooks/eventhub" 是两段事：事件怎么进入进程（传输，可替换）· 进程内怎么变成 run（点火，走 cron service 原有路径）

传输四种进法，入口适配器可替换

方式做法优点 / 代价
① Webhook 默认事件中心 POST 到 /hooks/eventhub，Bearer token原生 hooks 基建全现成；宕机期间靠事件中心缓存 + 重试
② 长连接流Gateway 主动连事件中心，cursor + ackNAT 友好、断线补投；连接管理要写，事件中心要支持
③ 本机 IPC同机部署：函数调用 / Unix socket延迟最低、免鉴权；仅同机
④ 轮询Gateway 定期拉 pending违背"订阅即推送"；只做启动对账兜底

抽象进程内只有一个入口函数

EventIngress.onEvent(envelope)        ← 唯一入口，传输方式在它前面
  ├ HttpHookAdapter  /hooks/eventhub    ← 默认
  ├ StreamAdapter    ws/grpc + cursor   ← 留扩展
  └ LocalAdapter     同机直调           ← 同机时切换，入口不变

谁不过模型零 token

  • 事件中心：单事件 filter 评估、投递、目录、publish；无 guards、不做 CEP

  • 主 session 收 announce 摘要：systemEvent 注入，不唤起主 loop，下次用户对话时才被读到
