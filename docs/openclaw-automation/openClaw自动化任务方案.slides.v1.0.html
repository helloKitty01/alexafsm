openClaw 自动化任务v1.0：目标与场景

以 openClaw cron service 为唯一任务中枢，按需新增 · 统一走 agentTurn
前提：存在统一事件中心（EventHub）——订阅即推送，filter / guards 在 事件中心评估，有 publish 接口；订阅由 Gateway 内部完成，模型不调订阅工具
v1.0 新增："当 xxxx 时"写不成脚本的条件，由受限判定 Agent 判定（trigger.kind="agent"，P15），四个复杂场景验证（P17）

目标场景用户原话 → openClaw 触发类型

#用户原话触发openClaw 里是
S1每天早上 9 点帮我干 xxx时间schedule.cron（原生）
S2明天下雨的时候帮我干 xxx脚本轮询cron + trigger 脚本（原生）→ publish 派生事件 → event
S3到家的时候帮我干 xxx外部事件schedule.event（新增）订阅 geofence.enter
S4收到 xxx 的电话时帮我 xxx外部事件schedule.event 订阅 phone.call_received
S5火车放票时帮我抢北京→上海的票时间（两阶段）at 前置确认（current）→ 运行中自建 at 执行任务（isolated）
S6–S9股票跌 10% / 30% 分档抛售 · 狗上沙发驱赶 5 分钟仍在则通知 · 开售后买卧铺没买到继续盯 · 曼联持续领先 30 分钟通知张三模型判定轮询every + trigger.kind="agent"（新增）：受限判定 agentTurn 维护 state，fire 才跑 payload（P15 / P17）
归类结论：四种触发——时间（原生）、脚本轮询（原生 trigger）、模型判定轮询（新增 trigger kind）、外部事件（新增 event kind）。执行统一为 agentTurn；四种触发汇入同一条 runJob 执行路径。

G1一个任务工具，一张表

模型只面对 openClaw 原生 cron 工具（at / every / cron / stream 是它 schedule.kind 的取值，不是多个工具）；job 表就是任务表。事件订阅作为 schedule 的一种 kind、模型判定作为 trigger 的一种 kind 加进去，另加的只有一个只读的 event_catalog。

G2触发尽量不过模型；过模型的触发受约束

时间到 / 脚本命中 / 事件推送到达，零 token。"当 xxxx 时"写不成脚本、要 Agent loop 才能判断时，用 trigger.kind="agent"：只读工具、小模型、短超时、每日预算、滞回，返回 {fire,message,state}，fire 才起执行 agentTurn（P15）。能用事件门 / 脚本门先筛的先筛，模型判定放最后一层。

G3运行上下文 = 冻结的任务定义

openClaw 原则："message is that run's entire context — self-contained"。事件启动的 Agent 拿到的是系统身份 + 事件事实 + 创建时冻结的任务定义，不读主对话历史（P11）。

G4门控归事件中心，openClaw 只做去重过期

filter / guards 由模型写在订阅里、openClaw 原样转发、事件中心评估。openClaw 侧对事件只做四件事：转发订阅、event_id 去重、occurred_at 过期、拼信封起 agentTurn。

G5派生事件是资产

"明天下雨"由 trigger 脚本产生后 publish 进 事件中心目录，可被多个任务订阅、被其他 Agent 发现（路 B）。

G6高危动作永不走默认路径

支付 / 对外发送 / 删除必确认：运行中用 ask_user 停下等用户，不在 message 里授权。S6–S9 要求免确认执行，与此冲突——"创建期预授权"作为开放问题 #1 待拍板（P17 / P18）。

openClaw 原生 cron 工具全貌：一个工具，不是多个

来源：src/agents/tools/cron-tool.ts 模型实际看到的工具描述 + 官方 Scheduled tasks 文档
结论：时间 + 脚本轮询 + 进程流三种触发原生就有，只缺外部事件订阅（schedule kind）和模型判定（trigger kind）

层级"cron" 一词既是工具名又是一种 schedule kind，先把层级摆清

工具 cron（显示名 Automations）                 ← 模型看到的唯一任务工具
 └ action: status | list | get | add | update | remove | run | runs | next_check | wake
    └ add 的参数 job:
       ├ schedule.kind ∈ { at | every | cron | stream | event(新增) }   ← 什么时候触发
       ├ trigger.kind ∈ { script | agent(新增) }, once             ← 可选：到点先判定，fire 才跑 payload
       ├ payload.kind ∈ { systemEvent | agentTurn | script }          ← 触发后干什么
       ├ sessionTarget ∈ { main | isolated | current | session:<id> } ← 在哪个 session 干
       └ delivery · pacing · contextMessages · enabled

三层同一件事：模型调 cron 工具 = Gateway RPC cron.add = 终端 openclaw cron add。"新增 event kind" = 在 schedule.kind 枚举里加一个值；"新增 agent kind" = 在 trigger.kind 枚举里加一个值。工具还是那一个。

ADD 的 job 结构{name?, schedule, payload, sessionTarget?, pacing?, trigger?, delivery?, enabled?}

字段取值说明
scheduleat / every / cron{expr,tz}at 无 tz 按 UTC、跑完自删；cron expr 是 tz 墙上时间不要预转 UTC，整点默认错峰 ≤5min，准时要 exact
stream{command, mode, match}受管进程输出行触发——schedule 已不是纯时间，是 event kind 的先例
payloadsystemEvent{text} / script{script}塞主 session（仅 main）/ 无模型脚本（路 B 的 publish 用它）
agentTurn{message, model?, thinking?, timeoutSeconds?}本方案统一执行形态；可加 toolsAllow
trigger{kind:"script", script, once?}条件监视器：挂在 every/cron 上的静默无模型检查（30s / 5 工具调用 / 16KB state）；返回 {fire, message?, state?}；用 state 去重；失败也 fire；脚本只读
{kind:"agent", prompt, …} 新增模型判定监视器：契约同上，判定者换成受限 agentTurn（只读、小模型、预算、滞回）；失败不算 fire。规格 P15
其他pacing{min,max} · contextMessages 0–10 · delivery自适应轮询 · 创建时聊天片段嵌入（冻结）· announce = 发渠道 + 主 session 一条摘要

ACTIONS

status · list · get · add · update · remove · run（force）· runs（历史）· next_check（自身 pacing）· wake（nudge 主 lane）

运行中的自动化任务受限：只能 status / list / get / runs / remove 自己 + next_check。

运行时保障（Gateway 内）

  • job / 状态 / 历史持久化 SQLite；每次执行产生 background task 记录；
  • 一次性任务限流类错误重试 3 次，周期任务 30s→60m 退避；maxConcurrentRuns 默认 8；
  • isolated 任务分阶段 watchdog；启动时过期任务重排不回放；
  • 失败通知独立 failureDestination；failureAlert 可按 job 配。
对方案的直接影响：v0.1 里"我们造 checker""我们造 Task 表""我们造 `/hooks/events` 入口"三件事，前两件原生已有（trigger / job 表），第三件收缩为 cron service 里的一个 事件中心适配器。trigger / script / stream 需 cron.triggers.enabled（已确认可开）。原生 checker 只有脚本判定者，v1.0 加第二种判定者（模型），契约不变。

执行 session：四选一，默认 isolated

由 sessionTarget 决定；事件型任务的"当前对话"无定义，所以 current 只用于时间型

四种 sessionTarget

sessionTarget跑在哪上下文本方案用法
main主 session 的 heartbeat lane有主对话上下文；cron 回合不写入人类聊天轨、不刷新新鲜度；payload 只能 systemEvent纯提醒
isolated每次新 session id cron:<jobId>零历史；只继承 thinking / model 偏好，不继承渠道路由、权限提升；出现在 openclaw tasks默认：S1–S4 全部、S5 执行阶段
current创建时绑定的对话读一段创建时对话的有界尾部，结果落回该对话S5 前置确认（要和用户对话）；"稍后继续"类自唤醒
session:<id>持久命名 session跨次累积需要跨次记忆且 last_run_summary 一行不够时

默认规则：systemEvent → main；agentTurn 从聊天创建 → current，从 API 创建 → isolated。本方案编译规则里强制显式写 sessionTarget，不依赖默认值。

为什么默认 isolated

  • token：主 session 动辄 100K；isolated 官方数字 2–5K；
  • context bleed：cron 产出污染主对话；
  • 权限隔离：不继承渠道路由与提升权限，toolsAllow 再收窄；
  • 与 openClaw 哲学一致：message 自包含，运行时不回头读对话。

跨次记忆的三个层级

  • L0 无：开灯、发提醒——绝大多数事件任务；
  • L1 一行摘要：job 表存 last_run_summary，起 agentTurn 时注入（P7 第 ⑤ 块）；"比昨天早还是晚"够用；
  • L2 命名 session：真的要在上一次基础上继续（每日站会式）；会累积，要配压缩。
结果回流原生就有：delivery=announce 把最终文本送到渠道，并往主 session 发一条简短摘要——双脑"任务摘要卡片"的会合点，不用另做。

新增 schedule.kind = "event" 规格与 事件中心契约

投递语义：事件中心 at-least-once + openClaw event_id 去重（24h） + 双侧 stale_after；先回 200 再执行

job.schedule（模型写）→ openClaw 原样转发 EventHub.subscribe

{
  "kind": "event",
  "eventType": "geofence.enter",            // 来自 事件中心目录
  "filter": "payload.zone=='home' && weekday(ts) && hour(ts)>=18",
  "guards": {                                // 全部由 事件中心评估
    "debounce": "5m", "cooldown": "2h",
    "maxFiresPerDay": 1,
    "activeWindow": "18:00-23:00 Asia/Shanghai"
  },
  "staleAfter": "10m",                       // 事件中心 丢弃 + openClaw 兜底校验
  "once": false                              // true = fire 一次后 disable
}

openClaw 侧不解释 filter / guards，只校验字段存在、eventType 在目录里。订阅成功后 subscription_id 存回 job；update 改 schedule → resubscribe；remove / enabled:false → unsubscribe / pause；Gateway 启动时用 EventHub.list 对账。

事件中心 → openClaw 推送（/hooks/eventhub，复用 hooks 鉴权；入口机制见 P7）

{
  "event_id": "evt_9c21",               // 幂等键
  "subscription_id": "sub_7f3a",
  "job_id": "job_7f3a",                  // 订阅时带过去，原样带回
  "event_type": "geofence.enter",
  "occurred_at": "2026-09-08T18:42:10+08:00",
  "payload": { "zone": "home", "source": "wifi+gps", "confidence": 0.93 }
}

openClaw 侧处理：四步，几十行

1
去重：event_id 24h 内见过 → 直接 200，不执行。
2
过期：now − occurred_at > staleAfter → 200 + 记 skipped，不执行。任一侧配错都不会"20 分钟前到家现在才开灯"。
3
先回 200，再异步进执行路径；否则 agent 跑 30s，事件中心早已超时重推。
4
拼信封（P11 五块）→ 与 trigger fire 后同一段代码起 isolated agentTurn；run 记进 runs，失败走 failureAlert。入口机制见 P7，时序见 P9 第 9–12 步。
对用户的三句承诺：事件不丢（at-least-once）· 动作不重复（幂等）· 过期不执行（双侧 TTL）。

事件入口：传输 × 点火——一个事件怎么变成一次 run

"POST /hooks/eventhub" 其实是两段事：事件怎么进入进程（传输，可替换）· 进程内怎么变成 agentTurn（点火，走 cron service 原有 run 路径）

传输四种进法，入口适配器可替换

方式做法优点 / 代价
① Webhook 推送
默认		事件中心主动 POST 到 Gateway /hooks/eventhub，Bearer token原生 hooks 基建全现成（hooks.enabled / token / safety wrapper）；代价：Gateway 要对事件中心可达，宕机期间靠事件中心缓存 + 重试
② 长连接订阅流Gateway 主动连事件中心（WebSocket / gRPC stream），带 cursor + ack不暴露入口、NAT 友好、断线按 cursor 补投；代价：连接管理 / ack / 补投都要写，事件中心要支持流推
③ 进程内 / 本机 IPC同机部署：函数调用 / Unix socket / Binder延迟最低、免鉴权；代价：耦合，仅同机
④ 轮询拉取Gateway 定期拉 pending违背"订阅即推送"；只做兜底（启动对账时拉一次积压）

抽象进程内只有一个入口函数

EventIngress.onEvent(envelope)          ← 唯一入口，传输方式在它前面
  ├ ① HttpHookAdapter   /hooks/eventhub  ← 默认，复用原生 hooks
  ├ ② StreamAdapter     ws/grpc + cursor ← 留扩展
  └ ③ LocalAdapter      同机直调          ← 事件中心同机时切换，入口不变
待确认（影响默认选 ① 还是 ③）：事件中心与 Gateway 是同进程 / 同机 / 跨设备？事件中心只有 HTTP POST 还是也有长连接推送？重试策略（次数 / 退避 / 死信）？

点火不走原生 /hooks/agent，走 cron service 的 job 执行路径

为什么不用现成的 /hooks/agent：它能直接起 isolated run（message / sessionMode / idempotencyKey / runId 都有），但不认识 job——没有 payload.message / toolsAllow / delivery / runs 历史 / last_run_summary / failureAlert / enabled。让事件中心打它 = 任务定义存到事件中心，方向反了。mapped hooks 同理，产出的是无 job 的 hook run。
① /hooks/eventhub（薄）token 鉴权 → 解析 envelope、校验字段 → 按 job_id 找 job；找不到 / disabled → 2xx + 退订
→
② cron service.fireJob(jobId, event)event_id 去重（SQLite 24h）→ occurred_at vs staleAfter → 落 run(queued) → 立即回 200 {ok, runId}；执行异步
→
③ runJob：与定时到点完全同一段代码session cron:<jobId>:<runId> → user message = 信封 → isolated agentTurn（toolsAllow）→ delivery → run 状态 / failureAlert

fireJob 不是新机制：at / every / cron 由定时器按、stream 由子进程输出行按、event 由 ingress 按——stream 已证明 run 路径与"谁按下 fire"解耦，我们只是多加一个按钮。改动点：event kind 的 job nextRunAt = null 不进定时队列 + 把 fireJob 暴露给 ingress（内部函数边界待到源码核实）。

回事件中心含义
2xx别再重试：正常受理 · 重复 event_id · 过期 · job disabled · job 不存在（顺手退订）
401token 错
5xx仅 Gateway 内部错误（落 run 失败）→ 事件中心重试
幂等键 = event_id + job_id，存 SQLite 24h（不用原生 hooks 的 5 分钟内存重放缓存，重启即清扛不住重试窗口）· 背压：超 maxConcurrentRuns 排 queued 不拒收 · 顺序：同 job 串行（两条"到家"不同时开灯），跨 job 并行，跨事件不保序。

端到端时序 ②：S2 明天下雨，路 B 两条 job 的接力

生产者 S2a（trigger + script）产生派生事件 → 事件中心 → 消费者 S2b（event job）
第 7 步之后与 P9 完全同一条路径

为什么是两条 job

  • S2a 是生产者：只负责"世界发生了什么"，publish 后结束，不知道谁在用；
  • S2b / S2c 是消费者：各自订阅、各自 filter；加一个消费者不动生产者；
  • 派生事件进目录后，其他 Agent 也能发现和订阅。

生产者 ② 模型判定型

第 2–3 步换成 trigger.kind="agent"：受限判定 agentTurn 判断"发布会结束了吗"，用 trigger_result 返回 {fire, message, state}（P15）；第 4 步 payload 仍是 script → event_publish。第 5 步之后完全相同。

对比路 A

路 A 没有第 4–8 步：第 3 步 fire:true 直接进第 9 步起 agentTurn。少一次事件中心往返，但派生事件不进目录、不可复用。

编译规则：公共可复用（天气 / 放票）→ B；私有一次性（我的包裹）→ A。

从一句话到 cron add：编译流程与 message 模板

编译期 LLM 的核心产出不是 JSON 字段，是 payload.message——它决定零历史的运行时模型能不能干对

对话回放

到家的时候帮我把客厅灯开了，放点音乐
好，你到家我就开客厅灯、放音乐。工作日晚上 6 点以后才触发，可以吗？
可以。你试一下
已模拟一次"到家"：客厅灯已开、正在播放你常听的歌单。以后真到家就会这样。
明天下雨的话提醒我带伞
好，每天晚上 8 点我看一次北京明天的预报，降雨概率超过 60% 就提醒你。
回读粒度：默认一句话；只有非常识默认值（60%、20:00）和高权限动作才显式追问。"试一下" = cron run jobId（force），走真实路径。

七步编译

1
意图路由：委托型且非立即执行 → 走 cron add，不就地干。
2
选触发（成本阶梯）：有时间词 → at/cron；调 event_catalog，目录里有 → event；规则写得出来 → every + trigger.script；写不出来（要看图 / 读页面 / 语义判断）→ every + trigger.kind="agent"。三者可级联做门（P15）。"持续 / 连续 / N 分钟后"类时序条件 → 必须落 trigger state，不能寄望 filter。
3
填槽：home / 灯 / 音乐 / 某人 / baseline / 车次 / match_id → 从画像与目录解析成具体对象；缺槽追问或写"执行时判断"。
4
补 filter / guards（event）或 写 trigger 脚本（script）或 写判定 prompt + state 初值 + 只读 toolsAllow + 预算（agent）：按类型给常识默认值（到家 debounce 5m + cooldown 2h；判定滞回 consecutive 2）。
5
写 message 三段 + 显式 sessionTarget / toolsAllow / delivery。
6
回读确认一句话。
7
cron add：openClaw 落 job 表；event kind 由 cron service 自动完成 EventHub.subscribe——模型不调任何订阅工具，一次调用结束。

payload.message 三段模板（必填）

## 任务
用户原话：<原句，不改写>
编译补充：<指代 → 具体对象；阈值 / 窗口 / 城市等已确认的参数；缺槽标"执行时判断">
策略：免确认 = <本任务涉及的白名单动作>；必确认 = 支付 / 对外发送 / 删除（ask_user）
      交付 = <silent | 发到当前聊天 | …>；失败必须通知

三段对应运行时模型的三个问题：干什么（原话）、指的是什么（补充）、能不能直接干（策略）。缺任何一段，isolated 模型只能猜。

新增 trigger.kind = "agent"：条件判定交给受限 Agent，契约不变

"当 xxxx 时"很多写不成脚本（看图 / 读页面 / 语义判断 / 需要多步查证）——判定者从脚本换成模型，{fire, message, state} 契约、fire:false 静默、state 跨 tick 三件事全部沿用；判定只读、动作另起

三种落法选 C，A 是零代码过渡

落法做法问题
A 判定动作一体every + payload.agentTurn，message 写"先判断 xxx；成立则做 yyy，否则 NO_REPLY"（原生今天能跑）每 tick 一个 run 全是噪音；判定与动作同一 loop，权限分不开；跨 tick 只有 last_run_summary
B 判定发事件生产者 ② → 事件中心 → 消费者 event job（P14）私有条件也得拆两条 job、绕一次事件中心；留给结果要复用的场合
C trigger.kind="agent"与 trigger.script 并列的第二种 checker：受限判定 agentTurn，trigger_result 收口，fire 才跑 payload判定 / 动作分离 · state 持久 · fire:false 无 run；改 cron service，与加 event kind 同一种扩展

六条约束写进 checker 实现与编译规则

约束内容
① 结构化收口只能通过调用 trigger_result({fire, message, state}) 结束；不调 / 超时 / 不合契约 = 判定失败。message = 证据摘要，进动作阶段信封 ②
② state 是核心≤16KB JSON，模型自己维护、逐 tick 传回：baseline / stage / phase / lead_since / first_seen。嵌套 = state.phase，时序 = 时间戳（P17）
③ 判定只读toolsAllow 只给查询类工具（行情 / 赛程 / 快照 / 网页）+ trigger_result；无 cron、event_publish、写工具
④ 预算小模型 + lightContext · timeoutSeconds 60 级 · maxToolCalls 5 · maxChecksPerDay；prompt 除 state 和新数据外全静态，KV cache 命中高
⑤ 滞回hysteresis.consecutive N（连续 N tick 为真才 fire）+ fire 后 cooldown；checker 实现，不靠模型自觉
⑥ 失败语义脚本 checker 失败算 fire（原生）；模型 checker 失败不算 fire：记 check error、下 tick 重试、连续 N 次 failureAlert

已定结论

  • 一个任务工具：cron（at / every / cron / stream 是 schedule.kind，不是多个工具）+ 一个只读 event_catalog；新增 schedule.kind="event" 与 trigger.kind="agent"；
  • 四种触发一条执行路径：时间 / 脚本轮询 / 模型判定轮询 / 外部事件，全部经 runJob；触发尽量不过模型，过模型的判定只读 + 预算 + 滞回 + 失败不 fire，用 trigger_result 收口，state 跨 tick（嵌套 = phase，时序 = 时间戳）；
  • 订阅由 cron service 内部完成：订阅方 = Gateway 单一主体，tag = job_id；job 拥有订阅生命周期；模型不调订阅工具；
  • 门控归事件中心：filter / guards 模型写、openClaw 转发、事件中心评估；openClaw 只做去重 / 过期 / 拼信封；
  • event_publish 主 loop 与判定阶段不可见：trigger / script ✓，动作 agentTurn 按 toolsAllow 默认关；
  • 路 B：公共可复用派生事件进目录；A / B（动作还是 publish）与 script / agent（谁判定）两维正交；私有一次性走路 A；
  • 统一 agentTurn + isolated；S5 = 两条 at + ask_user，时效搁置；上下文：系统身份（可 light）+ 事件事实 / trigger_result（标外部）+ message 三段 + contextMessages + last_run_summary；投递：at-least-once + 幂等 + 双侧 TTL。
