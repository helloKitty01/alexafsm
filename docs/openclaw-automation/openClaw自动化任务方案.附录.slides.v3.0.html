附录 · 规格filter 语法

filter 语法：单事件布尔，仅此而已

在事件中心侧逐事件评估、无状态；openClaw 只在 cron add 时静态校验，不解释。写不了的不扩语法，分别归 limits 与 trigger

文法EBNF

expr    := or
or      := and ( "||" and )*
and     := not ( "&&" not )*
not     := "!" not | cmp
cmp     := operand ( ("==" | "!=" | "<" | "<=" | ">" | ">=") operand )?
         | operand "in" "[" literal ( "," literal )* "]"
         | operand ( "contains" | "startsWith" ) string
         | "(" expr ")"
operand := field | literal
field   := ident ( "." ident )*          // 目录 fields 里的名字，不带 payload. 前缀
literal := string | number | "true" | "false" | "null"
string  := "'" … "'"                     // 单引号

例子全部来自主稿场景

需求filter
到家（S3 / S10 / S11）zone == 'home'
离开公司（S12）zone == 'office'（geofence.exit）
张三来电且非视频（S4 变体）contact_id == 'c_12' && !is_video
微信或钉钉的通知package_name in ['com.tencent.mm','com.alibaba.android.rimet']
电量低于 15%level <= 15（device.battery_low）
北京明天大概率下雨（派生事件消费者）city == 'beijing' && rain_prob >= 0.6

cron add 时校验四条，都对着目录

校验不通过怎么办
eventType 在目录（内建或已登记派生）拒绝，回"目录里没有这个事件"
每个 field ∈ 条目 fields；类型匹配拒绝，列出可用字段
enum 字段的值在枚举内拒绝，列出合法值
must_filter 字段已被约束拒绝："geofence.enter 必须约束 zone"

写不了的归哪

想写为什么不在 filter归哪
时间函数 hour() weekday()是 job 的属性，不是事件的limits.activeWindow
频率"别一直 / 每天一次"需要跨事件记忆limits.cooldown / maxRunsPerDay
另一个事件的字段、"之后 / 没有"跨事件 = CEP，事件中心不做trigger.script + state
当前状态"在充电时"不在事件 payload 里trigger.script 查 phone.lookup(state)
"持续 N 分钟"需要到点叫醒state 时间戳 + nextCheckAt
为什么限得这么死：语法小才能在 cron add 时机械校验、才能在事件中心侧零成本评估、才不会让事件中心长成 CEP。语法之外的每一类需求都已有归属。

三套编译模板：message 三段 · 判定 prompt 三段 · 组合脚本三例

编译期模型填槽而不是自由写；三套产物分别给动作模型、判定模型、脚本 checker——都是"给另一个执行者的程序"

① payload.message给动作模型（位置 ③）

## 任务
用户原话：{原话，逐字不改写}
编译补充：{槽 → 具体对象}；{歧义的取舍}；{执行时才知道的写"执行时判断"}
策略：{确认级别：免确认 / 越界 ask_user / 预授权范围}；
　　　{汇报：完成不汇报 / 一句汇报}；失败必须通知

槽外一个字不加；策略段只写与本任务相关的几行。

② trigger.prompt给判定模型（位置 ②）

## 判定
条件：{一句可判真假的问题}（{对象 id}）
步骤：phase={初始} → {查什么}；{阶段} → {查什么，state 怎么改}；
　　　{时序条件} → 记时间戳且 nextCheckAt={到点}；{成立} → fire
输出：只调 trigger_result，message 写{证据字段}

配套产出 state 初值与 stateSchema；步骤里凡"等 N 分钟"必写 nextCheckAt。

③ 组合脚本给 checker（trigger.script）；A / B = sources 下标，W = 秒；不含 cooldown / 每日一次（归 limits）

// 例 ①  事件 A 且 状态 Q          槽：{Q_fields} {Q_pred} {msg}
const st = await tools.call('phone.lookup', {kind:'state', fields: {Q_fields}});
return json({ fire: {Q_pred}(st), message: {msg}, state: {} });

// 例 ②  A 之后 W 内发生 B         state {a_at}   槽：{A} {B} {W} {msg}
const s = trigger.state ?? {}, i = tick.source.index;
if (i === {A}) return json({ fire:false, state:{ a_at: tick.now } });
if (i === {B} && s.a_at && tick.now - s.a_at <= {W})
  return json({ fire:true, message: {msg}, state:{} });
return json({ fire:false, state:s });

// 例 ③  A 之后 W 内没有 B         state {deadline}   槽：{A} {B} {W} {msg}
const s = trigger.state ?? {}, i = tick.source.index;
if (i === {A}) { const d = tick.now + {W};
  return json({ fire:false, state:{ deadline:d }, nextCheckAt: d }); }
if (i === {B}) return json({ fire:false, state:{}, nextCheckAt:null });            // B 来了，取消
if (tick.source.kind === 'self' && s.deadline && tick.now >= s.deadline)
  return json({ fire:true, message: {msg}, state:{} });
return json({ fire:false, state:s });

例 ①"且 / 并且 / 如果这时" + 一个状态（在充电、连着 WiFi、明天下雨）1 个事件—
例 ②"之后 N 分钟内 / 紧接着" + 第二个事件2 个事件{a_at: datetime|null}
例 ③"之后 N 分钟没有 / 还没 / 一直没"；更复杂的组合直接写脚本或改 trigger.agent2 个事件{deadline: datetime|null}

附录 · 编译产物时序 ②

端到端时序 ②：S2 明天下雨，派生事件两条 job 的接力

生产者 S2a（trigger.script → publish）→ 事件中心 → 消费者 S2b（event job）；第 7 步之后与时序 ① 完全同一条路径

为什么是两条 job

  • S2a 是生产者：只负责"世界发生了什么"，publish 后结束；
  • S2b / S2c 是消费者：各自订阅、各自 filter；加一个消费者不动生产者；
  • 派生事件进目录后，其他 Agent 也能发现和订阅；
  • 两条 job 的 runs 各自独立，failureAlert 各自配。

换成模型判定

第 2–3 步换成 trigger.agent：受限判定 agentTurn 用 trigger_result 返回同一契约，第 4 步之后完全相同。

对比"只给自己用"：没有第 5–8 步，第 3 步 fire:true 直接进第 9 步起 agentTurn。少一次往返，但派生事件不进目录、不可复用（主稿 P11）。

三条管线模型之间怎么传东西

编译期（位置 ①）一次性产出，全部冻结
  payload.message 三段 ──────────► ③ 信封块 ③
  trigger.prompt + state 初值 ───► ② 每 tick 的静态前缀

checker 接手非模型

模型怎么结束checker 做什么用户可见
fire:true校验 stateSchema → 记 check → state 写回 job → limits（maxRunsTotal 1：首次放行）→ message + state 进位置 ③ 信封块 ②run
fire:false（± nextCheckAt）只存 state，不产生 run；有 nextCheckAt 则到点造一个 self tick，周期 tick 照常不可见
未调 trigger_result / 不合契约或 stateSchema / 超 60s判定失败：记 check error，state 保留旧值，下 tick 重试；连续 N 次 → failureAlert仅告警
为什么是 self tick 而不是第 N 个每分钟 tick：前置 script 只在"比分有变化"时放行判定，22:40 比分没变，判定不会被唤起。所以判定在 22:10 自己设 nextCheckAt，到点造 self tick，前置 script 对 tick.source.kind=="self" 放行；"到点"由判定自己声明。本页是 S9 的 agent 变体（无比分 API）；有 API 时同一逻辑写成脚本（主稿 P9），零 token。

附录 · 实现事件入口

事件入口：传输 × 点火——一个事件怎么变成一次 run

"POST /hooks/eventhub" 是两段事：事件怎么进入进程（传输，可替换）· 进程内怎么变成 run（点火，走 cron service 原有路径）

传输四种进法，入口适配器可替换

方式做法优点 / 代价
① Webhook 默认事件中心 POST 到 /hooks/eventhub，Bearer token原生 hooks 基建全现成；宕机期间靠事件中心缓存 + 重试
② 长连接流Gateway 主动连事件中心，cursor + ackNAT 友好、断线补投；连接管理要写，事件中心要支持
③ 本机 IPC同机部署：函数调用 / Unix socket延迟最低、免鉴权；仅同机
④ 轮询Gateway 定期拉 pending违背"订阅即推送"；只做启动对账兜底

抽象进程内只有一个入口函数

EventIngress.onEvent(envelope)        ← 唯一入口，传输方式在它前面
  ├ HttpHookAdapter  /hooks/eventhub    ← 默认
  ├ StreamAdapter    ws/grpc + cursor   ← 留扩展
  └ LocalAdapter     同机直调           ← 同机时切换，入口不变
