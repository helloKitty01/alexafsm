① 总体原生能力

openClaw 原生 cron 工具全貌：一个工具，不是多个

来源：cron-tool.ts 工具描述 + Scheduled tasks 文档。结论：时间 / 脚本轮询 / 进程流原生就有，只缺外部事件（schedule kind）和模型判定（trigger kind）

层级"cron" 既是工具名又是一种 schedule kind

工具 cron（显示名 Automations）                             ← 模型看到的唯一任务工具
 └ action: status | list | get | add | update | remove | run | runs
    └ add 的参数 job:
       ├ schedule.kind ∈ { at | every | cron | stream | event(新增) }  ← 何时触发
       ├ trigger.kind  ∈ { script | agent(新增) }, once              ← 先判定，fire 才跑
       ├ payload.kind  ∈ { systemEvent | agentTurn | script }         ← 触发后干什么
       ├ sessionTarget ∈ { main | isolated | current | session:<id> } ← 在哪个 session
       └ delivery · pacing · contextMessages · enabled

job 字段取值与本方案用法

字段取值说明
scheduleat / every / cron{expr,tz} / streamcron expr 是 tz 墙上时间，整点默认错峰 ≤5min；stream（进程输出行触发）是 schedule 不止于时间的先例
trigger{kind:"script", script}条件监视器：挂在 every / cron 上，返回 {fire, message, state}；state 去重；失败也 fire
{kind:"agent", prompt, …}新增：判定者换成受限 agentTurn，契约不变（P10）
payloadagentTurn{message, toolsAllow, …}本方案统一执行形态；message 三段是编译产物（P15）
systemEvent / script塞主 session（仅 main）/ 无模型脚本（路 B publish 用）
其他contextMessages · delivery创建时聊天片段冻结 · announce = 渠道 + 主 session 摘要

运行时保障Gateway 内，原生

  • job / state / runs 持久化 SQLite；每次执行产生 background task 记录；
  • 一次性任务限流类错误重试 3 次，周期任务 30s→60m 退避；maxConcurrentRuns 默认 8；
  • isolated 任务分阶段 watchdog；启动时过期任务重排不回放；
  • failureAlert / failureDestination 可按 job 配。

运行中的限制

自动化任务运行中只能对自己 status / get / runs / remove；不能 cron add（是否也限制 current 待核实，P13）。

对方案的直接影响：v0.1 想造的 checker、Task 表、事件入口层，前两件原生已有（trigger / job 表）。本方案只做三件事：给 schedule 加 event kind，给 trigger 加 agent kind，在 cron service 里放一个事件中心适配器。trigger / script / stream 需 cron.triggers.enabled（已确认可开）。

② 四种触发时间 · 脚本轮询

触发 ① ②：时间 与 脚本轮询——原生已有，只定用法

全部是原生 cron 工具的 action:"add"；编译规则强制显式写 tz / sessionTarget / delivery

用法要点

项规则
时间at 一次性跑完自删；cron expr 是 tz 墙上时间，tz 必填；时效敏感加 exact
脚本 checker挂在 every / cron 上；返回 {fire, message, state}；fire:false 只存 state、不产生 run；失败 / 超时算 fire
state去重与跨 tick 记忆都靠它（"每天最多一次"= state.fired）；≤16KB
messagefire 时的证据摘要，进执行阶段信封 ②（P14），动作不必重查
适用条件能写成规则（阈值、余票、字段变化）。写不出来 → 模型判定（P10）

S1 每天 9 点时间

{"action":"add","job":{
 "name":"每日晨报",
 "schedule":{"kind":"cron","expr":"0 9 * * *","tz":"Asia/Shanghai"},
 "sessionTarget":"isolated",
 "payload":{"kind":"agentTurn","timeoutSeconds":600,
  "message":"## 任务\n用户原话：每天早上 9 点给我一份晨报\n编译补充：晨报 = 今日日程 + 北京天气 + 3 条科技新闻，300 字内\n策略：只读，无需确认；发到当前聊天"},

没有 trigger，到点直接进执行路径。tz、sessionTarget、delivery 全部显式写出；message 三段（P15）让零历史的 isolated 模型知道"干什么、指什么、能不能直接干"。

S2 明天下雨脚本轮询，路 B 生产者

{"action":"add","job":{
 "name":"派生事件：明天北京下雨",
 "schedule":{"kind":"cron","expr":"0 20 * * *","tz":"Asia/Shanghai"},
 "trigger":{"kind":"script","script":"
   const p = (await weather.forecast('beijing','tomorrow')).rain_prob;
   const today = new Date().toISOString().slice(0,10);
   if (trigger.state?.fired === today)
     return json({fire:false, state:trigger.state});

 "sessionTarget":"isolated",

② 四种触发外部事件 ⑴

触发 ③ 外部事件：新增 schedule.kind = "event" 规格与事件中心契约

投递语义：事件中心 at-least-once + openClaw event_id 去重（24h） + 双侧 staleAfter；先回 200 再执行

job.schedule模型写 → openClaw 原样转发 EventHub.subscribe

{
  "kind": "event",
  "eventType": "geofence.enter",            // 来自事件中心目录
  "filter": "payload.zone=='home' && weekday(ts) && hour(ts)>=18",
  "guards": {                                // 全部由事件中心评估
    "debounce": "5m", "cooldown": "2h", "maxFiresPerDay": 1,
    "activeWindow": "18:00-23:00 Asia/Shanghai"
  },
  "staleAfter": "10m",                       // 事件中心丢弃 + openClaw 兜底
  "once": false                              // true = fire 一次后 disable
}
字段谁写谁评估说明
eventType模型openClaw 校验在目录来自 event_catalog，不能凭空造
filter模型事件中心逐事件、无状态的表达式；字段来自 payload schema
guards模型事件中心debounce / cooldown / maxFiresPerDay / activeWindow
staleAfter模型双侧事件中心丢弃 + openClaw 兜底校验 occurred_at
once模型openClawfire 一次后 disable 并退订

openClaw 不解释 filter / guards，只校验字段存在、eventType 在目录里。filter 逐事件无状态——"持续 / 连续 / N 分钟后"类条件不能写在这里，要落 trigger state（P10）。

事件中心 → openClaw 推送POST /hooks/eventhub

{
  "event_id": "evt_9c21",               // 幂等键
  "job_id": "job_7f3a",                  // 订阅时带过去，原样带回
  "event_type": "geofence.enter",
  "occurred_at": "2026-09-08T18:42:10+08:00",
  "payload": { "zone": "home", "confidence": 0.93 }
}

openClaw 侧处理四步，几十行

1
去重：event_id 24h 内见过 → 直接 200，不执行。
2
过期：now − occurred_at > staleAfter → 200 + 记 skipped。不会"20 分钟前到家现在才开灯"。
3
先回 200，再异步执行；否则 agent 跑 30s，事件中心早已超时重推。
4
拼信封（P14）→ 与其他触发同一段 runJob 起 isolated agentTurn；失败走 failureAlert。
对用户的三句承诺：事件不丢（at-least-once）· 动作不重复（幂等）· 过期不执行（双侧 TTL）。

② 四种触发外部事件 ⑵

事件入口：传输 × 点火——一个事件怎么变成一次 run

"POST /hooks/eventhub" 是两段事：事件怎么进入进程（传输，可替换）· 进程内怎么变成 run（点火，走 cron service 原有路径）

传输四种进法，入口适配器可替换

方式做法优点 / 代价
① Webhook 默认事件中心 POST 到 /hooks/eventhub，Bearer token原生 hooks 基建全现成；宕机期间靠事件中心缓存 + 重试
② 长连接流Gateway 主动连事件中心，cursor + ackNAT 友好、断线补投；连接管理要写，事件中心要支持
③ 本机 IPC同机部署：函数调用 / Unix socket延迟最低、免鉴权；仅同机
④ 轮询Gateway 定期拉 pending违背"订阅即推送"；只做启动对账兜底

抽象进程内只有一个入口函数

EventIngress.onEvent(envelope)        ← 唯一入口，传输方式在它前面
  ├ HttpHookAdapter  /hooks/eventhub    ← 默认
  ├ StreamAdapter    ws/grpc + cursor   ← 留扩展
  └ LocalAdapter     同机直调           ← 同机时切换，入口不变

待确认（决定默认 ① 还是 ③）：事件中心与 Gateway 同进程 / 同机 / 跨设备？只有 HTTP POST 还是也有长连接？重试策略？

点火不走原生 /hooks/agent，走 cron service 的 job 执行路径

/hooks/agent 能直接起 isolated run，但不认识 job——没有 payload.message / toolsAllow / delivery / runs / failureAlert。让事件中心打它 = 任务定义搬到事件中心，方向反了。

① /hooks/eventhub（薄）token 鉴权 → 解析 envelope → 按 job_id 找 job；找不到 / disabled → 2xx + 退订
→
② cron service.fireJob(jobId, event)event_id 去重 → occurred_at vs staleAfter → 落 run(queued) → 立即回 200；执行异步
→
③ runJob：与定时到点完全同一段代码拼信封 → isolated agentTurn（toolsAllow）→ delivery → run 状态 / failureAlert
回事件中心含义
2xx别再重试：正常受理 · 重复 event_id · 过期 · job disabled / 不存在（顺手退订）
