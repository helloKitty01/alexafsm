openClaw 自动化任务 v3.0
一个工具 · 一条路 · 五项新增

把 openClaw 的定时任务扩展为统一的自动化任务：时间到点、事件到达、脚本判定、模型判定，全部汇入 cron service 同一条执行路径。前提：存在统一事件中心（EventHub，订阅即推送、单事件 filter、publish 接口）；openClaw 可改源码。

① 总体复用与新增

原生 cron 全部复用，新增只有五项、三个工具

来源：cron-tool.ts 工具描述 + Scheduled tasks 文档。原生已有 schedule / trigger.script / payload / session / delivery / runs，本方案在两处各加一个 kind、加一组 limits、一个适配器

层级"cron" 既是工具名又是一种 schedule kind

工具 cron（显示名 Automations）                        ← 模型看到的唯一任务工具
 └ action: status | list | get | add | update | remove | run | runs
    └ add 的参数 job:
       ├ schedule.kind ∈ { at | every | cron | stream | event(新增) } ← 谁叫醒
       ├ trigger.kind  ∈ { script | agent(新增) }                ← 谁判定；可选
       ├ limits(新增)  { activeWindow · cooldown · maxRuns… }      ← 此刻该不该跑
       ├ payload.kind  ∈ { agentTurn | script | systemEvent }       ← 跑什么
       ├ sessionTarget ∈ { isolated | main | session:<id> | current } ← 在哪跑
       └ delivery · contextMessages · enabled

原生复用清单一行不改

能力本方案怎么用
at / every / cron时间叫醒源；at 跑完自删（S5）；cron run --force 做"试一下"
trigger.script 契约{fire, message, state} 原样沿用，只多一个可选 nextCheckAt；state 持久化在 job 表
payload 三种agentTurn 是统一动作形态；script 用于 publish 派生事件；systemEvent 只给 main 提醒
runs / 状态机queued → running → waiting（ask_user）→ ok / error / skipped；重试、退避、maxConcurrentRuns、watchdog
delivery / failureAlertannounce = 渠道 + 主 session 摘要；none；失败必告警
运行中权限自动化 run 只能对自己 status / get / runs / remove——S6 / S8 "完成后自删"靠它

五项新增全部在 cron service 与主 loop prompt 里

#新增内容页
①event 源 + 适配器schedule.kind="event"，sources[] 1..n；add / remove 时订阅 / 退订；入口去重、过期、回 200、转 tickP7
②tick + nextCheckAt三种叫醒统一成 tick 进 onTick；trigger 可返回 nextCheckAt，到点造 self tickP9
③limits 限额器fire 与 run 之间：activeWindow / cooldown / maxRunsPerDay / maxRunsTotal / maxChecksPerDayP9
④trigger.agent只读 isolated agentTurn 当判定者，trigger_result 收口，失败不算 fire；前置 script 门P8
⑤编译期支撑目录（内建 + 派生）静态进 prompt；phone.lookup；event_publish + publishes 登记；三套模板P12

三个新工具各只对一种上下文可见

工具谁可见做什么

② 核心模型一条路 · 名词

一条路：tick → trigger → fire → limits → run，三道门各答一个问题

后面每一页只用这九个词。fire 的定义在 v3.0 改了：不是"条件为真"，是"trigger 认为现在需要执行一次 payload"

一条路叫醒源不同，后面完全相同；filter 站在路口之前、事件中心那一侧

filter · 事件中心这件事值不值得叫醒我？
zone == 'home'，不过就不推
⇢
tick · cron service叫醒：到点 / 事件到达 / 自设闹钟到期
→
trigger现在需要动作吗？可选；无 trigger 则 tick 即 fire
→
fire"需要执行一次 payload"；message 说明是哪种动作
→
limits此刻该不该跑？时段 / 冷却 / 每日 / 总次数

名词表定义 · 回答的问题 · 谁负责 · 在 cron add 的哪个字段

名词一句话定义回答的问题归属出现在
tickjob 被叫醒、给 trigger 一次判定机会的最小单位。三种来源：时间到点（at / every / cron）、订阅事件到达（event）、自设闹钟到期（self）谁、何时叫醒我cron servicetick = {source, event?, now}，trigger 的输入
trigger拿到 tick 后判定"现在是否需要动作"的一层，可选。script 由 checker 跑，agent 由判定模型跑；同一契约。负责检测跃迁（进入阈值、上 / 下沙发、到点仍领先）需要动作吗checker / 判定模型trigger.kind，返回 {fire, message, state, nextCheckAt?}
firetrigger 返回 fire:true（无 trigger 时 = tick 到达）。含义是"需要跑一次 payload"，message 告诉动作模型是哪个跃迁；还要过 limits 才 run要动了cron service内部状态；runs 里记为 fired / skipped
limitsfire 之后、run 之前的 job 级闸门。四种叫醒源共用，用户明说才写此刻该不该跑cron servicelimits {…}（P9）
run通过 limits 后真正执行 payload 一次；有 run 记录、delivery、failureAlert跑什么、在哪跑cron service → 会话payload · sessionTarget · toolsAllow
filter单事件布尔表达式，只引用目录 fields，在事件中心侧评估；不过就不推值不值得叫醒我事件中心sources[].filter（附录 A3）
nextCheckAttrigger 自设的一次 self tick 时刻。只加一个 tick，不减任何 tick；新值覆盖旧值，清空即作废下次何时再看cron servicetrigger 返回值（P9）
statetrigger 的跨 tick 记忆（阶段、时间戳、基线），≤16KB；stateSchema 可选，声明结构供 checker 校验上次看到什么cron service 存trigger.state 初值 · 返回值 state
派生事件某条 job 的 payload 调 event_publish 发布、登进目录的事件；与内建事件同构结果给谁用事件中心payload.kind="script" + publishes（P11）
为什么改 fire 的定义（拍板 D1）：S6 "跌 10% 卖一半、跌 30% 清仓"是两次不同动作，S7 "下沙发停声"里条件是变假。若 fire = 条件为真，两个场景都要两条 job 或另起机制；若 fire = 需要动作，trigger 检测跃迁、message 写 "half / all / play / stop"，一条 job 就够。
三道门不重叠：filter 管事件"是不是我要的"（事件级），trigger 管"需不需要动"（条件级，有 state），limits 管"此刻该不该跑"（job 级）。凡 filter 写不了的不扩 filter，分别归 trigger 与 limits。

  "contextMessages": 3 }

逐字段谁写 · 何时写

字段谁写何时写
schedule.kind模型时间词 → at / every / cron；目录里有对应事件 → event
sources[]模型event 时必填；"或 / 之后 / 没有"涉及第二个事件就写两个
sources[].filter模型只比较目录 fields；must_filter 字段必须约束
trigger模型条件不是"到点 / 事件到了就干"时才有；先 script，写不出才 agent
limits模型用户说了"只在…时段 / 别一直 / 每天一次 / 只一次"或确认了 Agent 提议
payload.message模型必填三段，编译核心产物（P12）
toolsAllow模型按动作反推收窄；判定面只读
subscription_ids[]cron service订阅副作用写回，模型不可见
debounce / staleAftercron service订阅时取目录 internal，模型不写
命名约定：job JSON 一律 camelCase（nextCheckAt maxRunsTotal）；事件目录 yaml 一律 snake_case（stale_after must_filter）；事件类型 group.verb_noun（geofence.enter）；点火入口叫 onTick。
与 v2.3 的差别：没有 multi（多源就是 sources 多写一个），时间源不再与事件源混排——需要"到点"用 nextCheckAt，需要"时段"用 activeWindow；没有 gate / hysteresis / budget / once。

② 核心模型事件源

事件源：模型只写 eventType + filter，订阅与投递全在 cron service

新增 ①。投递语义：事件中心 at-least-once + openClaw event_id 去重 24h + 双侧 staleAfter；先回 200 再执行

S3 的 schedule模型写的 vs cron service 实际发的

// 模型写的（cron add 里）
"schedule": { "kind": "event", "sources": [
   { "eventType": "geofence.enter",       // 必须在目录里
     "filter": "zone == 'home'" } ] },    // 只比较 fields；zone 是 must_filter
"limits": { "activeWindow": "18:00-23:00 Asia/Shanghai", "cooldown": "2h" }

// cron service 处理 add 时对每个 source 发的（模型不可见）
EventHub.subscribe({ eventType, filter, tag: job_id,
                     debounce: "5m", staleAfter: "10m" })   // 目录 internal 默认

事件中心 → openClawPOST /hooks/eventhub

{ "event_id": "evt_9c21",                 // 幂等键
  "job_id": "job_7f3a",                   // 订阅时的 tag，原样带回
  "event_type": "geofence.enter",
  "occurred_at": "2026-09-08T18:42:10+08:00",
  "payload": { "zone": "home", "confidence": 0.93 } }
对用户的三句承诺：事件不丢（at-least-once）· 动作不重复（event_id 幂等）· 过期不执行（双侧 TTL，不会"20 分钟前到家现在才开灯"）。

入口四步几十行，在 onTick 之前

1
鉴权 → 按 job_id 找 job；找不到 / disabled → 2xx + 顺手退订，不执行。
2
去重：event_id 24h 内见过 → 200，不执行（记 skipped）。
3
过期：now − occurred_at > staleAfter → 200，记 skipped。
4
先回 200，再 onTick(jobId, {source:{kind:'event',…}, event, now})——之后与时间到点完全同一段代码。5xx 只留给"落 run 失败"，事件中心据此重试。

update 改 sources按差集 unsubscribe / subscribe；改 limits / payload 不动订阅
enabled false / truepause / resume
remove（含 maxRunsTotal 到达）unsubscribe
Gateway 启动EventHub.list(tag=gateway) 与 job 表对账：多的退订、少的补订
入口选定（拍板 D5）：默认 webhook；同机部署切本机直调，入口函数不变。传输四选一与原生 stream 零改动验证路径见附录 A9。

② 核心模型trigger

trigger：脚本与模型同一契约，脚本是默认，模型是例外

新增 ④ 只是把"谁算 fire"换成受限 agentTurn；tick 输入、返回结构、state 持久、fire:false 静默全部沿用原生 trigger.script

契约输入 tick + state，输出四个字段

tick = { source: { kind: "time" },                        // at / every / cron 到点
       | { kind: "event", eventType, index },          // sources[index] 到达
       | { kind: "self" },                             // 自己设的 nextCheckAt 到点
         event?: { event_id, occurred_at, payload }, now }
→ { fire: bool,            // 需要跑一次 payload？
    message: "证据摘要",    // 进动作信封块 ②；写清是哪个跃迁
    state: {…},            // 写回 job，下 tick 原样传入
    nextCheckAt?: ts }     // 到点再给我一个 self tick

脚本运行时边界拍板 D2——全部数值规则场景成立的前提

项规定

② 核心模型limits · nextCheckAt

limits 管"此刻该不该跑"，nextCheckAt 管"到点叫我一次"

新增 ② ③。两者都在 cron service，模型运行期零感知。S9 用 trigger.script 走一遍：六个 tick，零 token

limits 规格job 级，fire 之后 run 之前；全部可选

字段语义用户话里的信号
activeWindow窗外不产生时间 tick、fire 不进 run；事件 / self tick 仍进 trigger 维护 state（D6）"只在晚上 / 交易时段 / 赛程内"
cooldown上次 run 起 N 内的 fire 丢弃，记 skipped"别一直提醒"；S8 防连续下单
maxRunsPerDay按 tz 自然日计 run；check 不计"每天最多一次"
maxRunsTotal累计 run 到达 → disable + 退订"通知我一次就行"（S9 = 1）
maxChecksPerDayagent 判定次数上限，超出暂停并告警编译规则默认 200，用户不说

nextCheckAt 三条语义

  • 只加不减：到点造一个 source.kind="self" 的 tick；周期 tick、事件 tick 照常。要省成本用 activeWindow 与前置 script，不靠它跳过。
  • 覆盖与作废：新返回值覆盖旧闹钟；返回时不带字段 = 保留；显式 null = 作废。
  • 用途：时序条件的"到点"（S9 30 分钟、S7 5 分钟、S12 1 小时）由 trigger 自己声明，event-only 的 job 因此不需要时间源。

"trigger":  { "kind": "script", "toolsAllow": ["weather"], "script": "
  const p = (await tools.call('weather.forecast', {city:'beijing', day:'tomorrow'})).rain_prob;

                             { "name": "rain_prob", "type": "number" } ] } },
"delivery": { "mode": "none" }

// 消费者：普通 event job，可以有 N 条（带伞 / 收衣服 / 改路线）
"schedule": { "kind": "event", "sources": [
  { "eventType": "weather.rain_tomorrow", "filter": "city == 'beijing' && rain_prob >= 0.6" } ] }

给自己用给别人用（派生事件）
job 数1生产者 1 + 消费者 N

limits一层：本 job 跑几次两层：生产侧管事件发几次；消费侧各管自己
