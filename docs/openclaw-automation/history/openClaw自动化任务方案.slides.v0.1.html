openClaw 自动化任务v0.1：目标与场景

从"每天 9 点帮我干 xxx"出发，扩展到事件驱动的自动化
前提假设：存在统一事件管理服务（EMS）——订阅即推送，不区分手机平台

五个目标场景用户原话 → 触发类型归类

#用户原话看起来是实际是
S1每天早上 9 点帮我干 xxx定时cron
S2明天下雨的时候帮我干 xxx事件poll：轮询 + 判定 → 派生事件
S3到家的时候帮我干 xxx事件event：geofence.enter
S4收到 xxx 的电话时帮我 xxx事件event：phone.call_received
S5火车放票时帮我抢北京→上海的票事件 / 监视at 精确触发 + 预编译动作，放票瞬间不过模型
归类结论：五个场景只落在四种触发上——cron/at（时间）、event（EMS 推送）、poll（自己轮询产生派生事件）。没有一个需要 openClaw 新增"订阅"原语，缺的是一层薄的事件入口 + 一张统一的 Task 表。

G1一种心智，一套工具

"每天 9 点"和"到家时"对用户是同一件事：委托一个将来执行的任务。模型只面对 create_task 一个入口，底层是 cron 还是 EMS 由代码路由，不让模型选路。

G2触发不过模型，执行才过

触发器（时间到 / 事件到 / 条件命中）全部是非 LLM、零 token、毫秒级；LLM 只在两个时刻介入：创建时编译、触发后执行。

G3默认隔离 session

自动化任务默认跑在 isolated 新 session，不污染主对话、不背 100K 历史；需要记忆用命名 session，纯提醒才进主 session。

G4不丢、不重、不过期

EMS at-least-once 投递 + 我们 event_id 去重 + 双侧 stale_after 过期校验。三句话就是对用户的全部承诺。

G5高危动作永不走默认路径

支付、对外发送、删除永远需要用户确认。抢票脚本最多锁单，然后唤醒主 session 找用户付款。

G6一切可查、失败可见

时间型 + 事件型 + 轮询型任务在同一张 Task 表里，用户随口能问"你在盯什么"；执行失败必须通知，不允许静默失败。

openClaw 定时任务现状盘点

来源：openClaw 官方文档 Scheduled tasks / Automation / Heartbeat（2026-09 核对）
结论：时间型触发已经够用，重试 / 超时 / 历史 / 模型覆盖都有，不必重造

执行位置与存储

  • cron 跑在 Gateway 进程内，不在模型内；任务定义 / 运行状态 / 历史持久化在共享 SQLite，重启不丢；
  • 每次执行产生一条 background task 记录，openclaw tasks list | audit 可审计；
  • Gateway 启动时过期的 isolated 任务重排而非立刻回放，避免开机风暴。

三种调度

种类参数注意
at--at "20m" / ISO一次性，成功后默认自删
every--every 1h固定间隔
cron"0 9 * * *" --tz Asia/Shanghai不带 tz 按 UTC；整点默认错峰 ≤5min，要准时必须 --exact

可靠性

  • 一次性任务：限流 / 过载 / 网络错误重试 3 次指数退避；周期任务 30s→60m 退避；
  • maxConcurrentRuns 默认 8；isolated 任务有分阶段 watchdog（模型未起、context 未加载分别报超时原因）；
  • 失败通知走独立的 failureDestination。

三种 payload决定"要不要叫醒模型"

payload做什么用途
systemEvent往主 session 塞一条系统事件，可 --wake now提醒
agentTurn起完整 agent 回合，可覆盖 --model --thinking --tools --timeout-seconds报告、后台活
command直接跑脚本，不经模型，stdout 即交付；输出 NO_REPLY 静默checker、抢票、省 token 的关键

交付

  • announce 回聊天渠道（Telegram / Slack / Discord / 飞书等）；webhook POST 到 URL；none 静默；
  • agent 自己用 message 工具发过了，runner 就跳过兜底 announce。

Heartbeat不是调度器

  • 本质是系统托管的一条 cron（Heartbeat (agent-id)），默认 30min 跑主 session，带一份 scratch 清单；
  • 官方明确：scratch 是 prompt 上下文，周期任务应建独立 automation。本方案不依赖 heartbeat。
S1 最朴素形态：openclaw cron create "0 9 * * *" "xxx" --tz Asia/Shanghai --exact --session isolated --announce

定时任务执行：新建 session 还是复用？

答案是四选一，由 --session 决定；本方案默认 isolated，按需升级

四种 session 目标

--session跑在哪上下文适合本方案
main主 session 的专用 cron 通道有主对话上下文；cron 回合不写入人类聊天轨、不刷新 session 新鲜度提醒、系统事件仅 wake 分支
isolated每次新 session id cron:<jobId>零历史；只继承 thinking / model 等安全偏好，不继承渠道路由、权限提升报告、后台活默认
current创建时绑定的对话读一段创建时对话的有界尾部，结果提交回该对话依赖对话上下文的周期工作事件场景不适用（事件到达时"当前对话"无定义）
session:<id>持久命名 session跨次运行累积"在上一次基础上继续"需要记忆时 session:<task_id>

默认规则：systemEvent → main；agentTurn 从聊天创建 → current，从 CLI/API 创建 → isolated；command → isolated。

为什么默认 isolated

  • token：主 session 动辄 100K，每天带着全部历史跑一遍是浪费；官方数字 isolated 可从 ~100K 降到 2–5K；
  • context bleed：cron 产出污染主对话，用户下次聊天时模型"记得"一堆早报；
  • 权限隔离：不继承渠道路由与提升权限，--tools 白名单可进一步收窄。

升级路径

  • 需要跨次记忆（"今天比昨天早还是晚"）→ session:<task_id>；
  • 需要知道我最近聊什么 → current，仅限时间型任务；
  • 纯提醒，不需要模型干活 → main + systemEvent。
与双脑设计一致：后台任务不读前台全量上下文，靠几十 token 的事件信封 + goal 原话启动，结果以摘要回合。

事件驱动：openClaw 有什么、EMS 做什么、我们补什么

关键事实：openClaw 没有"Agent 订阅事件"原语，订阅方向是反的——外部系统 push 到 Gateway

openClaw 现有入口

能力说明本方案用法
POST /hooks/wake塞系统事件进主 session提醒型事件
POST /hooks/agent起 isolated agent 回合，可带 model / tools / timeout主路径
hooks.mappings模板 / 代码变换任意 payload → wake 或 agent可做入口层的一部分
Gmail PubSub / IMAP专用集成不用
内部 lifecycle hooks/new /reset 压缩、启动运维事件，不是业务事件
缺事件注册表、订阅 API、条件表达式评估、跑脚本的 hook 动作由 EMS + 入口层补

EMS 承担（已确认）

  • 事件生产：手机 / 家居 / 通知等原始事件的采集与标准化，不区分平台；
  • 条件匹配：订阅里的 filter 表达式在 EMS 侧评估；
  • 有状态门控：debounce / cooldown / 每天最多 N 次 / 活跃时段；
  • 事件目录可程序化发现：类型、payload schema、可用字段；
  • 投递：命中后按订阅指定的 target 推送，at-least-once。

EMS 不承担（已确认）→ 我们补

  • 派生事件（"明天下雨""某车次放票"）：EMS 不轮询外部世界，由我们的 checker 产生（P8）；
  • Task 语义：goal / policy / 收件箱 / 暂停恢复，EMS 只认订阅；
  • 去重与过期：at-least-once 的必然代价，入口层做幂等；
  • 动作分发：wake / agent / command 三分支，尤其 command（openClaw hooks 不支持）。
分工一句话：EMS 负责"什么时候该叫我"，openClaw 负责"叫醒后怎么干"，我们补的入口层 + Task 表负责"叫谁、以什么身份、干什么"。

与 EMS 的两份契约：订阅 与 推送

投递语义已定：EMS at-least-once + 入口层 event_id 去重 + 双侧 stale_after 过期校验

订阅（我们 → EMS）以 S3 到家为例

{
  "subscription_id": "sub_7f3a",
  "task_id": "task_home_lights",        // 回推时原样带回
  "event_type": "geofence.enter",        // 来自 EMS 目录
  "filter": "payload.zone=='home' && weekday(ts) && hour(ts)>=18",
  "guards": {                            // EMS 侧有状态门控
    "debounce": "5m",   "cooldown": "2h",
    "max_fires_per_day": 1,
    "active_window": "18:00-23:00 Asia/Shanghai"
  },
  "lifetime": { "expires_at": null, "max_fires": null, "delete_on_fire": false },
  "delivery": {
    "target": "https://gateway/hooks/events",
    "auth": "bearer <dedicated-token>",
    "stale_after": "10m",                // 送不到就作废，不无限重试
    "semantics": "at-least-once"
  }
}

推送（EMS → 我们）

{
  "event_id": "evt_9c21",               // 幂等键
  "subscription_id": "sub_7f3a",
  "task_id": "task_home_lights",
  "event_type": "geofence.enter",
  "occurred_at": "2026-09-08T18:42:10+08:00",
  "delivered_at": "…",
  "payload": { "zone": "home", "source": "wifi+gps", "confidence": 0.93 }
}

投递语义：三选一，选 at-least-once

语义EMS 做法后果
at-most-once推一次不管结果Gateway 重启那几秒的事件永久丢
at-least-once没拿到 2xx 就退避重试（5s/30s/2m/10m），超 stale_after 丢弃不丢，可能重 → 我们去重
exactly-once跨系统不存在严格实现= at-least-once + 接收方幂等
  • 入口层 event_id 24h 内见过 → 直接 200 不执行；
  • 先回 200 再执行，否则 agent 跑 30s EMS 早已超时重推；
  • 入口层也校验 occurred_at，任一侧配错都不会"20 分钟前到家现在才开灯"。

从一句话到一条订阅：Agent 侧编译流程

LLM 只在这里介入一次；产物是结构化的 Trigger + Policy，Goal 保留原话不翻译

对话回放

到家的时候帮我把客厅灯开了，放点音乐
好，你到家我就开客厅灯、放音乐。工作日晚上 6 点以后才触发，可以吗？
可以。你试一下
已模拟一次"到家"：客厅灯已开、正在播放你常听的歌单。以后真到家就会这样。
明天下雨的话提醒我带伞
好，每天晚上 8 点我看一次北京明天的预报，降雨概率超过 60% 就提醒你。
回读粒度：默认一句话确认；只有非常识默认值（60% 阈值、20:00 窗口）和高权限动作才显式追问，不逐项审批。

七步编译

1
意图路由：委托型请求且 Trigger 不是 immediate → 走 create_task，不就地执行。
2
查事件目录：list_event_types 找到 geofence.enter，读 payload schema（有 zone）。查不到 → 判断能否用 poll 拼出派生事件；都不行就如实告知做不到。
3
填槽：zone=home ← 用户画像；"哪个灯"缺槽 → 追问，或留给执行时判断。
4
补 guards：到家类默认 debounce 5m + cooldown 2h——这是写在编译规则里的常识默认值，按事件类型给。
5
补 policy：attention=silent（开灯不用汇报）；authorization：家居控制在免确认白名单，支付 / 对外发送 / 删除永远在必确认清单。
6
回读确认：一句话。用户说"试一下" → test_fire_task 走真实入口路径模拟一次。
7
落库 + 注册：写 Task 表 → 调 EMS subscribe → subscription_id 回填 Task。时间型则调 openClaw cron；轮询型两者都建。

S5 抢票：唯一绕开 EMS 的特例

放票那一秒不能让模型思考。模型回合延迟是秒到十几秒级；事件 → EMS → 推送 → 入口 → 脚本这条链再加几百毫秒到几秒。所以：

前置（LLM，提前一天）对话确认车次、乘车人、席别、备选车次、是否接受候补、预算 → 编译成结构化执行参数 → 回读确认
→
触发（非 LLM）--at 精确到放票前 30s + --exact 关错峰，command payload 直接跑抢票脚本进入就位状态；放票事件（若有）只做兜底
→
红线（Policy）脚本最多做到锁单，然后 POST /hooks/wake 以 speak_now 级别找用户付款 —— 这就是 waiting_user 状态的标准用法
→
事后（LLM）汇报结果；失败自动转候补 / 备选车次
风险坦白：12306 有风控 + 滑块，脚本抢票有账号被限风险，合规灰色。倾向候补优先：放票时刻提交候补 + 备选车次，把"抢"改成"确保进候补队列最前面"。待拍板。

工具设计：合一，模型不接触 cron 和 EMS 两个后端

给两条路就会走错路 —— 时间型 / 事件型 / 轮询型统一到 create_task 的 trigger 判别联合
