能力扩展是四级台阶，整体逻辑是一条路

背景 · 能力扩展"叫醒"与"判定"是两个正交的轴

L0 定时原生已有　S1"每天 9 点帮我看新闻"　→ schedule.kind = cron
L1 事件　S3 S4 S5"到家 / 张三来电 / 放票时帮我…"
多一件事：叫醒源从时间扩到外部事件，到达即执行　→ sources[]: event
L2 条件　S2 S6 S7 S8 S9"跌 10% 卖一半 / 持续领先 30 分钟 / 狗上沙发 5 分钟仍在"

L3 组合　S10 S11 S12"到家且电量低 / 到家后 10 分钟内来电 / 离开 1 小时没到家"
多出的：没有新机制——L1 的多个源 + L2 的 state 记时间戳　→ sources[] 多写一个 + 同一段 script
横切 · 窗口与配额　"只在晚上" → sources[].window；"别连着来" → source cooldown / trigger 查 lastRunAt；次数上限 → 系统配额
横切 · 权限　支付 / 卖出 / 对外发送 → ask_user

① 总体复用与新增

原生 cron 全部复用，新增只有五项、三个工具

来源：cron-tool.ts 工具描述 + Scheduled tasks 文档。原生已有 schedule / trigger.script / payload / session / delivery / runs，本方案在两处各加一个 kind、加一组配额、一个适配器

层级"cron" 既是工具名又是一种 schedule kind

工具 cron（显示名 Automations）                        ← 模型看到的唯一任务工具
 └ action: status | list | get | add | update | remove | run | runs
    └ add 的参数 job:
       ├ schedule = 单源简写 {kind: at|every|cron|stream}
       │            | 通用 {sources:[{kind: at|every|cron|event(新增), window?, cooldown?}…]} ← 谁叫醒 · 什么时候
       ├ trigger.kind  ∈ { script | agent(新增) }                ← 谁判定；可选
       ├ payload.kind  ∈ { script(默认) | agentTurn | systemEvent }  ← 跑什么；动作确定就不起模型
       ├ quota(新增)   { maxRunsTotal · maxRunsPerDay · maxChecksPerDay } ← 系统默认，明说才覆盖
       ├ sessionTarget ∈ { isolated | main | session:<id> | current } ← 在哪跑
       └ delivery · contextMessages · enabled

原生复用清单一行不改

能力本方案怎么用
at / every / cron时间叫醒源；at 跑完自删（S5）；cron run --force 做"试一下"
trigger.script 契约{fire, message, state} 原样沿用，只多一个可选 nextCheckAt；state 持久化在 job 表
payload 三种script 是默认动作形态：编译期已确定的工具调用（S3 开灯、S7 播声）与 publish 派生事件；agentTurn 用于要生成内容 / 多步交互 / 必确认；systemEvent 只给 main 纯提醒
runs / 状态机queued → running → waiting（ask_user）→ ok / error / skipped；重试、退避、maxConcurrentRuns、watchdog
delivery / failureAlertannounce = 渠道 + 主 session 摘要；none；失败必告警
运行中权限自动化 run 只能对自己 status / get / runs / remove——只有 S8 "结果决定去留"靠它；trigger 知道结束的场景用 done

五项新增全部在 cron service 与主 loop prompt 里

#新增内容页
①sources[] + 事件适配器schedule.sources[] 1..n，每项 kind ∈ at / every / cron / event；event 项 add / remove 时订阅 / 退订；入口去重、过期、回 200、转 tickP9
②tick + nextCheckAt三种叫醒统一成 tick 进 onTick，tick 带 lastRunAt / runsToday；trigger 可返回 nextCheckAt（到点造 self tick）与 done（结束 job）P13
③源窗口 + 配额计数器sources[].window / cooldown 定叫醒源何时有效；maxRunsTotal / maxRunsPerDay / maxChecksPerDay 是 cron service 计数器，系统默认 + 用户覆盖，到顶暂停告警。不再有 fire 与 run 之间的"门"P13
④trigger.agent只读 isolated agentTurn 当判定者，trigger_result 收口，失败不算 fire；前置 script 门 + 可选 postScriptP10 / P12
⑤编译期支撑目录（内建 + 派生）静态进 prompt；phone.lookup；event_publish + publishes 登记；三套模板P18

三个新工具各只对一种上下文可见

工具谁可见做什么
phone.lookup(kind, q)主 loop · trigger script · 判定 agent · 动作只读：显示名 → key（contacts / apps / bluetooth / places）；state 读现况

取舍原则：每个机制都要能指出"没有它哪个场景跑不通"，指不出就不进字段集；不做 CEP、不加第二个任务工具、不让模型写订阅卫生参数；模板只有例子没有编号；判定动作一体的写法只用于离线验 prompt，不作方案项。

② 核心模型名词

九个名词：后面每一页只用这些

fire 是 trigger 的返回值，不是一个阶段：= "现在需要执行一次 payload"；配额是挂在 job 上的计数器，不在路上

名词表九个词，后面每页只用这些

名词 · 归属一句话定义 · 在 cron add 的哪个字段
tick
cron service		job 被叫醒的最小单位：时间到点 / 事件到达 / 自设闹钟到期，全进 onTick。无 trigger 时 tick 即 run。{source, event?, now, lastRunAt, runsToday}
filter
事件中心		单事件布尔，只引用目录 fields，不过就不推 → sources[].filter
window · cooldown
sources		叫醒源的有效范围：窗外该源不产生 tick；事件源 cooldown 覆盖目录 debounce；self 闹钟不受窗口约束 → sources[].window / cooldown
trigger
checker / 判定模型		可选，L2 起才有："现在要不要动"。script 默认零 token，agent 可选，同一契约；检测跃迁；依赖 run 事实的节流在这里查 lastRunAt → 返回 {fire, message, state, nextCheckAt?, done?}
fire
trigger 返回值		一条定义，不是节点：= "需要跑一次 payload"而不是"条件为真"；message 写跃迁名（不是动作名）
state · nextCheckAt
cron service 存		跨 tick 记忆（≤16KB，stateSchema 可校验）；nextCheckAt 自设一次 self tick，只加不减，新值覆盖、null 作废
run
沙箱 / 会话		执行 payload 一次：script（默认，编译期确定的工具调用，零 token）/ agentTurn（要生成 / 交互 / 确认）/ systemEvent；有 runs、delivery、failureAlert
配额
cron service		挂在 job 上的计数器 maxRunsTotal / maxRunsPerDay / maxChecksPerDay：系统默认，明说才覆盖；到顶暂停 + 告警；不经判定者，不在路上 → quota
派生事件
事件中心		payload script 调 event_publish 发布、登进目录的事件；与内建事件同构 → publishes（P16）
fire 的定义（拍板 D1）：S6 分档卖出、S7 下沙发停声——若 fire = 条件为真，都要两条 job；fire = 需要动作，trigger 写跃迁名、payload script 一段 switch，一条 job 就够。
三件事不重叠：sources 管"什么时候叫我"，trigger 管"现在要不要动"，配额管"最多花多少"。filter 写不了的不扩 filter，归 sources 或 trigger。

逐字段谁写 · 何时写

字段谁写何时写
schedule.kind模型只有一个时间源时的简写：at / every / cron
sources[]模型通用形式，每项 kind ∈ at / every / cron / event；有事件源、或"或 / 之后 / 没有 / 到点还没"涉及第二个源时用
sources[].window / cooldown模型"只在晚上 / 交易时段 / 赛程内"→ window（时间源直接写进 cron 表达式或 startAt–endAt）；"别一直提醒"→ 事件源 cooldown
sources[].filter模型只比较目录 fields；must_filter 字段必须约束
trigger模型条件不是"到点 / 事件到了就干"时才有；先 script，写不出才 agent。"刚做过别再做"这类依赖 run 事实的节流写在这里（查 tick.lastRunAt）
quota模型（覆盖）系统有默认；用户说了"只通知一次"（maxRunsTotal 1，无 trigger 的一次性 job）或 agent 判定要放宽 checks/day 时才写
payload.kind模型动作在编译期能写成固定工具调用 → script（默认）；要生成内容 / 多步交互 / 必确认 → agentTurn
payload.message / script模型agentTurn 时 message 三段；script 时一段 switch(trigger.message) 跃迁 → 动作表（P18）
toolsAllow模型按动作反推收窄；判定面只读
subscription_ids[]cron service订阅副作用写回，模型不可见

文法EBNF

expr    := or
or      := and ( "||" and )*
and     := not ( "&&" not )*
not     := "!" not | cmp
cmp     := operand ( ("==" | "!=" | "<" | "<=" | ">" | ">=") operand )?
         | operand "in" "[" literal ( "," literal )* "]"
         | operand ( "contains" | "startsWith" ) string
         | "(" expr ")"
