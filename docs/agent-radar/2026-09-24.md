## 深挖一：条件可以先睡，批准不能只看这一句

[arXiv:2609.22510](https://arxiv.org/abs/2609.22510)，Justin Szczepaniak、Elad Feldman、Naum Viner、Ben Nassi（特拉维夫大学），2026-09-18 投稿。

普通间接注入是读到就做。这篇把同一目标改成条件句：内容进上下文时不动作，等后来某一轮出现攻击者选好的触发，再去调工具。论文把它定义成训练时碰不到权重的后门，种在一份检索到的内容里。实验模型是 2026 年 8 月的快照（Grok-4.20、Llama-3.1、Gemini-2.5-flash、GPT-4.1、Qwen2.5），生产客户端也是 2026 年 8 月的版本。这不是 Fable 5.1、Opus 5.5 或 GPT-6 Astra 的分数。

基础模型上，祈使句几乎被拒绝的两家，条件式反而最高。Grok-4.20 的祈使句意图在两轮都是 0，条件式 33.9% 落在第二轮、0.3% 落在第一轮。Llama-3.1-70B 是 26.1% 对 0.1%。配对均值 16.5% 对 2.4%。祈使句的第二轮触发成功率在每家都是 0：多出来的那一轮本身不会让祈使句成功，差距来自「先睡后醒」。触发家族里，对话收尾（谢谢、再见）远高于动作动词和元话语。Grok-4.20 上收尾触发 59.6%，动作动词 19.3%，元话语 2.3%。这个顺序在每个容易中招的模型上保持。

生产试验把载荷放进受控仓库的 `README.md`。用户先让 agent 读仓库，再说一句含触发词的普通跟进。成功标准是研究者预先放好的数据到达攻击者控制的端点。九个目标、各 30 次：

| 当时的客户端 | 祈使句 | 条件式 |
| --- | --- | --- |
| Codex，5.4-mini-low | 0% | 43% |
| Gemini CLI，gemini-3.1-flash-lite | 3% | 83% |
| Claude Code CLI，Haiku 4.5 | 0% | 50% |
| Cursor CLI，Composer 2.5 Fast | 0% | 53% |
| GitHub Copilot，MAI Code-1-Flash-low | 0% | 70% |
| Devin CLI，Cascade SWE 1.6 SLOW | 0% | 57% |
| Amazon Kiro CLI，qwen3-coder-next | 0% | 57% |
| Qwen Code，qwen3-coder-next | 0% | 53% |
| Google Assistant（设备、位置、日历、视频） | 0% | 50% |

论文自己写了：n=30 是可行性估计，Wilson 区间很宽，43% 大约落在 27%–61%，0% 大约落在 0%–11%。不能把区间中点当成稳定效应量。八个编程 agent 量的是数据外带；Google Assistant 量的是设备操控、位置、删日历、视频。语音助手这一行和手机场景直接相关，但客户端版本同样停在 8 月。

防御侧：Prompt Guard 2、PIGuard、PIShield 按出厂阈值对这种句子校准失败。用爆炸式提示的数据再训练之后，编码器基线把真实工具执行从无防护的 34.3% 降到 7.5%–8.1%。作者的 DeFuse 在 5% 误报预算下把攻击成功率压到 3.0%（AUC 0.9994，约 1.16 ms/文档），但是表面形式检测器，要按长度调阈值，论文写明没有针对自适应攻击者做加固。SecAlign-70B 把祈使句从 18.7% 打到 0，也把条件式在注入那一轮打到 0，残余的 11.8% 全部发生在触发回合：此时载荷已经不在「不可信数据」通道里，而在对话历史里，进来的是一句看起来正常的用户话。单轮的数据/指令分离盖不住这个形状。

和已有设计的关系：

- 手机助手里，钱、对外发送、删除走 `waiting_user`，不能走默认路径。后来说的「谢谢」不是一次新的批准。触发词如果出现在用户回合，中枢仍要问：这个动作的依据是不是更早摄入的不可信内容。
- OpenClaw 的工作区（`AGENTS.md`、`SOUL.md`、每日 `memory/YYYY-MM-DD.md`、仓库里的 README）就是论文用的那类载体。文件被读入之后，后面任何一个低注意力回合都可能是保险丝。不可逆动作继续只走模板和批准卡；模型在后一轮「想起」文件里的条件，不能升格成 standing grant。
- 昨日的 ContrAgent 守的是工具迹。这条迹如果把触发回合记成用户主动要求，自动机会看成合法。合同要能记住「这段上下文在摄入时就被标脏」，而不是只看当前句子像不像命令。
- 昨日的工具幻觉论文守的是「名字在不在注册表」。爆炸式提示调用的可以是真工具、真参数。解析通过之后，仍要有一条跨回合的污点：不可信内容里的条件，不能靠后续用户口头禅解封。

## 深挖二：工具排序的误差方向会翻，弃权又做不到

[arXiv:2609.22819](https://arxiv.org/abs/2609.22819)，Jiapeng Li，2026-09-19 投稿。工作论文第 2 版。代码与材料：https://github.com/jaxblack/counterfactual-tool-ranking

问题是：比较两个工具策略时，到底在估什么。作者把三件事拆开：权限（这个动作允不允许）、历史支持（日志里两种策略是否都出现过）、比较本身估计的是增量还是绝对值。设置是十一件可执行的企业风格工具、精确倾向的日志、真实的本地 MCP。先有 45 次合成实验，再用 30 次已实现回报的对照和 15 组实验去挑战它，后者用了 1,930 道独立发布的 BFCL 任务。

数字不要合成一个「双重稳健更好」：

- 线性、全回报：直接回归 MAE 0.0139，双重稳健 0.0272。一开始有利于双重稳健的结果被反过来。
- 环境移位之后：双重稳健更好，0.0227 对 0.0948。
- 按函数名分组且两组不相交的 BFCL 切分：平衡准确率直接法 81.85%，双重稳健 79.83%。
- 两份钉死版本的本地 Qwen2.5，同一套 200 道保留题、固定提示，明显不会弃权。
- 两种策略都不支持的动作会在差分里抵消，于是增量可以点识别，两边的绝对值仍然不能。保留分歧的回退在全部 5 次支持缺口运行里保住了这个性质。保守抽样界没有证明「换上它部署会更好」。

作者在摘要里写死了边界：这是可证伪的评估方法和一份公开证据，不是新的双重稳健估计器，不是官方 BFCL 榜分数，不是生产 agent 的安全声明。

和我们的用法：OpenClaw 自动化里，模型只在五个固定模板里选一个并填参数，不可逆动作是模板而不是模型临时发明的调用。那条约束不要换成「用历史回报给工具打分，分高的放行」。这篇论文说的是，历史支持不足时绝对值估不出来，模型在固定提示下又不肯说「都不该调」。排序器如果不会弃权，空授权会被它填上一个看起来最有用的工具。手机助手的 Policy 仍然由中枢执行：排序可以当候选，不能当 `waiting_user` 的替代。
