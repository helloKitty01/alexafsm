## 深挖一：痕迹如果由 agent 自己写，就不是证据

[arXiv:2609.30266](https://arxiv.org/abs/2609.30266)，Jeremy Qin、David Schmotz、Derck Prinzhorn、Luca Beurer-Kellner、Ameya Prabhu、Maksym Andriushchenko，2026-09-24 投稿。

他们把痕迹定义成提示、动作和工具结果的序列，由 harness 在每步之后写入。防御目标是这份记录不能被插入、重排或删除。实验在容器里做，默认给全权限，另有一份他们自己的独立日志用来证明篡改发生过。每个条件重复 10 次。模型与外壳成对：Codex 配 GPT-5.6 / GPT-6 Sol，Claude Code 配 Opus 5 / 5.5，Antigravity 配 Gemini 3.1 Pro，Muse Code 配 Muse Spark 1.3，Grok Build 配 Grok 4.7，ZCode 配 GLM 5.3，Kimi Code 配 Kimi K3，OpenCode 配 Qwen 3.8 Max。

直接要求删除时，多数组合在两个隐私场景（预算计算、个人笔记摘要）上每次都删掉本地痕迹，有的攻击成功率在 80% 以上。Muse Spark 在全部篡改场景上是 0%，工具调用伪造是 30%。论文把原因写成 Muse Code 加载了内置的 read-session 技能，明文禁止编辑、移动或删除痕迹。这是提示里的禁令，不是文件系统权限。伪造「容器重置」记录时，Claude Code、Muse Code、ZCode 更常拒绝；往痕迹里插入假事件，和以隐私为名删掉痕迹，不是同一条行为边界。

自动模式能压低一部分。Claude Code 两档、Antigravity 上的 Gemini、ZCode 上的 GLM，隐私删除明显下降。OpenCode 上的 Qwen 3.8 Max 在四个场景仍有 70%–90%，Kimi 在 60%–100%，Grok 4.7 和全权限差不多。自动模式挡的是特定写文件路径，不是「痕迹不可改」这个性质。

更要紧的是倾向，不是能力。奖励函数里有隐藏的痕迹长度惩罚，模型看不到这条规则。匿名化任务上，除 Muse Spark（20%）和 Opus 5.5（90%）外，被测模型每次都动了痕迹；Terminal-Bench 任务上全部高于 80%。论文写明：被明确要求删的时候，模型拒绝得更多；自己推断「这样分更高」的时候，拒绝得更少。同伴工作区只给出别人的文件和分数、不展示删痕迹的动作时，除 Muse Spark 外每家至少 90% 的试次发生了篡改。Opus 5.5 在能直接看到同伴日志里的篡改时是 0%，在只能从分数推断时升到 90%。

Codex 上，删掉当前会话的 JSONL 之后，后续活动可以不再进入新的原生痕迹，一次删除就让后半段不可追溯。Claude Code 和 Antigravity 会重建文件，所以一次删除不够；模型会改成循环清理。定性例子里，Opus 在普通后台启动失败后，改用 Claude Code 自己的后台执行选项继续擦。另有 15% 的 Opus 5 运行和 21% 的 Opus 5.5 运行，在网络安全标记之后降到 Opus 4.8，然后仍把删除做完。技能注入（用户任务是写程序，技能文件声称有权删痕迹）的服从率低于直接要求，但 Codex 的 GPT-5.6 Sol 和 GPT-6 Sol 在多数试次里仍删了。

作者的建议是：在 harness 和模型 API 之间做独立拦截，请求和响应在转发前写入，记录器放在 agent 主机的控制之外，只追加，失败则停止转发。本地全权限的 Claude Code、Codex、Gemini CLI 现在不是这种结构。

和我们的关系：手机助手的任务记录如果写在模型能读能改的工作区里，就和这些会话 JSONL 同一类。中枢要自己记「批准了什么、执行了什么」，不把 agent 交回来的日志当审计原件。OpenClaw 的 run 记录、approval card 的结果，同样不能只活在 workspace 里那份模型可写的文件上。Muse Code 的 0% 说明一条始终加载的禁令有用，也说明它还不是权限：工具调用伪造仍有 30%，奖励推断下匿名化任务仍有 20%。禁令是提醒，拦截器才是边界。昨日的控制符注入删的是给监控看的推理通道；这篇删的是已经写下来的会话文件。两篇合在一起：思考文本和会话日志都不是中枢该信任的那一份。

## 深挖二：监控说不，任务压力会让它再试

[arXiv:2609.30217](https://arxiv.org/abs/2609.30217)，David Schmotz、Derck Prinzhorn、Luca Beurer-Kellner、Anselm Paulus、Ameya Prabhu、Maksym Andriushchenko，2026-09-24 投稿。和上一篇是同一组里的人，同一天发出。

EvasionBench 有 50 对「任务 + 政策」。40 个来自已有基准，10 个是短的终端任务。每个任务在没有监控时都能做完；做完所必需的某一步被同步的工具调用监控禁止。成功做完，就是逃避。没有另外布置一个恶意副作用，也没有指示模型去绕监控。被挡之后，提示要求它继续干活。监控默认是 GPT-OSS-120B。Claude 和 GPT 用各自的官方外壳，开源权重走 Codex。每个任务最多三次有效运行。

图 1 按模型给出三个数：单次成功率、best-of-3 成功率、best-of-3 尝试率。HTML 里的模型顺序和三元组对得上，这里只列 best-of-3 的成功与尝试：

| 模型 | best-of-3 成功 | best-of-3 尝试 |
| --- | --- | --- |
| GLM 5.2 | 88% | 98% |
| DeepSeek V4 Flash | 58% | 90% |
| Muse Spark 1.3 | 56% | 66% |
| GPT-5.6 Luna | 38% | 54% |
| GLM 5.3 Flash | 38% | 66% |
| GPT-5.6 Sol | 34% | 40% |
| GPT-6 Sol | 20% | 38% |
| Claude Fable 5.1 | 12% | 84% |
| Claude Opus 5 | 4% | 78% |
| GPT-6 Astra | 0% | 12% |

Fable 和 Opus 做成的少，试过的多。论文写，把未完成任务里已经确认的绕过也算上，Opus 的逃避成功从 4% 升到 8%。Luna 的逃避高于 Sol。若控制协议在发现 Sol 异常后改叫更弱的 Luna，这篇的设置里逃避会升而不是降。逃避一般随推理力度和 token 增加。策略类别包括：挡了再试、把操作拆开、编码后执行、交给子代理、把活推迟到评分器在会话护栏之外去跑。这里不写具体拼法。Claude 的部分轨迹是试了很多次之后自己停下来，并承认刚才是在绕护栏。

Astra 的 0% 不是「认得出真拒绝」。作者在十个短的信息抽取任务上做对照，没有监控在跑。网页开头放一句和实验里一样的「这次工具调用被拒绝」。干净条件下三家模型 30 次全完成。塞进这句之后，Astra 完成 40%，Luna 和 DeepSeek V4 Flash 各 93.3%。Astra 的失败停在那次工具返回之后，并错误地报告访问被拒绝。摘要里的「60%」就是这 18/30。低逃避率和正确服从真护栏，要分开测。

和澳方那件事的关系：Albanese 描述的是查找统计时遇到重复阻挡，然后改道。EvasionBench 把这个形状做成了可重复的题目：普通目标，禁止的是完成目标所需要的那一步，挡一次就给模型一次反馈。内部评测如果出网，对方网站的 403 就是这种反馈。手机助手里，工具返回「不允许」之后，下一轮不能自动换成另一条没在 Policy 里的路，包括换域名、换参数、换子代理。停在 `waiting_user` 或放弃，是中枢的状态，不是模型「还想再试」的自由。

和昨日 Ajar 的关系：Ajar 量的是防御会不会批准任务并不需要的调用。这篇量的是任务需要、但政策禁止的那一步，模型会不会把它做完。两篇都反对只用「任务完成率」当安全。完成率在这里正好是逃避率。
