基于 Skill 的 Agent Loop 端到端时延：拆解与分类

六类问题 · 两类杠杆 · 一个分析框架
T ≈ Σi=1..N ( TTFT + nout×tdecode + T安全校验 + T工具执行 )

N（loop 次数）是乘数，减一次 loop 省下整个单 loop 成本；括号内各项是单 loop 内的加数。所有优化都落在这两类杠杆上。

单 Loop 成本（上）：Skill 加载与参数生成

问题点 ① ② · 一个减 loop、一个减 token
①Skill 加载耗时 每次加载 = 一整个 loop（TTFT + 生成 + 工具执行），2s 起
典型问题
  • 加载"有时一次、有时两次"，先归因：是 search + load 两步，还是 load 错了重载——解法完全不同
  • 预加载若注入 system prompt，会击穿 KV cache（前缀全灭）
优化方向
  • 索引常驻稳定前缀：全量 skill 索引（名称+一句话描述）放静态区，模型直接 load，消掉 search 那次 loop
  • 按检索置信度分流：高置信 → 框架预取正文，随当轮 user message 被动注入（0 额外 loop，不破坏缓存）；低置信 → 模型主动 load
  • 会话内已加载的 skill 留在消息流历史里，不重复加载
②工具调用生成耗时（输出 token 数） 30ms/token，参数越长解码越久
典型问题
  • 参数直接输出原始绝对路径 / 长标识符，最多 300 token → 仅解码就 9s
  • 凭记忆写 bundleName 等标识符 → 幻觉，错一次再赔一个 loop
/data/storage/el2/base/.../report.pdf
~40 token，且易抄错 vs f1
1 token 短句柄
优化方向
  • 变量方案（已有设计）：${app.抖音.bundleName}，框架拦截器查表求值，顺带结构性消除标识符幻觉
  • schema 改写：把 bundleName 重定义为 appName，模型直接写"抖音"，零学习成本，主场景优先
  • 短句柄：工具结果里的长路径/长 ID 登记短句柄（f1），后续模型传句柄、拦截器还原，全工具通用
  • schema 卫生：默认值、枚举化、相对路径 + 会话级 cwd

单 Loop 成本（下）：安全校验、工具执行与推理性能

问题点 ③ ⑤ · 框架侧优化 + 模型/缓存侧优化
③安全校验与工具执行时长 校验 500ms 固定税 · 三个正交手段可叠加
典型问题
  • 每次工具调用前无差别同步校验 500ms，只读查询也要付
  • 个别工具本身执行超长，阻塞整个 loop
优化方向
  • 分级（按需校验）：只读/幂等工具白名单跳过同步校验、改异步审计；高危（删除/权限/支付）保留完整同步校验
  • 并行（藏进解码时间）：工具调用参数在输出流中完整出现的瞬间即开始校验，与模型剩余输出并行，多数情况体感为零
  • 缓存：相同（工具, 归一化参数）的校验结果复用；校验若走 LLM 判定，前置本地规则引擎，不确定才升级
  • 工具执行：独立超时预算（超时信息返回模型而非挂死）；天然长耗时工具异步化，返回任务句柄后续轮询
⑤推理性能（TTFT + 增量 token 时延） TTFT 1300ms · 增量 30ms/token · 候选模型 glm5.2 / deepseek v4
典型问题
  • TTFT 1300ms 中 prefill 占比未测——动态 skill 注入 system prompt 导致每 query KV cache 全量失效，是 prefill 的主要嫌疑
  • 只按裸时延选模型，忽略正确率下降对 loop 次数的反噬
优化方向
  • KV cache 排布（已有讨论）：动态内容移出 system prompt、消息流 append-only，前缀命中后 TTFT 可望降到数百 ms
  • 模型评测算总账：真实 trace 上比"工具调用正确率 × 时延"——错一次多付一整个 loop（2~11s）
  • 按 loop 类型路由：简单"选工具填参"用快模型 + 关/缩思维链；规划、纠错步骤用大模型
  • 限制无效输出：skill 中明确"直接输出工具调用，不复述计划"，省数十~上百 token

减少 Loop 次数与快慢双系统 · 优先级路线

问题点 ④ ⑥ · 乘数杠杆 + 长期架构
④工具 loop 效率（减少 loop 次数） 先做数据挖掘：高频调用序列 + 每工具首调失败率
典型问题
  • 幻觉先错后对：首次调用出错，反思后才正确，每错一次赔一个 loop
  • 工具粒度不合理：本可合并为一个的被拆成多个，串行多次往返
  • 相互独立的调用被串行执行（本可并行）
优化方向
  • 结构性消幻觉：变量方案 / 封闭词表注入（模型从列表选名，不自由发挥）
  • 错误消息工程：失败的 tool result 自带纠错线索（如附上应用列表），保证纠错一次到位而非多次试探
  • 复合工具 / 批量参数：日志挖掘高频二元/三元序列后合并；同类操作支持数组参数，N 次变 1 次
  • 并行工具调用：模型一次输出多个独立调用、框架并发执行——低成本高收益，常被忽略
⑥慢系统 → 快系统迁移（skill+loop → function call） 长期项 · "编译"关系而非替代关系
定位与边界
  • 慢系统 = 解释器（处理长尾），快系统 = 编译产物（小模型 FC，高频任务 1~2s）
  • 快系统只接：单意图、无条件分支、不需环境反馈的任务
关键设计
  • 三态路由：高置信→快；低置信/多步→慢；快系统失败→回退慢。回退时快系统时延白付，路由阈值要保守
  • 数据飞轮：慢系统成功轨迹 = 快系统训练/评测集；回退 case 反哺路由阈值
  • 一致性：两系统共享工具执行层（含拦截器）与安全校验，避免行为漂移
