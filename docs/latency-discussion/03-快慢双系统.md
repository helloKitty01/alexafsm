# 03 快慢双系统

对应原始问题点 6：慢系统（skill + loop，大模型）向快系统
（function call，更小模型）迁移。长期项，先讨论设计，不着急启动。

## 定位：编译关系，不是替代关系

慢系统是**解释器**：靠大模型 + skill 现场推理，能处理长尾和新任务，但慢。
快系统是**编译产物**：把慢系统里反复跑通的高频轨迹，固化为小模型的
意图识别 + 参数抽取 + 固定工具（序列）调用。

推论：快系统的能力边界由慢系统的成功轨迹数据决定——
**先有慢系统的日志积累，才有快系统的训练与评测集**。这是它排在优先级最后的原因，
也是为什么埋点测量（优先级 0）同时是本项的前置依赖。

## 路由设计：三态

```text
          ┌─ 高置信命中快系统能力集 ──→ 快系统（小模型 FC，数百 ms）
query ──→ 路由器
          └─ 低置信 / 长尾 / 多步 ────→ 慢系统（skill + loop）

快系统执行失败 / 参数抽取置信度不足 ──→ 回退慢系统
```

- **回退成本**：回退时快系统的时延白付，且总时延比直接走慢系统更差。
  所以路由阈值要保守：宁可把边缘 case 直接给慢系统，
  也不要让快系统"试一下不行再说"。
- 路由器本身必须极快（小分类模型或向量检索，几十 ms），否则给全部流量加税。

## 快系统的能力边界（收敛原则）

只接同时满足以下条件的任务：

1. **单意图**：一句话一个明确目标；
2. **无条件分支**：执行路径不依赖中间结果做决策；
3. **不需环境反馈**：不需要"看一眼再决定"（固定工具序列可以，动态编排不行）。

多步规划、纠错、探索类任务永远留在慢系统。
试图让快系统处理边界外任务，失败回退的代价会吃掉全部收益。

## 一致性约束

两系统必须共享：

- **同一工具执行层**：包括 pre-call 拦截器（变量解析、短句柄还原），
  避免同一操作两套行为；
- **同一安全校验**：快不等于跳过校验，01 的分级/并行/缓存优化对两系统同样生效；
- **同一日志 schema**：快慢系统的轨迹可以互相对比、互相转化。

## 数据飞轮

```text
慢系统成功轨迹 ──蒸馏──→ 快系统训练/评测集
       ↑                        │
       └── 快系统回退的 case ←──┘（暴露能力边界，反哺路由阈值与训练数据）
```

- 慢系统每条成功轨迹自动标注为 (query, 工具调用序列, 参数) 样本；
- 高频意图达到样本量阈值后进入快系统能力集；
- 快系统回退的 case 是最有价值的负样本。

## 预期收益量化（待实测校准）

| 路径 | 构成 | 端到端 |
| --- | --- | --- |
| 慢系统典型任务 | 2~4 loop × (TTFT 1300 + 生成 3000~9000 + 校验 500 + 执行) ms | 10~40s |
| 快系统 | 路由 ~50ms + 小模型 FC 数百 ms + 校验(优化后≈0) + 执行 | 1~2s |

若高频任务占流量的大头（待测量确认），P50 时延可望降一个量级；
P99（长尾走慢系统）由 01/02 的优化兜底。

## 开放问题

1. 高频任务的流量占比实际是多少？（决定本项 ROI，依赖埋点数据）
2. 小模型选型：通用小模型 FC 微调，还是 NLU 式意图分类 + 槽位抽取？
   后者更快但泛化差，可能按意图混合。
3. 路由器误判的用户体感：快系统答错 vs 慢系统偏慢，哪个伤害大？
   影响阈值取向。
4. skill 更新后如何同步失效快系统里对应的已编译能力？
   （工具 schema 变更、业务规则变更的传播机制）
