# 01 单 loop 成本优化

对应原始问题点 1（skill 加载）、2（工具调用生成）、3（安全校验与工具执行）、5（推理性能）。

## 1. skill 加载耗时（问题点 1）

### 先做归因：为什么"有时候一次，有时候两次"

两种成因解法完全不同，先在日志里区分：

| 成因 | 表现 | 解法 |
| --- | --- | --- |
| search + load 两步 | 先调 skill_search 再调 load_skill | skill 索引（名称 + 一句话描述）常驻稳定前缀（L0），模型直接 load，search 那次 loop 消失 |
| load 错了重载 | load A 后发现不对再 load B | 提升索引描述质量；skill 命名与描述的可区分性 |

### 预加载与缓存友好的张力

kv-cache 讨论的"通道二"（模型主动 load_skill）缓存友好，但天然 +1 loop（≈5s）。
预加载（框架检索后直接注入）省 loop，但注入位置决定缓存代价：
进 system prompt = 每 query 前缀全灭；随当轮 user message 注入（通道一）= 只增量 prefill。

**结论：混合策略，按检索置信度分流。**

```text
检索高置信（如 top-1 分数显著领先）：
  框架预取 skill 正文，随当轮 user message 被动注入（通道一）
  → 0 额外 loop，缓存只付增量 prefill

检索低置信 / 多候选：
  只靠 L0 常驻索引，模型自行 load_skill（通道二）
  → +1 loop，但避免注错 skill 浪费 token 与注意力
```

skill_search 由框架在模型调用前执行（几十 ms 量级），不占模型 loop，划算。
已加载的 skill 留在消息流历史里，会话内不重复加载。

### 预取（进一步优化，可选）

模型输出流中一旦出现 load_skill 的工具名与参数，框架即可开始读取 skill 正文，
与模型剩余输出并行——同"安全校验并行化"是一个模式（见第 3 节）。

## 2. 工具调用生成耗时（问题点 2）

已确认口径：平均 35 token ≈ 1.1s；长参数（原始绝对路径等）最坏 300 token → 仅解码 9s。
平均口径下增量已不是单轮大头（首 token 1.3s ≥ 增量），
本项定位为**长尾削峰**：封顶最坏情况、同时消除标识符幻觉。压缩输出 token 有三层手段：

### 2.1 变量方案（已有完整设计）

见 [`variable-resolution/`](../variable-resolution/工具参数变量解析机制方案.md)：
`${app.抖音.bundleName}` 替代长标识符，同时结构性消除幻觉（减 loop，见 02）。

注意事项：新语法有学习成本，模型写错变量语法会增加 loop 反噬时延。
所以能用 **schema 改写**（该文档 8.2 节：bundleName → appName，模型直接写"抖音"）
覆盖的主场景优先 schema 改写，变量语法保留为通用机制。

### 2.2 短句柄机制（通用化扩展）

变量方案解决"模型本来就不该知道的标识符"；短句柄解决"工具结果里出现过的长值"：

- 工具返回长路径 / 长 ID 时，框架在 tool result 中同时登记短句柄
  （如 `/data/storage/el2/base/haps/entry/files/report_2026.pdf` → `f1`）；
- 后续模型传 `f1`，pre-call 拦截器还原为真实值（复用变量解析的拦截器基建）；
- 对所有工具通用，模型少输出几十~几百 token，还避免长路径抄写错误。

### 2.3 schema 卫生

- 参数给默认值，模型只输出非默认参数；
- 能用枚举 / 布尔的不用自由字符串；
- 会话级 cwd 之类的全局状态放框架侧，路径参数支持相对路径。

## 3. 安全校验与工具执行（问题点 3）

500ms 固定税有三个正交的优化，可叠加：

### 3.1 分级（按需校验）

| 工具风险级 | 策略 |
| --- | --- |
| 只读 / 幂等（查询类） | 白名单跳过同步校验，改为异步审计留痕 |
| 可逆写操作 | 轻量规则校验 |
| 高危（删除、权限、支付） | 完整同步校验 |

### 3.2 并行（把校验藏进解码时间）

工具调用参数在模型输出流里**完整出现的瞬间**就开始校验，与模型剩余输出
（后续文本、第二个工具调用）并行。多数情况 500ms 能完全藏进解码时间，
体感为零。多工具调用时"校验第 N 个"与"执行第 N-1 个"流水线化。

### 3.3 缓存与校验自身提速

- 相同 `(tool, 归一化参数)` 的校验结果缓存复用；
- 若 500ms 来自 LLM 判定：前置本地规则引擎，规则能给出确定结论的不进 LLM，
  只在规则不确定时升级（此时也可用更小的判定模型）。

### 3.4 工具执行超长

- 每工具设独立超时预算，超时信息返回模型（含已完成部分），而非整体挂死；
- 天然长耗时的工具改异步化：提交后立即返回任务句柄，
  模型可继续其他步骤，后续轮询/回调取结果。

## 4. 推理性能（问题点 5）

### 4.1 TTFT：先测 prefill 占比

TTFT 1300ms 中 prefill 占比是关键。若占比高，
[`kv-cache-discussion/`](../kv-cache-discussion/) 的排布方案落地后、
前缀命中时 TTFT 应能降到几百 ms——两个讨论应合流推进。

### 4.2 增量 token：模型选择要算总账

glm5.2 vs deepseek v4 不建议只比时延，要在真实 trace 上比
**工具调用正确率 × 时延**：正确率下降会通过增加 loop 次数把省下的时延加倍还回去
（错一次 = 多付一整个 loop 的 5~11s）。

### 4.3 按 loop 类型路由模型

同一个任务内不同 loop 的难度差异很大：

- 简单的"选工具填参"步骤 → 快模型，且可关闭/缩短思维链；
- 规划、纠错、多约束步骤 → 大模型。

这也是 03 快慢双系统的会话内雏形。

### 4.4 限制无效输出

工具调用前的冗长"我现在要……"叙述纯付 30ms/token。
skill / system prompt 中明确"直接输出工具调用，不要复述计划"，
配合停止序列，可省数十~上百 token。
