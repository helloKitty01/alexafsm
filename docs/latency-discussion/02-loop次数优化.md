# 02 loop 次数优化

对应原始问题点 4。N 是时延方程的乘数：每减一次 loop 省下整个单 loop 成本（5~11s），
全局杠杆最大。skill 加载的 loop 已在 01 独立讨论，此处不重复。

## 先测量：loop 都花在哪

没有数据的合并是盲打。两个统计先行：

1. **高频工具调用序列**（二元 / 三元组）：哪些工具总是连着出现
   → 复合工具的候选清单，按频次 × 节省 loop 数排序。
2. **每工具首调失败率**：哪个工具经常第一次调错、反思后才对
   → schema / 描述 / skill 示例的问题定位。

## 成因一：幻觉先错后对

### 结构性消除（优先）

变量方案 / schema 改写（见 [`variable-resolution/`](../variable-resolution/工具参数变量解析机制方案.md)）：
模型永远只表达"哪个应用"，真实标识符来自查表，标识符类幻觉从机制上不可能发生。

### 封闭词表注入

模型自由发挥的地方尽量换成从封闭列表里选：
应用标准名列表、枚举参数、常见目录白名单——会话开始时由框架注入（不占 loop）。

### 错误消息工程（兜底纠错一次到位）

错误既然发生，目标就从"避免"降级为"纠错只付 1 次 loop"。
失败的 tool result 必须自带"怎么改对"的信息：

```text
差：  "error: app not found"           → 模型只能盲目试探，可能再错几次
好：  "未找到应用 XX。已安装应用列表：[抖音, 微信, ...]，请确认后重试"
                                        → 下一次 loop 必定改对
```

这是变量方案兜底设计的一般化：**每个工具的每种失败路径，都检查错误信息
是否包含足够的纠错线索**。

## 成因二：工具粒度不合理

### 复合工具 / 宏

把日志里的高频序列封装为一个工具：

```text
迁移前：getAllInstalledApps → forbidPermission        （2 loop）
迁移后：forbidPermissionByAppName("抖音", "麦克风")    （1 loop）
```

注意与变量方案的分工：变量方案已经把"查标识符"这类前置查询消掉了，
复合工具针对的是**真正的多步业务序列**（如"截图 → 裁剪 → 分享"）。
避免为每个场景造专用工具导致工具集膨胀（工具集变大又伤 prefill 和选择准确率），
只合并高频 + 稳定的序列。

### 批量参数

同类操作支持数组参数：`forbidPermission(apps=[...], permission=...)`，
N 个 loop 变 1 个。

## 成因三：本可并行的调用被串行执行

**并行工具调用**常被忽略、收益极大：模型一次输出多个相互独立的工具调用，
框架并发执行、一次性返回全部结果。

```text
串行：查天气(北京) → loop → 查天气(上海) → loop → 汇总     （3 loop）
并行：[查天气(北京), 查天气(上海)] 并发 → 汇总              （2 loop，且两次执行重叠）
```

- 模型侧：主流模型原生支持多工具调用输出，主要靠 skill / 提示词引导
  "相互独立的操作一次全部发出"；
- 框架侧：并发执行 + 结果按调用 ID 对应返回；
- 与 01 的流水线化叠加：第 1 个调用的校验/执行可在模型还在输出第 2 个调用时就开始。

## 成因四：模型"过度对话"

任务完成后多问一轮确认、中间步骤汇报进度，都各付一个 loop。
skill 中明确终止条件与"不需要中间汇报"，属于零成本改动。
