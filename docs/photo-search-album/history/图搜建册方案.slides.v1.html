图片搜索 × 创建相册 v1 · 1/6 问题与能力边界

按语义找一批图放进相册；同一句话再来时只处理还不在相册里的图；找图本身可能超过一次 500 张

讨论起点（原话压缩）

  • 两个 skill：图片搜索、创建相册；相册依赖搜图，搜图不强依赖相册
  • 搜索工具每次最多返回 500 张，超出要多次调用
  • 增量：「帮我把小猫的图片创建一个相册」→ 先找小猫再建册；一周后同一句话，期望只加新增的小猫
  • 需要给搜索工具加一个排除字段（排除小猫相册），搜索 skill 的工具要支持

拆成三个子问题

  1. 两个 skill 怎么依赖：相册用搜图，搜图不认相册
  2. 500 张/次上限：超出要翻页，不漏页、不提前停、不重复加
  3. 增量更新：搜索工具加可选 exclude_album，排除已在相册里的图

三个子问题分开说、合起来做：增量 = 找相册 + 带排除的搜索 + 翻页 + 幂等加入

能力边界与依赖方向（单向）

用户话术「找小猫的照片」→ 只搜
「把小猫的图片创建相册」→ 相册流程
→
创建相册 skill找相册 → 判断新建 / 增量
→ 搜图（增量带 exclude）→ 创建 / 追加
依赖 →
图片搜索 skill只讲：怎么查、怎么翻页、结果怎么交给下游
exclude_album 是可选参数，不写相册流程
→
搜索工具query / limit ≤ 500 / cursor
+ exclude_album（新增，可选）
「不强依赖」成立的条件：搜图 skill 单独可用；exclude_album 不填就是普通搜索；不要求「用搜图前先 load 相册 skill」

两条边界，先写明

  • 只加不删：相册里已有、这次不再命中的图默认保留；同步删除是另一条需求
  • 排除键是成员关系，不是时间：不用「上周之后拍的」代替「不在小猫相册里」——用户可能手动加过、拿掉过

每条带触发话术 / 期望动作 / 成功标准 · S3 与 S6 话术相似、策略相反，必须并列写
ID场景触发话术期望动作成功标准
S1只搜「找一下小猫的照片」只走搜图，不建相册能翻页；能告诉用户大约多少张
S2首次建册「帮我把小猫的图片创建一个相册」搜 → 建相册 → 全部加入相册存在；成员 = 本次全部命中（可能多页）

S7增量为空一周后没有新小猫告知「已是最新」不空跑创建、不误报「已添加」

S9中途失败第 2 页加入成功、第 3 页超时重试可续、不重复加入按成员去重（幂等）
S10跨会话一周后是新会话，没有上周上下文靠 find_album 发现已有册不依赖聊天记忆里的相册 ID

一个派生的坑（来自「排除键 = 成员关系」）

用户上周手动从相册里移出了 12 张误判的图；本周增量按「不在册」判断，会把这 12 张重新加回去。要么接受，要么相册记「移出记录」并一并排除——需要产品拍板（P6 附带项）。

图片搜索 × 创建相册 v1 · 3/6 两条主流程

首次建册与增量更新走同一条链路，差别只在：find_album 有没有命中、search 带不带 exclude_album

首次建册（S2 / S4）· 「帮我把小猫的图片创建一个相册」· 命中 1200 张

1. find_album("小猫")→ 没有
→
2. search("小猫", limit=500)→ 第 1 页 500 张
has_more=true, next_cursor=c1
→
3. create_album("小猫")→ album 句柄
→
4. add_to_album(album, ${r1.items})模型只写句柄，不抄 500 个 ID
→
5. search(cursor=c1) → add …直到 has_more=false
（第 2、3 页）
→
6. 汇报已创建「小猫」相册
共加入 1200 张

增量更新（S3 / S5）· 一周后同一句话 · 相册已有 320 张

1. find_album("小猫")→ 找到 1 本（320 张）
0 本→走首次；多本→S8 消歧
→
2. search("小猫", exclude_album=小猫)→ 排除后剩 18 张
has_more=false, total=18
→
3. 可选确认「已有 320 张，又找到 18 张新的，加进去吗？」
N 小可跳过；N 大或身份不确定时问
→
4. add_to_album(小猫, ${r2.items})幂等：已在册的跳过
→
5. 汇报已新增 18 张
（S7：0 张 → 「已是最新」）
排除后仍多页（S5）：第 2 步之后按上图同样方式翻页，每一页都是「排除后的 500 张」

skill 文本怎么分工

  • 搜图 skill：分页协议（has_more 为 true 就带 next_cursor 再搜）+ 一句「需要排除某相册里的图时填 exclude_album」
  • 相册 skill：找册 → 判断新建 / 增量 → 搜（增量带 exclude）→ 创建 / 追加 → 汇报；搜图用法直接写在正文（或编译期 include）

loop 账

增量 18 张：find + search + add = 3 个 loop（+1 次可选确认）。首次 1200 张：1 + 3 次搜 + 1 建 + 3 次加 = 8 个 loop——翻页驱动的可靠性是 P5 的第二条挑战。

图片搜索 × 创建相册 v1 · 4/6 工具契约草案

搜索工具加两类字段：cursor 翻页 与 exclude_album；相册工具三件：find / create / add（幂等、批量）

搜索工具（在现有基础上增量加字段）

search(
  query:         string        # 语义描述，如「小猫」
  limit:         int ≤ 500     # 单页上限（现有约束）
  cursor:        string?       # 翻页游标；首页不填
  exclude_album: string?       # 新增，可选：排除已在该相册中的图
)
→ {
  items:       [...]           # 本页图片（≤ 500）
  has_more:    bool
  next_cursor: string?
  total:       int?            # 排除之后的总数，用于汇报与确认
}

相册工具

find_album(name)
  → [{album, name, count}]   # 0 / 1 / 多 三种出口

create_album(name) → album

add_to_album(album, items)
  → {added, skipped}         # 幂等：已在册的跳过

# items 直接引用搜索结果句柄：
add_to_album(album, "${r1.items}")

exclude_album 与 album 都填可读名 / 句柄，模型不填内部 ID（对齐变量解析与变量句柄方案）。

正确性约束：排除必须发生在分页之前（不是体验优化）

✗ 错误：先取 500 再过滤

search("小猫", limit=500)          # 前 500 张里 480 张已在册
→ 客户端丢掉已在册的 → 本页只剩 20 张
→ has_more 按原始 500 判断 … 或模型以为「只有 20 张新的」就停了
后面还有几百张新图，系统性漏掉

✓ 正确：引擎内 query ∧ ¬in(album) 之后再 limit / cursor

search("小猫", exclude_album=小猫, limit=500)
→ items = 排除后的前 500 张新图
→ total = 800（排除后总数）, has_more=true, next_cursor=c1
500 的含义 = 「排除后的一页最多 500」
配套：用 cursor 而不是 offset——边翻页边往相册加图时 offset 会错页；add_to_album 幂等——即使某页被重复加入，结果仍正确

图片搜索 × 创建相册 v1 · 5/6 方案依赖与挑战

依赖按层列；挑战按会不会把方案做穿排序

方案依赖（按层）

搜索工具可选 exclude_album，排除在引擎内、分页之前；稳定 cursor + has_more；能给排除后 total
相册工具find_album 按名查找（重名返回多本）；add_to_album 幂等、批量 500
图库索引高效做「语义命中 ∩ 不在某相册」；相册成员要有索引，否则每次排除 = 拉全量成员做差集
框架结果句柄 ${resultId.items}：500 张 ID 不进上下文、模型不抄写
产品策略S3 vs S6 默认与确认门槛；重名消歧；是否排除「移出记录」
skill 文本搜图：分页协议 + 可选排除；相册：找册 → 判断 → 搜 → 加 的完整流程

挑战（按风险排序）

  1. 做穿排除 × 分页的正确性：exclude 不在引擎里做，500 上限就系统性漏图；客户端过滤不算支持
  2. 做穿翻页谁驱动：模型翻页常见失败 = 翻完第一页就停 / 漏传 cursor / 抄错 ID；另一路是相册工具内部吞掉翻页（add_from_search），一次调用完成一个用户动作但绑得更紧
  3. 意图同一句话两种意图：「创建相册」既像首次创建也像「整理成册」；没有「已有同名册则增量」的规则，S3 / S6 撞车
  4. 身份相册身份：新会话没有上周相册；依赖 find_album，重名 / 改名 / 已删除各要有出口
  5. 体积一页 500 张 ID 进模型既贵又易抄错 → 句柄引用，真实列表在框架侧
  6. 幂等add 天然幂等是重试安全的前提；不能按「任务已执行」去重
  7. 边界手动移出的图会被增量加回（只加不删 + 排除键 = 成员）
  8. 语义语义检索是排序不是过滤：翻到后几页精度下降，增量拿到的是首次没进前 N 的图；total 口径要说清或不承诺
  9. 规模首次 3000 / 增量 800：先报数再动手，大规模转后台任务、可中断

图片搜索 × 创建相册 v1 · 6/6 待拍板与下一步

三件事定了，skill 怎么写、工具 schema 怎么加字段就不会来回改

① 同一句话已有同名册，默认怎么办

  • A. 增量（推荐）：配一句确认兜住——「小猫相册已有 320 张，又找到 18 张新的，加进去吗？」；N 小直接加，N 大或身份不确定时问
  • B. 每次新建一本
  • C. 先问用户

「再创建一个 / 重新做一本」明确走新建（S6），新册名加后缀不覆盖。

② 「小猫相册」怎么认定

  • 名称匹配为主：find_album(name) 返回 0 / 1 / 多本
  • 多本 → 必问（S8），不把 exclude 糊上去
  • 可选增强：相册记录「来源 query」，改名后仍能认出、「小猫 / 猫咪」归一化在 query 层做

名称只是显示名，内部仍是 ID；模型填可读名，由工具解析。

③ 翻页谁来做

  • a. 模型按 skill 翻页：灵活、搜图保持通用；loop 多、易中途停
  • b. 相册工具内部吞掉翻页：一次调用一个用户动作、正确性好；相册工具变重
  • 建议：首期 a，页数多（如 > 3 页）转后台任务；看日志决定是否合成 b

附带项：是否排除「移出记录」（P2 派生坑）。

动手前先核实的事实

  • 现有搜索工具是 cursor 还是 offset 翻页；能否在引擎内做「命中 ∩ 不在某相册」
  • 500 的出处：引擎每页上限（可翻）还是总量上限（top-K 翻不下去）——后者 exclude 是唯一解
  • 相册 add 现在是否幂等；相册是否有成员索引；是否记录「移出」
