讨论起点 原话压缩

  • 两个 skill:图片搜索、创建相册;相册依赖搜图,搜图不强依赖相册
  • 搜索工具每次最多返回 500 张,超出要多次调用
  • 「帮我把小猫的图片创建一个相册」→ 先找小猫再建册;一周后同一句话,期望只加新增的小猫
  • 需要给搜索工具加一个排除字段(排除小猫相册),搜索 skill 的工具要支持

拆成三个子问题 分开说,合起来做

  • ① 依赖:相册用搜图,搜图不认相册 → skill 层单向
  • ② 500 上限:多批取数不漏、不提前停、不重复加
  • ③ 增量:「不在册」怎么定义、在哪一层排除

两条边界,先写明

  • 只加不删:相册里已有、这次不再命中的图默认保留;同步删除是另一条需求
  • 排除键是成员关系,不是时间:不用「上周之后拍的」代替「不在小猫相册里」——用户可能手动加过、拿掉过。由此派生:用户主动移出的图不能被增量加回(S11)

①

同名相册,默认增量,多本才问

当前:没有规则,模型每次问或每次新建 → 目标:默认增量;只有多本同名才和用户交互;「再创建一个 / 重新做一本」显式新建。
找册来源对话历史里有本意图产生的相册句柄(如 ${r3.album})→ 直接用,工具端校验存在性;否则 find_album(name)。校验失败(已删 / 改名)回落到按名查找,不报错给用户 三种出口0 本 → 首次建册;1 本 → 增量,不问;多本 → 问「用哪本」,问句带各本成员数与最近修改时间 确认门槛增量前先报数:「已有 320 张,又找到 18 张新的」;N 小直接加,N 大(阈值待定)再确认;total=0 → 「已是最新」 显式新建话术清单写进相册 skill;新册名加后缀不覆盖旧册
②

排除语义 = ¬in(members ∪ removed)

当前:「不在册」= 不在 members,用户移出的图下次会被加回(S11)→ 目标:相册服务多存一份 removed,排除时一并算进去。
存什么每本相册除 members 外多一个 removed: Set<photo_id>——用户从这本相册显式移出过的图 谁写相册服务的「从相册移除」操作;图库 UI 移出、助手移出都经过它。skill、搜索工具零感知 谁读检索引擎解析 exclude_album=A 时读 A.members ∪ A.removed 作为排除集 何时清用户手动把该图加回 A → 从 removed 删;图从图库删除 → GC;新建相册没有 removed 不做的不在助手侧记「我加过什么」再做差集——依赖助手持久化、还要给搜索传 ID 列表,位置放错了 话术可选:「另有 12 张是你之前移出的,不会加回」

备选:框架代练 工具改不动时

两个工具都不改。框架在结果信封里认出分页(has_more / next_cursor),当模型引用 ${r1.all_items} 这类「全集」句柄时,Resolver 在替换变量前把剩余页拉完、合并进 Working Memory 再喂给 add。是变量句柄方案 v4 的扩展;代价是 500 × N 个 ID 过框架内存、仍依赖 cursor。

复合工具的三条设计要求 对齐工具接入要求 04

  • 异步形态:1200 张要十几秒,属 long 档。阈值内同步返回;超过则返回任务句柄,后续查进度 / 完成回调,产品侧显示「已加入 800 / 约 1200」
  • 可中断、可续:取消时返回已加入数;重跑走同一循环,幂等保证不重复
  • 报数在前:复合工具不负责确认。相册 skill 先用 search(q, exclude_album=A, limit=5) 拿 total 报数——这一步仍是搜图 skill 的用法,依赖关系由此保住

什么时候不该合成复合工具

工具接入要求 §4.3:复合工具应由「高频 + 稳定」的序列驱动。这里 search → add 循环结构固定、次数由数据决定、中间不需要模型判断——正是最该内化的一类;若每页要让用户挑,就不该合。

关键推论:循环进了工具之后,游标对模型同样不可见——工具内部用什么方式翻页是实现选择,可以按引擎能力决定并后期切换,不改 skill。这是 P8 与 P11 的前提。

08优化 ④ 排除与游标的分工:exclude 定义「增量集合」,游标负责运行内定位;引擎能读己之写时两者合一三种翻页方式对比;「exclude 替代游标」成立的条件

✗ offset:边加边搜必漏

排除后有 1300 张新图。第 1 页 offset=0 拿 500 张并加入 → 「不在册」只剩 800。第 2 页 offset=500 = 跳过剩下 800 张的前 500 → 只返回 300 张,原第 501~1000 张永远漏掉,且 has_more=false 看起来一切正常。

△ cursor:正确,与时效性无关

keyset 游标编码「排序中的位置」(上一页最后一张的 score + photo_id),下一页 = 该位置之后且不在册。已加过的图位置在游标之前,不会再出现——不依赖索引是否已更新。代价:要有稳定排序、游标串要有人接力(当前是模型,目标是工具)。

✓ 排除即翻页:最简,但有前提

exclude_album 指向正在加的 A,反复 search(q, exclude_album=A),每次拿到「下一批不在册的 500 张」直到为空。不需要游标,首次与增量同一循环,重跑天然幂等。前提:add 之后 search 立刻看到新成员(读己之写),否则同一批反复回来——P9。

「exclude 替代游标」到底替代了什么

  • 模型视角:替代成立——模型不再需要理解、传递游标。但 P7 之后循环在工具里,游标本来就到不了模型;所以这项收益由 ③ 提供,与 ④ 用什么方式无关
  • 工具视角:exclude 与游标解决的是两个不同问题——exclude 回答「哪些图属于这次的增量集合」(跨运行,一周前的成员早已可见,时效无关);游标回答「这次运行内翻到哪了」(运行内,已加的图刚写入,时效敏感)
  • 结论:exclude 是增量语义的载体,必须有;游标是运行内定位的手段,引擎能读己之写时可以省掉(纯 exclude 循环),否则保留。两者对模型都不可见,可按引擎能力选择(P11)

正确性约束(两种方式共用)

  • 排除在引擎内、取 limit 之前完成:q ∧ ¬in(A) 再排序取 500;先取 500 再过滤,S5 直接做错
  • 排序稳定:同分按 photo_id 打破平局;同一 query、同一索引下顺序确定
  • add 幂等:即使某批重复加入,结果仍正确,只是计数与时长受影响

边界

  • 翻页期间新入库的图本轮可能漏,下轮增量按成员关系补上——增量相对当前成员,不相对上次结果快照
  • 语义检索是排序不是过滤:后几批精度下降;total 按阈值以上计数或不承诺
  • S1 纯搜索没有相册可排除,cursor 必须保留
相对 v2 的修正:v2 把「排除即翻页」列为首选;v2.1 改为「exclude 必有、游标按引擎能力保留」,因为纯 exclude 循环的正确性取决于索引时效——下面四页专门讲这件事。

11时效性专题 C · 工具内的翻页策略:三种写法,按引擎能力选择,对模型全部不可见推荐「exclude 播种 + 游标定位」——不依赖 T_sync,也不放弃增量语义

策略 1 · 纯 exclude 循环 需 T_sync ≈ 0

loop:
  p = search(q, exclude=A, 500)
  if 空: break
  r = add(A, p.items)
  if r.added == 0: raise

最简;翻页状态就是相册本身。只在 P10 实现二下成立。

策略 2 · exclude 播种 + 游标定位 推荐

p = search(q, exclude=A, 500)      # 播种
loop:
  if 空: break
  add(A, p.items)                  # 幂等
  p = search(q, exclude=A, 500,
             cursor=p.next_cursor) # 定位

exclude 定义增量集合(旧成员早已可见);游标保证已加的图不会再出现——与 T_sync 无关。两种实现下都正确。

策略 3 · exclude + 有界等待 兜底

loop:
  p = search(q, exclude=A, 500)
  if 空: break
  r = add(A, p.items)
  if r.added == 0:
    退避等待, 重试 ≤ N 次, 仍 0 则报错

把硬失败变成时延;只在既无游标、又无读己之写时用,并向用户展示进度。

决策表 按 V1 / V2 / V3 的核实结果对号入座

引擎能力读己之写cursor采用说明
查询时反连接(P10 实现二)✓有 / 无策略 1(或 2)纯 exclude 即可;有 cursor 时用策略 2 更稳,代价为零
烘进索引(P10 实现一)✗ T_sync 几十秒有策略 2游标绕开时效;exclude 只在播种与每页过滤旧成员时起作用
烘进索引✗无,仅 offset策略 3 + 推动加 cursoroffset 边加边搜必错(P8);等待重试是过渡,不是终态
引擎 top-K 有总量上限(V3)——exclude 是唯一解不排除则前 500 全是旧成员;此时读己之写成为硬要求,或运行内改用「exclude_ids = 本轮已加」

为什么这件事可以后置

  • 三种策略的输入输出相同:add_from_search(A, q) → {added, rounds};skill 与模型看不到差别
  • 可以先上策略 2(最保守),引擎升级到实现二后切策略 1,零 skill 改动
  • 唯一要在 schema 上预留的:search 同时支持 exclude_album 与 cursor 并用
一句话:exclude 负责「哪些是增量」,游标负责「翻到哪了」;引擎能读己之写时省掉游标是优化,不是前提。

12时效性专题 D · 对其他步骤的影响与验收:报数、连续两次调用、跨会话;怎么测、看什么指标时效性不只影响循环本身

影响 1 · 报数步骤 ② search(q, exclude=A, limit=5) → total

正常顺序是先报数再加,不受影响。但用户在 add_from_search 刚结束时立刻再说一遍同一句话:T_sync 未过,total 会把刚加的算成新图 → 「又找到 500 张新的」是误报;随后 add 幂等 → added=0,汇报与承诺不一致。

处理:复合工具结束前等排除集追上再返回(有界等待);或返回 syncing=true,skill 话术改「约 N 张、正在同步」;策略 1 / 实现二下不存在此问题。

影响 2 · 运行间隔很短的两次增量

两次 add_from_search 间隔 < T_sync:第二次的播种搜索会拿到第一次刚加的图 → 幂等兜住结果(不重复),但 rounds 多一轮、「新增 N」偏大。可接受,记入指标观察。间隔一周(S3)完全无影响。

影响 3 · removed 的时效

用户刚移出 12 张就说「把小猫创建相册」:实现一下 removed 也要同步,窗口内会被加回;实现二下立即生效。这是推荐实现二的又一个理由。

观测指标

  • T_sync 分布(P50 / P95):成员写入到排除集可见的延迟;决定策略选择是否需要调整
  • added == 0 触发率:目标 ≈ 0;> 0 说明策略与引擎能力不匹配
  • 单次 add_from_search 时长与 rounds:rounds 明显大于 ⌈total / 500⌉ 即有重复批

验收用例 在测试环境人为注入索引延迟

用例条件通过标准
S5-延迟增量 1300 张;注入 T_sync = 30 s全部加入;rounds = 3;不触发 added=0 护栏;总时长不含等待
S4-延迟首次 1200 张;T_sync = 30 s同上;首次与增量行为一致
连续调用结束后 2 s 内再说同一句汇报「已是最新」或「约 N 张、同步中」,不承诺错误的 N

13工具契约 v2.1:搜索工具加两个可选参数,相册加一个复合工具,相册服务加一份 removedexclude_album 与 cursor 可并用;模型填可读名 / 句柄,不填内部 ID

搜索工具 只加可选参数与返回字段,老调用方不受影响

search(
  query:          string          # 语义描述,如「小猫」
  limit:          int ≤ 500       # 单次上限(现有约束)
  cursor:         string?         # 运行内定位 / 纯搜翻页;可与 exclude 并用
  exclude_album:  string?         # 新增:排除已在该相册的图(members∪removed)
) → {
  items:        [...]             # 本批 ≤ 500
  total:        int?              # 排除后的总数(阈值以上),用于报数
  has_more:     bool
  next_cursor:  string?
}

约束:排除在引擎内、取 limit 之前完成;排序稳定(同分按 id);exclude_album 填可读名或历史句柄。

相册工具

find_album(name)   → [{album, name, count, updated_at}] # 0/1/多

  | {task_id}                                     # 长耗时异步

内部翻页策略按 P11 选择,不暴露给调用方;syncing 供 skill 调整话术(P12)。
