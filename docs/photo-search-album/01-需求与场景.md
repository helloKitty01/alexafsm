# 01 需求与场景：图片搜索 skill × 创建相册 skill（含 500 条分页与增量更新）

> 讨论起点（原话）：
> 我有一个图片搜索 skill，还有一个创建相册 skill，创建相册依赖图片搜索 skill，图片搜索 skill 不强依赖创建相册 skill；
> 搜索 skill 里的搜索工具每次只能返回 500 张图片，用户图片超出时需要多次；
> 还有增量更新场景：「帮我把小猫的图片创建一个相册」→ 先找小猫，再创建相册；一周后再说同一句话，
> 期望的是新增的小猫，而不是之前已经加进去的 → 需要给搜索工具增加一个排除字段（排除小猫相册）。
> 先把需求和场景描述清楚，再谈方案的依赖和挑战。

---

## 一、一句话钉住问题

**按语义找一批图，放进一个相册；同一句话再来一次时，只处理「还不在这个相册里」的图；找图这件事本身可能超过一次 500 张。**

三个子问题，分开说、合起来做：

1. **两个 skill 怎么依赖**：相册用搜图，搜图不认相册。
2. **500 张/次的上限**：超出时要翻页，翻页不能漏、不能提前停。
3. **增量更新**：搜索工具加一个可选的排除字段，排除「已在某相册里的图」。

## 二、能力边界与依赖方向

```text
创建相册 skill ──依赖──► 图片搜索 skill      （相册流程的第一步就是搜图）
图片搜索 skill ──不依赖► 创建相册 skill      （「找小猫的照片」可以单独用）

搜索工具 exclude_album（可选参数） ◄── 由相册 skill 传入；搜图单独使用时不填
```

写法上的两条纪律，保证「不强依赖」是真的：

- 搜图 skill 正文只讲：怎么查、怎么翻页、结果怎么交给下游。`exclude_album` 写成「如果调用方要排除某个相册里的图，填这个参数」，不写相册业务流程。
- 相册 skill 正文写完整流程：找相册 → 判断新建还是增量 → 搜图（增量时带 `exclude_album`）→ 创建/追加。搜图的调用方式在相册 skill 里写清楚（或编译期 include 搜图的用法片段），不要求「用相册前先 load 搜图 skill」。

## 三、场景矩阵

每条场景带：触发话术、期望动作、成功标准。S3 和 S6 表面话术相似、策略相反，必须并列写。

| ID | 场景 | 触发话术 | 期望动作 | 成功标准 |
| --- | --- | --- | --- | --- |
| S1 | 只搜 | 「找一下小猫的照片」 | 只走搜图，不建相册 | 能翻页；能告诉用户大约多少张 |
| S2 | 首次建册 | 「帮我把小猫的图片创建一个相册」 | 搜 → 建相册 → 全部加入 | 相册存在；成员 = 本次全部命中（可能多页） |
| S3 | 增量更新 | 一周后同一句话 | 找到已有「小猫」相册 → 带 `exclude_album` 搜 → 只加新图 | 旧图不重复进册；用户感知「新增了 N 张」 |
| S4 | 超过 500 | 命中 1200 张 | 翻 3 页，每页都加入 | 不丢页、不提前停、不重复加 |
| S5 | 增量也超过 500 | 排除后仍有 800 张新图 | 排除后再分页，翻 2 页 | 500 是「排除后的一页」，不是「先取 500 再过滤」 |
| S6 | 再做一本 | 「再创建一个小猫相册」「重新做一本」 | 新建，不增量 | 不写进旧相册；新册名字不冲突 |
| S7 | 增量为空 | 一周后没新小猫 | 告知「已是最新，没有新图」 | 不空跑创建、不误报「已添加」 |
| S8 | 重名相册 | 已有两本叫「小猫」 | 先问用哪本，再增量 | 不默默写进错的那本 |
| S9 | 中途失败 | 第 2 页加入成功、第 3 页超时 | 重试可续、不重复 | 加入按成员去重（幂等），重试不产生重复 |
| S10 | 跨会话 | 一周后是新会话，没有上周上下文 | 靠「查找相册」工具发现已有册 | 不依赖聊天记忆里的相册 ID |

两条边界，先写明避免后期返工：

- **只加不删**：相册里已有、但这次搜「小猫」不再命中的图，默认保留；「同步删除」是另一条需求。
- **排除键是「成员关系」，不是时间**：不要用「上周之后拍的」代替「不在小猫相册里」——用户可能手动加过、也可能手动拿掉过。
  - 由此派生一个坑：用户上周手动从相册里**移出**了 12 张误判的图，本周增量按「不在册」判断会把它们**加回去**。要不要记「移出记录」一并排除，需要产品拍板（见第七节）。

## 四、两条主流程

### 4.1 首次建册（S2 / S4）

```text
用户：帮我把小猫的图片创建一个相册
 1. find_album("小猫")            → 没有
 2. search("小猫", limit=500)      → 第 1 页 500 张, has_more=true, next_cursor=c1
 3. create_album("小猫")           → album 句柄
 4. add_to_album(album, 第 1 页)
 5. search("小猫", cursor=c1)      → 第 2 页 …  → add_to_album …
    …直到 has_more=false
 6. 汇报：已创建「小猫」相册，共加入 1200 张
```

### 4.2 增量更新（S3 / S5）

```text
用户（一周后）：帮我把小猫的图片创建一个相册
 1. find_album("小猫")                          → 找到 1 本（320 张）
 2. search("小猫", exclude_album=小猫, limit=500) → 排除后剩 18 张, has_more=false
 3. （可选确认）「小猫相册已有 320 张，又找到 18 张新的，加进去吗？」
 4. add_to_album(小猫, 这 18 张)
 5. 汇报：已新增 18 张
```

排除后仍多页时（S5），第 2 步之后按 4.1 同样的方式翻页；每一页都是「排除后的 500 张」。

## 五、工具契约草案

### 5.1 搜索工具（在现有基础上加两类字段）

```text
search(
  query:          string            # 语义描述，如「小猫」
  limit:          int ≤ 500         # 单页上限（现有约束）
  cursor:         string?           # 翻页游标；首页不填
  exclude_album:  string?           # 新增，可选：排除已在该相册中的图片
)
→ {
  items:          [...]             # 本页图片（≤ 500）
  has_more:       bool
  next_cursor:    string?
  total:          int?              # 排除之后的总数（能给就给，用于汇报与确认）
}
```

要点：

- **排除在分页之前**：`query ∧ ¬in(album)` 之后再取 `limit`。若先取 500 再在结果里过滤，会出现「这页只剩几十张、后面还有新图却以为结束了」——S5 直接做错。
- **游标翻页**而不是 offset：边翻页边往相册里加图时，offset 会错页。
- `exclude_album` 收的是相册的可读名或句柄，模型不填内部 ID（对齐 [变量解析机制](../variable-resolution/工具参数变量解析机制方案.md)）。

### 5.2 相册工具

```text
find_album(name)            → [{album, name, count}]   # 0 / 1 / 多 三种出口
create_album(name)          → album
add_to_album(album, items)  → {added, skipped}          # 幂等：已在册的跳过并计入 skipped
```

`add_to_album` 的 `items` 建议直接引用搜索结果的句柄 `${searchResultId.items}`（对齐 [变量句柄方案](../agent-variable-scheme/agent-variable-scheme-v4.md)），不让模型抄 500 个 ID。

## 六、方案依赖

| 层 | 依赖项 | 说明 |
| --- | --- | --- |
| 搜索工具 | 可选 `exclude_album` 字段 | 增量场景的核心；排除必须在引擎内、分页之前完成 |
| 搜索工具 | 稳定的 `cursor` 翻页 + `has_more` | 超过 500 时的正确性基础 |
| 相册工具 | `find_album` 按名查找 | 跨会话认出已有相册；重名时返回多本供消歧 |
| 相册工具 | `add_to_album` 幂等、支持批量 | 中途失败可重试；一页 500 张一次加入 |
| 图库索引 | 高效做「语义命中 ∩ 不在某相册」 | 相册成员要有索引，否则每次排除都是拉全量成员再做差集 |
| 框架 | 结果句柄 `${resultId.items}` | 500 张 ID 不进上下文、模型不抄写 |
| 产品策略 | S3 vs S6 的默认与确认门槛；重名如何消歧；是否排除「移出记录」 | 不拍板则 `exclude_album` 没人敢用 |
| skill 文本 | 搜图 skill：分页协议 + 可选排除；相册 skill：找册→判断→搜→加 的完整流程 | 保持搜图通用、相册组合 |

## 七、挑战（按会不会把方案做穿排序）

1. **排除 × 分页的正确性**。`exclude_album` 若不在引擎里做，500 上限会系统性漏图。这是第一技术风险，也是判断「工具是否真的支持增量」的唯一标准——客户端过滤不算支持。
2. **多页翻页由谁驱动**。1200 张 = 3 次搜 + 3 次加。让模型翻页，常见失败是：翻完第一页就停、漏传 cursor、把 ID 抄错。两条路：
   - 模型翻页：skill 教模型「has_more 为 true 就带 next_cursor 再搜」，灵活但 loop 多、易中途停；
   - 工具内吞掉翻页：例如相册工具提供 `add_from_search(album, query, exclude_album)` 内部翻完所有页，一次调用完成一个用户动作，但相册工具与搜索实现绑得更紧。
   建议：首期允许模型翻页，但页数多时（如 > 3 页）转为后台任务；中期看日志决定是否合成复合工具。
3. **同一句话的两种意图**。「创建相册」在中文里既像首次创建，也像「帮我整理成册」。没有「已有同名册则增量」的产品规则，S3 和 S6 会撞车。
4. **相册身份**。一周后是新会话，上下文里没有上周的相册。增量依赖 `find_album`，重名、改名、已删除三种情况分别要有出口（S8 / 新建 / 新建）。
5. **返回值体积与抄写错误**。一页 500 张的 ID 或 URI 进模型，既贵又容易抄错；用 `${resultId.items}` 引用，真实列表在框架侧。
6. **幂等与部分失败**。`add_to_album` 天然幂等（已在册则跳过）是重试安全的前提；不能按「这次任务已执行」的假设去重。
7. **手动移出的图被加回**。「只加不删」+「排除键 = 成员」的组合会把用户主动拿掉的图重新加入；要么接受，要么相册记「移出记录」并一并排除。
8. **语义检索是排序，不是过滤**。「小猫」的命中是按相似度排的，翻到后面几页精度会下降；增量拿到的是首次没进前 N 的图，质量天然低于首次建册。`total` 的口径（阈值以上的数量）要说清楚，或者不承诺。
9. **规模与可感知**。首次 3000 张、增量 800 张，都该先报数再动手，大规模转后台任务并可中断，否则「创建相册」变成一次超长静默写入。

## 八、待拍板（三件事定了，skill 与工具字段就不会来回改）

1. **同一句话已有同名册时的默认策略**：A 增量（推荐，配一句确认兜住大规模或不确定的情况）/ B 每次新建 / C 先问。
2. **「小猫相册」怎么认定**：名称匹配为主，重名必问；是否给相册记录「来源 query」以便改名后仍能认出——可选增强。
3. **翻页谁来做**：模型按 skill 翻页，还是相册工具内部吞掉翻页；以及多少页以上转后台任务。

附带一条：是否排除「移出记录」（第七节第 7 条）。
