# 01 需求与场景：图片搜索 skill × 创建相册 skill（含 500 条分页与增量更新）

> 讨论起点（原话）：
> 我有一个图片搜索 skill，还有一个创建相册 skill，创建相册依赖图片搜索 skill，图片搜索 skill 不强依赖创建相册 skill；
> 搜索 skill 里的搜索工具每次只能返回 500 张图片，用户图片超出时需要多次；
> 还有增量更新场景：「帮我把小猫的图片创建一个相册」→ 先找小猫，再创建相册；一周后再说同一句话，
> 期望的是新增的小猫，而不是之前已经加进去的 → 需要给搜索工具增加一个排除字段（排除小猫相册）。
> 先把需求和场景描述清楚，再谈方案的依赖和挑战。

---

## 一、一句话钉住问题

**按语义找一批图，放进一个相册；同一句话再来一次时，只处理「还不在这个相册里」的图；找图这件事本身可能超过一次 500 张。**

三个子问题，分开说、合起来做：

1. **两个 skill 怎么依赖**：相册用搜图，搜图不认相册。
2. **500 张/次的上限**：超出时要多批取，不能漏、不能提前停、不能重复加——v2 由工具内部吞掉，模型不感知（第四节 ③）。
3. **增量更新**：搜索工具加一个可选的排除字段，排除「已在某相册里的图」（成员 ∪ 已移出），排除在取数之前。

> 本文 v2：第四节的三项已拍板；相对 v1 的主要变化是「排除即翻页」替代模型翻页、复合工具 `add_from_search` 吞掉循环、移出记录由相册服务维护。

## 二、能力边界与依赖方向

```text
创建相册 skill ──依赖──► 图片搜索 skill      （相册流程的第一步就是搜图）
图片搜索 skill ──不依赖► 创建相册 skill      （「找小猫的照片」可以单独用）

搜索工具 exclude_album（可选参数） ◄── 由相册 skill 传入；搜图单独使用时不填
```

写法上的两条纪律，保证「不强依赖」是真的：

- 搜图 skill 正文只讲：怎么查、纯搜索时怎么翻页、结果怎么交给下游。`exclude_album` 写成「如果调用方要排除某个相册里的图，填这个参数」，不写相册业务流程。
- 相册 skill 正文写完整流程：找相册 → 判断新建还是增量 → 带 `exclude_album` 搜一次报数 → 确认 → `add_from_search` 一次调用完成加入 → 汇报。搜图的调用方式在相册 skill 里写清楚（编译期 include 搜图的用法片段），不要求「用相册前先 load 搜图 skill」。
- 复合工具 `add_from_search` 在**服务层**调搜索服务，这是工具实现之间的依赖，不改变 skill 层的单向关系。

## 三、场景矩阵

每条场景带：触发话术、期望动作、成功标准。S3 和 S6 表面话术相似、策略相反，必须并列写。

| ID | 场景 | 触发话术 | 期望动作 | 成功标准 |
| --- | --- | --- | --- | --- |
| S1 | 只搜 | 「找一下小猫的照片」 | 只走搜图，不建相册 | 能翻页；能告诉用户大约多少张 |
| S2 | 首次建册 | 「帮我把小猫的图片创建一个相册」 | 搜 → 建相册 → 全部加入 | 相册存在；成员 = 本次全部命中（可能多页） |
| S3 | 增量更新 | 一周后同一句话 | 找到已有「小猫」相册 → 带 `exclude_album` 搜 → 只加新图 | 旧图不重复进册；用户感知「新增了 N 张」 |
| S4 | 超过 500 | 命中 1200 张 | 翻 3 页，每页都加入 | 不丢页、不提前停、不重复加 |
| S5 | 增量也超过 500 | 排除后仍有 800 张新图 | 排除后再分页，翻 2 页 | 500 是「排除后的一页」，不是「先取 500 再过滤」 |
| S6 | 再做一本 | 「再创建一个小猫相册」「重新做一本」 | 新建，不增量 | 不写进旧相册；新册名字不冲突 |
| S7 | 增量为空 | 一周后没新小猫 | 告知「已是最新，没有新图」 | 不空跑创建、不误报「已添加」 |
| S8 | 重名相册 | 已有两本叫「小猫」 | 先问用哪本，再增量 | 不默默写进错的那本 |
| S9 | 中途失败 | 第 2 页加入成功、第 3 页超时 | 重试可续、不重复 | 加入按成员去重（幂等），重试不产生重复 |
| S10 | 跨会话 | 一周后是新会话，没有上周上下文 | 靠「查找相册」工具发现已有册 | 不依赖聊天记忆里的相册 ID |
| S11 | 手动移出 | 上周从相册里移出了 12 张误判的图 | 增量**不把它们加回** | 排除语义 = members ∪ removed（见第五节） |

两条边界，先写明避免后期返工：

- **只加不删**：相册里已有、但这次搜「小猫」不再命中的图，默认保留；「同步删除」是另一条需求。
- **排除键是「成员关系」，不是时间**：不要用「上周之后拍的」代替「不在小猫相册里」——用户可能手动加过、也可能手动拿掉过。S11 就是这条边界派生出来的：只加不删 + 排除键 = 成员，组合起来会把用户主动拿掉的图加回去，所以排除集要把「移出记录」算进去。

## 四、三项拍板（v2 已定）

### ① 同名相册默认增量，多本才问

- 找册优先级：对话历史里有本意图产生的相册句柄（如上一轮 `create_album` 的 `${r3.album}`）→ 直接用，**工具端校验**存在性；否则 `find_album(name)`。校验失败（已删 / 改名）回落到按名查找，不报错给用户。
- 三种出口：0 本 → 首次建册；1 本 → 增量，不问；多本 → 问「用哪本」，问句带各本成员数与最近修改时间。
- 增量前先报数：「已有 320 张，又找到 18 张新的」；N 小直接加，N 大（阈值待定）再确认。
- 「再创建一个 / 重新做一本 / 新建一个」显式走新建（S6），新册名加后缀不覆盖。

### ② `exclude_album=A` 的语义 = ¬in(A.members ∪ A.removed)，移出记录由相册服务维护

- 相册服务在 `members` 之外多存一个 `removed`：用户从这本相册显式移出过的 `photo_id` 集合。
- 写入点：相册服务的「从相册移除」操作。图库 UI 移出、助手移出都经过它；skill 与搜索工具零感知。
- 读取点：检索引擎解析 `exclude_album=A` 时，用 `A.members ∪ A.removed` 作为排除集。
- 清除时机：用户手动把该图加回相册 → 从 `removed` 删除；图从图库删除 → GC；新建相册没有 `removed`。
- 不采纳的做法：助手自己记「我往哪本相册加过什么」再做差集——依赖助手侧持久化，还要给搜索工具传 ID 列表，位置放错了。
- 可选话术：「另有 12 张是你之前移出的，不会加回」。

### ③ 相册流程里模型不翻页：排除即翻页 + 复合工具吞掉循环

- 主要挑战是**模型挑战**（翻完第一页就停、漏传 cursor、抄错 ID）。让模型理解「翻页 + 排除 + 幂等」三件事叠加，不如让它一件都不用理解。
- 机制见 4.1（排除即翻页）与 4.2（工具吞掉循环）。cursor 只保留给纯搜索（S1）。
- 代价：相册工具实现要能在服务层调搜索服务（skill 层的单向依赖不变）；长耗时必须提供异步形态。

### 4.1 排除即翻页：exclude 在相册流程里可以替代游标

三种翻页方式在「边搜边往相册里加」这个场景下的表现：

- **offset：必错。** 排除后有 1300 张新图。第 1 页 `offset=0` 拿 500 张并加入 → 「不在册」只剩 800 张。第 2 页 `offset=500` = 跳过剩下 800 张的前 500 → 只返回 300 张，原第 501~1000 张永远漏掉，且 `has_more=false` 看起来一切正常。
- **cursor：正确，但要模型接力。** keyset 游标编码「排序中的位置」（上一页最后一张的 score + photo_id），下一页 = 该位置之后且不在册；排除集变大只让列表变短，位置不漂。但模型要接力传不透明串、游标可能过期、顺序要稳定（同分按 id 打破平局）。适合 S1 的浏览翻页。
- **排除即翻页：相册流程首选。** `exclude_album` 指向的正是要加的那本 A。反复调 `search(q, exclude_album=A, limit=500)`，每次拿到的天然是「下一批还不在册的 500 张」，加进去，直到返回空。不需要游标；首次建册先建空相册 A，之后与增量是同一个循环。

```text
A = find_album(q) or create_album(q)          # 首次 A 为空册；增量 A 已有成员
loop:
  page = search(q, exclude_album=A, limit=500) # 引擎内 q ∧ ¬in(A.members ∪ A.removed) 再取 500
  if page.items 为空: break                    # 自然终止，不看 has_more
  res = add_to_album(A, page.items)            # 幂等：已在册跳过
  if res.added == 0: raise 索引未更新           # 护栏：同一页又回来了，说明读不到己写
  added += res.added
return {added, rounds}
```

终止条件是「搜出来为空」而不是 `has_more`，所以**翻页状态就是相册本身**——重跑、断点续跑、幂等三件事一次拿到。

成立的两个前提（待核实）：

- **读己之写**：`add_to_album` 返回后，下一次 `search` 的排除过滤立刻能看到新成员。若成员索引异步更新，会重复拿到同一页——护栏是 `added == 0` 即停并报错，不会死循环，但该轮会少加。
- **排除在引擎内**：每轮都重算 `q ∧ ¬in(A)`，相册成员必须有索引；2000 张成员做差集不能是拉全量再过滤。

边界：翻页期间新入库的图本轮可能漏，下轮增量按成员关系照样补上；语义检索是排序不是过滤，后几批精度下降，`total` 按阈值以上计数或不承诺；S1 纯搜索没有相册可排除，仍要 cursor，两个参数并存。

### 4.2 翻页由工具内部吞掉

现状是模型驱动循环：1200 张 = 3 搜 + 3 加，每页 2 个 loop，失败模式全在模型侧。两条落法：

- **相册侧复合工具（推荐）**：`add_from_search(album, query)`。相册工具内部在服务层调搜索服务（进程 / 服务调用，不经过模型），按 4.1 的循环跑到为空，返回 `{added, skipped, rounds}`；长耗时返回任务句柄。模型一次调用完成一个用户动作，与张数无关；`exclude` 与幂等 add 都在工具内部；500 张 ID 从不进上下文。skill 层「相册依赖搜图、搜图不认相册」不变。
- **框架代练（备选）**：两个工具都不改。框架在结果信封里认出分页（`has_more / next_cursor`），当模型引用 `${r1.all_items}` 这类全集句柄时，Resolver 在替换变量前自己把剩余页拉完、合并进 Working Memory 再喂给 `add`。工具零改动，是 [变量句柄方案 v4](../agent-variable-scheme/agent-variable-scheme-v4.md) 的自然扩展；代价是 500 × N 个 ID 过框架内存、仍需 cursor。适用于相册工具改不动、框架变量方案已落地的情况。

复合工具的三条设计要求（对齐 [工具接入要求 04](../latency-discussion/04-工具要求与建议.md)）：

- **异步形态**：1200 张要十几秒，属 long 档。阈值内（如 ≤ 2 轮）同步返回；超过则返回任务句柄，后续查进度 / 完成回调，产品侧可显示「已加入 800 / 约 1200」。
- **可中断、可续**：用户取消时返回已加入数；重跑走同一循环，幂等保证不重复。
- **报数在前**：复合工具不负责确认。相册 skill 先用 `search(q, exclude_album=A, limit=5)` 拿 `total` 报数（这一步仍是搜图 skill 的用法，依赖关系由此保住），用户点头后再调 `add_from_search`。

什么时候不该合成复合工具：工具接入要求 §4.3 说复合工具应由日志里「高频 + 稳定」的序列驱动。这里 search → add 循环结构固定、次数由数据决定、模型不需要在中间做判断——正是最该内化的一类；若中间需要模型判断（比如每页让用户挑），就不该合。

## 五、工具契约（v2）

### 5.1 搜索工具（只加可选参数，老调用方不受影响）

```text
search(
  query:          string          # 语义描述，如「小猫」
  limit:          int ≤ 500       # 单次上限（现有约束）
  cursor:         string?         # 纯搜索翻页用；相册流程不用
  exclude_album:  string?         # 新增：排除已在该相册的图（members ∪ removed）
) → {
  items:        [...]             # 本批 ≤ 500
  total:        int?              # 排除后的总数（阈值以上），用于报数与确认
  has_more:     bool
  next_cursor:  string?
}
```

正确性约束：排除在引擎内、**取 limit 之前**完成——`q ∧ ¬in(A)` 再排序取 500。先取 500 再过滤，S5 直接做错。`exclude_album` 填相册可读名或对话历史里的句柄，模型不填内部 ID（对齐 [变量解析机制](../variable-resolution/工具参数变量解析机制方案.md)）。

### 5.2 相册工具

```text
find_album(name)            → [{album, name, count, updated_at}]  # 0 / 1 / 多 三种出口
create_album(name)          → album
add_to_album(album, items)  → {added, skipped}                    # 幂等：已在册跳过；保留给零散加入
add_from_search(album, query)                                     # 新增，复合
  → {added, skipped, rounds} | {task_id}                          # 长耗时异步
```

### 5.3 相册服务：移出记录 `removed`

数据模型变更，见第四节 ②。改动清单汇总：搜索工具 +1 可选参数（`exclude_album`）+ 1 返回字段（`total`）；相册工具 +1 复合工具（`add_from_search`），`find_album` 返回加 `count / updated_at`；相册服务 +1 集合（`removed`）并挂到移除操作上；检索引擎支持「命中 ∩ 不在集合」下推。

## 六、收敛后的主流程

首次与增量同一条链路，3 个 loop，与张数无关；差别只在 `find_album` 是否命中。

```text
用户：帮我把小猫的图片创建一个相册

首次（命中 1200 张）
 ① find_album("小猫") → 0 本 → create_album("小猫") → A（空）
 ② search("小猫", exclude_album=A, limit=5) → total=1200, 5 张预览
 ③ 报数 / 确认：「找到约 1200 张，要创建相册吗？」（N 小直接做）
 ④ add_from_search(A, "小猫") → 内部 3 轮「排除搜索 → 加入」→ {added: 1200, rounds: 3} 或 task_id
 ⑤ 汇报：已创建「小猫」相册，加入 1200 张

一周后（相册已有 320 张，用户移出过 12 张）
 ① find_album("小猫") → 1 本 A（320 张）；多本 → S8 问；历史有句柄 → 直接用
 ② search("小猫", exclude_album=A, limit=5) → total=18（已排除 320 成员 + 12 移出）
 ③ 报数 / 确认：「已有 320 张，又找到 18 张新的，加进去吗？」；total=0 → S7「已是最新」，结束
 ④ add_from_search(A, "小猫") → 内部 1 轮 → {added: 18}
 ⑤ 汇报：已新增 18 张；（可选）12 张你之前移出的未加回
```

- loop 账：v1（模型翻页）首次 1200 张 = 8 个 loop；v2 首次与增量都是 3 个 loop + 1 次可选确认，与张数无关；①② 都是只读，可并行发出压到 2 个。
- skill 文本分工：**搜图 skill** 写 `search` 用法、cursor 翻页（S1）、一句「要排除某相册里的图时填 `exclude_album`」，不写相册流程；**相册 skill** 写找册（历史句柄优先 → `find_album`）→ 0/1/多 三出口 → 带 exclude 搜一次报数 → 确认门槛 → `add_from_search` → 汇报，「再做一本」走新建；搜图用法编译期 include 进正文（对齐 [skill 重组情形盘点](../skill-tool-rom-versioning/skill重组情形盘点.md) 情形 3）。
- 模型需要理解的只剩三件：要不要增量（找册结果 + 话术）、要不要先问（`total` 与阈值）、把相册名 / 句柄和 query 填对。翻页、游标、排除实现、幂等、ID 都不需要。

## 七、方案依赖与挑战

依赖（按层）：

| 层 | 依赖项 |
| --- | --- |
| 检索引擎 | `q ∧ ¬in(A.members ∪ A.removed)` 在取 limit 之前完成；相册成员有索引；成员变更后立刻可见（读己之写） |
| 相册服务 | `removed` 集合并挂到移除操作；`add` 幂等；`find` 返回 `count / updated_at` |
| 工具层 | `exclude_album` / `total` / `add_from_search`；复合工具能在服务层调搜索；long 档异步、可取消、返回已加入数 |
| 产品 / skill | 「N 大再问」的阈值；S6 显式话术清单；两份 skill 文本 |

挑战（按会不会把方案做穿排序）：

1. **排除 × 取数的正确性**（做穿）。`exclude` 不在引擎内做，500 上限就系统性漏图；客户端过滤不算支持。
2. **读己之写**（做穿）。`add` 后 `search` 若看不到新成员，「排除即翻页」会重复拿同一批；护栏 `added=0` 即停，但要确认索引更新时延。
3. **长耗时执行**。复合工具 3000 张可能几十秒，必须异步 + 进度 + 可取消，否则「创建相册」是一次静默长写入。
4. **相册服务改动面**。`removed` 是数据模型变更，涉及图库 UI 的移除路径；若图库 app 不在掌控内，S11 只能降级为话术提示。
5. **S3 vs S6 意图**。「创建相册」既像首次也像整理成册；默认增量 + 显式新建话术，需要评估集验证。
6. **检索是排序不是过滤**。增量拿到的图相关度低于首次；`total` 口径与阈值要说清。
7. **相册身份**。重名 / 改名 / 已删各有出口；历史句柄必须经工具校验。

v1 里的「模型翻页」「500 个 ID 进上下文」「模型侧幂等」三条挑战，在复合工具方案下已不存在。
