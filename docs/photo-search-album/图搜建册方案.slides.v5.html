01背景与场景:按语义找一批照片进相册;同一句话再来只追加「还不在册」的;单次搜索 ≤ 500 张两个 skill 单向依赖 · 现有能力盘点 · 场景即验收口径

现有能力盘点

照片搜索 skillsearchTool:query · 是否出卡 · 游标 | offset · filter(表达式,支持 字段 in [...] / not in [...])→ 每次 ≤ 500 张,只有 hasMore 没有总数。出卡 = 给用户展示结果卡片 相册整理 skillcreateAlbum(name) → album;appendAlbum(album, items)。依赖照片搜索 skill;照片搜索不强依赖相册整理 已有规则同名相册默认追加、多本才问;用户从相册移出的照片有移出记录,不会被再次追加

问题拆成三个子问题

  • ① 依赖:相册整理用搜索,搜索不认相册 → 相册侧的需求只能以搜索工具的通用能力出现
  • ② 500 上限:命中 1200 张要多批取数,不漏、不早停、不重复追加
  • ③ 增量:一周后同一句话只追加不在册的;「不在册」怎么表达、在哪一层过滤

两条边界

  • 只加不删:已在册、这次不再命中的照片保留
  • 排除键是成员关系,不是时间:不用「上周之后拍的」代替「不在小猫相册」;用户手动加过、移出过都要尊重

filter 的两条语义约束

  • 位置:在引擎内、取 pageSize 之前算——q ∧ filter 再排序再截断。先取 500 再过滤,S5 直接做错(前 500 可能全是旧成员)
  • album 字段的含义:album not in [A] = 不在 A.成员 ∪ A.移出记录;移出记录由相册服务维护,搜索侧只是读一个集合

createAlbum 不变

createAlbum(name) → album

appendAlbum 两种形态

# 形态一 · 已有:零散追加
appendAlbum(album, items) → {added, skipped}

# 形态二 · 新增:从搜索追加
appendAlbum(album, source:{
  query:  "小猫",
  filter: album not in [album]   # 可省,默认排除自身
}) → {added, skipped, rounds}
   | {task_id}                   # 首轮 hasMore 时异步
内部做什么服务层调搜索服务,循环「排除搜索 → 幂等追加」直到为空;翻页策略见 P4 排除搜索带 album not in [A] 搜:引擎截断 500 之前先扔掉已在 A 的,返回的每张都「不在册」;相册侧不用比 ID 幂等追加已在 A 的跳过计入 skipped,不报错不重复;同一批加两次结果一样——重跑 = 续跑(S8),索引延迟下也不出重复 异步首轮 hasMore=true 即返回 task_id;进度「已追加 800、还有更多」;可取消

04关键细节:排除定义「增量是什么」,游标定义「翻到哪了」,循环放进工具为什么不是 offset、为什么不只靠排除、索引更新不及时怎么办

✗ offset:边加边搜必漏

排除后 1300 张新照片。第 1 页 offset=0 取 500 并追加 → 「不在册」只剩 800;第 2 页 offset=500 跳过剩下 800 的前 500 → 只回 300,原第 501~1000 张永远漏掉,且 hasMore=false 看似正常。

△ 只靠排除:最简,但有前提

反复 searchTool(q, filter: album not in [A]),每次拿到的天然是「下一批不在册的 500 张」,直到为空;翻页状态就是相册本身。前提:appendAlbum 之后 searchTool 立刻看到新成员(读己之写)。

✓ 排除播种 + 游标定位

排除回答「哪些属于这次的增量集合」——跨运行,一周前的成员早已可见;游标回答「这次运行内翻到哪了」——已追加的照片位置在游标之前,不会再回来,与索引时延无关。两者对模型都不可见。

appendAlbum(source=search) 内部 推荐写法

p = searchTool(q, filter: album not in [A])   # 播种:排除定义增量集合
loop:
  if p.items 空: break
  appendAlbum(A, p.items)                     # 幂等
  p = searchTool(q, filter: album not in [A],
                 cursor = p.nextCursor)       # 定位:已加的不再出现
返回 {added, skipped, rounds}                 # 首轮 hasMore 时改为 task_id
  • 排序稳定(同分按 id)是游标正确的前提;filter 在取数前下推是排除正确的前提
  • 翻页期间新入库的照片本轮可能漏,下轮增量按成员关系补上——增量相对当前成员,不相对上次快照
  • 语义检索是排序不是过滤:后几批相关度下降;没有总数,进度只能报「已追加 N、还有更多」

引擎(V2 核实)读己之写采用
排除集查询时从相册服务读(反连接)✓ 时延 ≈ 0只靠排除即可;仍建议带游标,代价为零
