03三项拍板:默认增量 · 排除语义含移出记录 · 翻页由工具吞掉这三件定了,skill 怎么写、工具 schema 怎么加字段就不会来回改

①

同名相册,默认怎么办

已定:默认增量,只有多本同名才问用户。「再创建一个 / 重新做一本」显式走新建。
找册对话历史里有本意图产生的相册句柄(如 ${r3.album})→ 直接用,工具端校验存在性;否则 find_album(name) 出口0 本 → 首次建册;1 本 → 增量不问;多本 → 问「用哪本」,问句带各本成员数与最近修改时间 确认增量前先报数:「已有 320 张,又找到 18 张新的」;N 小直接加,N 大(阈值待定)再确认 失效历史句柄指向的相册已删 / 改名 → 校验失败回落到按名查找,不报错给用户
②

排除什么,记在哪

已定:exclude_album=A 的语义 = ¬in(A.members ∪ A.removed),移出记录由相册服务维护。
写入相册服务的「从相册移除」操作写 removed(图库 UI 移出、助手移出都走它);skill 与搜索工具不感知 清除用户手动把该图加回相册 → 从 removed 移出;图从图库删除 → GC;「重新做一本」是新相册,没有 removed 为什么只加不删 + 排除键 = 成员,组合起来会把用户主动拿掉的图加回去(S11);记录放相册服务是唯一不扯的位置——助手自己记 add_log 再做差集,依赖助手侧持久化且要给搜索传 ID 列表,不采纳 话术可选:「另有 12 张是你之前移出的,不会加回」
③

翻页谁来做

已定:相册流程里模型不翻页。复合工具 add_from_search 内部用「排除即翻页」循环吞掉分页;cursor 只保留给纯搜索(S1)。
为什么主要挑战是模型挑战:翻完第一页就停、漏传 cursor、抄错 ID。让模型理解「翻页 + 排除 + 幂等」三件事叠加,不如让它一件都不用理解 机制P4:exclude 指向正在加的相册 → 每次搜到的天然是「下一批不在册的 500 张」,不需要游标;P5:循环放进工具 loop首次 1200 张:v1 是 8 个 loop;现在 3 个 loop,且与张数无关 代价相册工具实现要能调搜索服务(服务层依赖,skill 层单向不变);长耗时必须有异步形态
三项的关系:① 决定要不要走增量;② 决定「不在册」怎么定义;③ 决定增量怎么执行。①② 是产品 / 服务层的事,③ 是工具形态的事——三者正交,可以分头推进。
待定阈值:①里「N 大再确认」的 N;②里 removed 是否对用户可见(相册设置里能不能清空)。

04排除即翻页:exclude 能不能替代游标——在相册流程里可以,而且更简单三种翻页方式对比;offset 在这个场景下不是「不够好」而是必错

✗ offset:边加边搜必漏

排除后有 1300 张新图。第 1 页 offset=0 拿 500 张并加入 → 「不在册」只剩 800 张。第 2 页 offset=500 = 跳过剩下 800 张的前 500 → 只返回 300 张,原第 501~1000 张永远漏掉,且 has_more=false 看起来一切正常。

△ cursor:正确,但要模型接力

keyset 游标编码「排序中的位置」(上一页最后一张的 score + photo_id),下一页 = 该位置之后且不在册。排除集变大只会让列表变短,位置不漂。但:模型要接力传不透明串、可能过期、顺序要稳定(同分按 id 打破平局)。适合纯搜索 S1 的浏览翻页。

✓ 排除即翻页:相册流程首选

exclude_album 指向的正是要加的那本 A。反复调 search(q, exclude_album=A, limit=500),每次拿到的天然是「下一批还不在册的 500 张」,加进去,直到返回空。不需要游标,首次与增量是同一个循环,中途失败直接重跑。

循环长什么样 首次建册先建空相册 A,之后与增量完全一致

A = find_album(q) or create_album(q)   # 首次 A 为空册;增量 A 已有成员
loop:
  page = search(q, exclude_album=A, limit=500)
        # 引擎内 q ∧ ¬in(A.members ∪ A.removed) 再取 500
  if page.items 为空: break             # 自然终止,不看 has_more
  res = add_to_album(A, page.items)        # 幂等:已在册跳过
  if res.added == 0: raise 索引未更新      # 护栏:同一页又回来了
  added += res.added
return {added, rounds}

终止条件是「搜出来为空」而不是 has_more,所以翻页状态就是相册本身——重跑、断点续跑、幂等三件事一次拿到。

成立的两个前提 待核实

  • 读己之写:add_to_album 返回后,下一次 search 的排除过滤立刻能看到新成员。若成员索引异步更新,会重复拿到同一页——护栏是 added == 0 即停并报错,不会死循环,但该轮会少加
  • 排除在引擎内:每轮都重算 q ∧ ¬in(A),相册成员必须有索引;2000 张成员做差集不能是拉全量再过滤

边界

  • 翻页期间新入库的图:本轮可能漏,下轮增量按成员关系照样补上——增量本来就是相对当前成员,不是相对上次结果快照
  • 语义检索是排序不是过滤:命中按相似度排,后几批精度下降;增量拿到的是首次没进前 N 的图。total 口径按阈值以上计数,或不承诺
  • S1 纯搜索仍要 cursor:没有相册可排除,用户「再看一页」只能靠游标。两条并存,搜索工具两个参数都保留
一句话:在相册流程里,exclude 让分页「自推进」,游标从必需变为可选;这是能把循环塞进工具、让模型完全不感知翻页的前提(P5)。

另一条落法:框架代练 备选

搜索工具、相册工具都不改。框架在结果信封里认出分页(has_more / next_cursor),当模型引用 ${r1.all_items} 这类「全集」句柄时,Resolver 在替换变量前自己把剩余页拉完,合并进 Working Memory 再喂给 add。

  • 优点:工具零改动,是变量句柄方案 v4 的自然扩展(从「存已返回的值」到「按需物化分页」)
  • 代价:500 × N 个 ID 都要过框架内存;框架多了一个「懂分页」的通用协议;仍需 cursor
  • 适用:相册工具改不动、但框架变量方案已落地时

复合工具的三条设计要求 对齐工具接入要求 04

  • 异步形态:1200 张要十几秒,属 long 档。同步返回阈值内(如 ≤ 2 轮)的结果;超过则返回任务句柄,后续查进度 / 完成回调,产品侧可显示「已加入 800 / 约 1200」
  • 可中断、可续:用户取消时返回已加入数;重跑走同一循环,幂等保证不重复
  • 报数在前:复合工具不负责确认。相册 skill 先用 search(q, exclude_album=A, limit=5) 拿 total 报数(这一步仍是搜图 skill 的用法,依赖关系由此保住),用户点头后再调 add_from_search

什么时候不该合成复合工具

工具接入要求 §4.3 说复合工具应由日志里「高频 + 稳定」的序列驱动。这里的 search → add 循环结构固定、次数由数据决定、模型不需要在中间做判断——正是最该内化的一类;若中间需要模型判断(比如每页让用户挑),就不该合。

结论:相册主流程用复合工具吞掉翻页;搜索工具保留 cursor 给 S1;框架代练作为工具改不动时的备选,不并行做。

search(
  query:          string          # 语义描述,如「小猫」
  limit:          int ≤ 500       # 单次上限(现有约束)
  cursor:         string?         # 纯搜索翻页用;相册流程不用

) → {
  items:        [...]             # 本批 ≤ 500
  total:        int?              # 排除后的总数(阈值以上),用于报数与确认
  has_more:     bool
  next_cursor:  string?

存什么每本相册除 members 外多一个 removed: Set<photo_id>——用户从这本相册显式移出过的图 谁写相册服务的「从相册移除」操作。图库 UI 移出、助手移出都经过它;skill、搜索工具零感知 谁读检索引擎在解析 exclude_album=A 时读 A.members ∪ A.removed 作为排除集 何时清用户手动把该图加回 A → 从 removed 删;图从图库删除 → GC;新建相册没有 removed 不做的不在助手侧记「我加过什么」再做差集——依赖助手持久化、还要给搜索传 ID 列表,放错了位置

挑战 按风险排序;做穿 不解决方案不成立

  1. 做穿 排除 × 取数的正确性:exclude 不在引擎内做,500 上限就系统性漏图;客户端过滤不算支持
  2. 做穿 读己之写:add 后 search 若看不到新成员,「排除即翻页」会重复拿同一批;护栏 added=0 即停,但要确认索引更新时延
