01背景与场景:按语义找一批照片进相册;同一句话再来只追加「还不在册」的;单次搜索 ≤ 500 张两个 skill 单向依赖 · 现有工具盘点 · 场景即验收口径

现有能力盘点 术语以此为准

照片搜索 skillsearchTool(query, 是否出卡, 游标 | offset, filter) → items ≤ 500。filter 是表达式,支持 字段 in [...] / 字段 not in [...];出卡 = 给用户展示结果卡片 相册整理 skillcreateAlbum(name) → album;appendAlbum(album, items)。依赖照片搜索 skill;照片搜索不强依赖相册整理 已有规则同名相册默认追加、多本才问;用户从相册移出的照片有移出记录,不会被再次追加

问题 拆成三个子问题

  • ① 依赖:相册整理用搜索,搜索不认相册 → skill 层单向,相册的需求只能以搜索工具的通用能力出现
  • ② 500 上限:命中 1200 张要多批取数,不漏、不早停、不重复追加
  • ③ 增量:一周后同一句话,只追加不在册的;「不在册」怎么表达、在哪一层过滤

两条边界

  • 只加不删:已在册、这次不再命中的照片保留
  • 排除键是成员关系,不是时间:不用「上周之后拍的」代替「不在小猫相册」;用户手动加过、移出过都要尊重

场景矩阵 S3 与 S6 话术相似、策略相反;方案每改一版按这张表过一遍

03关键方案细节:排除在取数之前 · 循环在工具之内 · 游标保运行内正确三件事分别回答「增量是什么」「谁来翻页」「索引更新不及时怎么办」

① 排除 = filter,语义与位置 D1

  • filter: album not in [A] 的语义 = 不在 A.成员 ∪ A.移出记录;移出记录由相册服务维护,搜索侧零感知
  • 必须在引擎内、取 limit 之前算:q ∧ ¬in(A) 再排序取 500。先取 500 再过滤,S5 直接做错(前 500 可能全是旧成员)
  • filter 只是表达式,下推与否是引擎的事 → V1 要核实的就是这一点

为什么 offset 不能用 边加边搜

排除后 1300 张。第 1 页 offset=0 取 500 并追加 → 「不在册」只剩 800;第 2 页 offset=500 跳过剩下 800 的前 500 → 只回 300,原第 501~1000 张永远漏掉且 has_more=false 看似正常。相册流程只用游标。

③ 报数、幂等、异步 D4

  • 报数用 searchTool 本身(不出卡、limit=5、要 total)——仍是照片搜索 skill 的用法,依赖关系由此保住
  • appendAlbum 幂等:已在册跳过,返回 {added, skipped};重跑 = 续跑(S8)
  • ≥ 2 轮走任务句柄:进度「已追加 800 / 约 1200」、可取消、取消返回已追加数

② 循环进 appendAlbum:排除播种 + 游标定位 推荐 D2 · D3

p = search(q, filter: album not in [A], 500)   # 播种:定义增量集合
loop:
  if p 空: break
  appendAlbum(A, p.items)                      # 幂等
  p = search(q, filter: album not in [A], 500,
             cursor=p.next_cursor)             # 定位:已加的不再出现
排除负责「哪些照片属于这次的增量集合」——跨运行,一周前的成员早已可见,与索引时效无关 游标负责「这次运行内翻到哪了」——已追加的照片位置在游标之前,不会再回来,不依赖 add 之后 search 立刻看见 为什么不纯排除「反复 search(排除 A) 直到为空」最简,但要求读己之写。若 album 成员关系是异步烘进索引(T_sync 几十秒):add 成功 → 2 s 后再搜 → 同一批 500 又回来 → added=0 护栏即停 → 1300 张只加 500,汇报「新增 500」,剩 800 静默丢失
引擎(V2 核实)读己之写采用
排除集查询时从相册服务读(反连接)✓ T_sync ≈ 0纯排除循环即可;仍建议带游标,代价为零
成员关系烘进索引,异步同步✗ 几十秒排除播种 + 游标定位;结束前等排除集追上再返回,或返回 syncing 让话术改「约 N 张、同步中」
引擎 top-K 有总量上限(V3)—排除是唯一解,读己之写成硬要求;或运行内用 id not in [本轮已加]——filter 本就支持

三种写法输入输出相同,skill 与模型看不到差别;先上保守的一种,引擎升级后切换,零 skill 改动。

动手前先核实 V1–V5

  • V1 filter 的 not in 是取数前下推,还是取 top-N 后过滤;album 能否成为 filter 字段
  • V2 成员关系烘进索引还是查询时读;T_sync 的 P50 / P95
  • V3 500 是每次上限还是 top-K 总量上限
  • V4 appendAlbum 是否幂等;能否在服务层调搜索(同进程 / IPC)
  • V5 大相册(万张)时 not in 数组 / 集合下推的性能

验收加两条

  • S5-延迟:注入 T_sync=30 s,增量 1300 张 → 全部追加、rounds=3、不触发 added=0
  • 连续调用:结束后 2 s 再说同一句 → 「已是最新」或「约 N 张、同步中」,不承诺错误的 N

下一步

  1. V1–V5 核实 → 定 D1–D3
  2. 定 searchTool filter 字段 / total 与 appendAlbum source 的 schema、异步形态
  3. 改写相册整理 skill,S6 话术清单;按 S1–S10 验收
