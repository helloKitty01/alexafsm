# 05 对我们系统的启示

把 GPT‑Live 的架构与工程经验对照到本仓库已有的几条讨论线上：

- [phone-assistant-automation](../phone-assistant-automation/)：前台 omni 全双工"秘书" +
  后台深度大脑的双脑架构、打扰管理器；
- [latency-discussion](../latency-discussion/)：agent loop 端到端时延、快慢双系统；
- [kv-cache-discussion](../kv-cache-discussion/)：上下文压缩与缓存断裂；
- [reminder-discussion](../reminder-discussion/)：运行期向对话流注入状态块。

GPT‑Live 是这些讨论里"omni 全双工前台 + 异步深度后台"这条路线**在业界的第一个
消费级大规模验证**。下面按"被验证的判断"、"要补的设计"、"要避的坑"三类整理。

## 一、被业界验证的判断

| 我们的判断 | GPT‑Live 的对应证据 |
| --- | --- |
| 全双工 omni 模型只做前台，不在实时会话里干重活（phone‑assistant 03 §2） | 语音模型只负责持续交互；搜索/推理/agent 任务全部委托 GPT‑5.5，对话不停 |
| 深度推理放后台，前台能力上限由后台决定 | BrowseComp 0.7% → 75.2%，语音模型没变大，变的是"知道何时放手" |
| 快慢双系统是编译关系不是替代关系（latency 03） | 语音层像"编译好的"实时策略，前沿模型是"解释器"；选更深推理等级不拖慢对话 |
| 重活异步化、通过收件箱/门控与前台会合 | 委托走异步 RPC 边界，"慢工具只能拖慢自己的结果，不能拖住媒体流" |
| 压缩会导致缓存全灭、重建要付 prefill（kv‑cache 07/08） | OpenAI 明确指出压缩使 KV cache 失效，因此把压缩做成受管的实例切换，在旁路完成 |

## 二、需要补进我们设计的东西

### 1. 两条时钟、三个度量

我们现有时延讨论基本围绕"agent loop 一次多少 ms、几个 loop"。语音前台需要另一
套口径：

| 时钟 | 含义 | 由谁保障 | 目标量级（参考 GPT‑Live 实测与三方建议） |
| --- | --- | --- | --- |
| 应答起点 | 第一次出声（"我看一下"） | 前台 omni | < 1 s，且**抖动**要小（GPT‑Live 标准差 ~100 ms） |
| 实质答案起点 | 有信息量的内容开始 | 后台大脑 / 工具 | 委托类 2–4 s 可接受，但必须有应答垫着 |
| 完成 | 说完 | 两者 | 无硬上限，前提是用户被持续 engage |

启示：**优化对象是分布而非中位数**（Go 重写的收益就是 p95 ≈ 旧 p50）；容量模型
从"GPU 能扛多少请求"改成"**能维持多少并发会话且每帧准时**"。
这条应进入 latency‑discussion 的埋点方案。

### 2. 前台"打圆场"能力是架构的一部分，不是话术

GPT‑Live 的应答起点能早触发，是因为模型被训练成会说"让我查一下"并在等待时
维持交流；但 OpenAI 也强调它"撑不住任意慢的响应"，所以整条委托链（路由、prompt
处理、推理、工具往返）都算进预算，并且：

- **委托前就把后台会话建好**：语音会话一开始就为后台模型创建推理会话、prefill
  初始上下文；
- **会话亲和 + prompt caching**：后续委托复用同一后台会话；
- **调参朝"更快得到有用结果"**：推理力度、输出上限、工具 schema、往返次数。

对应到我们的双脑架构：任务摘要卡片解决了"前台不用读后台全量上下文"，但还缺
"**后台大脑预热**"这一步——用户一开口，后台 agent loop 的 system prompt +
工具 schema 就应已 prefill 完毕，等待第一个委托。这与 kv‑cache 讨论里
"分层排布、静态前缀先热"是同一件事。

### 3. 连续语音 → 离散轮次的双视图

我们的中枢、日志、安全审计都以"消息/轮次"为单位。全双工前台产出的是重叠的
连续流，需要一个**分轮器**（OpenAI 放在应用服务器）：

- 用部分转写 + 时序推断谁持有发言权；
- 最新一条永远暂定，说话人持续持有发言权足够久才定稿；
- 附和（"嗯嗯"）不单独成消息，实质插话才成消息；
- 维护**推测视图**（给 UI，可回改）与**权威记录**（给分析/安全，只追加）。

这项在 phone‑assistant 方案里尚未出现，应作为中枢的一个组件补上。它也决定了
reminder 机制的注入点——reminder 只能附着在权威记录的 append 前沿。

### 4. 打断的三种形态与"截断"

Realtime API 的 `conversation.item.truncate` 与 Alexa+ 的上下文化打断指向同一
要求：**模型的历史必须与用户实际听到的一致**。我们需要：

- 用户打断 → 真正停止生成，而不只是客户端静音；把未播出的部分从上下文删掉；
- 模型主动插话 → 走打扰管理器（GPT‑Live 里"模型判断你是不是真的要打断我"是
  同一决策的镜像：既判断该不该让，也判断该不该插）；
- 上下文化打断（"等下，第二个"）→ 要求前台知道自己说到哪。

Agora 实测 GPT‑Live 被打断后**多花 ~500 ms 让出**，但 30/30 拒绝了背景人声。
这说明"让出速度"与"抗误触发"是一对权衡，应当作为打扰管理器 / 前台策略的
显式参数，而非追求单边最快。

### 5. 会话状态迁移与压缩即切换

如果我们的前台 omni 也是有状态流式推理，则必须有：

- **预热 → prefill → 并行推理 → 切换**的实例迁移机制（应对扩缩容、故障、长会话）；
- 把**上下文压缩当作一种迁移**：原实例继续聊，旁路压缩并准备新实例，就绪后切换。

这与 kv‑cache 讨论"分代冻结"互补：分代冻结是**尽量不触发**缓存断裂，切换机制
是**断裂不可避免时把重建藏到活跃路径之外**。算力照付，但不在用户能感知的路径上。

### 6. 会话建立本身是关键路径

GPT‑Live 把"点下按钮到音频进模型"全程视为关键路径：WARP（6 RTT → 1 RTT）、
Instant Connect（SDP 预协商、单 UDP 包起会话）、Global Relay（近处进网）。
对端侧助手而言，对应物是：唤醒 → 前台模型就绪 → 后台会话预建。这一段的时延
预算应单列，不与"话轮响应时延"混算。

## 三、要避的坑（OpenAI 踩过的）

| 坑 | 表现 | 对策 |
| --- | --- | --- |
| 容量只按 GPU 吞吐估 | CPU 侧流处理器/队列/网络先于推理饱和，请求堆积、时延复利 | 容量单位改为"并发会话 × 每帧准时"，配套组件与推理一起扩 |
| 地理被忽视 | 路由到远处容量在启动与流式多处加延迟 | 发布与区域容量、流量调度一起验证；时延按来源地理拆分 |
| 只做短压测 | 长会话的内存/持久化压力、重连触发的压缩与恢复、断开时的关闭竞态都看不到 | 用真实生命周期的影子流量测；专门覆盖长会话、重连、异常断开 |
| 指标混淆时延来源 | 看板聚合掩盖单个不健康引擎；测试与部署配置漂移 | 细粒度遥测、对照已知良好配置校验、分阶段爬坡、可快速隔离单条路径 |
| 把全双工模型当轮次制用 | 应用层再加"等用户说完"门控，退化成更慢的流水线 | 围绕持久会话 + 事件流建模，轮次决策交给模型 |
| 沉默作为失败态 | 后台超时/出错时前台不说话 | 委托路径单独设预算与兜底话术；宁可"我再想想"也不要静默 |
| 引用未证实数字 | "sub‑300 ms"之类 | 只引用可核实的：官方 p95≈旧 p50、WARP 6→1 RTT、第三方 ~1.1 s 首音、+314 ms 丢包退化 |

## 四、一句话共识

> **前台守时钟，后台守深度，中间用异步边界隔开，一切重活（委托、压缩、迁移、
> 持久化、分轮）都不上活跃路径。** 这既是 GPT‑Live 六个月工程的总结，也是我们
> 双脑架构应当坚持的边界。

## 五、待讨论

1. 我们的前台 omni 是自研全双工还是在第二代（S2S + 语义 VAD）上先做产品？
   若是后者，`eagerness` 类参数如何按场景（客服快 / 陪伴慢）配置？
2. 分轮器放在端侧还是云侧？端侧省往返但转写质量受限。
3. 后台大脑"预建会话"的成本：每个语音会话都常驻一个深度模型上下文，
   并发多时的 KV 占用如何与 kv‑cache 讨论的分层排布结合？
4. GPT‑Live API 落地后，我们是自建全栈还是前台接第三方全双工模型、后台自研？
   两条路的边界正是 03 章那条"异步 RPC 边界"。
