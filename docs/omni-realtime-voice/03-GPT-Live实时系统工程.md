# 03 GPT‑Live 实时系统工程

来源：OpenAI《How we built a realtime system for responsive voice AI in six months》
（Justin Uberti、Zahan Malkani，2026‑08‑03），以及其前置工作
《How OpenAI delivers low-latency voice AI at scale》（Yi Zhang、William McDonald，
2026‑05‑04）。前者讲 GPT‑Live 的推理与会话层，后者讲它脚下的 WebRTC 基础设施。

## 总原则：the voice must flow

整篇文章可以压缩成一条设计原则：**系统的首要任务是维持一个不间断的媒体环路**，
其他一切（调用前沿模型、持久化对话、压缩上下文、实例调度）都必须在**环路之外**
异步完成，不允许任何东西阻塞它。

推导链：全双工模型 → 对话是连续媒体流 → 传输/处理/推理任何一处延迟都是可听见
的停顿 → 轮次制系统能容忍"音频 blob 晚到一点"，实时媒体系统必须**每一帧按时
送达** → 因此活跃路径（live path）要尽可能小，其余全部搬到异步路径。

```text
                       ┌──────────── live path（必须按帧准时）────────────┐
 client ═ WebRTC ═══▶ 媒体前端(Go) ═══▶ 有状态流式推理(全双工语音模型) ═══▶ 媒体前端 ═ WebRTC ═▶ client
                       └───────────────────────┬───────────────────────────┘
                                               │ 异步 RPC 边界
                    ┌──────────────────────────┴──────────────────────────────┐
                    │ 应用服务器：委托前沿模型(GPT-5.5) / 工具 / 转写分轮 / 持久化   │
                    │ 会话管理：实例预热与切换 / 上下文压缩 / 容量与地理调度          │
                    └─────────────────────────────────────────────────────────┘
```

## 一、流式推理与媒体快路径

### 有状态流式推理

第二代已经能把音频直接流进流出系统（Realtime API 基础设施），GPT‑Live 更进
一步：**媒体一路流到模型**，由一个全新的**有状态推理系统**持续消费音频帧、持续
产出语音帧。这与 batch 推理的 request‑response 形态根本不同：一个会话的上下文
活在一个模型实例里。

### 媒体流与业务逻辑物理分离

早期决策：音频在 client 与语音模型之间走**专用快路径**；委托、工具调用和其他
应用工作放在**异步 RPC 边界**之后。一个慢工具或慢后端只能拖慢它自己的结果，
**不能拖住媒体流**。

副产品是一个干净的定制边界：应用可以改工具、改策略、改后端，不碰负责
"让音频流动"的媒体前端。ChatGPT 桌面端新上的"用语音控制电脑、协调 agent"
就是建在这个边界之外的。

### Go 重写

媒体前端和推理逻辑从 Python `asyncio` 重写为 Go。收益不是峰值速度，而是
**帧交付的平滑度：新系统 p95 ≈ 旧系统 p50**。对实时音频，用户感受到的是
最坏情形，整体分布左移比 benchmark 峰值更重要。

### WebRTC 作为传输基础

WebRTC 为低时延媒体设计，能在丢包、时钟漂移、client 网络切换下持续工作。
包晚到时可以细微拉伸音频避免空洞，再短暂加速播放追回实时。全链路减少
缓冲与阻塞，才能拿到人类对话预期的亚秒级响应。

## 二、有状态会话的运维难题：实例切换与上下文压缩

有状态带来两个运维矛盾：会话可能很长且上下文持续增长；模型实例却要随
负载弹性伸缩。

### 无缝实例切换（seamless handoff）

需要迁移时：**在旁边预热一个替换实例 → 用当前会话上下文 prefill → 两个实例
并行推理 → 新实例完全就绪后切换**。用户听不到任何过渡。

### 压缩即切换

对话过长会超出上下文上限。压缩能缩小上下文，但：

1. 压缩本身耗时；
2. 压缩**改变了历史上下文**，使 KV cache 全部失效，重建需要一次新的 prefill。

OpenAI 的做法是把压缩当作**又一种受管的切换**：原实例继续聊，系统在旁路压缩
上下文、用新上下文准备替换实例，就绪后无媒体中断地切过去。这使长时通话可以
随时压缩。

> 与本仓库 [kv-cache-discussion](../kv-cache-discussion/) 的关联：这是"缓存断裂
> 不可避免时，用并行实例把重建时延藏到活跃路径之外"的服务端解法。算力照付，
> 只是不在用户能感知的路径上付。

## 三、委托不阻塞对话

说/想分离在系统层面要解两个问题：委托结果要**快到足以对正在进行的交流有用**；
周边系统仍需要**离散消息**。

### 把整条委托链纳入响应预算

语音模型能"打个圆场"撑一会儿，但撑不住任意慢的响应。因此路由、prompt 处理、
推理、工具调用**整条链**都算进响应预算。具体手段：

| 手段 | 做法 | 效果 |
| --- | --- | --- |
| 预建会话 | 语音会话开始时，应用服务器即为前沿模型创建推理会话并用初始上下文 prefill | 第一次委托到来时 prompt 已处理完 |
| 会话亲和 | 前沿模型推理会话在整个语音会话期间保持可用，后续请求走稳定亲和 | 配合 prompt caching 降时延，worker 故障仍易恢复 |
| 调参 | 推理力度、输出上限、工具 schema、模型‑工具往返次数 | 全部朝"更快得到有用结果"调 |

### 从连续语音推导离散轮次

模型在连续语音流上工作，但 ChatGPT 会话 UI、分析、安全基础设施都以
user/assistant 轮次为单位。应用服务器负责把**重叠、偶尔模糊**的对话拆成离散
消息：

- 音频到达时，用**部分转写 + 时序信号**推断谁持有发言权（floor），维护消息队列；
- **最新一条消息始终是暂定的**：文本、时序、说话人归属都可能随新语音改变；
- 某说话人持续持有发言权足够久、归属可靠后，才**定稿**对应消息。

重叠的处理策略：用户说话时 assistant 一句"mm hmm"不应单独成消息；实质性插话
则应该。显示 assistant 回复时优先保证连贯，即便用户在中间说话。

**分段策略的本质权衡：新鲜度 vs 确定性。** 提交太早 → 历史碎片化、顺序不稳；
等太久 → 转写和依赖它的功能延迟。因此系统维护**两个视图**：

| 视图 | 消费者 | 性质 |
| --- | --- | --- |
| 推测视图（speculative） | 会话 UI（能处理更新） | 当前状态，可回改 |
| 权威记录（authoritative） | 分析管线、日志 | 定稿转写，只追加 |

这让 ChatGPT 其余部分拿到稳定的对话视图，而**不把轮次制强加回活跃语音路径**。

## 四、更快的会话建立协议

对 GPT‑Live 来说，"点下按钮"到"音频进模型"之间的每一步都在关键路径上。
香草 WebRTC 建立会话需要意外多的握手和往返——它早于 QUIC 那一代"最小化 RTT"
的思潮，几个子协议叠在一起时还各自重复做反 DoS。

### WARP：6 RTT → 1 RTT

WebRTC Abridged Roundtrip Protocol，一组**向后兼容**的协议改进，已作为公开
规范提交 IETF TSVWG，libwebrtc 与 Pion 已支持：

| 组件 | 做法 | 省下 |
| --- | --- | --- |
| SNAP | SCTP 跑在 DTLS 之上时其防劫持/反 DoS cookie 交换多余，去掉；剩余 INIT 参数是声明式的，直接塞进 SDP 预协商 | 2 RTT |
| SPED | 给 ICE 的 STUN 消息加 DATA 属性，把 DTLS 握手搭在 STUN 上，与 ICE 首次交换并发 | 1 RTT |
| DTLS 1.3 | 1‑RTT 握手取代 DTLS 1.2 的 2‑RTT | 1 RTT |
| 预协商 data channel | 不用 DCEP 动态开通道 | 0.5 RTT（client 发起时） |

原始路径：4 RTT 媒体就绪、6 RTT 数据就绪。WARP 全开后：1 个信令 RTT + 1 个媒体
RTT。服务端用 ICE Lite + `a=setup:passive` 时可在 **1.5 RTT** 开始发送。
一次生产部署观察到 p50 省约 4 RTT、**p95 省约 12 RTT**——尾部收益来自握手
包变少、遇到丢包的概率随之下降。

### Instant Connect：把 SDP 交换挪出关键路径

WARP 优化了媒体握手后，剩下最显眼的延迟是**信令阶段的 SDP 参数交换**。
Instant Connect **提前协商这些参数**，不预留服务端容量，也不改任何现有 WebRTC
实现：

- 它与标准信令流**并行**运行；
- 若预协商参数有效，服务端在**第一个媒体包到达时物化会话**；
- 若参数过期/无效，标准信令流已经在跑，client 无额外时延地回退。

两者叠加：**client 用一个 UDP 包就能启动会话**，服务端立即响应，系统开始做用户
真正关心的事——听与答。

## 五、脚下的地基：relay + transceiver（2026‑05 的前置工作）

GPT‑Live 的媒体路径建在 OpenAI 早几个月重构的 WebRTC 栈上。它解决的是
**WebRTC 与 Kubernetes 的冲突**：

| 冲突 | 说明 |
| --- | --- |
| 端口耗尽 | 一会话一 UDP 端口的模式需要暴露/管理海量公网端口，负载均衡器、防火墙、自动伸缩都吃不消 |
| 状态粘性 | ICE/DTLS 有状态，创建会话的进程必须持续收到该会话所有包；单端口多路复用只解决单机，跨集群第一个包仍可能落错实例 |
| 首跳时延 | 全球 9 亿+ 周活用户，媒体必须从离用户近的地方进网 |

方案：**无状态 relay + 有状态 transceiver** 分离。

- **transceiver**（Go + Pion）：唯一拥有 WebRTC 会话状态的服务——ICE 连通性检查、
  DTLS 握手、SRTP 密钥、会话生命周期；把媒体和事件转换成更简单的内部协议
  交给推理/转写/语音生成/编排。后端服务因此像普通服务一样伸缩，不必扮演
  WebRTC peer。
- **relay**：轻量 UDP 转发层，不解密媒体、不跑 ICE 状态机、不参与编解码协商。
- **首包路由钥匙 = ICE ufrag**：服务端生成的 ufrag 内嵌路由元数据（目标集群 +
  归属 transceiver）。relay 只解析首个 STUN 包读出 ufrag 即可转发，之后 DTLS/RTP/RTCP
  按内存中的流表直转；relay 重启后下一个 STUN 包即可重建映射，Redis 缓存
  进一步加快恢复。
- **Global Relay + 地理调度信令**：Cloudflare 按地理/邻近把 HTTP/WebSocket 信令
  导到近处 transceiver 集群，SDP answer 返回近处 Global Relay 地址；信令与
  媒体都从近处进网，会话始终锚定同一个 transceiver。
- **实现取舍**：用户态 Go、`SO_REUSEPORT` 多 worker 共享端口、`runtime.LockOSThread`
  绑核保持流与 CPU 亲和、预分配缓冲避免 GC。**不用内核旁路**——窄实现足够撑起
  全球流量。
- **为什么不用 SFU**：流量绝大多数是 1:1（一用户对一模型），SFU 的多方转发能力
  用不上；TURN 则多一次分配往返且难以跨服务器迁移。

架构比较（OpenAI 原表精简）：

| 方案 | 优点 | 缺点 |
| --- | --- | --- |
| 每会话独立 IP:port | 直连、无转发层 | 需海量公网 UDP 端口，K8s/LB 不友好 |
| 每服务器独立 IP:port | 公网面小，单机多路复用 | 跨 LB 集群首包可能落错实例 |
| TURN relay | client 只需连 relay，可集中策略 | 分配多一 RTT，跨服务器迁移难 |
| 无状态转发 + 有状态终结（OpenAI） | 公网面小，transceiver 完整拥有会话 | 多一跳转发，relay/transceiver 需自定义协同 |

教训：**复杂度最好加在一层薄薄的路由层里**，而不是加进每个后端服务或 client
行为；**用协议里已有的字段（ufrag）做路由**，就不需要热路径上的外部查表。

## 六、用真实流量安全地灰度：静默测试

上线前，把一小部分（逐步增加）生产 ChatGPT Voice 会话**同时**路由到 AVM 和新
系统：AVM 照常服务用户，新系统在只读模式下跟跑推理。真实 client、真实网络、
真实会话长度与地理分布，用户听到的东西不变。学到的东西：

| 教训 | 具体 |
| --- | --- |
| **容量 ≠ GPU 吞吐** | 语音会话持续开着并连续发帧，CPU 侧流处理器、队列、网络路径必须与推理同步扩容。真实负载下某个配套组件早于压测预估饱和，推理请求堆积、时延复利。容量问题从"一张 GPU 能扛多少请求"改成"**系统能在每帧准时的前提下维持多少并发会话**" |
| **地理是一等公民** | 会话被路由到远处容量会在启动与流式多个环节加延迟。模型发布要与区域容量、流量调度配置一起验证，并按来源地理拆分时延 |
| **失败只在真实生命周期里出现** | 长会话暴露内存与持久化压力；重连触发压缩与状态恢复；普通断开暴露关闭握手的竞态。短压测看不到，因为它们依赖时间、累积状态与跨服务边界行为 |
| **可观测性与发布控制** | 发现了混淆不同时延来源的指标、聚合掩盖单个不健康引擎的看板、测试与部署配置漂移。对策：更细粒度遥测、对照已知良好配置校验、分阶段爬坡、可快速隔离/禁用单条路径 |

静默测试因此成了一次**发布彩排**：不只演练系统能吃多少流量，更演练
多快能发现、隔离、恢复故障。

## 七、六个月做了什么：按层归纳

| 层 | 改造 | 关键指标 / 结果 |
| --- | --- | --- |
| 模型推理 | 有状态流式推理，全双工模型持续消费/产出音频 | 拆掉轮次检测器 |
| 会话状态 | 预热‑prefill‑并行‑切换的实例迁移；压缩即切换 | 长通话无感压缩 |
| 媒体前端 | Python asyncio → Go；媒体与业务逻辑分离 | 帧交付 p95 ≈ 旧 p50 |
| 委托 | 预建前沿模型会话、亲和、prompt caching、调参 | 委托结果快到能接进对话 |
| 对话表示 | 推测视图 + 权威记录双视图分轮 | 周边系统拿到稳定轮次 |
| 传输协议 | WARP（SNAP/SPED/DTLS 1.3/预协商 DC）+ Instant Connect | 6 RTT → 1 RTT，单 UDP 包起会话 |
| 基础设施 | relay + transceiver，ufrag 路由，Global Relay | K8s 上跑 WebRTC，无需海量端口 |
| 发布 | 静默影子测试、地理拆分、细粒度遥测 | 容量模型改为"并发会话 × 每帧准时" |

文章结尾点明：这套架构已成为更广的实时交互平台——支撑 ChatGPT Voice 从对话
扩展到 agent 协同，并将承载即将推出的 GPT‑Live API。
