# 01 演进脉络与 omni 架构总览

本章回答两个问题：**"omni" 到底指什么**，以及**语音 AI 系统三代架构各自
解决了什么、没解决什么**。后续章节围绕 OpenAI 的 GPT‑Live（第三代）展开。

## "omni" 的定义：一个模型、多种模态、原生端到端

"omni" 一词进入大众视野是 2024 年 5 月的 GPT‑4o（o = omni）。它的核心主张
只有一句话：**文本、音频、图像用同一个神经网络端到端处理**，而不是把
ASR、LLM、TTS 三个模型串起来。

这带来三个结构性变化，所有 omni 系统都共享：

| 变化 | 级联系统（ASR→LLM→TTS） | omni 系统 |
| --- | --- | --- |
| 信息保真 | 转写成文本后语气、语速、笑声、背景声全部丢失 | 模型直接"听到"音频，可感知副语言信息，也能"说出"语气 |
| 时延结构 | 三段串行，总时延 ≈ 各段之和（常见 2–3 s） | 单模型，音频 token 流式进出，理论上可到几百 ms |
| 决策主体 | 何时回话由 VAD/轮次检测器（外部小模型）决定 | 有条件让模型自己决定何时开口（第三代才真正做到） |

但要注意：**omni ≠ 全双工**。GPT‑4o / Advanced Voice Mode 是 omni 模型，
却仍是轮次制（turn-based）——模型能直接吃音频，但仍要等一个独立的
轮次检测器说"用户说完了"才能开始推理。这正是 GPT‑Live 要拆掉的东西。

## 三代架构一览

OpenAI 在《How we built a realtime system for responsive voice AI in six months》
中把自家语音系统分为三代，这个划分对整个行业同样适用：

```text
第一代 级联（Cascaded）        第二代 语音到语音 + 轮次制         第三代 全双工（Full-duplex）
                                (Speech-to-speech, turn-based)

 mic ─→ VAD ─→ ASR ─→ LLM ─→ TTS   mic ─→ 轮次检测器 ─→ omni 模型 ─→ spk   mic ══╗
                                                                           ╠═ 全双工语音模型 ═══╗
 每段串行，文本为中介                单模型吃音频，但仍等"说完"信号             ║   ↓ 异步委托     ║
 时延 2–3 s，丢副语言信息            时延 ~1 s，切话/抢话靠阈值               ╚══ 前沿模型(GPT-5.5) ╝
                                                                           音频持续进出，模型自决何时开口
```

| 维度 | 第一代 级联 | 第二代 S2S 轮次制 | 第三代 全双工 |
| --- | --- | --- | --- |
| 代表 | 原版 ChatGPT Voice（Whisper→GPT→TTS） | GPT‑4o Advanced Voice Mode、Realtime API（`gpt-realtime` 系列） | GPT‑Live‑1 / mini（2026‑07） |
| 输入单元 | 完整一段音频 blob | 完整一段音频 blob | 连续音频帧流 |
| 谁决定开口 | VAD 静音阈值 | 轮次检测器（tiny model） | 语音模型本身，每秒多次决策 |
| 能否边听边说 | 否 | 否（被打断 = 取消响应重来） | 是（可"嗯嗯"附和、可被打断、可主动插话） |
| 深度推理 | 同一 LLM | 同一 omni 模型 | 异步委托给前沿模型，对话不停 |
| 推理形态 | request‑response | request‑response | 有状态流式推理（stateful streaming） |
| 典型问题 | 慢、生硬 | 抢话/迟钝二选一，停顿或背景噪声会误触发 | 工程复杂度极高：状态、切换、协议、容量模型全部要重做 |

## 第二代的死结：轮次检测器的两难

第二代系统已经用了 omni 模型，为什么体验还是"对讲机"？因为**推理只能在轮次
检测器做出判断之后开始**。检测器面对一个无解的权衡：

- 判早了 → 用户还没说完就被打断；
- 判晚了 → 每轮都多几百毫秒到一秒的"死气"。

更根本的问题是：**VAD 是在对"静音"做推理，而不是对"语义"做推理**。它分不清
"我在想下一个词"和"我说完了"。Realtime API 后来引入的 `semantic_vad`
（带 `eagerness` 参数）是在这个框架内的改良——用语义判断代替纯静音阈值，
但架构上仍是"先判断、再推理"的两阶段。

## 第三代的核心转变：从"生成问题"变成"控制问题"

全双工模型的输入永远不会停。用户音频是持续流，模型必须一边持续消费输入，
一边持续决定输出。OpenAI 的原话是：模型**每秒多次**做出交互决策——
**说话、继续听、停顿、插话、调用工具**。

这与标准自回归文本生成是根本不同的推理模式：

| | 文本 LLM | 全双工语音模型 |
| --- | --- | --- |
| prompt 何时固定 | 生成开始前固定 | 永远在变 |
| 每步决策 | 下一个 token 是什么 | **先决定要不要出声**，再决定说什么 |
| 更像什么 | 序列生成 | 实时控制策略（policy over a small action space） |
| 对时延的容忍 | 首 token 慢一点无妨 | 每一帧音频必须按时送达，否则是可听见的停顿/伪音 |

结论：第三代不是"把第二代做快一点"，而是把语音交互重新建模为
**一个持续运行的媒体环路 + 若干异步旁路**。这是后面所有工程决策的根源。

## 业界 omni / 全双工架构谱系

GPT‑Live 没有公开技术报告，但把它放进业界谱系里能看清它的选择。

### 谱系一：Moshi（Kyutai，2024）——最早公开的全双工基础模型

- **多流建模**：把用户音频、模型自己的音频建成两条并行 token 流，由同一个
  Temporal Transformer（7B，Helium 初始化）处理，**不显式建模说话人轮次**，
  重叠、插话、附和都是自然涌现的序列模式。
- **Inner Monologue**：在生成音频 token 之前先预测时间对齐的文本 token 作为
  前缀，显著提升语言质量，顺带得到流式 ASR 和 TTS。
- **Mimi codec**：24 kHz 音频压到 12.5 Hz、8 个码本、1.1 kbps，完全流式（80 ms 帧）。
  帧率接近文本 token 速率（3–4 Hz），减少自回归步数。
- **Depth Transformer**：小模型在同一时间步内建模 8 个码本间的依赖。
- 理论时延 160 ms（80 ms 帧 + 80 ms 声学延迟），单张 L4 上实测 ~200 ms。

Moshi 证明了"全双工可以是模型的内生属性"。GPT‑Live 在公开描述上属于同一族。

### 谱系二：Qwen2.5/3‑Omni（阿里，2025）——Thinker‑Talker 解耦

- **Thinker** 负责跨模态理解与文本生成，**Talker** 是双轨自回归解码器，直接
  从 Thinker 的隐状态生成流式语音 token——语音生成可以在推理尚未完全落成
  文本前就开始。
- Qwen3‑Omni 进一步：Thinker/Talker 都改 MoE；自研 AuT 音频编码器（2000 万小时
  监督数据，块状窗口注意力支持实时 prefill 缓存）；多码本 + MTP 模块每步出
  一帧；Code2Wav 用轻量因果 ConvNet 替代块状 DiT，实现**首帧即可合成**；
  输入输出音频码率降到 12.5 Hz。
- 冷启动理论首包时延 234 ms（纯音频）/ 547 ms（音视频）；并发 6 路时退化到
  1172 / 2284 ms——**时延随并发急剧上升**这一点，正是 GPT‑Live 工程文章里
  "容量不能只看 GPU 吞吐"的另一面印证。

Thinker‑Talker 是**模型内部**的"想/说"解耦；GPT‑Live 是**系统层面**的
"说（GPT‑Live）/想（GPT‑5.5）"解耦。两者解决的是同一个矛盾：
说话要快、思考要深，一个模型很难两头都占。

### 谱系三：单模型直出（Gemini Live、Grok Voice）

- Gemini Live：原生 audio‑to‑audio，持久双向 WebSocket 同时流音频、视频帧和
  转写；公开模型处理时延 100–200 ms（Flash Live，TPU）。未公开是否存在向更大
  模型的显式委托。
- Grok Voice：单一 S2S 模型，不经文本中介，Think Fast 2 把首音时延从 ~1.25 s
  压到 ~0.70 s。押注单模型极速，代价是深度推理上限受限于这个模型自身。

### 谱系四：环境感知型（Alexa+）

- 新增设备指向性（device‑directedness）判断：区分"对 Alexa 说"和"对屋里
  其他人说"，融合音频与视觉信号在端侧完成。
- 上下文化打断（contextual barge‑in）："那个"要能解析到 Alexa 刚读到列表的
  第几项——要求模型确切知道自己说到了哪里。这与 Realtime API 的
  `conversation.item.truncate` 解决的是同一类问题。

### 谱系对照

| 系统 | 核心架构 | 轮次/打断 | 深度推理去哪 | 已公开时延 |
| --- | --- | --- | --- | --- |
| GPT‑Live | 全双工对话模型 + 后台前沿模型两层 | 每秒多次策略决策 | 显式委托 GPT‑5.5，对话不停 | 官方未公布；第三方实测首音中位 ~1.1 s |
| Moshi | 单模型多流，Inner Monologue | 序列建模自然涌现 | 无（7B 自身） | 160 ms 理论 / 200 ms 实测 |
| Qwen3‑Omni | Thinker‑Talker MoE | 依赖上层 VAD/轮次 | Thinker 自身（可选 Thinking 变体） | 234 ms 理论首包（单路） |
| Gemini Live | 单原生音频模型 | barge‑in 即停音频缓冲 | 未公开 | 100–200 ms 模型处理 |
| Grok Voice | 单 S2S 模型 | 单模型内连续 | 无公开委托层 | ~0.70 s 首音 |
| Alexa+ | S2S 模型 + 设备指向性模型 | 上下文化打断 | 未按此维度公开 | 未按此口径公开 |

## 设计轴总结：omni 系统的五个自由度

综合上面谱系，一个 omni 实时语音系统的架构选择可以拆成五个正交轴：

1. **模态融合深度**：级联 → 单模型 S2S（omni）→ 单模型全双工多流。
2. **轮次控制权**：外部 VAD → 语义 VAD → 模型内生决策。
3. **想/说解耦位置**：不解耦 → 模型内（Thinker‑Talker）→ 系统级（对话模型 + 委托模型）。
4. **推理形态**：无状态 request‑response → 有状态流式推理（带实例切换与压缩）。
5. **传输与接入**：WebSocket 搬 base64 → WebRTC → 协议级裁剪（WARP / Instant Connect）。

GPT‑Live 在每个轴上都选了最右端。第 02 章讲它在轴 1–3 上的产品与模型形态，
第 03 章讲轴 4–5 的系统工程，第 04 章讲开发者能碰到的 Realtime API 表面。
