# 06 全双工输出状态盘点

讨论题：**全双工模型在输出侧到底有哪些"状态"？** 本章先盘点权威文献与业界实践
对状态的定义方式，再归纳出一张可供我们讨论的统一状态表。

三层视角必须分开谈，否则会把"现象"、"模型内部表示"和"系统事件"混成一团：

| 层 | 问的问题 | 代表来源 |
| --- | --- | --- |
| 会话现象层 | 人类对话里实际发生哪些轮次事件 | Sacks/Schegloff/Jefferson 1974；Skantze 2021 综述；VAP |
| 模型表示层 | 模型用什么 token / 分类头 / 序列布局把这些事件编码成可预测的目标 | Moshi、SyncLLM、Freeze‑Omni、SALMONN‑omni、BayLing‑Duplex、FLM‑Audio、Chronological Thinking |
| 系统事件层 | 编排层 / API / 产品对外暴露什么状态与事件 | GPT‑Live 五动作、Realtime API 事件、Deepgram Flux、TEN / Easy Turn / Smart Turn、Full‑Duplex‑Bench 行为标签 |

## 一、会话现象层：轮次组织的基本概念

### Sacks, Schegloff & Jefferson（1974）"最简系统学"

- **TCU**（turn‑constructional unit）：构成一个轮次的语言单元（词、短语、从句、句子）。
- **TRP**（transition‑relevance place）：轮次可能结束、说话人可能更替的位置，
  通常与句法、韵律、语义边界重合。
- **轮次分配**：当前说话人选定下一位 / 他人自选 / 无人接则当前说话人**保持**（hold）。
- 三个核心动词：**hold（持有）/ yield（让出）/ abandon（放弃）**。
- 设计目标：最小化间隙与重叠——但重叠在真实口语中占 **10–20%** 的时间
  （Moshi 论文引 Çetin & Shriberg 2006），不是异常，是常态。

### Skantze（2021）综述：对话系统里的轮次问题

把系统需要建模的事件归为：**end‑of‑turn 检测、用户打断处理、轮次线索生成、
多方交互**。关键论点：静音阈值只是最粗的替代物，轮内停顿（hold）与轮间停顿
（shift）在声学上不可区分，必须用**连续、预测式**的模型（而非等 IPU 结束再判）。

### VAP（Voice Activity Projection）与 TurnGPT

- VAP 直接预测未来 2 s 内两位说话人的语音活动分布，由此派生出四类事件：
  **turn‑yielding（shift）/ turn‑holding（hold）/ backchannel / interruption**。
- TurnGPT 从文本侧预测轮次完成概率；两者并用可同时覆盖韵律与语义线索。
- 这四类事件是后面所有工程状态定义的"最小公分母"。

### backchannel 的特殊地位

"嗯嗯 / 对 / uh‑huh"是**不夺取发言权的输出**：它出现在重叠里，邀请线索与 TRP 线索
相似但不相同。所以 backchannel 必须是输出侧的一个**独立状态**，不能归到
"说话"或"沉默"任何一边——这是几乎所有实践都单列它的原因。

## 二、模型表示层：各家如何把状态编码进模型

### 总览

| 模型 | 状态是否显式 | 状态载体 | 状态集合 | 时间粒度 |
| --- | --- | --- | --- | --- |
| **Moshi**（Kyutai 2024） | 隐式 | 文本流 `PAD` / `EPAD` + 音频流"自然静音" | 无枚举；沉默 = PAD + 近静音波形；`EPAD` = 即将开口（可强制采样让它立刻说话） | 80 ms 帧 |
| **SyncLLM**（2024） | 隐式 | 周期同步 token + 双方 chunk 交错 | 无枚举；靖音去重，由序列建模涌现 backchannel / 重叠 / 打断 | 固定 chunk |
| **LSLM**（2024） | 半显式 | `IRQ` 中断 token | 说 / 被打断停 | 帧 |
| **Freeze‑Omni**（VITA 2024） | 显式分类头 | LLM 末层附加分类层，按 chunk 预测 | `0` 继续收音 / `1` 用户打断→新一轮生成 / `2` 说完、无需打断 | chunk 末帧 |
| **SALMONN‑omni**（2024） | 显式状态 token | `<start_speak>` / `<end_speak>` + "thinking" 机制 | speaking / non‑speaking 两态；处理 turn‑taking、barge‑in、回声 | 时间块 |
| **BayLing‑Duplex**（2026） | 显式状态 token | 文本通道内 4 个对话状态 token | `[SILENCE]` 保持沉默 / `[ASSISTANT]` 开始回复 / `[PAD]` 文本已写完、语音还在播 / `[EPAD]` 文本与语音都结束 | 0.8 s 块（N=10 语音 token : M=5 文本槽） |
| **FLM‑Audio**（2025） | 半显式 | 连续独白 + `<wait>` 填充 | 说（独白领先语音 0–2 token）/ 等（wait）/ 被有意义语音打断 | 句级对齐 |
| **Chronological Thinking**（StepFun 2025） | 隐式→"想" | 用**思考链替换沉默 token** | 沉默不再是空态，而是"边听边想" | 帧 |
| **Fun‑Audio‑Chat‑Duplex**（通义，Qwen3 底座，2025） | 隐式 | 并行 speech‑text 输入流 + `<\|SIL\|>` 静音 token | 无枚举；重叠为附和→继续、为新指令→停；自报 turn‑taking 成功率 100%，Instruct‑FD IAS 仅 46.2% | 5 Hz 共享骨干 / 25 Hz 语音头 |
| **Qwen3‑Omni**（Thinker‑Talker，2025） | 不定义输出状态 | — | 轮次制 S2S，发言权交给外部 VAD；解耦的是"想/说"（THINKING 态首包时延），不是"听/说" | 12.5 Hz |
| **Unit‑based agent**（2026，半级联） | 显式状态机 | MLLM 输出动作 | 状态 `listen` / `speak` × 动作 `continue` / `switch`；listen 中判语义完整→switch；speak 中判 backchannel（continue）vs 真打断（switch） | 单元 |
| **GPT‑Live**（OpenAI 2026） | 官方描述为动作集 | 未公开 | **speak / continue listening / pause / interrupt / invoke a tool**，"每秒多次"决策 | 未公开 |

### 几条值得注意的设计脉络

1. **从"要不要说"到"说什么"是两步决策。** Moshi 把 `EPAD`（结束填充）与下一个词
   分开预测，论文明说这是"把结束一个词和决定下一个词拆成两步"；BayLing 用
   `[ASSISTANT]` 单独标记"开口"这一事件。GPT‑Live 的动作集同样先决定动作再生成。
2. **沉默不是一种状态，而是几种。** Moshi 的沉默是 PAD + 自然静音；BayLing 区分
   `[SILENCE]`（还没轮到我）与 `[PAD]`（我说完了文本但语音还没播完）；
   Chronological Thinking 更把沉默期变成思考期。所以"沉默"至少分为
   **听 / 播放尾音 / 思考** 三种内部状态，外观相同、内部不同。
3. **打断的判定归属在迁移。** Freeze‑Omni 靠外部 VAD 触发 + 分类头判"是不是打断"；
   Unit‑based agent 在 speak 态里区分 backchannel 与真打断；GPT‑Live 把
   "是不是真的要打断我"完全交给模型（Agora 观察到它让出慢 ~500 ms 但 30/30 拒绝
   背景人声）。趋势是**从声学触发 → 语义判定 → 模型内生决策**。
4. **显式 token 的代价是类别不平衡。** BayLing 指出 `[SILENCE]` 在序列中占绝对多数，
   `[ASSISTANT]` 每轮只出现一次，必须用逐 token 权重防止稀有角色 token 被淹没，
   并用 DPO 单独优化"时机"。Moshi 也报告英语对话中 PAD 占 65%。任何显式状态设计
   都要面对这个问题。
5. **粒度决定最小响应时延。** Moshi 80 ms 帧可以 160 ms 理论时延；BayLing 选 0.8 s 块，
   论文承认块太小则轮次抖动、块太大则最小时延超过可接受阈值。状态的时间粒度是
   架构级参数，不是实现细节。
6. **"轮次成功率"不是状态指标。** Fun‑Audio‑Chat‑Duplex 技术报告自报 turn‑taking
   成功率 100%（Moshi 99.77%、Freeze‑Omni 93.87%），但在 Instruct‑FD 上 IAS 只有 46.2%
   （Backchannel 0%、Acknowledge 5.4%，典型的 Continue‑default 坍缩）。"该开口时开口了"
   与"在附和/纠正/插话上做对了"是两件事，评测必须直接测状态判定。

### Qwen 系在三层里的位置

Qwen 不是一条线，而是三条，分属不同层，不应合并成"Qwen 一行"：

| Qwen 系工作 | 所属层 | 对状态问题的贡献 |
| --- | --- | --- |
| **Qwen2.5/3‑Omni**（Thinker‑Talker MoE） | 架构层（01 章谱系二） | 模型内"想/说"解耦，给 THINKING 态的首包时延预算提供参照：单路 234 ms，6 并发 1172 ms；对发言权状态无直接贡献 |
| **Qwen Realtime API**（`qwen3-omni-flash-realtime` / `qwen3.5-omni-*-realtime` / `qwen-audio-3.0-realtime`） | 系统事件层 | 与 OpenAI Realtime 同构：`turn_detection` = `server_vad` / `semantic_vad`（qwen3.5 起）、`interrupt_response`、`speech_started` 即取消响应；Qwen‑Audio 3.0 的 **`smart_turn`** 声学 + 语义判轮，"嗯 / 呃"不触发打断——Easy Turn 四态在 API 上的落地 |
| **Fun‑Audio‑Chat‑Duplex**（通义，Qwen3 底座） | 模型表示层 | Qwen 系唯一原生全双工；并行输入流 + `<\|SIL\|>`；是 Continue‑default 坍缩的典型反例 |

### 用户侧状态（输入判定）与输出状态的对应

不少实践把状态定义在**用户话语**上，再映射为系统动作：

| 用户话语状态 | Easy Turn（2025/ICASSP 2026） | TEN Turn Detection | Deepgram Flux 事件 | 期望的系统输出状态 |
| --- | --- | --- | --- | --- |
| 语义完整 | complete | finished | EndOfTurn（高置信）/ EagerEndOfTurn（中置信、可投机生成） | 开口回答 |
| 语义未完 | incomplete | unfinished | TurnResumed（用户接着说，取消投机结果） | 继续听（hold 给用户） |
| 用户附和 | backchannel | — | — | 继续说（不让出） |
| 用户要求闭嘴 / 暂停 / 结束 | wait | wait | — | 立即停、进入纯聆听 |
| 用户开口 | — | — | StartOfTurn | 若在说，进入让出判定 |

Flux 的 **Eager / Resumed** 一对事件值得单独记：它把"投机开始生成、发现用户没说完
再撤回"做成了一等公民，代价是 50–70% 更多 LLM 调用换 150–250 ms 提前。这与
GPT‑Live"先应答、后实质"的两时钟是同一思想在级联系统里的落地。

## 三、系统事件层：API 与产品暴露的状态

### OpenAI Realtime API（第二代表面）

| 服务端事件 | 对应输出状态变化 |
| --- | --- |
| `input_audio_buffer.speech_started` | 用户开口；若模型在说 → 自动取消响应（`response.cancelled`）并需 `conversation.item.truncate` |
| `input_audio_buffer.speech_stopped` | 用户停止；VAD 模式下自动 commit 并 `response.create` |
| `response.created` → `response.output_audio.delta` → `response.done` | 进入"说话"、持续说、说完 |
| `response.cancelled` | 被打断 → 让出 |
| `turn_detection.create_response=false` | 听到了但不自动开口（保留人工触发） |
| `conversation: "none"` 旁路响应 | "边想边说"的雏形：后台推理不进主对话 |

`semantic_vad.eagerness` 是对"多快判定用户说完"的单一旋钮——第二代把 hold/yield
的判定做成了可配置参数，第三代把它收回模型。

Qwen Realtime API 与之同构（`server_vad` / `semantic_vad` + `interrupt_response`），
Qwen‑Audio 3.0 另有 `smart_turn` 模式（声学 + 语义联合判轮，"嗯 / 呃"不触发打断）。
两家的第二代 API 状态都是**外部驱动**的，这也是 Instruct‑FD 排除 GPT‑Realtime 的理由。

### GPT‑Live（第三代）

官方公开的动作集只有五个：**speak / continue listening / pause / interrupt / invoke a tool**。
但结合工程文章，系统层还存在几个用户听不见、但决定行为的状态：

- **委托中**（delegating）：前沿模型在跑，语音模型"打圆场"或附和；
- **切换中**（handoff）：实例迁移 / 上下文压缩，媒体不断；
- **分轮暂定**（provisional message）：应用服务器尚未定稿谁持有发言权。

这些是"系统状态"而非"模型输出状态"，但它们直接约束模型能做什么
（例如委托中不能给出实质答案）。

### Full‑Duplex‑Bench 的评测视角（反向定义"期望状态"）

评测基准实际上给出了业界对"正确输出状态"的共识：

**v1.0 四维度**（Lin et al. 2025）

| 场景 | 期望行为 | 指标 |
| --- | --- | --- |
| Pause handling（用户轮内停顿） | **不**接管（hold 给用户） | Takeover Rate ↓ |
| Backchanneling（用户在说、系统附和） | 短反馈、不接管 | TOR、附和频率、与人类时机分布的 JSD |
| Smooth turn‑taking（用户说完） | 及时开口 | 响应时延 |
| User interruption（用户打断） | 接管、让出、回应新意图 | TOR ≈ 1、GPT‑4o 质量分、打断后时延 |

**v1.5 四种重叠场景 × 四类行为标签**

| 重叠场景 | 期望行为 |
| --- | --- |
| 用户打断（新请求） | **Respond**（停下、回应新意图） |
| 用户附和（uh‑huh） | **Resume**（忽略、继续原话） |
| 用户对旁人说话 | Resume，允许少量 **Uncertain**（"你是在跟我说吗？"） |
| 背景人声 | Resume，近零 Respond |

行为标签：**Respond / Resume / Uncertain / Unknown**；时序指标：**stop latency**
（重叠开始 → 系统停嘴）、**response latency**（重叠结束 → 系统再开口）；另有韵律
适应（音高、强度、语速）。v1.5 观察到两种策略取向：**repair‑first（快速让出）**
vs **continuity‑first（维持连贯）**——GPT‑4o 属前者（打断 Respond 0.78，但对旁人
说话也 Respond 0.91，误接管高），Sonic/Gemini 属后者（Resume 高但打断响应低）。
**没有一种策略在四个场景全优**，这直接说明输出状态的选择是场景相关的产品决策。

### Instruct‑FD：状态不仅要"有"，还要"可被指令控制"

Instruct‑FD（Tang et al., Boson AI, arXiv 2607.20460, 2026）把轮次管理重新表述为
**指令遵循问题**：同一段对话配不同的自然语言策略指令，模型应表现出不同的正确状态。
912 用例 × 29 场景 × 6 系统，WebRTC 多轮编排器 + LLM 裁判（与人一致 88.9%）。

按"谁持有发言权"分为两组、五条策略：

| 组 | 策略 | 定义 | 对应统一模型状态 |
| --- | --- | --- | --- |
| Proactive（用户在说） | **Listen** | 沉默，不附和不插话 | LISTENING |
| | **Backchannel** | 在触发点短应答，不夺发言权 | BACKCHANNEL |
| | **Interrupt** | 触发（矛盾 / 安全错误）时夺取发言权 | INTERJECTING |
| Responsive（模型在说） | **Continue** | 用户"嗯嗯"视为支持，不让出 | RESUMING |
| | **Acknowledge** | 用户纠正 / 加约束 / 转向 → 立即承接调整 | YIELDING → SPEAKING |

结果（IAS，指令遵循率）：Gemini Live 总体最高 **64.4%**；Continue 普遍 40–97.5%，
Acknowledge 最高 86.3%；而 **Backchannel 0–50%、Interrupt 1.7–11.7%**——主动性状态是
全行业短板。四个系统性失败模式：

1. **语义合规 ≠ 时序合规**：说了对的话，但在错的时刻（该在用户说话中附和，却等说完才"嗯"）。
2. **Continue‑default 坍缩**：Fun‑Audio‑Chat / MiniCPM‑o Continue ≈ 100%、Acknowledge ≈ 5%，
   分不清"继续者"与"纠正"。
3. **触发层级**：Gemini 对显式触发（"你懂吗？"100%）能附和，对隐式触发（子句边界 0%）失灵。
4. **指令可能反而破坏**：Fun‑Audio‑Chat 加指令后 Acknowledge −11.2%；PersonaPlex 基线比
   Moshi 好一倍但 ΔIAS 仍小——**基线好 ≠ 可控**。

值得注意的排除：GPT‑Realtime 因"API 要求用户显式发出打断信号、不允许模型自主管理
发言权"被排除——第二代 API 的状态是外部驱动的，第三代才把决策交回模型。

### 时序指标的三时钟

Agora 对 GPT‑Live 的实测补上了"说了以后"的维度：**应答起点 / 实质答案起点 / 完成**。
与 FDB 的 stop / response latency 合在一起，一个全双工系统至少要测五个时间点：
用户停 → 系统首音；用户打断 → 系统停嘴；重叠结束 → 系统再开口；
首音 → 实质内容；实质内容 → 说完。

## 四、统一状态模型（讨论稿）

综合以上三层，提出一张**输出通道状态表**供讨论。原则：每个状态对用户**可感知地
不同**，或对系统**可操作地不同**；两者都不满足的不单列。

```text
                    ┌─────────────┐  用户语义完整 / TRP        ┌─────────────┐
   用户开口 ───────▶│  LISTENING  │───────────────────────────▶│  SPEAKING   │
                    │ (沉默、持有权在用户)│◀──────── 说完 EPAD ──────────│ (持有发言权) │
                    └──┬───┬───┬──┘                            └──┬───┬───┬──┘
      用户轮内停顿      │   │   │ 附和时机                  用户附和 │   │   │ 用户真打断
      (hold 给用户)     │   │   ▼                                  │   │   ▼
                        │   │ ┌────────────┐                      │   │ ┌────────────┐
                        │   │ │BACKCHANNEL │──▶ 回 LISTENING      │   │ │  YIELDING  │──▶ 停嘴+截断 ──▶ LISTENING
                        │   │ └────────────┘                      │   │ └────────────┘
                        │   ▼                                     │   ▼
                        │ ┌────────────┐                          │ ┌────────────┐
                        │ │  THINKING  │ 需要委托/工具            │ │  RESUMING  │ 判定为附和/旁人/背景 → 继续原话
                        │ │(可带填充语) │──▶ 结果到 ──▶ SPEAKING   │ └────────────┘
                        │ └────────────┘                          ▼
                        ▼                                   ┌────────────┐
                  ┌────────────┐                            │  HOLDING   │ 自己的轮内停顿（思考、换气），不让出
                  │   MUTED    │ 用户说"别说话/等一下"        └────────────┘
                  │(显式禁言)   │──▶ 用户解除 ──▶ LISTENING
                  └────────────┘
   任意状态 ── 需要澄清 ──▶ REPAIR("没听清 / 你是在跟我说吗") ──▶ LISTENING
   LISTENING ── 有高价值信息且允许 ──▶ INTERJECTING(模型主动插话，经打扰管理) ──▶ SPEAKING
```

| 状态 | 定义 | 对用户可感知 | 文献 / 实践对应 |
| --- | --- | --- | --- |
| **LISTENING** | 沉默，发言权在用户，持续消费输入 | 安静 | Moshi PAD+自然静音；BayLing `[SILENCE]`；GPT‑Live continue listening；Unit‑agent listen |
| **HOLDING** | 自己的轮内停顿，仍持有发言权（思考、换气、节奏） | 短停顿但不像说完 | Sacks hold；GPT‑Live pause；BayLing `[PAD]`（文本完、语音未完的尾段） |
| **THINKING / DELEGATING** | 需要工具或后台模型，沉默或用填充语撑住 | "让我看一下…"或短暂沉默 | GPT‑Live invoke tool + 委托；Chronological Thinking；Realtime API 异步函数调用 / 旁路响应 |
| **BACKCHANNEL** | 不夺发言权的短输出 | "嗯嗯 / 对" | VAP backchannel；FDB backchanneling；GPT‑Live "mhmm" |
| **SPEAKING** | 持有发言权，产出实质内容 | 正常说话 | BayLing `[ASSISTANT]`+内容；SALMONN `<start_speak>`；Realtime `response.*` |
| **YIELDING** | 判定用户真打断，停嘴并截断未播内容 | 立刻闭嘴 | Freeze‑Omni state 1；LSLM IRQ；Realtime `response.cancelled` + `truncate`；FDB Respond；stop latency |
| **RESUMING** | 判定重叠为附和 / 旁人 / 背景，继续原话 | 不受影响地说下去 | FDB Resume；Unit‑agent speak+continue；Agora "拒绝背景人声" |
| **INTERJECTING** | 用户在说，模型主动实质性插入 | 被模型插话 | GPT‑Live interrupt；OpenAI 分轮规则"实质性插话应成消息"；须经打扰管理 |
| **MUTED** | 用户显式要求禁言 / 暂停 | 长时安静直到解除 | Easy Turn / TEN `wait`；GPT‑Live "让它闭嘴听" |
| **REPAIR** | 表达没听清 / 确认是否在对我说 | "你是在跟我说吗？" | FDB Uncertain；Alexa 设备指向性；v1.5 允许少量 Uncertain |

### 状态间的关键判定（转移守卫）

| 判定 | 输入线索 | 难点 | 现有做法 |
| --- | --- | --- | --- |
| 用户说完了吗（LISTENING → SPEAKING） | 语义完整性 + 韵律 + 停顿长度 | hold vs shift 声学不可分 | TurnGPT/VAP；Easy Turn complete/incomplete；Flux eager/resumed 投机 |
| 这是附和还是打断（SPEAKING → RESUMING / YIELDING） | 长度、内容、是否含新意图 | 短句"对对对 / 等一下"歧义 | Unit‑agent；Freeze‑Omni 分类头；GPT‑Live 内生（让出慢 500 ms 换零误触发） |
| 是对我说的吗（→ REPAIR / RESUMING） | 说话人、方向、内容指向 | 多方 / 背景 | Alexa 设备指向性；FDB v1.5 talking‑to‑others |
| 该插话吗（LISTENING → INTERJECTING） | 信息价值 × 紧急度 × 用户状态 | 主动性的社会成本 | 打扰管理器（phone‑assistant 03 §4）；GPT‑Live 未公开策略 |
| 该沉默多久（THINKING 时长上限） | 后台进度 | 沉默是语音里最差的失败态 | 填充语 + 三时钟预算；超时兜底话术 |

## 五、我们要决定的事

1. **显式还是隐式。** Moshi/SyncLLM 路线靠数据涌现，可控性差；Freeze‑Omni/BayLing
   路线加显式 token 或分类头，可控、可加权、可用 DPO 单调时机，但要面对类别不平衡
   与数据构造成本。建议：**对外接口层一律显式**（上表状态），模型内部可隐式，
   但至少要能从输出中**可靠地读出**当前状态（如 BayLing 的文本通道）。
2. **状态归属。** 哪些状态由模型决定（SPEAKING/BACKCHANNEL/YIELDING/RESUMING），
   哪些由编排层决定（MUTED、INTERJECTING 的最终放行、THINKING 的超时）。
   GPT‑Live 的分法是：模型管"说不说"，应用服务器管"委托、分轮、持久化"。
3. **粒度。** 80 ms 帧级还是数百 ms 块级？直接决定最小响应时延与轮次抖动。
4. **策略取向要成为可配置参数。** repair‑first 与 continuity‑first 没有全局最优；
   客服倾向前者、陪伴/辅导倾向后者。对应到状态表就是 YIELDING 与 RESUMING 的
   判定阈值。Instruct‑FD 进一步证明同一对话在不同指令下正确状态不同——转移守卫
   应是可被策略指令参数化的函数，其五条策略可直接作为策略 profile 的词表。
5. **评测集要先于模型。** 至少覆盖 FDB v1.0 四维度 + v1.5 四重叠场景 +
   Instruct‑FD 五策略指令遵循（IAS / ΔIAS），加上三时钟。重点补主动性场景。
   现有基准均为英文，中文子集需自建。没有这套评测，状态设计无法被验证。
7. **主动性是最大风险。** 双脑架构依赖前台"主动播报 / 插话"，而这正是业界 IAS
   最低（≤ 11.7%）的能力。要么把 `speak_at_pause` 设为默认、`speak_now` 仅限高紧急，
   要么专项训练（显式 token + DPO 调时机）并先在评测集上验证。
6. **与分轮器、reminder 的接口。** 状态转移事件（尤其 YIELDING/INTERJECTING）应
   进入权威记录，供分析与安全审计；reminder 注入点应对齐到状态边界。

## 附录：来源 Top 10——对"输出状态"问题的贡献排序

排序标准四条：① 是否给出可枚举的状态集合；② 是否有可复现数据；③ 是否经生产 /
规模验证；④ 与我们双脑架构的相关度。排序针对"输出状态"这一问题，不是模型整体优劣。

| # | 来源 | 贡献的核心洞察 | 排序理由（含扣分项） |
| --- | --- | --- | --- |
| 1 | **GPT‑Live**（公告 + 六个月工程文） | 五动作 + 三个系统影子状态（委托中 / 切换中 / 分轮暂定）；"说/想"两时钟 | 唯一生产级第三代，即双脑架构的业界样本；④ 最高。扣分：机制不公开，只能当目标形态 |
| 2 | **Instruct‑FD** | 状态从"有没有"变成"可不可控"；按 floor 分五策略；量化主动性短板（Interrupt ≤ 11.7%） | 直接命中我们最大风险（打扰管理器依赖主动插话）；排除 GPT‑Realtime 的理由说清两代分水岭 |
| 3 | **Full‑Duplex‑Bench** v1.0 / v1.5 | 用期望行为反向定义正确状态（Respond / Resume / Uncertain / Unknown）；repair‑first vs continuity‑first | 给出指标口径（TOR、stop / response latency）；不测可控性，故居 Instruct‑FD 之后 |
| 4 | **BayLing‑Duplex** | 4 个状态 token、零新增模块、40 万样本 + DPO 调时机；类别不平衡加权 | "接口层显式、模型可读出"建议的最直接工程依据；比 Moshi 可复制 |
| 5 | **Moshi** | 全双工内生范式原型；PAD / EPAD 把"停下"与"说什么"拆两步；PAD 占 65% | 理论价值最高；但 IAS 21.1%、停顿接管率 1.0——涌现路线可控性差，作为反例同样重要 |
| 6 | **Sacks 1974 / Skantze 2021 / VAP** | hold / yield / abandon；shift / hold / backchannel / interruption；重叠 10–20% | 状态枚举的语言学锚点，防止发明伪状态；不给工程答案 |
| 7 | **Freeze‑Omni** | 分类头三态 + frozen LLM + "model as server" | 最易落地的显式路线；IAS 10.7% 说明三态过粗——"显式 ≠ 够用" |
| 8 | **第二代实践层**：OpenAI Realtime · Qwen Realtime（`semantic_vad` / `smart_turn`）· Flux · Easy Turn / TEN | 状态以事件暴露、外部驱动；投机开口再撤回；`wait` 单列 | 短期可用件；MUTED 与投机 SPEAKING 的来源；Qwen 在这一层 |
| 9 | **Fun‑Audio‑Chat‑Duplex**（通义，Qwen3 底座） | 并行输入流 + `<\|SIL\|>`；Continue‑default 坍缩典型 | 反面证据：自报 turn‑taking 100% vs IAS 46.2%——评测必须含 Acknowledge / Backchannel |
| 10 | **Qwen3‑Omni**（Thinker‑Talker） | 模型内想/说解耦；6 并发首包 234 → 1172 ms | 对 THINKING 态时延预算与"容量 ≠ GPU 吞吐"有价值；对发言权状态无直接贡献 |

排序逻辑一句话：GPT‑Live 定目标，Instruct‑FD 与 FDB 定量尺，BayLing / Moshi / Freeze‑Omni
定实现路线，Sacks–Skantze 定语言学边界，第二代实践层（含 Qwen Realtime）定短期可用件，
Fun‑Audio‑Chat 与 Qwen3‑Omni 提供反例与时延旁证。
