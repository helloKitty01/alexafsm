在 06 章「统一 10 态讨论稿」基础上演进：状态从场景推导，图分四层，词表协议化
事实源：08-场景全集与状态交互分层.md

v2 回答三个问题

  • 有哪些状态？从 34 个交互场景推导，不从直觉枚举——场景里"系统必须在此刻做一个判定"的点才产生状态需求。
  • 状态怎么转？一张完整状态交互图：系统侧主干 6 态 + 扩展 3 态，用户侧 4 态，外加独立变量 floor（话轮归属）。
  • 状态谁产生？四层分层：信号源 → 判定窗口 → 事件（控制面词表）→ 交互状态；外部 7 项词表校订后落入事件层。
方法论一句话：交互态锚定在可观测事实（播放首帧 / VAD）上；模型输出是意图声明；两者永远可能不一致，对账是系统层职责。

S1三分类，别把一切画成状态

交互态（稳定、UI 可渲染）/ 判定窗口态（短暂、带计时器、结论出来就坍缩）/ 决策事件（瞬时、驱动转换）。状态图复杂化的根源就是把窗口和事件画成了节点。

S2补上 v1 的遗漏段：PREPARING

用户说完到系统首帧之间是时延、工具、委托的堆积区。v1 的 THINKING/DELEGATING 按"是否已出声"拆分：未出声 = PREPARING，出声宣告后等待并入 HOLDING。

S3工具 / 委托不建交互态

交互层只关心：持没持话轮、用户耳朵里是什么。工具运行中只有 PREPARING（未出声）或 HOLDING（已宣告）两种归属，生命周期做成决策事件——异步动作再多，节点数不变。

S4时延不是状态

PREPARING / HOLDING 内部用 T0（无感）/ T1（出填充）/ T2（兜底）三阈值把连续时延切成可设计的体验分段，两个态的填充与兜底话术分别配置。

S5外部词表：事件层骨架可用

7 项定义与 OpenAI Realtime 控制面几乎一一对应，但缺窗口层与状态层、混入状态（listen）、stop 语义过载——逐项校订见 P9。

S6新需求：外挂 ASR 外部标识

挂在判定窗口进出沿上：asr_prearm / start / stop / cancel 两段式，泛化为 segment 级外部协处理触发（拒识复核、合规、热词同协议）。

方法论：状态从场景来，三分类防膨胀

承接 06 章三层视角（现象 / 模型表示 / 系统事件）的工程化落地

推导链场景 → 判定点 → 状态需求

① 枚举交互场景（34 个，P3）：按一轮交互的时间线切五阶段 + 贯穿并发，不是拍脑袋列状态
↓ 每个场景里找
② 判定点："系统必须在此刻做一个判断 / UI 必须有一个表现"——只有判定点才产生状态需求
↓ 归纳、去重、分类
③ 三分类落位：交互态 / 判定窗口态 / 决策事件（右表）——大量"候选状态"其实是窗口或事件
↓ 验收
④ 纯函数推导验收：给定模型输出流 + 播放时间戳，任一交互态可被纯函数推导，不需要额外启发式
锚定原则（LiveKit 源码验证）：SPEAKING 以首帧音频进播放通道为准、不以模型开始生成为准；打断后用播放毫秒数 truncate 服务端上下文到用户实际听到的位置。状态是"用户感知"，不是"系统内部忙闲"。

三分类交互态 / 窗口态 / 事件

类别特征画法本方案条目
交互态稳定、UI 可渲染、产品文档可引用节点系统 6+3+2 态、用户 4 态
判定窗口态短暂、有超时、结论出来就坍缩到某个交互态边上的胶囊，不占节点起音确认窗 / 端点窗 / 打断判定窗 / 暂停待判窗
决策事件瞬时判定、驱动转换边的标签拒识三分、打断三分、committed、tool / escalation 生命周期、T1/T2 超时
反例（不这么做会怎样）：把"打断判定中""端点等待中"都画成节点 → 状态数翻倍、每个节点又要定义超时出边，图不可维护——这正是多数状态图失控的原因。
独立变量 floor：话轮归属（user / agent / open / contested / agent-expecting-user）不塞进状态机——"提问后等答"靠 floor 表达，不另设状态。

场景全集：五阶段 × 34 场景

时间线：A 静默 → B 用户输入 → C 响应准备 → D 系统输出（+ X 贯穿并发）｜加粗 = v2 新补或重点

A 静默与边界

  • A1 会话建立预热 INITIALIZING
  • A2 双方静默，谁先说 IDLE
  • A3 长静默 → away → 主动关怀
  • A4 系统主动发起（提醒到达）
  • A5 会话结束 / 断连恢复

B 用户输入期

  • B1 疑似起音→确认 / 误报（ASR 标识触发点）
  • B2 系统伴随附和 BACKCHANNEL
  • B3 停顿 ≠ 说完（持轮换气 vs 释放）
  • B4 端点确认 committed
  • B5 拒识三分 respond/reject/defer
  • B6 超长说话无端点，强制分段
  • B7 旁路人声 / 多人（→ REPAIR）
  • B8 显式禁言（→ MUTED）

C 响应准备期（v2 新增阶段）

  • C1 快路径：T0 内出声，用户无感
  • C2 慢生成：超 T1 → 出声占位
  • C3 先调工具再答（检索类）
  • C4 委托大模型：升级 → 等待 → 回灌代言
  • C5 准备期用户又开口：合并 / 丢弃 / 保留
  • C6 超时 / 工具失败 → T2 兜底话术
  • C7 预提交：停顿期预生成，端点确认立刻播（Flux Eager 思路）
用户说完 → 首帧之间的 gap 是时延、工具、委托的堆积区，v1 没有覆盖——这就是 PREPARING 存在的理由。

D 系统输出期

  • D1 正常说话，转写随播放进度
  • D2 用户附和 → 不让出（继续）
  • D3 真打断 → YIELDING → 截断对账
  • D4 假打断 → 暂停待判 → 恢复
  • D5 边说边调（双流同帧）
  • D6 宣告后持轮等待 HOLDING
  • D7 HOLDING 中用户开口：取消 / 催促 / 无关
  • D8 HOLDING 超时 → 道歉降级
  • D9 说完去向：释放 vs 提问等答（floor）
  • D10 工具缺参数 → 澄清追问（waiting_user）

X 贯穿并发

  • X1 同时开口碰撞 floor=contested
  • X2 外部事件插话时机（打扰管理）
  • X3 反向打断用户（默认禁用）
  • X4 非语音并行输入（不破坏 floor）

人机 ≠ 人人：六条差异，每条逼出一个机制

差异不是缺陷清单，而是状态设计的需求来源——每条差异对应一个必须显式建模的机制

#人人对话人机对话逼出的机制
1没有"拒识"，受话人总有某种反馈误唤醒、旁路收音、多人在场拒识决策事件（respond / reject / defer），全双工下从一次性判定变成持续判定（B5 / B7）
2靠句法韵律预测话轮结束，接话间隙常为负等 VAD 阈值，慢半拍且在换气口抢话用户 PAUSED（停顿 ≠ 说完）、语义 endpoint、预提交（停顿期预生成不出声，C7）
3听者"嗯 / 对"是自然伴随，不干扰说者每个"嗯"都可能触发 barge-in打断判定窗：backchannel / 真打断 / 噪声三分（D2 / D3）
4被打断者说完当前小句，优雅让出立刻闭嘴生硬、不理会霸道YIELDING 显式过渡态 + 截断对账 + 假打断暂停恢复（D3 / D4）
5人不会"挂起等待"工具、检索、大模型都有秒级等待PREPARING / HOLDING + T0 / T1 / T2 填充与兜底策略（阶段 C、D6–D8）
6有视线、张嘴、呼吸等视觉线索只有音频（或有限视觉）起音确认窗、端点窗不可省；窗口大小 = 体验参数，即 06 章"粒度决定最小时延"（B1 / B3）
与评测的呼应：差异 2 / 3 / 4 正是 Full‑Duplex‑Bench 四维度（pause handling / backchannel / turn‑taking / interruption）；差异 1 是 FDB v1.5 的 talking‑to‑others 与背景人声；差异 5 是 Agora 三时钟（应答起点 / 实质答案 / 完成）测的东西——场景清单与业界评测口径能对上。

PREPARING / HOLDING：时延、工具与委托的容器

v1 的 THINKING/DELEGATING 按「是否已出声」拆分｜时延不是状态，工具不建态

时延分段用户说完 → 系统首帧的时间轴

T0 内（~0.5s）
静默，用户无感
快路径直接出声 C1
超 T1（~1.5s）
出声占位："嗯，我看一下"
filler / 背景音 C2–C4
超 T2（~8s）
兜底：道歉 / 降级 / 转异步任务 C6
playout_started
首帧 → SPEAKING

三个阈值把连续时延离散成可设计的体验分段；取值按场景类型分档（闲聊 / 检索 / 委托），上线后按打断率与放弃率调。C7 预提交（停顿期预生成）可把有效 T0 压成负值。

对比PREPARING vs HOLDING：同是等待，两种体验

PREPARING（v2 新增）HOLDING（v1 扩容）
定义话轮已接、还没出声出过声、仍持轮、暂无新内容
典型场景生成中 C1‑C2 / 先调工具 C3 / 委托 C4宣告"我查一下"后等结果 D6 / 轮内停顿、[PAD] 尾音
filler 目标从静默到开口（打破沉默）维持在场感（别像掉线）
超时兜底"这个我需要多点时间，稍后告诉你""还在查，再等我一下 / 先聊别的"
用户开口时C5：合并重生成 / 丢弃 / 保留D7：判定取消 / 催促 / 无关

原则工具 / 委托不建交互态

  • 交互层只关心两件事：持没持话轮、用户耳朵里是什么。
  • 工具运行中只有两种归属：未出声 = PREPARING，出声宣告过 = HOLDING。
  • 工具的开始 / 结束 / 失败是决策事件（invoke_tool / tool_done / tool_failed），驱动两态进出，不占节点。
  • 委托大模型与工具同构，只多一步"结果由全双工模型代言回灌"；大模型对交互层透明（GPT‑Live 委托、双脑架构同款分工）。
  • 好处：以后加检索、设备控制、任意异步动作，状态图节点数不变。
边说边调（D5）是特例中的关键：说话的同时在控制 / 内容双流上发出工具调用（同帧共存），说完刚好结果到 → SPEAKING → HOLDING 甚至无缝续接——这是对模型输出协议的硬需求（P11）。

外部词表校订：7 项定义逐条归位

总评：一份单层事件词表，与 OpenAI Realtime 控制面几乎一一对应——事件层骨架可用，但缺窗口层与状态层、混入状态、stop 语义过载

外部定义原意归类校订建议场景
speech_started感知用户开口感知事件 ✓保留；拆两段 prearm（疑似）+ confirmed（确认）供外挂 ASR 与打断判定；补 speech_cancelled（误报回收）B1
speech_stopped感知用户说完感知事件 ✓保留但正名：语义 = 后沿 VAD，不等于说完——与 committed 的差就是"停顿 vs 说完"（用户 PAUSED 的依据）B3
committed语义完整决策事件 ✓保留；= 端点确认 + 话轮释放；payload 带端点置信度（支持 Eager 投机 / 预提交 C7）B4
listen本轮说完✗ 状态混入移出事件层：改为感知事件 playout_done + 状态 LISTENING；"本轮说完"还需区分释放 vs 提问等答（floor）D9
speak决定响应 / 回复决策事件 ✓拆三分 respond / reject / defer——拒识必须显式（日志与外挂 ASR 复核都要用）；payload 带 expect_reply 写 floorB5 / C
invoke_tool工具调用和委托决策事件 ✓保留，kind = tool / escalate；补生命周期 done / failed；不改交互态，只决定 PREPARING / HOLDING 归属C3/C4/D5/D6
stop判定新一轮、停止播报决策+动作，过载拆 interrupt / pause / resume：真打断 = 停播+截断+开新轮；假打断 = 暂停待判；"判定新一轮"与"停止播报"解耦——backchannel 不开新轮D3 / D4
补充缺失项：playout_started（首帧，SPEAKING 的锚点——缺它状态只能锚在模型开始生成上，字幕与打断对账全错位）、playout_done、backchannel（双向）、hold / filler（T1）、timeout（T2）、away、floor 转移、asr_* 外发标识、session close / error。
映射存档：speech_started/stopped ↔ Realtime input_audio_buffer.*；committed ↔ commit；speak ↔ response.create；stop ↔ response.cancel + truncate。

  • asr_prearm：疑似起音（B1 窗开启）即发，外挂 ASR 预热建流，吃掉启动延迟；
  • asr_start：起音确认发出，音频从起音点回补（含确认窗回溯量），不从确认点开始；
  • asr_stop / asr_cancel：committed 时 stop；确认窗判为误报时 cancel 回收。
为什么这验证了窗口层的必要性：标识的四个触发点正好是起音确认窗与端点窗的进出沿——如果窗口不显式建模，这组信号就没有挂点，只能散落在各处 if/else 里。

泛化segment 级外部协处理触发

  • 载荷 = segment_id + 时间窗 + 音频路由；
  • ASR 是第一个订阅者；拒识复核（B5/B7）、合规记录、热词检测挂同一组信号，不再加协议；
  • 产地可以是系统 VAD，将来换成模型控制流输出的起音 / 端点声明——协议不变，产地可渐进迁移（P6 混合路线）；
  • 外挂 ASR 结果回流：作为③层事件（transcript_final）参与拒识复核与大模型委托的文本输入。
注意：外发标识属于控制面，与内容面共享时间基准（segment_id）；ASR 转写与全双工模型自身的文本流（inner monologue / Talker 文本）并存不互替——前者精确、后者低延迟，消费方各取所需。

对模型输出的五条需求与两条验收

系统需求层：让四层协议闭环，模型侧要给出的增量能力

R1边说边调（同帧共存）

工具调用字段与音频字段可在同一帧输出（D5）——半双工"说完才调"在全双工里不成立。

R2异步结果中途注入

LISTENING / SPEAKING 任意态下接受注入，模型自行决定接续时机（接着说 / 等话轮空隙），C4 / D6。

R3升级信号 + 代言回灌

能输出"回答不了、请升级"控制字段；大模型文本结果回灌由全双工模型代言播出，期间交互状态机不断线（C4，双脑架构接口）。

R4细分意图控制字段

voice_intent（silence/speak/backchannel/yield）、floor_intent（keep/release/take）、拒识声明——业界二元 listen/speak 之外的增量；Instruct‑FD 证明 Backchannel / Interrupt 是全行业短板（IAS ≤ 11.7%）。

R5共享时间基准

所有输出携带 segment_id + 帧内偏移；控制信号放超前流上。没有这条，截断对账与词表协议全部落空。

验收两条硬标准

  • 纯函数推导：给定模型输出流 + 播放侧时间戳，交互层任一状态可被纯函数推导，不需要额外启发式——达不到说明字段设计有漏。
  • 五个必须跑通的场景：抢话（D3）、假打断（D4）、边说边查（D5）、等待超时（C6/D8）、大模型接管中被打断（C4 × D3，最容易暴露跨层漏洞）。
评测衔接（06 章 §五）：FDB v1.0 四维度 + v1.5 四重叠场景 + Instruct‑FD 五策略 + 三时钟；本页五场景是其工程化子集，中文子集需自建。
风险提示：R4 主动性字段（backchannel / interject）是业界 IAS 最低的能力——要么 speak_at_pause 为默认、speak_now 仅限高紧急，要么专项训练（显式 token + DPO 调时机）并先过评测。
