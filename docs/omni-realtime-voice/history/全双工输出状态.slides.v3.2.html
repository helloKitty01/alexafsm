为什么全双工需要显式状态

人与人之间的轮次交替是免费的，机器必须建模——下面每一条差异都逼出一个必须显式设计的机制

#人人对话人机对话逼出的机制对应场景
1受话人总有某种反馈，不存在"这句不是对我说的"误唤醒、旁路收音、多人在场拒识决策：respond / reject / defer 三分，且在全双工下从一次性判定变成持续判定B5 / B7
2靠句法与韵律预测话轮结束，接话间隙常为负等静音阈值，慢半拍，还会在换气口抢话用户侧 PAUSED（持轮停顿）：停顿 ≠ 说完；语义端点；停顿期预生成不出声B3 / B4 / C7
3听者的"嗯 / 对"是自然伴随，不干扰说者每个"嗯"都可能触发打断打断判定窗：真打断 / 附和 / 噪声三分出口D2 / D3 / D4
4被打断者说完当前小句，优雅让出要么生硬地立刻停，要么不理会显式 YIELDING（让出） 过渡态 + 截断到用户实际听到的位置D3 / D4
5人不会"挂起等待"某个子系统工具、检索、大模型委托都有秒级等待PREPARING（备答） / HOLDING（持轮等待） + 三档时延 T0 / T1 / T2：静默 → 垫话 → 兜底C1–C6 / D6–D8
6有视线、张嘴、呼吸等视觉线索只有音频（或极有限的视觉）起音确认窗与端点窗不可省略；窗口时长是产品参数而非实现细节B1 / B3
与业界评测口径对齐：差异 2 / 3 / 4 正是 Full‑Duplex‑Bench 的四个维度（停顿处理、附和、轮次交替、打断）；差异 1 是其 v1.5 的"对旁人说话 / 背景人声"；差异 5 是 Agora 三时钟测量（应答起点 / 实质起点 / 完成）所覆盖的内容。我们的场景集能与公开基准一一对上。

完整状态清单：系统 11 态 · 用户 4 态 · 话轮变量 floor

每个状态对用户可感知地不同，或对系统可操作地不同；两者都不满足的不单列｜话轮归属单独记，不塞进状态机

系统侧 11 态

状态定义用户听到什么典型场景类别
LISTENING（聆听）沉默；话轮在用户或空置；持续消费输入安静B1–B8主干
PREPARING（备答）话轮已接、还没出声；生成、工具、委托都在这里发生安静（≤T0）或垫话C1–C7主干
SPEAKING（说话）音频正在播放；以首帧进入播放通道为准正常说话D1–D3主干
HOLDING（持轮等待）出过声、仍持话轮、暂无新内容（等工具、轮内停顿、尾音）短停顿，但不像说完D5–D8主干
BACKCHANNEL（附和）不夺话轮的短反馈"嗯嗯 / 对"B2主干
YIELDING（让出）判定真打断；停止播放并截断未播内容立刻安静D3 / D4主干
INTERJECTING（主动插话）系统主动发起实质性发言（提醒、告警）；须经打扰管理放行被插话A3 / A4 / X2 / X3扩展
MUTED（禁言）用户显式要求闭嘴，直到解除长时安静B8扩展
REPAIR（澄清）元对话："你是在跟我说吗？"一句反问B7扩展
INITIALIZING（建立） / IDLE（待机）会话预热（缓冲用户先说的话）/ 双方静默—A1 / A2边缘

用户侧 4 态

SPEAKING（说话中）起音已确认
PAUSED（持轮停顿）停了但没说完，话轮仍在用户手上——B3 的依据
SILENT（已释放）话轮已交出（committed）
AWAY（离开）双方长时间静默

话轮变量 floor谁持有话轮

user用户在说或持轮停顿
agent系统备答、说话或持轮等待
open双方都没持有（静默期）
contested双方同时开口，待让步（X1）
agent-expecting-user系统提问后等答（D9 / D10）
为什么单独记：系统问完"你要哪天出发？"后状态回到 LISTENING，但 floor 标为"等用户回答"——系统因此知道该追问而不是干等。没有 floor 就得为此多造状态。

三条设计原则：让状态机小、可验证、可扩展

原则的用处是在加功能时拒绝新状态——三条原则各挡住一类最常见的膨胀来源

原则一状态以用户耳朵听到的为准

SPEAKING 从第一帧音频进入播放通道开始算，不是从模型开始生成算。字幕跟播放进度走。被打断后，对话历史截断到用户实际听到的那一毫秒，未播出的内容不进历史。

  • 挡住的膨胀：不再需要"生成中""缓冲中"这类系统内部忙闲态。
  • 实践验证：LiveKit Agents × OpenAI Realtime 就是按播放毫秒数截断；锚在生成进度上会让字幕和截断全部错位。

原则二时延是计时器，不是状态

无论在生成、调工具还是等大模型，都只是 PREPARING 或 HOLDING 变长了。状态内部用三个阈值切分体验：T0 ≈ 0.5 秒静默无感 · T1 ≈ 1.5 秒出垫话（"嗯，我看一下"）· T2 ≈ 8 秒道歉兜底。

  • 挡住的膨胀：不再需要"思考中""等待工具""委托中"等状态。
  • 阈值按状态分别配置（备答与持轮等待的垫话目标不同），上线后按打断率和放弃率调。

原则三工具与委托不新增状态

交互层只关心两件事：话轮在谁手上、用户耳朵里是什么。工具运行中，没出过声就是 PREPARING，宣告过就是 HOLDING。工具的开始 / 完成 / 失败是事件，不是节点。委托大模型与工具同构，只多一步：结果由全双工模型代言播出。

  • 挡住的膨胀：以后加检索、设备控制、任意异步动作，节点数不变。
  • 与 GPT‑Live 分工一致：语音模型管"说不说"，应用服务器管委托、分轮、持久化。
三条原则底下的同一条分类规则：只有交互态（稳定、UI 可渲染）画成节点；判定窗口（短暂、带计时器、结论出来就坍缩）画在边上；决策事件（瞬时）是边的标签。绝大多数状态图失控，都是把窗口和事件画成了节点——"打断判定中""端点等待中"一旦成为节点，每个还要定义自己的超时出边，图就不可维护了。

一轮对话的五段：场景从时间线推导，不是拍脑袋列

每段有一个核心考点；场景里"系统必须在此刻做一个判定"的点才产生状态需求

A

静默期与会话边界

会话建立、双方静默、长静默离开、系统主动发起、会话结束与断线重连。

考点：什么时候该开口，什么时候该保持安静。

涉及：INITIALIZING / IDLE / INTERJECTING

A1–A5 · 5 个

B

用户输入期

起音确认、系统附和、停顿 vs 说完、端点确认、拒识、超长说话、多人在场、禁言。

考点：停顿不等于说完，绝不在换气处抢话。

涉及：LISTENING 常驻；用户侧 PAUSED；起音窗、端点窗

B1–B8 · 8 个

C

响应准备期

从用户最后一个字到系统首帧出声：快路径、慢生成、先调工具、委托大模型、用户又开口、超时、预提交。

考点：沉默别太久，超时要垫好。

涉及：PREPARING + T0/T1/T2 三档

C1–C7 · 7 个

D

系统输出期

字幕同步、用户附和、真打断、假打断、边说边调、宣告后等待、等待中用户开口、等待超时、说完去向、缺参数追问。

考点：分清真打断和"嗯嗯"。

涉及：SPEAKING / HOLDING / YIELDING；打断判定窗

D1–D10 · 10 个

X

贯穿性并发

双方同时开口、外部事件在说话中到达、系统需要打断用户（告警）、非语音并行输入。

考点：碰撞与外部事件的处置。

涉及：floor = contested；INTERJECTING 放行策略

P0 九个必做场景：最小可用闭环

其中两个是命门（红底）：一个是抢话的代价，一个是被叫停却不停的代价——这两个做砸了，其他都白搭

编号场景与具体例子状态轨迹窗口 / 事件
A1会话建立。戴上耳机 1 秒内听到"我在"；预热期间用户先说的半句话进缓冲，不丢。INITIALIZING ─session_ready→ LISTENINGsession_open / ready
A2双方静默。开场后 5 秒没人说话，系统保持安静，不催促。IDLE（floor = open，无输入不转移）—
B1起音确认。0.3 秒的咳嗽不算开口；"哎对了…"约 200 毫秒内确认——这里同时发出外挂 ASR 启动信号。用户 SILENT [起音确认窗] → 用户 SPEAKING；系统 LISTENING 不变asr_prearm → asr_start / asr_cancel
B3停顿 ≠ 说完。"帮我订一张…（停 1.2 秒想日期）…周五去上海的高铁票"。换气处绝不能抢答。判据是静音时长 与 语义完整性 同时满足。用户 SPEAKING [端点窗：不坍缩] 用户 PAUSED ─再开口→ 用户 SPEAKING；系统全程 LISTENING端点窗 = VAD 后沿 + 语义判定
B4端点确认。说完后静音 600 毫秒且语义完整 → 话轮交给系统。用户 PAUSED/SPEAKING ─committed→ 用户 SILENT；LISTENING ─respond→ PREPARINGcommitted + asr_stop
C1快路径。"现在几点？"→ 0.4 秒内"十点二十"；中间的处理用户完全无感。LISTENING → PREPARING（≤T0 静默）─playout_started→ SPEAKINGT0 内出首帧
D1字幕跟播放。播报行程时，屏幕文字跟随实际已播放的内容，不是跟随已生成的内容。SPEAKING（字幕、打断对账全部锚定播放时间戳）playout_started / delta / done
D3真打断。读新闻读到一半，用户"停停停，换国际的"→ 300 毫秒内闭嘴，历史里只保留用户真听到的那半句。SPEAKING [打断判定窗：真打断] ─interrupt→ YIELDING ─停播+truncate→ LISTENING → PREPARING → SPEAKINGstop latency ≤ 300 ms；truncate 到播放位置
D9提问后持有。"你要哪天出发？"说完不释放话轮，标记为"等用户回答"。SPEAKING ─playout_done→ LISTENING（floor = agent‑expecting‑user）释放 vs 等答由 floor 表达
轨迹记法：大写英文 = 系统侧状态；紫色 = 用户侧状态；[方括号] = 判定窗口；箭头上的字 = 驱动转换的事件。B3 与 D3 合起来就是全双工的两条底线：不抢用户的话，听到"停"就真的停。

P1 十五个体验分水岭场景：像人，而不是像对讲机

这一级集中了全双工的核心价值：等待时有人在、被打断时优雅、说错了能改、别人的话不上钩

编号场景与具体例子状态轨迹窗口 / 事件
A5收尾与重连。"就这样，拜拜"→ 系统收尾；蓝牙断开重连后上下文还在。SPEAKING（收尾）─close→ 会话止；重连 INITIALIZING（状态重建）→ LISTENINGsession close / error
B5别人的话不上钩。旁边同事对用户说"中午吃什么"→ 判定非对我说，保持安静，记一条 defer 日志。LISTENING ─reject / defer→ LISTENING（交互态不变）拒识三分 respond / reject / defer
B8显式禁言。"你先别说，听我说完"→ 禁言；"好了你说吧"→ 解除。任意态 ─禁言→ MUTED ─解除→ LISTENINGmute / unmute
C2慢回答垫话。"把这段翻成英文"1.5 秒还没出首帧 → 先"嗯…"垫一下，再出译文。PREPARING ─T1→ SPEAKING（垫话）→ HOLDING → SPEAKING（译文）T1 超时 → 垫话；决策 3
C3先查再答。"明天北京天气？"→ 静默调天气 API 0.8 秒 →"明天晴，3 到 12 度"。PREPARING (invoke_tool → tool_done) ─playout_started→ SPEAKINGtool_started / done / failed
C4委托大模型。"帮我规划三天成都行程"→"好，我好好想想哈"→ 大模型跑 6 秒 → 结果回灌，由小模型代言播出。PREPARING (escalate) ─T1→ SPEAKING（宣告）→ HOLDING ─result→ SPEAKING（代言）escalation_started / done
C5备答中改口。"查下天气"刚说完又补"哦对，是后天的"→ 合并重新生成，旧答案服务端丢弃。PREPARING ─用户再开口→ LISTENING（合并）─committed→ PREPARING合并 / 丢弃 / 保留三策略
C6准备超时兜底。查询 8 秒无结果 →"这个查得有点慢，出来我马上告诉你"，转为异步任务。PREPARING ─T2→ SPEAKING（兜底话术）→ LISTENING（后续经 INTERJECTING 回报）T2 超时
D2用户附和不让出。介绍方案时用户"嗯嗯 / 对 / 好的"→ 系统不停顿继续说。SPEAKING [打断判定窗：附和] → SPEAKING（自环）floor 不变，不开新轮
D4假打断。说话中背景"砰"一声 → 暂停 0.5 秒，无有效转写 → 从暂停处续播。SPEAKING [暂停待判窗] YIELDING（暂停）─超时 resume→ SPEAKING暂停待判窗
D6"我查一下哈"。说完去调 API，等 2 秒 →"查到了，周五有三趟…"——话轮始终没让出。SPEAKING（宣告）→ HOLDING ─tool_done→ SPEAKING决策 1：续说时延归属
D7等待中被叫停。等结果时用户"算了，不用查了"→ 取消工具，"好的那不查了"。HOLDING ─用户开口∧判取消→ tool_cancel → SPEAKING（确认）→ LISTENING取消 / 催促 / 无关三分
D8等待超时。等待超过 8 秒 →"还在查，稍等我一下"，或降级放弃。HOLDING ─T2→ SPEAKING（道歉 / 降级）→ LISTENING 或续 HOLDINGT2 超时（持轮等待档）
D10缺参数追问。"帮我订高铁票"→"要几点出发的？"→ 等 15 秒没回应，再问一次或放弃。SPEAKING（追问）→ LISTENING（expecting，计时）─超时→ SPEAKING（再问）/ 释放D9 特例
X1同时开口。系统刚要开口，用户也开口 → 系统立刻让，用户优先。PREPARING ─用户起音→ floor = contested ─让步→ LISTENING让步策略可配

P2 十个有意暂缓的场景 + 双向覆盖检查

暂缓只有两个理由：业界目前做不好，或低频。暂缓是决策，不是遗漏

编号场景与具体例子状态轨迹暂缓理由
B2系统主动附和。用户讲了 20 秒需求，系统在语义边界轻声"嗯，明白"，不抢话。LISTENING ─附和时机→ BACKCHANNEL → LISTENINGInstruct‑FD 实测业界遵循率 0–50%，全行业最弱
B7多人在场。车内两人聊天夹杂指令，判不准时问"是在跟我说吗？"LISTENING ─指向不明→ REPAIR → LISTENING依赖外挂 ASR 与声纹
D5边说边调。"我先给你念着新闻，同时帮你查着路况"——说话与工具调用并行。SPEAKING (+invoke_tool 同帧) → HOLDING ─tool_done→ SPEAKING依赖模型能力 R1（同帧双流）

最难的判定：打断三分——用户在系统说话时出声了

一个判定窗、三种出口；同一个窗口的阈值决定产品性格，没有全局最优，必须做成可配置策略

打断判定窗在 SPEAKING 中收到 speech_started

真打断 → YIELDING（让出）

"停，换国际的"——含新意图。停播 ≤ 300 毫秒，历史截断到已听到的位置，开新一轮。指标：stop latency（重叠开始 → 系统停嘴），目标 ≤ 300 ms。

附和 → SPEAKING 自环，继续说

"嗯嗯 / 对 / 好的"——短、无新意图。话轮不变、不开新轮、播放不中断。指标：误让出率（把附和当打断的比例），目标接近 0。

噪声 / 不是对我说 → 暂停待判 → 恢复

"砰"一声、背景人声、屋里另一个人。暂停最多 0.5 秒，无有效转写则从暂停处续播。指标：response latency（重叠结束 → 系统再开口）与误接管率（对旁人说话也停下来的比例）。

策略取向是参数两种性格

快让出（repair‑first）重连贯（continuity‑first）
倾向快速让出，容忍一些误接管坚持说完，容忍让出慢一点
适合客服、任务执行陪伴、辅导、朗读
业界样本GPT‑4o Realtime：真打断响应 0.78，但对旁人说话也响应 0.91Gemini Live / Sonic：恢复率高，打断响应低
窗口参数判定窗短、置信阈值低判定窗长、置信阈值高

Full‑Duplex‑Bench v1.5：没有一种策略在四种重叠场景全优。因此判定窗阈值必须做成策略 profile，按产品线配置。

业界现状：GPT‑Live 把这个判定放进模型内部（Agora 实测：让出慢约 500 毫秒，但 30 次背景人声 30 次拒绝）。第二代 API（OpenAI / Qwen Realtime）默认把任何用户出声都当打断，除非另配。我们的设计把判定显式化在窗口层，产地可以先是系统启发式，日后迁移到模型控制输出，协议不变。

工具与委托是事件，不是状态

  • invoke_tool（kind = tool / escalate）→ tool_done / tool_failed 驱动 PREPARING 或 HOLDING 的进出，本身从不改变交互态。
  • 委托大模型与工具结构相同，只多一步：大模型的文本结果由全双工模型代言播出。大模型对交互层完全透明。
  • 所有"宣告 → 等 → 续说"的情形——垫话 C2、委托 C4、边说边调 D5、"我查一下"D6——全部收敛为同一个模式：SPEAKING → HOLDING → SPEAKING。
  • C6 / D8 超时转异步后，结果回来经 INTERJECTING 回报，走打扰管理——与 phone‑assistant 的长时异步任务同一条路。
与 GPT‑Live 分工一致：语音模型决定"说不说"；应用服务器负责委托、分轮、持久化——正是我们双脑架构的接口划分。Agora 实测 GPT‑Live 的"应答起点 / 实质起点 / 完成"三时钟，对应到这里就是 T1 垫话、代言首帧、播完三个事件。

外挂 ASR 外部标识新需求

系统对外发出信号启动外挂 ASR（另有其他用途）。信号挂在判定窗口的进出沿上——这正是第②层必须显式建模的证明。

asr_prearm疑似起音 → ASR 预热建流，吃掉启动延迟

对模型输出的五条需求

  • R1 同帧双流：工具调用字段与音频字段可在同一帧输出（边说边调 D5）。
  • R2 异步结果中途注入：任意状态下接受注入，模型自行决定接续时机（C4 / D6）。
  • R3 升级信号 + 代言回灌：能输出"回答不了、请升级"控制字段；大模型文本由全双工模型代言播出。
  • R4 细分意图字段：voice_intent（silence / speak / backchannel / yield）、floor_intent（keep / release / take）、拒识声明——超出业界二元 listen / speak。
  • R5 共享时间基准：所有输出携带 segment_id + 帧内偏移，否则截断对账与词表协议全部落空。
