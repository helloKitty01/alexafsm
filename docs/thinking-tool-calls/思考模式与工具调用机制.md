# 思考模式（Thought）与 Function Call 的时序机制

> 问题：大模型的 thought 模式和 function call 一般是怎么配合的？是先 thought 再 tool call 吗？
> 为什么观察到"有些出 thought、有些不出 thought"？
>
> 结论先行：**是的，原生顺序是同一个 assistant 响应内先 thinking 块、后 tool_use 块**。
> "有些出、有些不出"由三层原因叠加造成：模型类型与开关、厂商暴露策略、
> 以及同一模型在**轮内位置**的差异（最容易被忽视的一层）。

---

## 一、基本时序：thinking 与 tool call 是同一响应里的兄弟块

推理/思考模型（Claude extended thinking、OpenAI o 系列及 GPT-5 等）在开启思考后，
一次 assistant 响应的 content 结构是：

```text
assistant 响应:
  [thinking]  "用户要禁用抖音麦克风……我需要先确认 bundleName……"   ← 内部推理（CoT）
  [tool_use]  forbidPermission(bundleName=..., permission="麦克风")  ← 工具调用
```

即**先想后调**：thinking 块和 tool_use 块按序出现在同一个响应中，thinking 承载
"为什么调这个工具、参数为什么这么填"的推理过程。历史上的 ReAct 模式
（Thought → Action → Observation 用普通文本模拟）就是这个时序的提示工程版，
现已被原生 thinking 取代。

## 二、"有些出 thought、有些不出"的三层原因

### 第一层：模型类型与开关

- **非推理模型 / 未开启 thinking**：经典 function calling，模型直接输出 tool_use，
  没有任何 thought——这是最基本的一类"不出"。
- **推理模型 + thinking 开启**：按第一节的时序出 thinking。Claude 通过
  `thinking.budget_tokens` 配置；OpenAI 通过 `reasoning.effort` 配置。
  同一个模型，开关/预算不同，行为就不同。

### 第二层：厂商暴露策略（想了，但不给你看）

| 厂商 | 暴露形式 | 回传要求 |
| --- | --- | --- |
| Anthropic（Claude） | `thinking` 块**明文可见**，带加密签名；敏感内容变成 `redacted_thinking`（加密不可读） | tool use 期间必须**原样回传**（含签名、含 redacted 块），修改或丢弃直接 400 报错 |
| OpenAI（Responses API） | `reasoning` item **不透明**：raw CoT 永不返回，可选开启人类可读的 summary；ZDR/无状态场景返回 `encrypted_content` | 函数调用期间必须把上个 user 消息以来的全部 reasoning item + function_call + output 一起传回，否则报错或降智 |

所以"OpenAI 的模型不出 thought"很多时候是**看不到**而不是**没想**——
reasoning token 照样计费，只是 API 不吐明文。这一层解释了跨厂商的"有的出、有的不出"。

### 第三层：同一模型在轮内位置不同（最容易误判的一层）

Claude 默认（非 interleaved）模式下，**一个 assistant 轮只在开头 think 一次**：

```text
默认模式：
Response 1: [thinking] → [tool_use A]
  ← tool result A
Response 2: [tool_use B]          ← 没有 thinking 块！
  ← tool result B
Response 3: [text 最终回答]        ← 也没有 thinking 块
```

tool result 回来后的后续响应**不再产生新的 thinking 块**，直到下一个
非 tool_result 的 user 轮。如果你在多 loop 的 agent 轨迹里观察，就会看到
"第一步有 thought、后面几步没有"——这不是异常，是设计如此。

开启 **interleaved thinking**（Claude 4 系需 beta header
`interleaved-thinking-2025-05-14`；新模型的自适应思考已默认支持）后，
每个 tool result 之后都可以插入新的 thinking：

```text
interleaved 模式：
Response 1: [thinking] → [tool_use A]
  ← tool result A
Response 2: [thinking]（对 A 的结果推理）→ [tool_use B]
  ← tool result B
Response 3: [thinking] → [text 最终回答]
```

此时 `budget_tokens` 是整个 assistant 轮内所有 thinking 块的总预算，可以超过
`max_tokens`。另一个相关限制：thinking 开启时 `tool_choice` 只支持 `auto` / `none`，
不支持强制指定工具——因为强制调用会跳过"先想"的环节。

## 三、对 harness 的工程含义

1. **思维链是工具调用循环的状态，必须当不可变内容透传**。
   Claude：assistant 轮的 content 原样入历史（thinking + tool_use 一个不少）；
   OpenAI：reasoning item 随 function_call/output 一起回传
   （`previous_response_id` 或手动拼 input）。两家的共同模型是：
   工具调用把模型"一次响应的构建"从中间截断，thought 就是断点处的现场，
   丢了现场就接不回去。
2. **与 append-only 排布天然一致**。"原样保留、只追加"的要求与
   [kv-cache-discussion/02](../kv-cache-discussion/02-上下文分层与排布.md) 的
   UAT 消息流纪律完全重合——保留 thinking 块既是 API 正确性要求，也是缓存友好做法。
   （注：Claude 会在内部把**前几轮**的 thinking 从 prompt 中剥离，这属于厂商侧行为，
   harness 不需要也不应该自己动手剥。）
3. **可见 thought 与内部 thought 是两回事**。一些 harness 额外约定模型在 tool call
   前输出一句简短的可见文本（preamble，"我现在去查询前台应用……"），用于 UX 进度展示。
   这是普通 text 块，与内部 CoT 无关；观察轨迹时不要把两者混淆。
4. **自建/开源模型的对应物**。DeepSeek-R1、QwQ 类开源推理模型输出
   `<think>...</think>` 段，harness 需要自己决定是否回传（多数推荐轮内保留、
   跨轮丢弃），与商用 API 的托管机制原理相同、纪律相同。

## 四、与 skill 分支场景的联动

回到"skill 分支依赖前台应用"的场景（见
[skill环境变量传入方案](../skill-env-variables/skill环境变量传入方案.md)）：
分支判断正是发生在 thinking 里——模型在 thinking 块中读取 env_context /
最近工具结果里的 `foreground_app`，推理该走哪条分支，然后输出对应的 tool_use。
因此：

- 若分支判断需要发生在**工具结果之后**（如"打开应用后再判断"），
  interleaved thinking 是否开启会直接影响判断质量——未开启时模型只能
  "凭第一次 thinking 的预案"行动，开启后才能对每步结果重新推理；
- 这也再次说明方案 C'（工具结果带回前台应用）要配合 interleaved thinking
  才能发挥最大价值：值到了，还得有"想"的机会。
