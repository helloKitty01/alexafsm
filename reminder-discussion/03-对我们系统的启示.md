# 03 对我们系统的启示

## 定位：reminder 是"通道一"的成熟形态，且补出了"通道三"

kv-cache-discussion 02 定义了两条动态内容通道。对照业界，完整图景是三条：

| 通道 | 谁决定 | 进入形式 | 业界对应 |
| --- | --- | --- | --- |
| 通道一：被动注入 | 系统 | user message 附带 | Claude Code system-reminder |
| 通道二：主动加载 | 模型 | tool result | Anthropic just-in-time / load_skill |
| 通道三：自我复诵 | 模型 | 反复重写计划到尾部 | Manus recitation / TodoWrite |

我们原方案把通道一定位为"环境增量 + 高置信检索命中"的运输通道。
业界经验说明它的能力上限远不止于此——它是一个**通用的二级指令通道**，
还能承载：规则刷新、模式切换、状态通知、时效标注、安全兜底。

## 建议的落地设计

### 1. 建立标签契约（一次性，进 L0）

在 system prompt（L0）中预声明标签语义，这段文字是静态的，不破坏缓存：

```text
user message 和 tool result 中可能包含 <system-reminder> 标签。
其内容由系统自动添加，与所附着的消息本身无关；
包含需要遵守的提醒与状态信息，无需对其作出回复。
```

### 2. 定义触发器清单（事件驱动，不是每轮固定注入）

结合我们的系统，首批建议：

| 触发器 | 注入内容 | 服务的目标 |
| --- | --- | --- |
| 环境状态与上轮有 diff | `<env_context>` 增量 | 状态同步（原通道一） |
| 检索命中高置信条目 | `<retrieved>` 未注入过的条目 | 知识供给（原通道一） |
| 连续 N 轮未调用 load_skill 且任务疑似需要 | "skill 索引中有 X 可能相关" | 弥补主动加载的漏加载风险 |
| 压缩刚发生 | 重申任务目标 + 关键约束 | 对抗压缩后的目标漂移 |
| 长对话超过阈值（如 80K token） | 刷新最常被违反的 1–2 条规则 | 对抗 context rot |

### 3. 与压缩策略（03）的衔接

- reminder 属于**时效性内容**：环境增量、规则刷新在压缩时可直接丢弃
  （过期的提醒没有保留价值），压缩后按当前状态重新注入一条即可。
  这比"skill 正文压缩为已加载标记"更简单——reminder 是可再生的。
- **压缩后重注入锚点**是业界共识动作（Claude Code 的 SessionStart/compact
  hook、Anthropic 的 memory 笔记回读）：压缩摘要 + 一条"当前目标与约束"
  reminder，配合使用。

### 4. 通道三（recitation）是否引入

我们的 todo/计划类工具如果已存在，等价机制已经具备；若没有，建议引入
TodoWrite 风格的工具而非让模型自由维护文件，理由：

- 结构化工具调用比自由重写文件更可控、更省 token；
- Manus 的教训：executor 直接维护清单浪费约 1/3 动作。如果任务复杂度到
  50+ 工具调用量级，考虑计划维护与执行分离。

## 待讨论的取舍

1. **reminder 保留还是原位删除（ephemeral）？**
   有些框架把 reminder 做成"下一轮就从历史里删掉"以省 token——但原位删除
   改写历史，其后全部缓存失效，违反 append-only 原则。Claude Code 选择
   保留在历史中，靠压缩时统一清理。建议跟随：**保留 + 压缩时丢弃**。

2. **注入频率与 token 成本的平衡。**
   每轮都注入等于给每轮加固定开销；纯事件触发可能漏。建议事件触发为主，
   外加一个低频兜底（如每 20 轮或每次压缩后刷新一次核心规则）。
   需要度量：reminder 占总 input token 的比例。

3. **reminder 与 skill 的边界。**
   短小、时效性强、系统判断"此刻必须知道" → reminder；
   大体积、按需、模型自己判断 → load_skill。中间地带（如高置信检索命中的
   skill top-1）按 02 的混合模式走 reminder 通道注入摘要 + 提示可 load 全文。

4. **谁生产 reminder 文案。**
   Claude Code 的 40+ 条 reminder 全部是人工精修的固定文案（模板 + 变量）。
   不建议用 LLM 动态生成 reminder 文案：不确定性会引入缓存和行为的双重抖动。

5. **命名。**
   建议对外统一叫 reminder 机制；"notion 方案"作为内部历史代号保留，
   文档中注明对应关系，避免与 Notion 产品混淆。
