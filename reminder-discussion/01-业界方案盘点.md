# 01 业界方案盘点

reminder 机制的定义：**在 agent loop 运行期间，由系统（而非用户或模型）向
UAT 消息流中注入的短小、结构化的指令/状态块**。通常附着在 user message 或
tool result 上，用 XML 标签（如 `<system-reminder>`）标识，并在 system prompt
中预先声明其语义。

业界有三条清晰的实现路线，按"谁来提醒"划分：

| 路线 | 代表 | 谁触发 | 进入位置 |
| --- | --- | --- | --- |
| 系统注入 | Claude Code `<system-reminder>` | 系统事件触发器 | user message / tool result 附带 |
| 模型自我复诵 | Manus todo.md recitation | 模型自己 | 文件系统 + 消息流尾部 |
| API 原生支持 | Anthropic memory tool / compaction | 平台 API | 独立 block / 工具调用 |

---

## 路线一：Claude Code 的 system-reminder（最完整的系统注入实现）

Claude Code 是目前公开可考的最完整实现（源码泄露后有大量逆向分析），
内置 **40+ 种** reminder，全部注入到消息流（user message 或 tool result），
**一条都不进 system prompt**。

### 前置契约：在 system prompt 中预声明语义

```text
Tool results and user messages may include <system-reminder> tags.
<system-reminder> tags contain useful information and reminders.
They are automatically added by the system, and bear no direct
relation to the specific tool results or user messages in which they appear.
```

这段声明做了三件事：
1. 告诉模型这是**系统的话**，不是用户输入的一部分（权威性区分，防注入混淆）；
2. 告诉模型 reminder 与其附着的消息**无关联**（避免模型把提醒误解为对当前
   tool result 的注释）；
3. 告诉模型不要**回复** reminder 本身。

### 使用方式分类（按触发事件）

| 类别 | 触发条件 | 示例 |
| --- | --- | --- |
| 行为提醒 | 任务类工具长期未使用 | "The task tools haven't been used recently. If you're working on tasks that would benefit from tracking progress, consider using TaskCreate…" |
| 模式切换 | 用户切换 plan/autonomous 模式 | "Plan mode is active… you MUST NOT make any edits…" |
| 状态同步 | 文件被外部修改（linter/用户） | "Note: /path/to/file.ts was modified, either by the user or by a linter… take it into account." |
| 动态上下文 | 每次 API 调用前置 | 日期、git 分支、CLAUDE.md 内容（注入消息流而非 system prompt） |
| 记忆时效 | 加载记忆文件时 | "this memory was written N days ago"（给指令文件加时效标注） |
| 安全兜底 | 每次读文件 | 恶意代码分析提醒（每次 file read 都附加） |
| 环境变化 | 可用 subagent 列表变化 | agent roster 变更通知（放消息流避免 tool schema 抖动破坏缓存） |
| 用户插话 | 执行中用户发side question | 包装用户插话并附带专门处理指令 |
| 压缩边界 | 压缩前/压缩被阻止 | 向模型解释压缩状态 |

### 工程细节

- **消息规范化管线**：`smooshSystemReminderSiblings` 把相邻的 reminder 文本块
  折叠进 tool result，减少消息碎片。
- **hooks 生态开放扩展**：用户 hook（如 `SessionStart`、`UserPromptSubmit`、
  `PostToolUse`）返回 `additionalContext` 字段，系统自动渲染为 system
  reminder 注入。reminder 因此成为**平台级扩展点**，第三方无需碰 system
  prompt 即可注入运行期指令。
- **缓存视角**：所有 reminder 都出现在消息流（前缀之后），system prompt
  保持静态；整个代码库的设计准则被总结为一句话——
  "does this invalidate the prompt cache?"

### 官方总结的写作规范

- 标签必须在 system prompt 中预声明，否则模型可能尝试"回复"reminder；
- 保持短小：reminder 不是第二个 system prompt，一次只放 1–2 条关键规则；
- 不与 system prompt 矛盾：reminder 只做补充和强化，不做覆盖。

## 路线二：Manus 的 recitation（模型自我复诵）

Manus 的方案方向相反：不是系统提醒模型，而是**让模型提醒自己**。

### 使用方式

- 处理复杂任务时，agent 主动创建一个 `todo.md` 文件；
- 每完成一步就**重写**该文件、勾掉已完成项；
- 重写动作本身把最新的全局计划以 tool result 形式推到**上下文末尾**。

### 为什么这么做

Manus 一个典型任务平均约 50 次工具调用。长循环中模型容易偏题、忘记早期目标
（lost-in-the-middle）。通过不断把目标"复诵"到上下文尾部，把全局计划推入
模型的 recency 高注意力区——用自然语言操纵自己的注意力，无需修改模型架构。

### 演进教训

早期由执行 agent 直接维护 todo.md，结果**约 1/3 的动作浪费在维护清单**上
（记账不推进任务）。后来改为专门的 planner 子 agent 负责任务分解与清单维护，
executor 专注执行。——recitation 有真实的动作开销，需要架构上隔离。

### 与 KV cache 的关系

recitation 表面上与"稳定前缀"矛盾（内容一直在变），实际不冲突：变化的内容
永远以新增 tool result 出现在**尾部**，前缀（system prompt、工具定义）纹丝
不动。稳定在缓存关心的地方，变化在注意力关心的地方。

## 路线三：Anthropic 官方 API 的原生模式

Anthropic 把相关实践收敛为官方 context engineering 指南和 API 原语：

1. **just-in-time context**：上下文只保留轻量标识符（路径、链接、查询），
   运行时用工具按需加载。（≈ kv-cache-discussion 的"通道二：主动加载"）
2. **structured note-taking / memory tool**（Claude 4.5 Sonnet 起公测）：
   agent 通过工具读写一个 memory 目录，笔记持久化在上下文之外，跨压缩、
   跨会话恢复。这是 recitation 的平台化版本。
3. **compaction**（服务端自动压缩）：`context_management` 参数配置阈值触发，
   压缩后 agent 读自己的笔记继续。
4. 内部测试数据：memory tool + context editing 使 agent 搜索任务性能提升
   39%；100 轮 web search 场景 token 消耗下降 84%。

另外可观察到的行业共性：Cursor 等编码 agent 产品同样采用
`<system_reminder>` / `<system_notification>` 附着于 user message 的注入方式，
说明"系统注入 + 标签预声明 + 附着消息流"已经是事实标准。
